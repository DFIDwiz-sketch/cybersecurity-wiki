흐름 검색 화면이 조용하면 실제 통신이 없었을 수 있습니다. 트래픽이 관측 범위를 벗어났거나 흐름 레코드가 내보내지지 않았거나, 수집기가 받은 레코드를 해석하지 못했을 수도 있습니다. 이 장에서는 UDP로 전송하는 IPFIX 버전 10을 관측 지점부터 검색 인덱스까지 따라갑니다.

## 1. 실제 패킷이 흐름 레코드가 되기까지

**IPFIX(IP Flow Information Export)**는 내보내기 장치와 수집기 사이에서 구조화된 측정값을 전달합니다. **관측 지점**은 특정 인터페이스의 한 방향처럼 트래픽을 보는 위치입니다. **관측 도메인**은 하나의 계측 프로세스에서 흐름 정보를 집계할 수 있는 관측 지점들을 묶습니다. 도메인 번호는 해당 내보내기 프로세스 안에서 식별에 쓰이므로 조사할 때는 장치 식별자와 함께 기록하세요.

**계측 프로세스**는 설정된 기준으로 관측 패킷을 묶습니다. 출발지·목적지 주소와 포트, 전송 프로토콜을 합친 방향별 5-튜플이 흔한 기준입니다. 레코드를 해석할 때 실제 묶음 기준과 샘플링, 인터페이스 설정을 먼저 확인하세요. 캐시 만료에 따라 같은 5-튜플 통신이 여러 레코드로 나뉠 수 있습니다. **내보내기 프로세스**는 템플릿과 데이터 레코드 중 하나 또는 둘 다를 메시지에 담습니다. **템플릿**은 전송 필드의 순서, 종류, 길이를 기술하며, 템플릿 ID는 해당 범위 안에서 이 구조를 식별합니다. **수집기**는 맞는 템플릿으로 데이터 세트를 해석하고 저장·검색 단계에 넘깁니다. 옵션 템플릿의 일부 필드는 관측 도메인이나 계측 프로세스처럼 값이 적용되는 범위를 알려 줍니다.

## 2. 정상 내보내기 한 건을 읽어 보세요

가상의 지사에서 클라이언트가 승인된 서버에 요청을 보냅니다. 장치는 흐름을 계측하고 설정된 템플릿에 따라 주소와 바이트 수를 기록합니다. 수집기 측 캡처에서 관측 도메인 7의 메시지 하나가 시퀀스 100에서 시작하고 템플릿 256과 그 형식의 데이터 레코드 네 개를 담고 있다고 가정합니다. 같은 세션과 도메인의 다음 메시지는 104에서 시작합니다. 이후 시퀀스 108에서 템플릿만 새로 보내면 그 다음 데이터 메시지도 108에서 시작할 수 있습니다. 템플릿 갱신 때문에 번호가 반복되는 정상 상황입니다. 캡처 프레임이나 세트가 아니라 메시지를 해석해 데이터 레코드 수를 세세요.

| 항목 | 값이 알려 주는 것 |
| --- | --- |
| IPFIX 시퀀스 번호 | 이 내보내기 프로세스가 같은 스트림과 도메인에서 앞서 내보낸 데이터 레코드의 누적 위치입니다. 옵션 템플릿으로 해석하는 데이터도 포함합니다. |
| 템플릿·옵션 템플릿 레코드 | 데이터의 구조를 알려 주며 시퀀스 번호를 증가시키지 않습니다. |
| NetFlow v9 시퀀스 | 해당 장치와 도메인 범위의 내보내기 패킷 누적값입니다. 버전 9에는 그 버전의 규칙을 적용합니다. |
| Export Time | IPFIX 메시지가 장치를 떠난 시각입니다. 흐름 시작·종료 시각, 수집기 수신 시각과 각각 대조합니다. |
| 인덱스의 행 | 해석, 정규화, 색인을 거쳐 검색할 수 있는 값입니다. 수집 필터나 데이터 모델에 따라 달라질 수 있습니다. |

같은 범위에서 다음 예상 번호는 `(이전 번호 + 이전 메시지 데이터 레코드 수)를 2^32로 나눈 나머지`입니다. 100번 메시지에 레코드가 네 개 들어 있고 다음 시작 번호가 107이면 계산상 데이터 레코드 세 개의 차이가 납니다. 그 차이에는 옵션 데이터 레코드도 포함될 수 있습니다. 원래 네트워크 패킷, 개별 연결, 내보내기 데이터그램의 개수는 이 차이로 셀 수 없습니다. 번호가 최댓값을 넘는 `4294967294 + 2 → 0`은 정상입니다.

## 3. 누락 신호를 어떻게 해석하나요?

- **UDP 전송과 도착 순서.** 데이터그램이 유실되거나 중복되거나 순서가 바뀔 수 있습니다. 정해진 재정렬 대기 구간 안에 늦게 도착한 메시지가 차이를 메웠는지 확인하세요. 번호가 뒤로 이동하면 먼저 장치 재시작이나 세션 변경 여부를 봅니다. UDP에서는 장치 식별자, 출발지 포트, 수집기 주소와 목적지 포트, 관측 도메인을 같이 봅니다. NAT나 중계기가 관측 주소·포트를 바꾸는지도 확인하세요. TCP는 연결별로, SCTP는 전송 세션 내 스트림까지 구분합니다.
- **템플릿 누락과 재시작.** 수집기가 중간에 합류하거나 재시작하면 템플릿보다 데이터 세트를 먼저 받을 수 있습니다. 전송 헤더를 읽을 수 있어도 데이터 레코드 수는 모를 수 있습니다. UDP에서는 활성 템플릿을 주기적으로 다시 보냅니다. 세션·도메인 범위, 템플릿 수신, 해석 결과를 함께 확인하세요. 템플릿만 담긴 메시지의 유실은 데이터 레코드 시퀀스에 직접 차이를 만들지 않습니다.
- **샘플링, 캐시 포화, 설정 변경.** 표본에 들어오지 않은 패킷이나 내보내지 못한 흐름은 시퀀스가 연속이어도 검색에 나타나지 않을 수 있습니다. 패킷 캡처와 비교하기 전에 카운터가 표본 실측인지 환산값인지 확인하고 계측과 내보내기 설정을 확인하세요. 템플릿 변경으로 기존 검색에 필요했던 필드가 사라질 수도 있습니다.
- **신뢰하기 어려운 관측값.** 미등록 장치, 스키마 불일치, 시퀀스 이상은 인덱스를 오염시킬 수 있습니다. 승인된 장치와 수집 경로를 기준으로 출처를 표시하고 수집기 접근을 제한하며 설정을 자산 목록과 대조하세요. 장비가 지원하면 환경에 맞는 보호된 전송을 사용합니다. 이상 원인은 독립적인 관측을 함께 보고 판단하세요.

## 4. 수집·탐지·대응에 활용하세요

| 수집 지점 | 확보할 근거 |
| --- | --- |
| 계측 및 내보내기 장치 | 인터페이스와 방향, 관측 도메인, 샘플링·만료 설정, 소프트웨어와 재부팅·변경 시점, 가능한 경우 캐시·큐·내보내기 카운터 변화 |
| 전송 경로와 수집기 입구 | UTC, 전송 주소·포트와 범위, 메시지 버전·시퀀스·도메인·템플릿 ID, 수신 소켓이나 캡처의 드롭. 패킷 캡처는 승인된 지점에서만 수행합니다. |
| 해석기와 검색 파이프라인 | 알 수 없는 템플릿과 해석 실패 수, 수집기 재시작과 파서 변경, 색인된 행 수, 지연과 거부된 이벤트 |

먼저 장치 하나, 관측 도메인 하나, UTC 시간 구간 하나를 정하고 인터페이스와 전송 경로를 확인하세요. 장치 쪽에도 같은 불연속이 있는지, 메시지가 수집기 측 캡처에 도착했는지, 당시 해석기에 템플릿이 있었는지를 차례대로 확인합니다. 양쪽 캡처가 승인되고 확보됐다면 중복 전송, NAT, 캡처 손실을 고려해 메시지와 시각을 대조하세요. 독립된 관측으로 근거를 확보한 지점까지만 보고하고 파서·인덱싱 오류도 같은 시간표에 기록합니다.

범위별로 장시간 이어지는 시퀀스 차이 또는 알 수 없는 템플릿의 급증을 탐지하고 평상시 수치 및 정비 일정과 비교하세요. 번호가 연속인데 검색 결과가 줄면 샘플링, 캐시, 해석기, 색인 적체부터 살펴보세요. 수집기를 재시작하기 전에 설정과 캡처를 보존하고, 수정한 뒤 새 템플릿과 사전에 알고 있는 흐름이 해석과 검색까지 도달하는지 확인합니다. IPFIX가 설정된 지원 Prisma SD-WAN ION에서 `inspect ipfix exporter-stats`는 제품 문서상 5.5.1부터 Super 또는 Read Only 역할에 제공됩니다. 설치 버전과 카운터 정의를 확인하세요. 이 명령은 문서로 검토했습니다.

## 5. 오프라인 실습으로 가상 사례 열 쌍 비교하기

<a href="{{ '/assets/labs/ipfix-export-evidence.py' | relative_url }}" download="ipfix-export-evidence.py">Python 스크립트</a>와 <a href="{{ '/assets/labs/ipfix-export-evidence-cases.csv' | relative_url }}" download="ipfix-export-evidence-cases.csv">가상 CSV</a>를 같은 폴더에 내려받고 소유하거나 승인받은 작업 공간에서 Python 3으로 실행하세요. CSV의 각 행은 형식을 정리한 두 관측을 담습니다. 범위 값은 전송 세션과 도메인을 모두 담은 식별자를 대신합니다. 빈 레코드 수는 셀 수 없었다는 뜻이고 0은 해석에 성공했지만 데이터 레코드가 없었다는 뜻입니다. `options_data`의 이전 메시지는 일반 흐름 레코드 두 개와 옵션 데이터 레코드 한 개를 담습니다. `restart`의 세대(epoch) 변경은 실습에서 이미 확인된 값입니다. 번호가 갑자기 바뀌었다는 사실만으로 새 세대라고 판단할 수는 없습니다. 실습은 로컬 파일만 읽습니다.

```bash
python3 ipfix-export-evidence.py ipfix-export-evidence-cases.csv
```

```text
normal: consistent
template_only: consistent
gap: forward_gap:3
wrap: consistent
unknown_count: count_unknown
other_domain: scope_changed
restart: scope_changed
older_arrival: ambiguous_order
options_data: consistent
netflow_v9: unsupported_version
```

실행 전에 이유를 설명해 보세요. 스크립트는 서로 가까운 두 관측을 가정하고, 원형 번호 차이가 전체 범위의 절반 이상이면 순서를 판단하지 않습니다. 캡처를 재정렬하거나 누락 원인을 판단하지 않습니다. 파일을 열 수 없으면 이름과 현재 폴더를 확인하세요. 예상 밖 차이가 나면 옵션 데이터 레코드를 포함하고 템플릿 레코드를 제외했는지 보세요. 이 가상 자료에서 Python 실행을 검증했습니다. IPFIX 장비와 수집기, Wireshark 실행은 별도 검증 범위입니다.

## 6. 확인 문제와 완료 기준

- **차이 3은 클라이언트 패킷 세 개 유실인가요?** 두 메시지 사이의 계산상 데이터 레코드 차이입니다. 클라이언트 통신은 별도의 패킷 관측으로 확인하세요.
- **데이터 세트는 캡처에 있는데 수집된 필드가 없습니다. 어디를 보나요?** 동일 범위의 템플릿이 있었는지, 해석 오류와 수집기 재시작, 갱신 시점이 언제인지 확인하세요.
- **시퀀스는 연속인데 검색 화면이 조용하면 캡처가 완전한가요?** 관측 범위, 샘플링, 캐시, 해석 및 인덱싱 상태를 점검하세요. 시퀀스로 확인할 수 있는 범위는 내보내기 경로의 일부입니다.

결과 열 줄이 일치하고, 전송 데이터그램 유실과 템플릿 누락, 색인 단계 실패를 각각 어떤 기록으로 구분할지 설명할 수 있으면 완료입니다.
