**학습 목표.** Suricata 룰 경보와 연결되는 HTTP 트랜잭션을 근거로 찾아내고, 센서와 애플리케이션에서 각각 무엇을 확인할 수 있는지 설명합니다. 세 도구의 역할이 처음이라면 [Zeek, Suricata, Arkime 비교]({{ '/ko/wiki/network-monitoring/' | relative_url }})를 먼저 읽어 보세요.

## 1. 플로를 먼저 찾고 트랜잭션을 좁히기

**EVE**는 Suricata의 JSON 이벤트 출력입니다. 일반적인 `eve.json` 한 파일에는 `alert`, `http`, `flow` 등 여러 이벤트 유형이 섞일 수 있습니다. **플로**는 센서가 추적하는 통신 흐름입니다. **트랜잭션**은 파서가 관측한 HTTP 요청과 관련 응답 같은 애플리케이션 단위의 교환입니다. HTTP/1.1 지속 연결은 요청을 여러 건 처리하므로 연결이 일치하면 우선 후보 범위를 찾은 셈입니다. 이 장에서 다루는 HTTP/1.1 기록에는 최상위 `tx_id`가 남을 수 있습니다. 이 값까지 일치하면 같은 플로 안에서 트랜잭션을 좁힐 수 있습니다. `0`도 유효한 값입니다.

각 기록에 **센서와 엔진 실행 인스턴스 또는 재생 데이터셋**을 식별할 정보를 함께 남기세요. 이 실습에서는 수집 메타데이터에 `sensor`, `run`이라는 이름을 붙이고 EVE 객체 바깥에 둡니다. 필수 EVE 필드가 아닌 예시입니다. 실제 수집 환경의 출처와 실행 범위를 기준으로 `flow_id`를 해석하세요. 정수 ID를 원래 값으로 읽은 다음 연계용 문자열로 저장합니다. JSON 숫자를 이진 64비트 부동소수점으로 반올림하는 파서는 서로 다른 큰 ID를 같은 값으로 합칠 수 있습니다. 다른 센서와 비교할 때는 [Community ID 조사]({{ '/ko/wiki/community-id-evidence/' | relative_url }})를 참고하고 관측 지점, 튜플, 재생 범위, 시각을 대조하세요.

## 2. 평범한 연결에서 기록이 어떻게 남는지 보기

10:00 UTC에 승인된 테스트 클라이언트가 데모 포털에 HTTP/1.1 지속 연결을 맺습니다. 무해한 테스트 표식을 찾는 룰이 `GET /catalog`에서 일치합니다. 가상의 경보와 `http` 행에 같은 센서, 실행, 플로 ID와 `tx_id=0`이 남고, HTTP 행에는 상태 200이 기록됩니다. 이후 같은 연결의 `GET /account`에는 `tx_id=1`과 상태 403이 남습니다. 403을 표식이 포함된 요청의 응답으로 보고하면 다른 트랜잭션을 잘못 연결한 셈입니다. 포털이 `/catalog` 요청을 어떻게 처리했는지는 애플리케이션 요청 로그로 확인할 수 있습니다. HTTP 상태는 관측한 구간에서 본 응답입니다.

| 자료 | 수집할 값 | 해석 |
| --- | --- | --- |
| EVE 경보 | `gid`, `signature_id`, `rev`, 룰셋, 시각, 플로와 기록된 트랜잭션 ID | 관측한 방향에서 어떤 룰 조건이 일치했는지 확인 |
| EVE HTTP | 같은 범위의 플로, 기록된 `tx_id`, 메서드, 호스트, 경로, 기록된 응답 상태 | HTTP 파서가 로그 범위 안에서 관측한 교환 |
| EVE 플로 | 시작·종료, 방향별 집계, 기록된 상태와 종료 사유 | 통신의 시간과 방향 맥락. `flow.end`는 마지막 관측 패킷 시각이므로 이벤트 기록 시각보다 앞설 수 있음. |
| 프록시 또는 앱 | 구간, 시각, 신뢰할 수 있는 요청 식별자, 응답이나 상태 변경 | 해당 구성 요소가 무엇을 처리했고 앱 결과까지 설명할 수 있는지 확인 |

경보의 바깥쪽 주소와 포트는 룰이 일치한 패킷의 방향을 따를 수 있습니다. 클라이언트와 서버를 구분할 때 플로 방향과 룰 조건을 확인하세요. HTTP 행, 경보 메타데이터, 플로 요약은 같은 통신을 겹쳐 보여 줄 수 있습니다. 행이 세 개라고 요청도 세 건이라고 볼 수는 없습니다.

## 3. 룰 동작과 최종 패킷 판정 읽기

Suricata 8.0.8에서는 경보의 `alert.action`과 선택적으로 기록되는 `verdict.action`을 구분합니다. 전자는 일치한 룰에 해당하는 동작이고, 후자는 관련 룰과 조건을 종합한 센서의 최종 패킷 판정입니다. 인라인 IPS에서 한 룰은 `alert.action=allowed`를 기록하고 다른 조건이 패킷을 차단해 같은 이벤트에 `verdict.action=drop`이 남을 수도 있습니다. 수동 IDS는 트래픽의 복사본을 받습니다. 집행 결과를 설명할 때 배포 모드, 실제 경로와 룰을 함께 기록하세요.

| 관측 | 근거가 뒷받침하는 결론 | 다음 확인 |
| --- | --- | --- |
| `alert.action=allowed`, verdict 없음 | 일치한 룰에 대해 allowed로 기록. 최종 패킷 처리는 이 기록에서 미관측. | 센서 설정, 다른 경보나 인라인 판정, 경로 증거 확인. |
| 인라인 IPS에서 `alert.action=allowed`, `verdict.action=drop` | 센서가 해당 패킷을 드롭했다고 보고함. | 해당 경로에서 대조. 이전 시도나 재시도가 앱에 도달했는지는 별도 확인. |
| 같은 트랜잭션에 경보와 HTTP 2xx | 룰이 일치했고 센서에서 2xx 응답을 봄. | 침해 여부는 룰 범위, 프록시 응답 출처, 앱과 호스트 기록으로 조사. |
| 경보는 있으나 HTTP 행이나 명확한 집행 기록 없음 | 일치 패턴은 관측됨. HTTP 결과는 미확인. | 출력 설정, 파서 가시성과 캡처 무결성 확인. |

클라이언트가 보내는 일반 문자열은 정상 테스트와 침해 시도 모두에서 같은 룰에 일치할 수 있습니다. 공격자가 평범해 보이는 문자열을 보낼 수도 있습니다. 실제 룰 ID와 리비전, 일치 방향, 패킷이나 요청 식별 정보를 보존하세요. 룰 조건과 요청 전체의 맥락을 살펴 정상 동작으로 설명되는지 확인합니다. 서명 이름, User-Agent나 포트 하나만으로 행위 주체를 판단하기 어렵습니다.

## 4. 판단에 필요한 증거 수집하기

1. 센서와 인터페이스 또는 캡처 파일, 엔진 버전, 룰셋 리비전, 실행 범위와 UTC 시간대를 기록하세요. 파싱한 필드와 EVE 원본을 함께 보존합니다. 연계하기 전에 재시작 구간과 예상 시계 오차를 확인하세요.
2. 관련 EVE 출력에서 `alert`, `http`, `flow`가 활성화됐는지 확인합니다. 스레드별 로그 또는 여러 출력을 사용한다면 관련 파일을 모두 확인하세요. Suricata 8.0.8 문서는 EVE의 `http` 유형 아래에 `extended: yes`를, `alert` 아래에 `verdict: yes`를 안내합니다. 실제 빌드와 설정을 확인하세요. 자격 증명이나 개인정보가 포함될 수 있는 헤더와 본문은 필요한 범위에서만 수집합니다. 필드가 없는 이유를 해석하기 전에 원본과 수집 범위를 점검하세요. 플로 요약은 마지막 패킷과 경보보다 늦게 기록될 수 있습니다.
3. 필요한 경우 양방향 트래픽을 캡처하는지, HTTP 파서가 트래픽을 볼 수 있는지, TLS 종료 지점 바깥 센서에 필요한 가시성이 있는지 확인하세요. 캡처 손실, 스트림·애플리케이션 파싱 공백, 파일 교체와 전달도 점검합니다. 승인된 PCAP 재생에서 `pcap_cnt`가 있으면 정확히 그 입력 파일의 패킷 번호입니다. 내부 처리 이벤트에는 없을 수 있고, 다른 PCAP 내보내기의 번호는 다른 패킷 순서를 가리킵니다.
4. 시각, 서비스, 메서드, 경로와 검증된 요청 식별자를 이용해 프록시 또는 앱 기록으로 넘어가세요. 주소가 같다고 결론 내리기 전에 NAT와 프록시 경계를 확인합니다. 인라인 판정이 무엇에 영향을 줬는지 확인하려면 후단 캡처나 집행 로그를 대조하세요. 증거를 보존하고 차단 등 대응을 결정하기 전에 서비스 담당자와 조율합니다.

## 5. 가상 경보 여섯 건을 오프라인에서 조사하기

[suricata-eve-review.py]({{ '/assets/labs/suricata-eve-review.py' | relative_url }}){: download="suricata-eve-review.py" }와 [suricata-eve-cases.jsonl]({{ '/assets/labs/suricata-eve-cases.jsonl' | relative_url }}){: download="suricata-eve-cases.jsonl" }을 본인 작업 공간의 같은 디렉터리에 저장하고 Python 3.12로 실행하세요. 자료는 가상입니다. 프로그램은 Suricata를 설치하거나 네트워크에 접속하지 않고 파일을 읽습니다.

```sh
python3 suricata-eve-review.py
```

| 가상 룰 ID | 기대 결과 |
| --- | --- |
| 7001 | `tx=0`, `GET /catalog`, 상태 200. 다른 센서나 실행에서 같은 ID를 가진 행과 숫자가 1 차이 나는 큰 플로 ID는 제외. |
| 7002 | 같은 플로에서 후보 두 건. 어느 트랜잭션인지는 미확정. |
| 7003 | 트랜잭션 ID는 있으나 일치하는 HTTP 기록을 확보하지 못함. |
| 7004 | `alert=allowed`, `verdict=drop`. 대응하는 HTTP 행은 없음. |
| 7005 | 같은 범위의 트랜잭션 키에 기록 두 건. 선택하기 전에 중복 수집이나 서로 다른 증거인지 확인. |
| 7006 | 플로 ID가 없어 연계 결과를 미확정으로 유지. |

출력은 여섯 줄입니다. 파일이 없거나 읽을 수 없다면 두 파일이 같은 디렉터리에 있고 JSON 객체가 줄마다 하나씩 있는지 확인하세요. 다른 도구로 같은 작업을 했는데 7001이 잘못 연계되면 숫자 정밀도와 센서·실행 범위를 점검하세요. 실습 프로그램은 트랜잭션 중복 후보를 하나로 선택하거나 앱 상태를 추정하지 않습니다. Python 3.12.14에서 여섯 결과를 기대 값과 대조했습니다. Suricata 엔진 재생과 실제 인라인 네트워크는 검증 범위에 포함되지 않습니다.

## 6. 확인 문제와 해설

1. **같은 플로에 200과 403이 있습니다. 어느 쪽이 경보와 관련 있나요?** 올바른 센서와 실행에서 트랜잭션 ID를 비교하세요. ID가 없다면 두 결과를 후보로 두고 요청 단위 기록을 찾습니다.
2. **IPS 경보는 allowed이고 같은 이벤트의 verdict가 drop입니다. 어떻게 보고하나요?** 일치 룰의 동작과 센서의 최종 패킷 판정을 각각 기록합니다. 무엇이 막혔는지 설명하려면 앱 증거도 확인하세요.
3. **다른 센서의 HTTP 행에 같은 플로 ID와 트랜잭션 ID가 있습니다. 연결해도 되나요?** 각 도구의 ID는 출처 범위에서 해석합니다. 여러 센서를 연계할 때는 관측 지점, 시각과 플로 메타데이터로 독립된 연계 근거를 확인하세요.

**완료 기준.** 여섯 결과를 재현하세요. 두 사례를 골라 관측 지점, 어떤 결과를 해당 요청에 연결할 수 있는지, 다음에 확인할 자료 한 가지를 기록하면 완료입니다.
