**학습 목표.** 애플리케이션이 비밀번호 검증값을 저장하는 이유와 로그인에서 이를 사용하는 방법을 설명합니다. 검증값 데이터베이스가 복사됐을 때 어떤 증거로 피해 범위를 확인할 수 있는지 익힙니다.

## 1. 서버는 무엇을 저장하나요?

**비밀번호 검증값**은 서비스가 입력된 비밀번호를 확인하는 데 사용하는 저장 데이터입니다. 여기서 다루는 **비밀번호 해싱 방식**은 비밀번호, 무작위 **솔트**, **비용 매개변수**를 입력으로 받아 값을 계산합니다. 레코드마다 솔트를 새로 만들고 계산 결과와 함께 저장합니다. 비용 설정은 계산에 시간과 자원이 들게 합니다. 메모리 사용량을 높이는 방식도 있습니다. 버전은 어떤 규칙으로 레코드를 읽고 검증할지를 알려줍니다.

| 구성 요소 | 비밀번호 저장에서 하는 일 |
| --- | --- |
| 빠른 해시, 예를 들어 SHA-256 한 번 | 다이제스트를 빠르게 계산합니다. 솔트를 넣어도 한 번의 빠른 해시만 쓰면 추측을 시도하는 비용이 낮습니다. |
| Argon2id나 scrypt 같은 비밀번호 해시 | 추측 한 번에 드는 자원을 늘립니다. 유지보수되는 라이브러리를 쓰고 실제 환경에서 비용 설정을 측정합니다. |
| 암호화 | 복호화 키로 원본을 되찾을 수 있습니다. 일반적인 비밀번호 검증에는 원본 복구가 필요하지 않습니다. |
| 솔트 | 같은 비밀번호를 사용해도 보통 다른 결과가 나오게 합니다. 검증값과 함께 저장합니다. |
| 페퍼 | 일부 환경에서 검증값을 추가로 보호하는 별도의 비밀입니다. 비밀을 어디에 보관하고 무엇이 노출됐는지에 따라 보호 효과가 달라집니다. |
| 패스키 | 서비스는 공개키를 저장하고 챌린지에 대한 서명을 검증합니다. 서명 자격 증명은 인증기가 보관합니다. |

이 장은 서버에서 검증하는 애플리케이션 비밀번호를 다룹니다. 디렉터리 프로토콜, 운영체제 자격 증명 형식, 장치 잠금 해제 PIN에는 다른 요구와 증거가 적용됩니다.

## 2. 정상 가입과 로그인을 따라가기

가상의 시험 계정 두 개를 같은 실습용 문구로 등록합니다. 서비스는 암호학적으로 안전한 난수 생성기로 각 계정의 솔트를 새로 만듭니다. 버전, 솔트, 비용 매개변수와 계산 결과를 저장합니다. 솔트가 다르므로 두 레코드의 검증값은 보통 서로 다릅니다.

1. 서비스는 상대를 인증한 보호 연결을 통해 비밀번호를 받습니다. 입력 인코딩과 정규화 규칙을 일관되게 적용합니다. 규칙을 바꾸면 기존 레코드 검증이 실패할 수 있습니다. 애플리케이션 로그나 관측 자료에 입력을 남기지 않습니다.
2. 계정의 검증값을 찾고 신뢰하는 라이브러리와 맞는 버전을 선택합니다. 솔트와 정책 범위 안의 비용을 읽어 입력에서 검증 후보를 계산하고 라이브러리의 비교 절차를 사용합니다. 실습에서는 같은 길이의 바이트를 일정 시간 비교를 위한 함수로 대조합니다.
3. 일치하면 입력 비밀번호가 저장된 검증값을 통과한 것입니다. 추가 인증 요소를 요구하거나 접근 정책으로 세션을 거부할 수 있으므로, 로그를 볼 때 어떤 단계가 성공했는지 확인합니다.
4. 지원 중인 이전 정책에서 확인에 성공했다면 입력된 비밀번호로 새 매개변수와 새 솔트를 적용할 수 있습니다. 동시에 진행된 비밀번호 재설정을 덮어쓰지 않도록 레코드를 갱신하고, 이전 버전이 얼마나 남았는지 추적합니다. 로그인하지 않는 계정까지 이전하려면 재설정이 필요할 수 있습니다.

비교 함수는 값 비교 단계만 담당합니다. 계정 조회 경로, 비용 설정, 동시 요청은 전체 응답 시간과 자원 소비에 영향을 줍니다. 운영 환경에서는 허용 매개변수를 제한하고, 동시 처리량과 요청 빈도를 제어하며, 부하 시험을 해야 합니다.

## 3. 노출 가능성을 해석하기

검증값 데이터베이스가 복사되면 로그인 서버를 거치지 않고 비밀번호를 추측해 볼 수 있습니다. 서버의 요청 제한은 이런 오프라인 추측에 적용되지 않습니다. 솔트가 서로 다르면 한 번 계산한 값을 다른 솔트의 레코드에 그대로 쓸 수 없고, 같은 비밀번호인지도 결과만 보고 쉽게 연결할 수 없습니다. 비용이 큰 해시를 써도 비밀번호 자체가 약하면 추측될 수 있습니다. 페퍼를 별도로 보관하면 데이터베이스만 유출된 상황에서 도움이 될 수 있습니다. 보호 효과를 판단하려면 앱 프로세스, 백업, 비밀 관리 시스템에도 접근할 수 있었는지 확인하세요.

다른 곳에서 유출된 자격 증명을 로그인 서비스에 넣어 보는 크리덴셜 스터핑은 다른 흔적을 남깁니다. 로그인 성공·실패를 볼 수 있어도 그 기록만으로 자격 증명의 출처를 알 수 없습니다. 실패가 반복되지 않아도 오프라인 노출 가능성은 남습니다. 로그인 한 건, 낯선 IP 또는 공유 네트워크 주소 하나로 계정 탈취를 확정하지 않습니다.

| 기록 또는 발견 | 확인할 질문 |
| --- | --- |
| 데이터베이스 조회·내보내기 또는 백업 감사 | 검증값 데이터에 대한 접근이 성공했나요? 기록이 있다면 호출 신원, 대상, 시간과 목적지를 확인합니다. |
| 검증 정책과 배포 목록 | 당시 신규·이전 레코드에 적용된 알고리즘과 비용은 무엇인가요? 해시를 내보내지 않고 통제된 메타데이터에서 버전별 수를 확인합니다. |
| 비밀 관리 서비스나 하드웨어 서비스 감사 | 해당 기능이 있다면 페퍼를 읽거나 키 연산 서비스를 사용한 기록이 있나요? 수집 범위와 접근 권한을 확인합니다. |
| 인증과 세션 기록 | 비밀번호 확인, 추가 요소 승인, 세션 발급과 사용 중 무엇이 관측됐나요? 앱의 시각과 식별자를 대조합니다. |

## 4. 수집·탐지·대응하기

1. **범위를 정합니다.** 의심 시간대를 UTC로 기록하고, 데이터베이스 또는 백업 대상, 호출 신원, 작업 결과를 확인합니다. 보존·라우팅·조회 이벤트 수집 범위를 점검하고 원본은 접근을 제한해 보존합니다.
2. **정상 업무와 비교합니다.** 대량 내보내기나 백업 읽기를 예약 작업·승인 기록·예상 신원과 대조합니다. 데이터베이스 활동을 저장소와 목적지 기록에도 연결합니다. 로그인 오용은 실패 건수뿐 아니라 여러 계정에 나타난 패턴과 예상 밖의 성공 세션을 함께 살펴봅니다.
3. **노출을 확인하고 차단합니다.** 문제가 된 접근 경로를 제한하고 증거를 보존합니다. 영향받은 검증값 버전과 계정, 실제 저장된 민감 자료 및 수집 가능한 로그를 확인합니다. 사고 대응 절차에 따라 비밀번호 재설정, 세션 무효화, 복구를 결정합니다. 침해에 따른 재설정과 정기 만료 정책은 목적이 다릅니다.
4. **복구를 검증합니다.** 의도한 세션이 무효화됐는지, 재설정·이전 레코드에 새 정책이 적용됐는지 확인합니다. 페퍼를 사용하는 경우 키 사용이 승인된 경로에서 이뤄지는지 점검합니다. 기존 비밀번호 없이 검증값을 이전할 수 없는 설계라면 유출된 페퍼를 교체하면서 재설정이 필요할 수 있습니다. 공유 티켓이나 경보에 비밀번호, 해시, 계정과 연결된 솔트, 복구 토큰이나 비밀 키를 포함하지 않습니다.

## 5. 오프라인 검증 실습

<a href="{{ '/assets/labs/password-storage-evidence.py' | relative_url }}" download="password-storage-evidence.py">Python 스크립트</a>를 내려받습니다. 본인 소유 또는 승인된 작업 공간에서 OpenSSL 기반 `hashlib.scrypt`를 제공하는 Python 3.13 또는 지원되는 다른 Python 3과 충분한 메모리로 실행합니다. 내장된 가상 입력과 무작위 16바이트 솔트 두 개를 사용합니다. 계산된 검증값은 표시하지 않으며 계정 데이터베이스에 접속하거나 네트워크 요청을 보내지 않습니다.

```bash
python3 password-storage-evidence.py
```

```text

PASS: an incorrect password is rejected

```

실습은 Argon2id를 사용할 수 없을 때 OWASP가 제시한 scrypt 설정 중 `N=2^17, r=8, p=1`을 사용합니다. 한 번 계산할 때 주요 메모리 요구량은 약 128 MiB입니다. 예제는 부가 사용량을 포함해 OpenSSL에 256 MiB 제한을 지정합니다. scrypt를 제공하지 않는다는 오류가 나면 OpenSSL 지원 Python을 확인하세요. 메모리 할당 오류가 나면 실행 환경의 메모리와 암호 설정을 확인합니다. 실습은 계산을 순차적으로 실행하며, 실제 서비스 처리량이나 전체 인증 서비스를 검증하지 않습니다.

## 6. 확인 문제와 완료 기준

- **두 계정이 같은 실습용 문구를 썼는데 검증값이 왜 다른가요?** 각자 다른 솔트로 계산합니다. 솔트를 알아도 비밀번호나 검증에 사용하는 별도 비밀 키를 얻는 것은 아닙니다.
- **비밀번호 일치로 계정 탈취를 입증할 수 있나요?** 주변 인증 단계와 세션·활동 기록을 대조해 누가 사용했고 어떤 동작이 이어졌는지 판단합니다.
- **실패 로그가 급증하지 않았습니다. 유출을 배제할 수 있나요?** 복사된 데이터베이스에서의 오프라인 추측은 로그인 서버를 거치지 않습니다. 데이터베이스·백업·비밀 접근을 각각 확인합니다.

네 가지 검사를 모두 통과하고 비밀번호 일치, 세션 발급, 데이터베이스 내보내기, 이후 오용을 뒷받침하는 증거를 구분해서 설명하면 실습을 마친 것입니다.

## 공식 참고자료

2026년 11월 23일에 검토했습니다. NIST의 2025년 최종 개정판은 그 적용 범위에 속하는 검증 서비스의 요구사항을 제시합니다. OWASP는 애플리케이션에 적용할 알고리즘과 매개변수를 권고합니다. 기존 bcrypt 레코드는 이전이 필요할 수 있습니다. 배포 환경과 준수 요건에 맞춰 설정을 선택하세요.

- 검증값 저장, 이전 메타데이터, 보호 연결과 요청 제한. [NIST SP 800-63B-4, 2025년 7월](https://pages.nist.gov/800-63-4/sp800-63b.html#passwordver)
- 알고리즘 권고, 비용 설정과 페퍼 관리. [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
- scrypt 알고리즘과 매개변수. [RFC 7914, 2016년 8월](https://www.rfc-editor.org/rfc/rfc7914.html)
- 표준 라이브러리 동작. [Python 3.13 hashlib](https://docs.python.org/3.13/library/hashlib.html#hashlib.scrypt)
