인증서를 교체한 직후 거래처의 메일이 지연됐습니다. MX에는 접속할 수 있고 일반 TLS 클라이언트로 연결도 됩니다. 하지만 발신 메일 서버가 이전 키에 연결된 TLSA를 DNSSEC으로 검증했다면 배달을 보류할 수 있습니다. 이 장에서는 TCP 25 포트를 쓰는 메일 서버 간 직접 전송 한 구간을 살펴봅니다. 앞 개념은 [DNSSEC 검증]({{ '/ko/wiki/dnssec-validation-evidence/' | relative_url }})과 [SMTP 전송 증거]({{ '/ko/wiki/smtp-delivery-evidence/' | relative_url }})에서 확인할 수 있습니다.

## 1. TLSA는 무엇을 연결하나요?

**MX 레코드**는 수신 도메인으로 보낸 메일을 받을 서버의 이름을 알려 줍니다. **RRset**은 DNS 소유자 이름, 클래스, 유형이 같은 레코드 묶음입니다. 검증 리졸버는 **DNSSEC**으로 이 묶음의 출처와 무결성을 검증하거나 레코드의 부재를 확인합니다. DNSSEC 서명이 유효하더라도 관리자가 잘못된 값을 게시했을 가능성은 남습니다.

**DANE**은 DNSSEC을 이용해 수신 TLS 서비스를 어떤 방식으로 인증할지 발신 서버에 알려 줍니다. 이 정보는 **TLSA** RRset에 들어 있습니다. 별칭 없이 `mx1.example.test`의 25번 포트로 직접 연결한다면 수신 주소가 `@example.test`로 끝나더라도 TLSA 소유자 이름은 `_25._tcp.mx1.example.test.`입니다. MX 검증과 TLSA 검증은 각각 필요합니다. DNSSEC으로 보호되지 않는 MX 응답에서 호스트를 골랐다면 그 호스트의 TLSA가 일치해도 해당 호스트가 수신 도메인의 정당한 MX라는 점까지 인증되지는 않습니다.

| TLSA 구성 요소 | `3 1 1`에서의 의미 | 다른 값의 범위 |
| --- | --- | --- |
| 인증서 용도 `3` | DANE-EE. 연결 상대가 제시한 리프 인증서를 대상으로 확인 | `2`는 DANE-TA. 지정한 신뢰 앵커까지 유효한 체인을 구성하고 해당 서버 이름을 검증 |
| 선택자 `1` | 공개키와 알고리즘 정보가 포함된 DER 형식의 SubjectPublicKeyInfo(SPKI) | `0`은 전체 DER 인증서를 선택 |
| 일치 유형 `1` | 선택한 바이트의 SHA-256 다이제스트 | `0`은 선택한 바이트 자체, `2`는 SHA-512 |
| 연결 데이터 | 이 조합에서는 리프 SPKI의 SHA-256을 16진수로 표현한 값 | 인증서 지문, PEM 텍스트 해시, DNSSEC DS 다이제스트는 각각 다른 바이트를 대상으로 계산 |

SMTP의 DANE-EE에서는 DNSSEC으로 검증한 연결 데이터가 상대 신원의 근거입니다. 이 신원을 확인할 때 공개 CA 체인 검증과 인증서의 이름 검사는 적용하지 않습니다. TLS 핸드셰이크는 성공해야 하며 상대가 해당 개인키를 보유하고 있음을 확인해야 합니다. RFC 7672의 SMTP 프로파일은 용도 0과 1을 정의하지 않아 구현체가 이를 사용할 수 없는 값으로 처리할 수 있습니다. Exchange Online도 이 동작을 문서화했습니다. 일반적인 HTTPS 인증, SMTP의 DANE-TA, MTA-STS는 다른 검증 조건을 적용합니다.

## 2. 정상 배달 한 건을 따라가세요

1. 가상의 발신 서버가 10:00 UTC에 `example.test`를 조회합니다. 리졸버는 `10 mx1.example.test.`와 `20 mx2.example.test.`가 담긴 MX RRset을 검증합니다. 발신 서버는 우선순위 숫자가 작은 후보부터 시도합니다.
2. `mx1`의 TLSA를 조회합니다. DNSSEC 검증이 성공했고 키 A에 대응하는 `3 1 1` 레코드를 사용할 수 있습니다.
3. 발신 서버는 상대의 EHLO 응답에 있는 `STARTTLS`를 확인하고 TLS로 전환합니다. 리프 SPKI의 다이제스트가 키 A의 연결 값과 일치합니다. 세션을 만들 때 사용하는 임시 키와 인증서의 공개키는 역할이 다릅니다.
4. TLS에서 SMTP를 계속합니다. 메일 본문을 보낸 뒤 최종 `250`을 받았다면 이 구간에서 상대 서버가 메시지를 수락한 것입니다. 이후 처리는 수신 서버의 대기열과 배송 기록을 확인하세요. 핸드셰이크 성공만으로는 메시지 수락이나 받은편지함 도착을 판단할 수 없습니다.

## 3. 실패가 발생한 단계부터 구분하세요

아래 표는 RFC 7672 제2.2절에서 설명하는 기회적 DANE의 적격 MX별 판단을 요약합니다. 실제 대기열 동작은 발신 서버가 적용한 경로, 커넥터 설정, 공급자 동작도 확인해야 합니다.

| 발신 서버에서 관찰한 결과 | 해석과 다음 확인 |
| --- | --- |
| DNSSEC으로 검증된 TLSA와 일치하고 TLS 성공 | 해당 엔드포인트의 DANE 인증 성공. 같은 SMTP 트랜잭션의 최종 수락 응답 확인 |
| 사용할 수 있는 TLSA가 검증됐지만 불일치하거나 STARTTLS가 작동하지 않음 | 해당 엔드포인트에서는 전송을 진행할 수 없음. 다음 적격 MX로 넘어가거나 지연. 서버가 제시한 리프와 당시 RRset 비교 |
| TLSA가 검증됐고 비어 있지 않지만 모든 레코드를 사용할 수 없음 | 제2.2절에서는 TLS 암호화를 요구하며 이 경우 DANE 인증은 요구하지 않음. 지원하는 값 조합과 TLS 성공 여부 확인 |
| DNSSEC으로 보호되지 않는 TLSA 또는 검증된 TLSA 부재 | 기회적 TLS가 기본 권고. 평문 허용 여부를 판단하기 전에 더 강한 로컬 정책이나 MTA-STS 확인 |
| DNSSEC 위조·오류 판정(bogus) 등을 포함한 조회 오류 | 가능한 경우 다음 적격 MX를 시도하거나 지연. 검증 리졸버와 위임을 조사하고, 확인된 레코드 부재와 구분해 오류 보존 |

네트워크 중간에서 평문 STARTTLS 안내를 방해할 수 있습니다. 사용할 수 있는 TLSA를 검증한 DANE 발신 서버는 인증된 TLS를 요구하므로, 보호된 경로에서 이런 방해는 배달 지연으로 이어질 수 있습니다. DNS 관리 권한을 누군가 허가 없이 사용했다면 서명이 유효해도 연결 값 자체를 바꿀 수 있습니다. 예상 밖의 DNS, 엔드포인트, 키 변경은 승인 기록과 비교하세요. 이전 RRset이 캐시에 남았거나 일부 노드가 다른 키를 제시했거나 선택자를 잘못 지정해도 불일치가 생깁니다. 두 정책이 적용될 때 RFC 8461은 MTA-STS 검증 성공으로 DANE 검증 실패를 덮어쓰지 못하도록 규정합니다.

## 4. 블루팀 수집·탐지·대응

| 수집 위치 | 수집 조건과 필드 |
| --- | --- |
| 발신 MTA 또는 공급자 메시지 추적 | UTC 이벤트 및 시도 시각, 실제 적용 정책, 해당 MTA 범위의 대기열 ID, 수신 도메인, 선택한 MX와 IP, STARTTLS·TLS 결과, 연결 값 검증 결과, 최종 SMTP 응답. 지원한다면 재시도별 진단을 보존 |
| 발신 서버가 사용한 리졸버 | 리졸버 식별 정보, 소유자 이름, 질의 유형, 검증 상태, 부재 증명 또는 오류, 응답 TTL, 당시 레코드. 직접 검증하거나 신뢰할 수 있는 경로로 검증 리졸버 사용. 임의 서버가 보낸 패킷의 AD 비트만으로 판단하지 않음 |
| 수신 서비스와 변경 관리 시스템 | 접속 시각, 백엔드, 인증서 또는 SPKI 다이제스트, 배포 ID, DNS 게시 이력, 키 활성화·롤백 시각. 가능하면 MX, 주소 계열, 백엔드별로 수집 |
| 참여 발신자의 TLS-RPT | UTC 보고 기간, 보고자, 정책 도메인, 제공된 MX 필드, `tlsa` 정책 유형 및 `tlsa-invalid`, `dnssec-invalid` 같은 결과. 영향받은 경로를 찾는 데 집계 사용. Microsoft가 문서화한 Exchange Online 진단 코드에는 `4.7.323`과 `4.7.324`도 있음 |

실패한 **시도**는 발신 서버, MX, 실패 단계, 시각으로 묶고, 메시지 수는 범위를 아는 대기열 또는 메시지 ID로 따로 집계하세요. 같은 발신 서버의 마지막 성공과 최초 실패를 DNS 변경 및 키 활성화 시각과 비교합니다. 한 주소 계열이나 백엔드만 실패하면 각 엔드포인트가 실제로 제시한 키를 비교하세요. 여러 리졸버가 서로 다른 레코드 유형에 대해 DNSSEC 오류를 보고하면 영향을 받은 신뢰 체인부터 살펴봅니다. 원본 시각과 정규화한 UTC를 모두 보존하세요.

정기 교체에서는 새 키를 서비스하기 전에 기존 키와 새 키에 해당하는 TLSA를 함께 게시합니다. 변경 전 TTL을 기준으로 이전 RRset이 캐시에서 만료될 시간을 확보합니다. 발신 쪽에서 두 값이 보이는지 확인한 뒤 모든 대상 엔드포인트에 새 키를 반영합니다. 기존 키를 모두 내리고 롤백에도 필요하지 않을 때 이전 연결 값을 제거합니다. 키 유출이 의심되면 DNS와 메일 운영 담당자와 함께 차단 및 교체 시점을 정하세요. 유출된 키를 계속 허용하는 중첩 기간은 상황에 맞게 조정해야 합니다. 실제 대기열에서 배달이 회복됐는지 확인하고 재시도 실패도 계속 관측하세요.

**가상 장애 사례.** 기존 키 A만 담은 RRset의 TTL은 3,600초였습니다. DNS 운영자는 10:05 UTC에 A와 B를 함께 게시했고, 10:10 UTC에 백엔드 하나가 B를 쓰기 시작했습니다. 10:04 UTC에 A만 캐시에 넣은 발신 서버는 10:12 UTC에도 그 값을 볼 수 있습니다. 당시 발신 측에는 A만 있고 백엔드 기록에는 B가 있다면 두 기록으로 TLSA 불일치를 설명할 수 있습니다. 다른 발신 서버의 성공 여부도 배포 시점과 DNS 상태를 비교해 해석할 수 있습니다. 재시도가 성공했는지는 대기열 기록에서 확인합니다.

## 5. 승인된 오프라인 실습

[Bash·OpenSSL 실습 파일]({{ '/assets/labs/smtp-dane-evidence.sh' | relative_url }}){: download="smtp-dane-evidence.sh"}을 내려받아 본인이 소유하거나 사용 승인을 받은 환경에서 실행하세요. 임시 전용 디렉터리에 일회용 인증서를 만들고 DER SPKI를 추출해 전체 인증서와 별도로 해시한 뒤 임시 파일을 정리합니다. 메일을 보내거나 DNS·네트워크 요청을 만들지 않습니다. Bash, EC P-256을 지원하는 OpenSSL, 기본 유닉스 도구가 필요합니다.

```bash
openssl version
bash smtp-dane-evidence.sh
```

| 대조 조건 | 기대 결과 |
| --- | --- |
| 인증서 A와 갱신본 A′의 키는 같고 일련번호는 다름 | SPKI 해시 동일, 전체 인증서 해시는 다름 |
| 이전 연결 값만 있는데 새 키 B를 제시 | 불일치 |
| 키 A와 B 연결 값을 동시에 게시했다고 가정 | 두 키 모두 각각 일치 |
| 교체가 끝나 새 값만 사용 | B는 일치, A는 불일치 |
| SPKI 대신 전체 인증서의 다이제스트를 입력 | `3 1 1`에서는 불일치 |

대조가 실패하면 스크립트는 0이 아닌 상태로 종료합니다. 키 생성에 실패하면 OpenSSL에서 EC를 지원하는지 확인하세요. 손으로 계산한 결과가 다르면 리프 인증서를 사용했는지, `openssl pkey -pubin -outform DER`로 얻은 바이너리 DER을 입력했는지, 선택자가 맞는지 확인한 뒤 16진수 전체를 비교합니다. 이 실습은 그 자리에서 생성한 자료로 바이트 선택과 키 교체 중 일치 여부만 검증합니다. 3절의 판단 규칙은 표준을 검토한 결과이며 실제 리졸버, TLS 핸드셰이크, 제품 로그, 대기열은 실습 범위 밖입니다.

## 6. 확인 문제와 완료 기준

1. **공개 CA 인증서가 정상인데 거래처에서 `tlsa-invalid`를 보고할 수 있나요?** 가능합니다. 공개 CA 검증과 TLSA 대조가 확인하는 항목이 다릅니다. 해당 시도의 RRset과 리프 SPKI를 확보하세요.
2. **DNSSEC에서 `SERVFAIL`이 났으면 TLSA가 없다고 판단할 수 있나요?** 검증 리졸버에서 실패 이유를 확인하세요. DNSSEC으로 검증된 부재와 조회 실패에는 다른 정책이 적용됩니다.
3. **MX 후보 둘 모두 인증된 TLS를 지원합니다. 어느 쪽이 메시지를 받았는지 어떻게 알 수 있나요?** 해당 트랜잭션의 발신 결과와 수신 대기열 기록을 확인하세요. 두 서버에 연결해 보는 것만으로는 실제 수락을 알 수 없습니다.
4. **키를 바꾸는 동안 양쪽 키가 허용되려면 어떤 순서가 필요한가요?** 두 연결 값을 먼저 게시하고 이전 값만 담은 캐시가 만료될 시간을 확보한 뒤, 각 엔드포인트에서 현재 정책에 포함된 키를 제시합니다.

**완료 기준.** 표 없이 `3 1 1`을 설명하고 일치·불일치 대조를 재현하세요. 가상 시도 한 건을 골라 실패 단계와 추가로 필요한 증거를 말할 수 있으면 됩니다. 다음은 [MTA-STS와 TLS-RPT]({{ '/ko/wiki/smtp-mta-sts-evidence/' | relative_url }})입니다.

## 공식 참고자료

검토일은 2026-11-26입니다. 괄호 안의 연도는 표준 발행 시점이며, Exchange Online 동작은 검토일의 Microsoft Learn 문서를 기준으로 설명했습니다.

- TLSA 필드 및 DANE 운영 지침을 다루는 [RFC 6698(2012)](https://www.rfc-editor.org/rfc/rfc6698.html)과 [RFC 7671(2015)](https://www.rfc-editor.org/rfc/rfc7671.html)
