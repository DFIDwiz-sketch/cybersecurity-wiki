한 브라우저는 곧바로 HTTPS로 접속하고 다른 브라우저는 301을 받은 뒤 같은 페이지에 도착합니다. 최종 URL은 같지만 남는 증거는 다릅니다. 실제로 HTTP를 보냈는지, 브라우저가 언제 정책을 저장했는지, 애플리케이션에 요청이 도착하기 전에 어디서 실패할 수 있는지 살펴봅니다.

## 1. HTTPS로 연결되는 여러 경로

**HTTP Strict Transport Security(HSTS)**는 호환 클라이언트가 오류 없는 HTTPS 응답의 유효한 `Strict-Transport-Security` 헤더에서 학습할 수 있는 정책입니다. 브라우저는 동적 정책을 DNS 호스트 이름별로 저장합니다. 활성 정책이 적용되는 이름에서는 HTTP 요청을 보내기 전에 URL을 HTTPS로 바꿉니다. 이후 TLS 검증에 실패하면 HSTS를 적용한 클라이언트는 연결을 종료합니다. IP 주소를 직접 사용한 URL은 RFC에서 정의한 HSTS 호스트 이름 범위에 포함되지 않습니다.

| 동작 | 누가 언제 처리하나요? | 확인할 증거 |
| --- | --- | --- |
| 서버의 HTTP 리디렉션 | 엣지나 서버가 평문 요청을 받은 뒤 `Location`이 담긴 3xx를 보냄 | 응답한 지점의 HTTP 요청과 응답 |
| 저장된 HSTS | 클라이언트가 HTTP 전송 전에 이미 저장한 정책을 적용 | 앞선 정상 HTTPS 응답, 정책 범위와 시각, 클라이언트의 전환 기록 |
| HSTS 사전 탑재 | 지원 브라우저가 배포판에 포함된 정책을 적용 | 브라우저 종류·버전, 공급자 목록이나 브라우저 정책 증거 |
| HTTPS 우선 또는 전용 설정 | 브라우저의 설정에 따라 HTTPS를 먼저 시도하거나 요구 | 브라우저 설정, 요청 추적 기록, 버전 |

3xx는 서버에 도착한 요청에 대한 응답입니다. 개발자 도구는 클라이언트에서 일어난 전환을 내부 리디렉션으로 표시할 수도 있습니다. 서버 응답으로 해석하기 전에 네트워크 추적과 엣지 로그를 대조하세요.

## 2. 시간에 따라 정책이 적용되는 과정

가상 브라우저가 0초에 `http://learn.example.test/`에 접속합니다. 이미 저장한 정책, 적용되는 사전 탑재 항목, 다른 HTTPS 전환 설정은 없다고 가정합니다. HTTP 엣지는 `https://learn.example.test/`를 가리키는 301을 보냅니다. 클라이언트가 유효한 TLS 연결을 맺으면 다음 헤더를 받습니다.

```http
Strict-Transport-Security: max-age=300; includeSubDomains
```

- `max-age`는 받은 시점부터 유지할 초 단위 시간입니다. 같은 호스트의 유효한 새 헤더는 만료 시각을 갱신하고 하위 도메인 설정을 바꿀 수 있습니다. 이후 응답에 헤더가 빠져도 기존 항목이 즉시 지워지지는 않습니다. 평문 HTTP로 받은 HSTS 헤더는 무시됩니다.
- 60초에 부모 정책의 `includeSubDomains` 때문에 `http://media.learn.example.test:80/`가 HTTP 전송 전에 `https://media.learn.example.test:443/`으로 바뀝니다. 80이 아닌 포트를 명시했다면 포트는 유지됩니다. `other.example.test` 같은 형제 이름에는 이 부모 정책이 적용되지 않습니다.
- 120초에 자식 호스트가 오류 없는 HTTPS 응답으로 `max-age=0`을 보내면 자식이 직접 저장한 항목만 삭제됩니다. 부모 항목이 활성 상태라면 자식에게 계속 적용됩니다. 부모 정책이 갱신 없이 만료되면 상속받은 적용 범위도 사라집니다. 자식이 별도로 저장한 정책이나 브라우저에 탑재된 정책은 각각 확인해야 합니다.
- 사전 탑재는 지원 클라이언트의 첫 방문에도 적용될 수 있습니다. 응답에 `preload` 토큰이 있다고 해서 배포된 목록에 실렸다는 뜻은 아닙니다. Chromium의 등록·제거 절차가 별도로 있습니다. 헤더를 변경한 뒤에도 기존에 설치된 버전의 목록을 고려해야 합니다.

시각, 이름, 응답은 설명을 위한 가상 자료입니다.

## 3. 실패 원인 좁히기와 증거 수집·대응

첫 방문에 평문 HTTP가 전송되면 리디렉션을 받기 전에 통신이 가로채이거나 바뀔 수 있습니다. 활성 HSTS가 적용되는 이름에서는 이 평문 요청을 보내지 않습니다. HSTS는 만료된 인증서나 호스트 이름 불일치를 해결하지 못하며, 앱 작업의 권한도 판단하지 않습니다. HTTP로만 제공하는 하위 호스트가 있는데 부모에 `includeSubDomains`를 적용하면 브라우저가 그 호스트에 접속하지 못할 수 있습니다. 앱이 요청을 받기 전에 TLS에서 실패할 수 있습니다.

1. **클라이언트와 응답한 엣지 양쪽을 확인합니다.** UTC 시각, 브라우저 종류와 버전, 새 프로필인지, 처음 입력한 URL의 스킴과 포트, 실제 전송한 스킴, TLS 검증 결과와 내부 전환 표시를 기록합니다. 민감한 값을 제거한 브라우저 추적 자료를 엣지 리디렉션 로그나 클라이언트 방향 HTTPS 응답 헤더와 연결합니다. 엣지에서 리디렉션했다면 원본 서버에는 요청이 기록되지 않을 수 있습니다.
2. **호스트 이름과 시각을 기준으로 정책을 확인합니다.** 관측한 헤더와 응답 상태, 응답 지점, 상위 이름에서 적용되는 항목과 만료 시각, 사전 탑재 또는 브라우저 설정을 기록합니다. 동일한 설정에서 새 프로필과 정책을 저장한 프로필을 비교하세요. 새 프로필에도 브라우저의 사전 탑재 목록은 적용될 수 있습니다. 한 엣지에서 받은 헤더는 그 요청의 응답을 보여 줍니다.
3. **정상과 이례적인 결과를 대조합니다.** 배포 후 HTTPS 응답의 헤더가 의도치 않게 사라지거나 바뀌었는지, 정책이 적용될 것으로 예상한 이름에 평문 요청이 생기는지 살핍니다. 계획된 점검에서 스킴과 상태 코드를 관측하고, 엣지 설정 변경·인증서·브라우저 자료와 연결합니다. 새 프로필, HSTS 미지원 클라이언트, 만료된 정책, 적용 범위 밖의 이름도 평문 요청을 설명할 수 있습니다.
4. **엣지와 앱 담당자와 대응합니다.** 원본 헤더와 클라이언트 자료를 보존합니다. 적용 대상 이름에서 인증서 오류가 있다면 유효한 TLS를 먼저 복구합니다. 하위 도메인 정책을 넓히려면 먼저 대상 호스트를 파악합니다. 승인된 정책 변경에서는 학습 항목 만료나 유효한 `max-age=0` 응답, 부모 정책, 브라우저 사전 탑재를 각각 확인하세요. 영향받은 클라이언트에서 HTTPS 접속과 정책 적용 범위를 다시 확인합니다.

승인된 호스트나 동등한 스테이징 경로에서 스킴별 첫 응답을 확인할 수 있습니다. 아래 이름은 가상이므로 직접 운영하며 점검 권한이 있는 이름으로 바꾸세요. 명령은 GET을 사용하고 리디렉션을 따라가지 않으며 본문을 버립니다. 인증서 검증은 유지합니다.

```bash
curl -q -sS -D - -o /dev/null http://learn.example.test/
curl -q -sS -D - -o /dev/null https://learn.example.test/
```

HTTP 상태 및 `Location`을 HTTPS 응답과 `Strict-Transport-Security` 값에 대조하세요. 정책이 적용된 클라이언트에서 HSTS가 동작하려면 HTTP 포트가 열려 있을 필요는 없습니다. 네트워크나 TLS 오류로 헤더를 받기 전에 실패할 수 있습니다. 명령은 curl 공식 문서로 검토했습니다. 이 조회는 서버 응답을 보여 주며 브라우저의 저장 정책, 사전 탑재 정책, HTTPS 우선 동작을 재현하지 않습니다.

## 4. 오프라인 실습

승인된 학습 환경에서 <a href="{{ '/assets/labs/http-hsts-evidence.py' | relative_url }}" download="http-hsts-evidence.py">정책 계산 스크립트</a>와 <a href="{{ '/assets/labs/http-hsts-evidence.json' | relative_url }}" download="http-hsts-evidence.json">가상 이벤트</a>를 같은 디렉터리에 저장하세요. Python 3.8 이상에서 실행합니다.

```bash
python3 http-hsts-evidence.py http-hsts-evidence.json
```

각 사례는 비어 있는 프로필에서 시작합니다. 입력은 헤더를 해석한 지시문과 HTTPS 검증 여부를 제공합니다. 예제의 소문자 DNS 이름에 대해 동적 정책의 만료, 상속, 명시적 포트를 계산합니다. 네트워크에 연결하지 않으며 헤더 구문, TLS, 사전 탑재 목록, 다른 브라우저 전환 기능을 구현하지 않습니다. `no_hsts`는 이 모델에서 적용할 동적 정책을 찾지 못했다는 뜻입니다.

| 사례 | 기대 결과 |
| --- | --- |
| `first_and_later` | 첫 URL에는 정책 없음. 유효한 HTTPS 헤더 수신 후 대상 URL 전환 |
| `plaintext_header` | 평문 응답의 헤더는 무시 |
| `invalid_tls` | TLS 오류가 있는 응답의 헤더는 무시 |
| `expiry` | 99초에는 적용, 100초에는 만료 |
| `child_removal` | 자식 정책은 삭제되지만 부모 정책 적용은 유지. 80은 443으로 전환 |
| `port_preserved` | 명시한 포트가 80이 아니면 유지 |
| `no_subdomains` | 부모에 `includeSubDomains`가 없으면 자식에 미적용 |
| `refresh` | 나중에 받은 유효한 헤더로 만료 연장 |

파일을 열 수 없다면 파일 이름과 디렉터리를 확인하세요. 결과가 예상과 다르면 이벤트 순서와 헤더 수신 시각, 부모의 활성 정책을 확인합니다. `child_removal`에서 부모의 `include_subdomains`를 false로 바꿔 보세요. 자식 정책을 삭제한 뒤 `no_hsts`가 나와야 합니다. 게시 사례는 가상 자료로 실행했습니다. 실제 브라우저의 사전 탑재 목록이나 배포된 엣지 정책은 이 실습의 검증 범위에 포함하지 않았습니다.

## 5. 확인 문제와 완료 기준

1. **301이 서버에서 왔는지 어떻게 아나요?** 클라이언트 방향 지점에서 기록한 HTTP 요청과 거기에 대응하는 301을 대조합니다. 개발자 도구의 내부 전환만으로는 서버 응답을 증명할 수 없습니다.
2. **평문 HTTP 응답으로 HSTS를 학습할 수 있나요?** 동적 정책은 오류 없는 보안 연결에서 유효한 헤더를 받았을 때 학습합니다.
3. **자식에서 `max-age=0`을 받았는데 왜 HTTPS로 바뀌나요?** 자식은 자기 항목만 바꿉니다. `includeSubDomains`가 있는 부모의 활성 정책과 사전 탑재 정책을 확인하세요.
4. **전환 후에도 앱 로그에 아무 기록이 없을 수 있나요?** TLS 검증에 실패하면 보안 연결로 HTTP 요청을 보내기 전에 중단될 수 있습니다.

첫 방문과 이후 요청의 차이를 설명하고, 호스트 이름과 시각으로 하위 도메인에 정책이 적용되는지 판단해 보세요. 장애 조사에 필요한 브라우저·TLS·엣지 증거를 각각 말할 수 있으면 완료입니다.
