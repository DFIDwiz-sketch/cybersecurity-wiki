TLS 종료 지점에는 재개된 연결이 기록됐고, API 로그에는 같은 작업에 대한 요청이 두 건 남았습니다. TLS 기록으로 연결을 맺은 방식은 알 수 있습니다. 중복을 설명하려면 종료 지점이 조기 데이터를 받아들였는지, 애플리케이션이 작업을 두 번 반영했는지 각각 확인해야 합니다.

## 1. 티켓, TLS 연결, HTTP 세션의 차이

**TLS 세션 재개**는 이전 연결의 암호학적 상태를 이용해 새 TLS 연결을 맺는 방식입니다. TLS 1.3 서버는 클라이언트의 Finished 메시지를 받은 뒤 **NewSessionTicket**을 보낼 수 있습니다. 티켓은 이전 핸드셰이크에서 파생된 재개용 **사전 공유 키(PSK)**를 식별합니다. 새 연결에서 클라이언트는 티켓을 PSK 식별자로 제안하고, 그 키를 안다는 것을 **바인더(binder)**로 증명할 수 있습니다. 서버가 제안을 받아들이지 않아도 조건이 맞으면 전체 핸드셰이크를 진행할 수 있습니다.

재개 핸드셰이크도 새 연결의 트래픽 키를 파생합니다. PSK에 일회용 Diffie–Hellman 키 교환을 더하는 `psk_dhe_ke`는 순방향 비밀성을 위해 RFC 9325가 권고하는 방식입니다. **0-RTT 조기 데이터**는 선택 기능입니다. 클라이언트는 서버의 핸드셰이크 메시지를 받기 전에 앱 데이터를 보낼 수 있습니다. 이 데이터는 이전 PSK와 ClientHello에서 파생한 조기 트래픽 키로 암호화됩니다. 이때는 새 연결의 일회용 키 교환 결과가 아직 반영되지 않습니다. 세션 재개 수락과 조기 데이터 수락은 별개의 판단입니다. HTTP 세션 쿠키나 앱 토큰은 별도의 자격 증명이며 여러 TLS 연결에 걸쳐 쓰일 수 있습니다.

| 관측 | 확인할 수 있는 사실 | 다음 확인 |
| --- | --- | --- |
| 티켓 수신 | 클라이언트가 이후 재개를 제안할 수 있음 | 다음 연결 확인 |
| 관측 가능한 ClientHello의 PSK | 클라이언트가 PSK 식별자를 제안함 | 서버의 선택과 종료 지점 로그 |
| ServerHello의 PSK 선택 | 서버가 이 핸드셰이크에서 PSK를 선택함 | 핸드셰이크 완료와 재개 결과 |
| 종료 지점의 조기 데이터 수락 | TLS가 조기 단계에서 앱 바이트를 수락함 | HTTP 요청과 앱 감사 기록 |
| 요청 완료·작업 반영 | 감사 종류에 따라 앱 처리나 상태 변경을 확인할 수 있음 | 작업 ID, 재시도와 영향 범위 |

## 2. 정상 연결 두 건 따라가기

가상 예시에서 클라이언트가 에지의 TLS 종료 지점을 거쳐 공개 상태 페이지를 읽습니다. 10:00:00 UTC에 TCP로 연결하고 전체 TLS 1.3 핸드셰이크에서 서버 인증서를 검증합니다. 응답을 읽는 과정에서 핸드셰이크가 끝난 뒤 발급된 티켓도 처리합니다. 10:00:05에 새 TCP 연결을 열어 그 티켓을 제안합니다. 종료 지점이 재개를 수락하고, 클라이언트는 핸드셰이크가 끝난 뒤 두 번째 HTTP 요청을 보냅니다. 이 사례에서는 **TCP 연결 두 건**, **재개 핸드셰이크 한 건**, **조기 데이터 없음**, **앱 요청 두 건**을 기록할 수 있습니다. HTTP keep-alive처럼 이미 열려 있는 연결을 계속 쓰는 경우라면 두 번째 TLS 핸드셰이크가 없습니다.

다른 클라이언트가 조기 데이터를 제안했다면 에지가 실제로 수락했는지 확인하세요. 수락 신호는 암호화된 `EncryptedExtensions`에 있으므로 키가 없는 일반 수동 캡처로는 확인할 수 없습니다. 관측 가능한 ClientHello의 `early_data` 확장은 제안에 해당합니다. PSK 확장도 ECH 내부 ClientHello에 있으면 보이지 않을 수 있습니다. 에지에서 원본 서버로 가는 구간에서는 핸드셰이크 이후에 보냈더라도, 이전 구간의 조기 요청이 중계됐을 수 있습니다. RFC 8470의 `Early-Data: 1`은 이전 구간의 위험을 전달하는 신호입니다. 신뢰하는 프록시의 설정과 함께 해석하고, 헤더 하나로 어느 구간에서 조기 바이트를 수락했는지 단정할 수 없습니다.

## 3. 요청이 중복됐을 때 조사할 이유

TLS 1.3의 조기 데이터에는 재전송 공격을 본질적으로 막아 주는 보장이 없습니다. 특히 노드 간 재전송 방지 상태가 일관되지 않으면 둘 이상의 에지가 같은 조기 요청을 받아들일 수 있습니다. 타임아웃이나 정책 거부 뒤의 정상 재시도도 비슷한 요청 로그를 남깁니다. 동일한 요청 ID나 쿠키, 2xx 응답으로 공격자를 판단할 수 없습니다. 실제 상태 변경이 한 번인지 여러 번인지, 재시도에 기존 처리 결과를 응답한 것인지 확인하세요.

HTTP의 안전한 메서드는 의미를 기준으로 정의합니다. GET으로 제공하는 경로에도 구현상 의도하지 않은 부수 효과가 있을 수 있습니다. 실제 처리 로직을 검토한 뒤 조기 처리 여부를 판단하세요. 상태가 바뀌거나 재전송에 민감한 작업은 해당 프로토콜 지침과 앱 정책이 위험을 처리하는 경우에만 조기 데이터 사용을 검토합니다. 서버가 재전송될 수 있는 요청을 처리하지 않기로 하면 HTTP **425 Too Early**를 반환할 수 있습니다. 이 응답에 대한 재시도는 조기 데이터로 보내면 안 됩니다. TLS 계층에서 먼저 조기 데이터를 거절하는 경우에는 HTTP 상태 코드가 없을 수 있습니다.

## 4. 수집·탐지·대응

1. **TLS가 끝나는 곳에서 수집합니다.** 에지에서 TLS 버전, 핸드셰이크 완료, 재개 여부, 조기 데이터 제안·수락, 종료 노드, 연결 ID와 UTC 시각을 기록할 수 있는지 확인하세요. 필드의 이름과 제공 여부는 제품마다 다릅니다. 값이 없거나 수집에서 제외된 것과 거짓으로 기록된 것을 구분합니다. 승인된 정상 동작으로 기록 범위를 확인하고, 원본 티켓, PSK, 키 로그, 세션 쿠키나 불필요한 본문은 로그로 남기지 않습니다.
2. **실제 요청이 지난 경로를 대조합니다.** 클라이언트 쪽 연결 ID와 원본 서버 쪽 연결 ID는 따로 유지합니다. 신뢰할 수 있는 요청 ID를 에지에서 원본까지 전달하고 HTTP 메서드, 경로와 상태 코드를 기록하세요. 업무 작업 ID, 처리 결과와 해당하는 경우 중복 제거 판단을 서비스 감사 기록에서 확인합니다. 서로 다른 설정을 한데 묶지 않도록 정책 버전과 노드도 남깁니다.
3. **가능한 원인을 비교합니다.** 같은 시간대에서 에지 노드, 경로, 정책 버전별 조기 데이터 처리 결과와 425 비율을 비교하세요. 상태를 바꾸는 경로에서 조기 데이터 수락을 발견하면 중복이 관측되지 않았어도 검토합니다. 중복 반영이 의심되면 타임아웃 재시도, 앱 작업자, 중복 제거 범위와 독립적인 에지·앱 기록을 비교합니다. 재개율이 낮아진 것은 배포나 만료, TLS 종료 지점 변경 때문일 수도 있습니다.
4. **승인된 정책이 적용됐는지 확인합니다.** 재전송에 민감한 경로가 모든 진입점에서 조기 데이터를 처리하지 않는지 확인하세요. 필요하면 여러 노드가 일관된 저장소를 사용하는 등 앱의 작업 단위 중복 제거도 검토합니다. 정상 입력으로 응답과 실제 반영 결과를 확인합니다. 일반 세션 재개와 조기 데이터 처리 지표를 따로 검증하세요. QUIC은 제품의 HTTP/3·0-RTT 관측 항목과 RFC 9001의 전송 제약을 따로 확인합니다.

## 5. 승인된 루프백 실습 · 세션 재개 관측

<a href="{{ '/assets/labs/tls-resumption-lab.py' | relative_url }}" download="tls-resumption-lab.py">Python 루프백 실습 다운로드</a>

승인된 Linux 환경에서 PATH에 Python 3와 OpenSSL 3.x 명령줄 도구를 준비하세요. 스크립트는 `127.0.0.1`에 임시 TLS 서버를 열고 실습 클라이언트에서만 수명이 짧은 테스트 인증서를 신뢰합니다. TLS 1.3 핸드셰이크 뒤 읽기 전용 요청을 세 번 보냅니다. 조기 데이터, 재전송 공격, 운영 트래픽, 신뢰 저장소 변경은 실습 범위에 포함하지 않습니다.

~~~bash
python3 tls-resumption-lab.py
~~~

| 연결 | 제안한 세션 | 예상 OpenSSL 결과 |
| --- | --- | --- |
| 1 · 전체 핸드셰이크 | 없음. 발급받은 세션 저장 | `New, TLSv1.3`, HTTP 200 |
| 2 · 재개 | 1번 연결에서 받은 세션 | `Reused, TLSv1.3`, HTTP 200 |
| 3 · 전체 핸드셰이크 대조 | 저장한 세션을 넘기지 않음 | `New, TLSv1.3`, HTTP 200 |

첫 클라이언트가 HTTP 응답을 읽는 동안 OpenSSL이 핸드셰이크 이후의 티켓을 처리합니다. 핸드셰이크 직후 종료하면 티켓을 놓칠 수 있습니다. 재개 단계에서 `New`가 나오면 티켓을 저장했는지와 같은 TLS 서버가 계속 실행됐는지 확인하세요. 티켓 누락, 바인드 실패, 이름 검증 실패, 타임아웃은 오류로 처리합니다. 정상적으로 종료할 때 임시 폴더와 세션 파일을 삭제합니다. 내보낸 세션 파일은 민감한 자료로 다루세요.

## 6. 확인 문제와 완료 기준

1. **OpenSSL에 Reused가 나오면 요청이 조기 데이터로 전송됐나요?** 재개된 핸드셰이크라는 근거입니다. 조기 데이터는 종료 지점과 클라이언트에서 별도로 확인합니다.
2. **클라이언트가 조기 데이터를 제안했는데 원본에는 기록이 없습니다. 어디를 볼까요?** 원본의 기록 부재를 해석하기 전에 TLS 수락 여부, 에지의 전달 판단과 요청 경로를 확인합니다.
3. **첫 요청은 425, 재시도는 200입니다. 재전송 공격인가요?** 프로토콜에 따른 정상 재시도에서도 볼 수 있습니다. 재시도가 조기 데이터 밖에서 전송됐는지, 앱에서 어떻게 처리됐는지 확인한 뒤 원인과 영향을 판단합니다.
4. **두 노드에서 동일한 업무 작업 ID를 기록했습니다. 실제 영향은 어떻게 확인하나요?** 최종 상태를 기록하는 앱 감사 자료에서 반영 결과와 중복 제거가 기존 결과를 반환했는지 확인합니다.

세 가지 로컬 연결을 재현하고 PSK 제안, 재개 성공, 조기 데이터 수락, 애플리케이션 작업을 구분하는 증거를 설명하면 완료입니다.
