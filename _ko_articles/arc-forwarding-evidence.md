**학습 목표.** 중계를 거친 메일을 조사하면서 최종 게이트웨이가 어떤 항목을 직접 검증했는지, 어떤 이전 인증 기록을 참고했는지, 그 기록이 실제 처리에 쓰였는지 설명합니다. 도메인 정렬이 처음이라면 [SPF·DKIM·DMARC 증거]({{ '/ko/wiki/mail-auth-evidence/' | relative_url }})를 먼저 읽어 보세요.

## 1. 전달을 거치면 인증 증거가 달라지는 이유

**전달 서버**는 메일을 받아 다시 보냅니다. **메일링 리스트**는 바닥글을 붙이는 등 메시지를 수정하기도 합니다. 다음 수신기는 실제 SMTP 연결을 맺은 서버의 IP와 적용되는 봉투 도메인을 기준으로 SPF를 검사합니다. 처음의 발신 도메인에 대해 SPF가 실패하거나, SPF를 통과한 봉투 도메인이 화면의 From과 정렬되지 않을 수 있습니다. 리스트가 원래 DKIM 서명이 보호하던 내용을 바꾸면 그 서명도 실패할 수 있습니다. 최종 수신기에서 SPF와 DKIM 중 정렬된 통과 결과가 없다면, 이전 수신기의 DMARC가 통과했더라도 현재의 직접 평가는 실패할 수 있습니다.

**Authenticated Received Chain(ARC)**은 메일을 처리한 시스템이 이전 인증 평가와 처리 경로의 근거를 서명해 남기는 방식입니다. **ARC 서명자(sealer)**는 세트 하나를 추가하는 처리 시스템입니다. 한 세트의 헤더는 인스턴스 번호인 `i=` 값이 같습니다. 이 번호는 ARC 세트가 붙은 순서입니다. 세트를 추가하지 않는 서버도 메일이 지나갈 수 있습니다. 최종 수신기는 전달받은 체인을 암호학적으로 검증한 뒤, 그 평가를 신뢰하고 정책에 사용할지 별도로 결정합니다.

## 2. ARC 헤더 세 가지 읽기

| 헤더 | 기록하는 내용 | 확인할 값 |
| --- | --- | --- |
| `ARC-Authentication-Results` (AAR) | 해당 처리 시스템이 기록한 인증 평가. 받은 시점의 SPF, DKIM, DMARC 등이 포함될 수 있음. | 인스턴스 번호, 인증 서비스, 검사한 식별자와 화면에 보이는 From과의 관계 |
| `ARC-Message-Signature` (AMS) | 처리 시스템이 보내는 메일의 헤더·본문 일부를 보호하는 DKIM 방식의 서명 | 인스턴스와 서명 도메인, 검증기 결과 |
| `ARC-Seal` (AS) | 해당 ARC 세트와, 유효한 연속 체인에서는 이전 세트까지 묶는 서명. 서명자 도메인과 서명자의 체인 평가인 `cv=`가 포함됨. | 수신 경계에서 체인 검증 결과와 서명자 신원 |

유효한 체인의 첫 세트에서는 이전 체인이 없으므로 `cv=none`입니다. 이후 서명자는 이전 체인이 통과했다고 `cv=pass`로 기록할 수 있습니다. 이 값은 그 서명자가 남긴 평가이고, 최종 수신기가 직접 검증한 결과는 따로 확인해야 합니다. RFC 8617의 검증 절차는 세트 구조, 가장 최근 AMS와 ARC-Seal을 확인합니다. 이전 AMS는 메일이 정상적으로 수정된 뒤 최종 바이트와 일치하지 않을 수 있으므로, 모든 이전 AMS가 현재 메일과 같아야 ARC 체인이 통과하는 것은 아닙니다. 체인 검증은 어떤 암호학적 검사를 통과했는지 알려 줍니다. 서명자의 평가와 운영 통제를 신뢰할지는 수신기 정책에 달려 있습니다.

## 3. 정상 메일링 리스트 사례 따라가기

가상 사례에서 `billing.example.test`의 안내 메일이 승인된 중계 서버에 도착하고 정렬된 DKIM과 DMARC를 통과합니다. 중계 서버는 그 결과를 기록하고 리스트 바닥글을 붙여 보낼 버전에 ARC 세트를 추가합니다. 전달 서버는 자기 봉투 도메인으로 보냅니다. 최종 메일 서비스에서 그 도메인의 SPF는 통과하지만 화면의 From과 정렬되지 않고, 원래 DKIM 본문 서명도 실패합니다. 직접 DMARC는 실패합니다. 수신기는 ARC 체인을 검증하고 승인된 서명자를 확인합니다. 수신 정책에 따라 이전 통과 결과를 사용했다는 기록을 남기고 배달합니다. 직접 평가, 체인과 신뢰, 정책 사유, 실제 배달을 각각 기록하세요. 배달만으로 어떤 정책이 적용됐는지는 확인할 수 없습니다.

| 최종 수신기 관측 | 근거가 뒷받침하는 해석 | 다음 확인 |
| --- | --- | --- |
| 직접 DMARC 실패, 신뢰하는 서명자의 ARC 통과 | 체인이 유효하고 이전 평가를 정책에 쓸 수 있음 | 이전 평가의 식별자, 수신기의 정책 적용 사유와 추적 결과 |
| 직접 DMARC 실패, 알 수 없는 서명자의 ARC 통과 | 서명은 유효할 수 있지만 평가의 신뢰는 미확인 | 커넥터와 승인된 공급자 기록 |
| 전달 이후 ARC 실패 | 도착한 체인을 검증하지 못함 | 메시지 변경, 불완전한 내보내기, 세트 구조, DNS 키 조회와 검증 오류 |
| 메일의 `Authentication-Results`가 통과라고 주장 | 메일의 텍스트만으로 어느 서버가 썼는지 알기 어려움 | 수신자의 신뢰 경계 안에 있는 인증 서비스 확인 |
| 최종 추적에 배달 기록 | 해당 단계에서 배달이 기록됨 | ARC 예외나 다른 정책을 썼는지, 메일이 실제로 도달한 위치 |

신뢰하지 않는 서명자도 구조와 서명이 유효한 체인에 수신기가 받아들여선 안 되는 평가를 담을 수 있습니다. 정상 메일도 본문 수정이나 헤더 손실로 체인이 깨질 수 있습니다. 체인이 통과해도 URL, 첨부 파일, 표시 이름이나 결제 요청의 안전성은 별도 문제입니다. 큐, 인계와 최종 수신자 처리 확인은 [SMTP 배달 증거]({{ '/ko/wiki/smtp-delivery-evidence/' | relative_url }})를 참고하세요.

## 4. 블루팀이 수집하고 판단하는 순서

1. 승인된 게이트웨이나 사서함에서 원본 전체를 내보내 원본 헤더와 바이트를 보존합니다. 민감한 헤더와 본문을 외부 분석 사이트에 붙여 넣지 마세요. 수신자, UTC 시간대, 전달 경로와 게이트웨이 추적 ID를 기록합니다. 메시지 ID를 대조할 때는 출처와 시간 범위를 함께 사용하세요.
2. 수신자 쪽에서 신뢰하는 `Authentication-Results`를 작성한 서비스를 확인하세요. 해당 구간의 원래 From과 보고된 작성자 도메인, 통과한 인증 식별자를 비교합니다. 상위 서버의 주장과 최종 수신기 평가를 구분하세요. 일반 `Authentication-Results`는 작성자와 신뢰 경계에서의 처리 방식이 확인돼야 근거로 사용할 수 있습니다.
3. 검증기의 체인 결과, 검토된 서명자 신뢰 정책, 이전 인증 결과, 실제 정책에 그 결과를 사용했다는 기록을 확보하세요. 나중에 다시 검증할 때는 DNS 키가 바뀌었거나 내보내고 가린 사본이 수신 당시의 바이트와 다를 수 있습니다. 사건 시점의 게이트웨이와 커넥터 기록을 대조합니다.
4. Microsoft 365는 자사 서비스가 추가한 최신 AAR의 `arc=pass`와 `oda=1`을 이전 서명자를 검증하고 신뢰했다는 근거로 설명합니다. Microsoft가 작성한 Authentication-Results의 `compauth=pass`와 `reason=130`은 신뢰하는 ARC 평가를 DMARC 실패의 예외 처리에 사용했다는 제품별 표시입니다. 헤더 출처와 당시 테넌트 설정을 확인하고, 배달은 메시지 추적으로 대조하세요.
5. 평소 신뢰하는 경로에 실패가 생기면 영향받은 커넥터를 좁히고, 승인된 무해한 테스트 메일을 각 구간으로 전달해 양쪽 원본 헤더를 비교하세요. 신뢰하던 중계 서비스가 침해에 연관돼 있다면 메일·보안 담당자가 신뢰 설정을 바로잡고 영향을 받은 메일을 찾도록 조율합니다. URL과 첨부는 일반 조사 정책에 따라 검토한 뒤 처리 상태를 바꾸세요.

## 5. 가상 수신 기록 여덟 건 실습하기

[arc-forwarding-review.py]({{ '/assets/labs/arc-forwarding-review.py' | relative_url }}){: download="arc-forwarding-review.py" }와 [arc-forwarding-cases.jsonl]({{ '/assets/labs/arc-forwarding-cases.jsonl' | relative_url }}){: download="arc-forwarding-cases.jsonl" }을 본인 작업 공간의 같은 디렉터리에 둡니다. Python 3.12로 실행하세요.

```sh
python3 arc-forwarding-review.py
```

JSONL은 조사에 필요한 일부 필드만 담은 가상 내보내기 자료입니다. `prior_aligned`는 이 자료에서 이전에 정렬된 인증 통과를 확인했는지 나타냅니다. null은 정보가 없다는 뜻입니다. `evidence_source`로 수신기 기록과 메일 안의 주장을 구별합니다. 프로그램은 이미 표시된 결과를 읽으며 DNS 조회, 암호 검증 또는 정책 변경을 수행하지 않습니다.

| 사례 | 기대 판단 |
| --- | --- |
| A | 직접 DMARC 실패. 신뢰하는 ARC 예외 적용과 배달이 기록됨. |
| B | 체인은 통과했으나 서명자 신뢰는 미확인. 격리 기록이 있음. |
| C | 체인 실패. ARC 예외를 뒷받침할 근거가 없으며 거절이 기록됨. |
| D | 메일 안의 주장만 있음. 수신기의 평가와 처리 결과는 미확인. |
| E | 신뢰 가능한 이전 통과 결과와 배달이 보이지만 ARC 예외를 사용했는지는 미확인. |
| F | ARC 없이 직접 DMARC 통과. 실제 처리 결과는 미확인. |
| G | 신뢰하는 체인 통과. 정렬된 이전 통과의 근거는 없으며 격리가 기록됨. |
| H | 기록된 ARC 예외 사용과 체인 실패가 충돌함. 출처 재확인. |

출력은 여덟 줄입니다. 파일을 못 찾으면 두 파일이 같은 디렉터리에 있는지 확인하세요. 한 줄마다 완전한 JSON 객체가 있어야 합니다. 실제 조사에서 H처럼 기록이 어긋나면 정책을 판단하기 전에 시각, 독립 출처와 기록 생산자를 확인합니다. Python 3.12.14에서 여덟 사례를 실행해 예상 출력과 정확히 대조했습니다. 실제 ARC 암호 검증, Exchange Online과 다른 메일 게이트웨이의 실행 동작은 검증 범위에 포함되지 않습니다.

## 6. 확인 문제와 해설

1. **최종 수신기의 ARC는 통과했고 직접 DMARC는 실패했습니다. 어느 쪽이 틀렸나요?** 두 결과는 서로 다른 검사를 설명하므로 둘 다 맞을 수 있습니다. 서명으로 보호된 이전 평가, 서명자 신뢰 정책과 정확한 처리 사유를 확인하세요.
2. **첫 ARC-Seal에 `cv=none`이 있습니다. 체인이 깨졌나요?** 첫 세트 앞에는 검증할 체인이 없습니다. 도착한 메시지에 대한 최종 수신기의 검증 결과를 봅니다.
3. **낯선 경로에서 온 메일이 배달됐습니다. ARC가 사용됐나요?** 배달만으로 정책 사유는 확인할 수 없습니다. 신뢰하는 수신기 평가와 메시지 추적 결과를 대조하세요.

**완료 기준.** 여덟 결과를 재현하세요. A와 E에서 직접 인증, 체인 검증, 서명자 신뢰와 처리 사유를 따로 적습니다. E의 미확인 사유를 해결할 수신 측 자료를 설명하면 완료입니다.
