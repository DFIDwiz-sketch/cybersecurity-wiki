클라이언트가 1,000바이트짜리 파일을 나눠 요청했습니다. 엣지 접근 로그에는 성공 응답 세 건에 본문 1,100바이트가 기록됐습니다. 1,000바이트 전체가 빠짐없이 전달됐을까요? 그 바이트는 원본 서버가 보냈을까요? 응답 범위, 표현 식별자, 로그를 수집한 위치를 나눠서 살펴봅니다.

## 1. 범위 요청이란 무엇인가요?

**표현**(representation)은 요청에 대해 선택된 리소스의 형태입니다. 같은 URL이라도 파일 버전이나 콘텐츠 인코딩이 달라질 수 있습니다. **바이트 오프셋**은 표현의 바이트 열에서 0부터 세는 위치입니다. 범위의 양 끝은 모두 포함됩니다. 따라서 `0–399`는 400바이트입니다. gzip처럼 콘텐츠 코딩이 적용되면 오프셋도 인코딩된 바이트를 기준으로 계산합니다.

다운로드를 이어 받거나 미디어 일부를 가져올 때 범위 요청을 사용합니다. `Range: bytes=400-799`는 400번 위치부터 400바이트를, `bytes=400-`는 그 위치부터 끝까지를, `bytes=-200`은 마지막 200바이트를 요청합니다. `Accept-Ranges: bytes`는 범위 지원을 알립니다. 특정 범위 요청이 실제로 반영됐는지는 응답을 읽어 판단합니다.

| 증거 | 읽는 법 | 이어서 확인할 내용 |
| --- | --- | --- |
| `Range` | 클라이언트가 요청한 위치 | 실제 제공 범위는 응답에서 확인 |
| `If-Range: "r1"` | 선택된 표현에 강한 일치가 성립할 때 범위 적용 | 표현이 바뀌면 전체 200이 올 수 있음 |
| 단일 부분 `206` | 표현 일부분을 보내는 응답 | `Content-Range`와 실제 전송 증거 |
| 멀티파트 `206` | 각 부분에 자체 `Content-Range`가 있음 | MIME 경계와 부분 헤더를 순수 바이트 범위에서 제외 |
| `Range`를 보낸 GET에 `200` | 전체 응답. `If-Range` 불일치나 범위 무시 등이 원인 | 표현, 본문 길이와 전송 완료 확인 |
| `416` | 서버가 범위 요청을 거절함 | `Content-Range: bytes */1000`은 현재 길이를 알려 줄 수 있음 |

단일 부분 응답에서 `Content-Range: bytes 400-799/1000`은 양 끝을 포함한 위치와 표현 전체 길이를 알려 줍니다. `Content-Length: 400`이 함께 있으면 응답 본문의 길이를 나타냅니다. 헤더에 선언된 길이, 송신 계층이 전송 후 기록한 값, 클라이언트의 검증 결과는 서로 다른 증거입니다.

콘텐츠 코딩이 없는 1,000바이트짜리 가상 학습 파일을 예로 들어 봅시다.

```text
GET /training.bin
Range: bytes=0-399

HTTP 206
Content-Range: bytes 0-399/1000
Content-Length: 400
ETag: "r1"
```

1. 첫 응답의 범위는 0–399, 버전은 `"r1"`입니다. 클라이언트가 `Range: bytes=300-699`와 `If-Range: "r1"`로 이어 받습니다. 엣지는 같은 강한 ETag와 함께 300–699를 제공합니다.
2. 클라이언트가 동일한 검증자로 700–999를 요청합니다. 엣지는 세 응답이 모두 끝났고, 각각 400, 400, 300바이트를 보냈다고 기록했습니다. 합계는 1,100바이트입니다. 100바이트가 중복되므로 범위 합집합은 0–999입니다. 엣지 증거상 전체 바이트 범위를 관측했습니다.
3. 마지막 요청 전에 표현이 바뀌었다면 `If-Range`가 일치하지 않아 서버가 범위를 무시합니다. 일반 GET이 성공하면 새 표현을 200으로 돌려줍니다. 이 기록은 `"r1"`과 구분합니다. `W/`가 붙은 약한 ETag만으로는 여러 조각이 바이트 단위로 동일한 표현에서 왔는지 확인할 수 없습니다. 강한 ETag도 해당 리소스와 표현 변형 안에서 비교합니다. 암호학적 파일 해시는 별개의 증거입니다.

CDN은 캐시로 응답하거나 원본에서 다른 범위를 가져올 수 있습니다. AWS는 CloudFront가 클라이언트가 요청한 것보다 넓은 범위를 원본에 요청할 수 있다고 설명합니다. 원본 로그에 요청이 없다면 캐시 상태와 수집 범위를 확인하세요. 캐시가 조각을 결합하거나 다시 검증하는 과정은 아래 HTTP 캐시 학습 장으로 이어집니다.

## 3. 수집·탐지·대응

클라이언트에 응답하는 HTTP 종료 지점에서 수집하세요. 복호화할 수 없는 암호화 구간에서 네트워크 센서가 HTTP 헤더나 범위 위치를 보는 것은 일반적으로 어렵습니다. 요청과 응답 필드를 함께 수집하고, 각 행이 어느 구간의 관측인지 표시합니다.

- UTC 시각, 신뢰할 수 있는 엣지 요청 ID, 리소스 또는 객체 ID, 표현 변형과 콘텐츠 코딩을 기록합니다. 가능하면 인증된 주체나 다운로드 세션을 가명화해 남깁니다. 출발지 IP와 User-Agent는 맥락으로 대조합니다. 한 IP나 UA가 서로 관련 없는 여러 클라이언트에 해당할 수 있습니다.
- `Range`와 `If-Range`, 상태 코드, 응답 ETag와 `Content-Range`, 관측한 본문 바이트 수, 완료 또는 중단 표시, 캐시 상태를 남깁니다. 원본까지 연결했다면 두 구간의 상관 ID도 기록합니다. 조사용 내보내기에서 자격 증명, 인증 헤더, 쿠키, 서명 URL의 매개변수는 제외합니다.
- NGINX 필드 예시는 `$http_range`, `$http_if_range`, `$sent_http_content_range`, `$sent_http_etag`, `$body_bytes_sent`, `$request_completion`입니다. 접근 로그 형식에 필요한 필드를 명시해야 합니다. 완료 변수는 NGINX가 관측한 요청 완료를 나타냅니다. 사용 중인 버전과 프로토콜에서 정상 완료와 통제된 중단을 각각 시험해 바이트와 완료 필드의 의미를 확인합니다.
- 단일 부분 요청의 경우 승인된 다운로드 맥락, 리소스, 표현 변형, 코딩, 강한 검증자별로 묶습니다. 범위 길이와 관측된 본문 바이트를 비교하고, 원시 전송량과 중복을 뺀 범위를 함께 보존합니다. 필드 누락, 표현 변경, 수집 공백, 전송 중단으로 판단을 유보해야 할 때도 있습니다. 멀티파트라면 가능할 때 부분별 자료를 확보합니다. 전체 응답 헤더만으로 부분별 위치를 복원하기는 어렵습니다.

**탐지 단서.** 영상 탐색, 재시도, 새 클라이언트 출시로도 범위 요청량이 늘어납니다. 범위 처리 비용을 과도하게 늘리는 오용도 가능합니다. 같은 시간대와 경로에서 요청률, 범위 패턴, 오류율, 엣지·원본 지연이나 자원 사용량을 대조합니다. 비인가 열람이 의심되면 인증 주체와 인가 판정, 자료의 민감도, 클라이언트 방향 응답을 연결합니다. 패턴이나 상태 코드 하나로 사고나 행위자를 확정할 수 없습니다.

**대응.** 엣지·원본·인가 원본 기록을 보존하고 수집 공백을 문서화합니다. 서비스 담당자와 정상 고객 동작을 확인하세요. 자원 부담이 있다면 운영 담당자와 요청 제한 및 캐시 동작을 검토하고, 승인된 변경 후 정상 재생과 이어 받기를 시험합니다. 자료 노출이 의심되면 담당자와 접근을 제한하고 영향을 받은 객체 버전과 주체를 보존합니다. 최종 기록에는 요청, 엣지 전송, 중복을 제외한 범위, 클라이언트 검증 중 무엇을 관측했는지 명시하세요.

## 4. 오프라인 증거 실습

승인된 학습 환경에서 Python 3.8 이상을 사용합니다. <a href="{{ '/assets/labs/http-range-evidence.py' | relative_url }}" download="http-range-evidence.py">범위 계산 스크립트</a>와 <a href="{{ '/assets/labs/http-range-evidence.json' | relative_url }}" download="http-range-evidence.json">가상 증거 파일</a>을 같은 디렉터리에 저장하세요. 스크립트는 로컬 JSON만 읽습니다. 각 사례에는 클라이언트 방향 구간의 리소스 하나와 클라이언트 세션 하나가 들어 있습니다.

```bash
python3 http-range-evidence.py http-range-evidence.json
```

| 사례 | 기대 관측 결과 |
| --- | --- |
| `overlap_complete` | 조건을 충족한 행의 본문 합계 1,100바이트, 중복 제외 1,000바이트 |
| `gap` | 완료된 206 두 건이 있어도 1,000바이트 중 800만 관측 |
| `version_switch` | `"r1"`에서 400, `"r2"`에서 600바이트. 두 그룹을 분리 |
| `interrupted` | 두 번째 행은 미완료. 400바이트만 인정하고 중단 행의 200바이트는 범위 계산에서 제외 |
| `weak_etag` | 저장된 부분 응답을 검증된 그룹으로 묶을 수 없음 |
| `full_fallback` | 200은 별도 보고. 그 전 206은 이전 버전에서 400바이트를 관측 |
| `unsatisfied` | 416은 별도 보고. 오류 본문은 표현의 범위에 포함하지 않음 |
| `different_encoding` | 가상 ETag 문자열이 같아도 identity와 gzip을 분리 |

파일을 열 수 없다면 작업 디렉터리와 두 파일 이름을 확인하세요. 행이 제외됐다면 상태, ETag, 범위 경계, 완료 여부, 실측값을 확인합니다. `gap` 사례의 복사본에서 두 번째 완료 범위를 400–999, 실측값을 600으로 고쳐 보세요. 전체 범위를 관측했다는 결과가 나와야 합니다. 게시한 예제는 가상 파일로 실행했습니다. CloudFront와 NGINX 동작은 공식 문서로 검토했습니다.

## 5. 확인 문제와 완료 기준

1. **1,000바이트짜리 파일에서 왜 합계 1,100바이트가 나올까요?** 재시도나 범위 중복으로 같은 오프셋이 여러 번 전송될 수 있습니다. 조건을 충족한 범위의 합집합을 계산하세요.
2. **ETag `"r1"`의 앞 절반과 `"r2"`의 뒤 절반으로 한 버전 전체를 확인할 수 있을까요?** 각각 따로 추적합니다. URL과 전체 길이가 같아도 바이트 동일성을 입증할 수 없습니다.
3. **파일이 정상적으로 저장됐는지는 어떻게 확인하나요?** 클라이언트의 완료 기록, 크기, 가능하면 신뢰할 수 있는 해시를 확인합니다. 엣지 접근 로그는 송신 지점에서 본 증거입니다.
4. **416에도 작은 바이트 수가 찍혔다면 무엇을 뜻하나요?** 오류 응답에도 본문이 있을 수 있습니다. 해당 바이트는 요청한 파일에 포함되지 않습니다.

정상 사례의 범위 합집합을 계산하고, 버전 변경과 전송 중단 사례에서 전체 범위를 확인할 수 없는 이유를 설명하세요. 클라이언트 검증과 인가를 확인하려면 어떤 증거가 더 필요한지도 말할 수 있으면 완료입니다.
