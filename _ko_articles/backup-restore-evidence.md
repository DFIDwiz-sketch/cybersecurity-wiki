**학습 목표.** 백업 기록과 복원 결과를 보고 어떤 검사가 통과했고 어떤 근거가 더 필요한지 설명합니다. 데이터가 유실됐을 수 있는 구간을 계산하고, 복구 목표에 따라 재개 또는 보류 결정을 기록합니다.

## 1. 무엇을 복구해야 하나요?

**백업**은 데이터나 시스템 상태를 되살리기 위해 보관한 사본입니다. **스냅샷**은 특정 시점의 상태를 담습니다. 원래 계정이나 저장소, 암호화 키를 잃고도 스냅샷을 읽을 수 있는지는 보관 위치와 변경·삭제 권한에 달려 있습니다. **복원**은 데이터나 상태를 사용할 환경으로 가져오는 일입니다. **서비스 복구**에는 접근 권한, 필요한 외부 시스템, 보안 확인과 업무 재개까지 포함됩니다.

| 용어 | 뜻 | 확인할 근거 |
| --- | --- | --- |
| 복구 시점 목표(RPO) | 어느 시점까지의 데이터가 복구돼야 하는지 정한 목표. 감수할 수 있는 유실 가능 시간으로 표현할 수 있음 | 합의한 목표와 검증된 애플리케이션 처리 시점 |
| 복구 시간 목표(RTO) | 합의한 서비스 범위에서 허용하는 복구 소요 시간 | 시작 시각, 완료 기준, 해당 단계를 포함한 훈련의 측정 기록 |
| 백업 명세서 | 어떤 사본을 보관했는지 식별하기 위한 기록 | 백업 ID나 객체 버전, 범위, 해시, 보존 기간이나 복제 위치 |
| 애플리케이션 체크포인트 | 처리가 어느 시점 또는 순번까지 완료됐는지 보여 주는 경계 | 애플리케이션 기록, 트랜잭션 순번 또는 별도의 신뢰할 수 있는 자료 |

백업 작업이 09:56에 성공으로 끝났어도 일관되게 담긴 데이터는 09:52까지일 수 있습니다. 하나는 작업 종료 시각이고 다른 하나는 데이터의 기준 시각입니다. 아래 예시의 백업 명세에는 두 값이 모두 기록돼 있습니다. 일부 시스템에서는 백업 뒤의 트랜잭션 로그를 재생해야 목표 시점에 도달합니다. 전체 복원 경로를 시험한 뒤 애플리케이션이 실제로 어디까지 처리했는지 증거로 남기세요.

## 2. 정상 복구 결정 한 건을 따라가세요

작은 주문 서비스가 **10:00 UTC**에 중단됐다고 가정합니다. 훈련 목표는 **RPO 15분, RTO 60분**입니다. 시간은 장애 발생부터 서비스 담당자의 재개 승인까지 잽니다. 다른 자료와 대조한 결과 선택한 사본은 **09:52 UTC**까지의 데이터를 빠짐없이 담고 있습니다. 따라서 **데이터 유실 가능 구간은 8분**이고 예시의 RPO 범위 안입니다. 실제 주문 몇 건이 유실됐는지는 트랜잭션이나 정산 기록을 별도로 대조해야 알 수 있습니다.

![근거가 있는 시점을 선택하고 격리 환경에 복원한 다음, 데이터 검증과 서비스 시험을 거쳐 재개를 승인합니다.]({{ '/assets/diagrams/restore-verification-ko.svg' | relative_url }})

*백업 원본과 사고 증거는 시험용 사본과 분리합니다. 검사에 실패하면 근거를 남긴 뒤 승인된 다른 시점을 선택하거나 담당자에게 알리세요.*

가상 훈련에서 팀은 복구용 계정으로 사본을 가져오고, 보호된 명세서를 확인한 뒤 격리된 환경에 복원했습니다. 담당자는 예상한 주문 기록을 대조하고, 시험용 연동 시스템에서 로그인과 주문 조회도 확인했습니다. **10:42 UTC**에 재개를 승인했으므로 합의한 범위의 복구 시간은 **42분**입니다. 그 시각에 데이터베이스만 준비됐다면 전체 서비스에 걸린 시간은 아직 모릅니다.

| 검사 대상 | 통과하면 알 수 있는 것 | 이어서 볼 자료 |
| --- | --- | --- |
| 사본과 접근 권한 | 승인된 복구용 계정으로 선택한 버전을 읽고 복호화 키를 사용할 수 있음 | 원래 계정이나 키 저장소, 네트워크가 없을 때도 가능한지 확인 |
| 바이트 | 해당 파일의 SHA-256이 별도로 신뢰하는 명세와 일치함 | 형식과 내부 데이터 무결성 |
| 데이터베이스 | 형식과 내부 구조 검사가 통과함. 참조 관계는 별도 검사 | 예상 레코드, 합계, 복구 시점 |
| 서비스 | 정해진 업무 흐름과 보안 통제를 합의한 범위에서 시험함 | 승인, 소요 시간, 재개 후 모니터링 |

## 3. 백업은 어떤 상황에서 함께 영향을 받나요?

동기화된 사본에는 원본의 삭제나 손상도 빠르게 반영될 수 있습니다. 운영 환경과 복구 환경이 관리자 계정을 공유하면 한 계정의 침해가 원본과 백업 모두에 영향을 줄 수 있습니다. 변경 불가 버전이나 오프라인 사본은 변경 위험을 줄이는 데 도움이 됩니다. 실제 효과는 보존 설정과 저장 방식, 접근 정책에 달려 있습니다. 복구하려면 사본을 읽을 수 있어야 하고, 독립적인 접근 수단과 복호화 키, 호환 소프트웨어도 필요합니다.

이상이 발견되기 전부터 원치 않는 설정이나 지속성이 사본에 들어 있을 수 있습니다. 해시가 일치해도 그 기준 사본 자체가 이미 영향을 받았을 가능성은 남습니다. 가장 이른 이상 징후와 그 기간을 확인할 수 있는 로그 범위를 기록하세요. 근거가 있는 시점을 골라 격리 환경에서 검사합니다. 오래된 사본을 쓰면 보안 위험은 줄어들 수 있지만 데이터 유실 범위는 커지므로 서비스 담당자와 함께 판단하세요. 복원에 성공해도 마지막으로 안전했던 시점이 불확실할 수 있습니다.

## 4. 블루팀 수집·탐지·대응

**사고 전에 기준을 정하세요.** 서비스 담당자와 함께 알려진 레코드 조회, 합계 대조, 격리 환경에서의 무해한 테스트 거래처럼 대표 검사를 정합니다. 복구 범위, 허용 유실, 시간 측정의 시작과 끝을 합의하세요. 백업 대상, 사본 ID나 객체 버전, 원본 체크포인트, 보호된 명세서, 보존 기간과 암호화 키 의존성을 기록합니다. 백업 관리 권한을 제한하고 운영 계정 없이도 복구에 필요한 접근이 가능한지 시험하세요. 원본 워크로드가 수정할 수 없는 곳에 검증 근거를 보관합니다.

**복구 가능성을 떨어뜨리는 변화를 살피세요.** 반복되는 백업 실패, 예상 밖의 보존 기간 변경, 백업 관리자 활동, 키 접근 불가, 사본 누락을 관찰합니다. 예를 들어 보존 정책 변경 알림을 조사하려면 플랫폼의 관리 감사 기록, 백업 또는 정책 ID, 행위자, 확인할 수 있는 이전·현재 설정과 작업 승인 기록이 필요합니다. 해당 계정과 저장소의 로그를 실제로 수집하는지 확인하세요. 정책 변경은 승인된 이전 작업에서도 발생하며, 백업 작업 성공 상태는 전체 복구 근거 중 하나입니다.

**복구 중에도 원본을 보존하세요.** 백업 버전과 사고 자료를 남겨 두고 유일한 사본 위에 복원하지 않습니다. 승인된 접근, 필요한 최소 연결, 호환되는 소프트웨어를 갖춘 격리 환경을 사용하세요. 구성, 신원 시스템, 암호화 키, 상위 연동 시스템을 필요한 순서대로 되살립니다. 합의된 서비스 완료 기준까지 시간을 잽니다. 복구 시점, 확인한 업무, 실패한 검사, 미확인 범위와 승인 근거를 남깁니다. 사고 대응 절차에 따라 서비스를 재개하고 복원된 시스템을 관찰하세요. 예상과 다르면 재개를 보류하고 근거를 기록한 뒤 승인된 다음 선택지를 검증합니다.

## 5. 오프라인 실습 · SQLite 복원 5건

[restore-verification.py]({{ '/assets/labs/restore-verification.py' | relative_url }})를 내려받아 Python 3과 표준 `sqlite3` 모듈이 있는 자가 소유 환경에서 실행하세요. 입력 파일을 받지 않으며 임시 폴더에 가상 데이터베이스만 만듭니다. SQLite 백업 API로 스냅샷을 만들고, 닫힌 스냅샷을 복원용 파일에 복사합니다. 해시를 확인한 뒤에는 작업 사본을 읽기 전용으로 엽니다. 보호된 백업 명세서와 주문 금액의 기준값이 별도로 있다고 가정합니다. 실습용 값 하나로 서비스의 처리 완료 시점을 표현합니다.

~~~bash
python3 restore-verification.py
~~~

| 사례 | 예상 결과 | 의미 |
| --- | --- | --- |
| A · 예상한 데이터 | `ready_for_lab_use`, 8분 | 실습의 해시, 구조, 참조, 복구 시점, 예상 레코드 검사를 통과 |
| B · 오래된 사본 | `outside_rpo`, 95분 | 사본은 열리지만 08:25까지의 기록은 10:00 중단 시각과 15분 목표에 비해 오래됨 |
| C · 잘못된 주문 금액 | `business_check_failed`, 8분 | 시점과 SQLite 구조는 맞지만 주문 금액이 기준과 다름 |
| D · 끊어진 참조 | `integrity_check=ok` 뒤에 `foreign_key_failed` | 주문이 존재하지 않는 가상의 고객을 가리킴. SQLite는 참조 무결성을 별도의 검사로 확인 |
| E · 바이트 변경 | 파일을 열기 전에 `digest_mismatch` | 작업 사본이 실습에서 보호된 것으로 가정한 기준 해시와 다름 |

마지막 줄에 `PASS: 5 cases`가 나와야 합니다. 표시된 초 단위 시간에는 실습용 파일을 만드는 시간도 포함됩니다. 운영 복구 시간을 추정하는 데 사용할 수 없습니다. `sqlite3`가 없으면 SQLite를 지원하는 Python을 사용하세요. 임시 파일을 만들 수 없다면 임시 폴더 권한과 여유 공간을 확인합니다. 예상과 다르면 검사를 느슨하게 바꾸기 전에 원본을 다시 받고 어느 검사에서 멈췄는지 확인하세요. Python 3.12.14와 SQLite 3.53.1로 실행했습니다. 관리형 백업 서비스, 랜섬웨어 실행, 운영 장애 전환은 시험하지 않았습니다.

## 6. 확인 문제와 완료 기준

- **해시가 맞고 데이터베이스가 열리면 15분 목표를 충족했나요?** 검증된 데이터의 기준 시각과 사고 기준 시각을 비교해야 합니다. 서비스에서 데이터가 빠짐없이 처리됐는지 어떻게 확인하는지도 보세요.
- **유실 가능 구간이 8분이면 정확히 8분간의 거래를 잃었나요?** 손실이 있을 수 있는 시간 범위입니다. 실제 미복구 건수는 독립적인 거래 기록으로 계산합니다.
- **복원은 20분 만에 끝났지만 로그인과 주문 조회가 안 됩니다. 어떤 시간을 보고하나요?** 데이터베이스 복원 시각과 서비스 완료가 미확인이라는 사실을 각각 남기세요. RTO는 합의한 범위에 맞춰 평가합니다.

B, C, D가 서로 다른 이유로 실패하는지 설명하세요. 한 사례를 골라 백업 ID, 검증된 시점, 유실 가능 구간, 검사별 결과, 재개 전에 필요한 다음 확인을 기록하고 재개 또는 보류를 판단하면 완료입니다.
