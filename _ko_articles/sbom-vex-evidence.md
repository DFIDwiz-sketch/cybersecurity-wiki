**학습 목표.** 패키지 경보가 어느 배포 빌드에 해당하는지 확인합니다. 구성 요소와 공급자의 판단 근거를 대조하고, 경보를 계속 조사할지, 수정할지, 범위가 제한된 예외로 검토할지 설명합니다.

## 1. 각 기록은 어떤 질문에 답하나요?

**SBOM(소프트웨어 구성 명세서)**은 특정 소프트웨어 산출물의 구성 요소와, 제공되는 경우 의존 관계를 기록합니다. 작성 도구가 어떤 자료를 읽었는지에 따라 범위가 달라집니다. 소스의 잠금 파일, 빌드 중 만든 목록, 실제 배포 이미지에서 만든 목록은 서로 다를 수 있습니다. **직접 의존성**은 소프트웨어가 직접 선언한 패키지이고, **전이 의존성**은 다른 의존성을 통해 들어온 패키지입니다.

**PURL(Package URL)**은 생태계나 유형, 이름, 선택적인 네임스페이스와 버전, 필요에 따라 한정자나 하위 경로를 표시하는 패키지 식별자입니다. 예를 들어 `pkg:pypi/example-logging@2.4.1`과 `pkg:npm/example-logging@2.4.1`은 이름과 버전이 같아도 서로 다른 생태계의 패키지입니다. **아티팩트 다이제스트**는 OCI 이미지 매니페스트처럼 특정 산출물을 식별하는 해시 값입니다. 구성 요소의 PURL과 배포 빌드의 다이제스트는 식별하는 대상이 다릅니다.

| 자료 | 확인할 질문 | 일반적인 한계 |
| --- | --- | --- |
| 배포 기록 | 이 환경에서 실제로 어느 빌드와 플랫폼을 사용했나요? | 태그는 바뀔 수 있고, 여러 플랫폼을 묶는 인덱스와 각 플랫폼의 매니페스트는 다이제스트가 다름 |
| SBOM | 이 산출물의 목록에는 어떤 구성 요소가 기록됐나요? | 목록 범위에 따라 빠진 구성 요소가 있을 수 있음 |
| 스캐너 경보 | 어떤 구성 요소가 취약점이나 탐지 조건에 일치했나요? | 이름, 생태계, 버전 범위, 배포판 패치는 따로 확인해야 함 |
| VEX 판단 | 이 발행자는 이 제품과 취약점의 관계를 어떻게 판단했나요? | 적용 범위, 발행자, 시점, 조건과 근거를 검토해야 함 |

**VEX(Vulnerability Exploitability eXchange)**는 특정 취약점이 특정 제품 또는 제품 집합에 어떤 영향을 주는지 전달합니다. 구성 요소가 포함돼도 배포 제품에서 문제가 되는 코드 경로가 제외되거나 비활성화될 수 있습니다. 그러한 판단은 해당 빌드의 근거와 설정에 달려 있습니다. 실제 공격이 있었는지는 별도의 사고 증거로 확인합니다.

## 2. 정상적인 경보 검토를 따라가세요

가상의 보고서 렌더링 서비스에 대해 스캐너가 `pkg:pypi/example-logging@2.4.1`에 `TRAINING-2026-001` 경보를 냈다고 합시다. 배포 기록의 Linux amd64 이미지 다이제스트는 **A**이고, A에 연결된 SBOM에서 같은 PURL을 찾았습니다. 릴리스 보안팀은 이 빌드와 경보에 대해 `not_affected`를 발행했습니다. 근거에는 영향받는 코드 경로가 이 빌드에서 실행되지 않는다는 설명과 검토한 빌드 구성이 포함돼 있습니다. 경보 ID는 학습용 가상 값입니다.

![실제로 배포된 빌드와 구성 목록을 대조하고, 취약점 판단의 적용 범위를 확인한 뒤 다음 조치를 정합니다.]({{ '/assets/diagrams/sbom-vex-triage-ko.svg' | relative_url }})

*경보를 제외하기 전에 각 자료가 어떻게 연결되는지 기록하세요. 태그가 같아도 다이제스트 A에 대한 판단은 다른 빌드에 그대로 적용되지 않습니다.*

분석가는 허용된 발행자인지 확인하고 문서 출처를 검증합니다. 담당자와 함께 빌드, 플랫폼, 기능 설정과 판단 근거를 확인한 뒤, 이 배포에 한해 예외 검토에 올립니다. 원래 경보와 예외 조건을 보존하고 이미지, 설정, 권고나 출처가 바뀌면 다시 검토합니다. 서명은 신뢰 정책에 따라 문서의 출처와 무결성을 확인하는 근거입니다. 문서에 담긴 모든 판단이 사실인지는 해당 증거로 따로 확인해야 합니다.

| VEX 상태 | 검토 방법 |
| --- | --- |
| `affected` · 영향받음 | 노출 범위를 확인하고 승인된 수정의 우선순위를 정합니다. 발행자의 조치 안내도 확인합니다 |
| `not_affected` · 영향받지 않음 | 사유나 영향 설명, 정확한 제품 조건을 확인한 뒤 한정된 예외를 검토합니다 |
| `fixed` · 수정됨 | 수정된 제품 버전이나 다이제스트를 찾고 실제 배포에 반영됐는지 확인합니다 |
| `under_investigation` · 조사 중 | 조사를 계속하고 담당자와 다음 확인 날짜를 남깁니다 |

## 3. 어떤 경우에 근거가 빗나가나요?

배포판은 상위 프로젝트의 새 버전 번호를 그대로 쓰지 않고 기존 버전에 패치를 반영할 수 있습니다. 버전 번호만 비교하면 이런 백포트를 놓칩니다. 해당 배포판의 권고와 패키지 리비전을 확인하세요. 이름만 같으면 다른 생태계의 패키지를 연결할 수 있습니다. PURL은 패키지 식별에 도움이 되며, 실제 적용 여부는 권고의 버전·릴리스 범위를 봐야 합니다. 다이제스트가 여러 플랫폼을 묶은 인덱스라면, 런타임이 고른 플랫폼 매니페스트가 SBOM에 포함되는지 확인하세요.

빌드나 문서 배포 경로가 침해되면 실제 산출물과 다른 정보가 전달될 수 있습니다. 오래된 예외가 새 빌드에도 적용되면 유효한 경보가 숨겨질 수 있습니다. SBOM에서 구성 요소를 못 찾았다면 목록 범위, 함께 묶여 배포되는 코드, 빌드 환경과 런타임의 차이를 확인하세요. 신뢰하는 자료끼리도 판단이 다르다면 발행 순서, 발행자, 제품 범위, 환경과 조건을 대조합니다. 해소되지 않은 충돌은 기록하고 검토 상태를 유지하세요.

## 4. 블루팀 수집·탐지·대응

**실제 배포에서 시작하세요.** 환경, 담당자, 관측 시각, 이미지 저장소, 다이제스트와 플랫폼을 남깁니다. OCI 기반 배포에서는 관측한 다이제스트가 인덱스인지 플랫폼 매니페스트인지 확인하고 필요한 경우 대응 관계를 기록하세요. 스캐너 버전, 권고 데이터베이스 시각, 패키지 식별자, 일치 조건과 함께 원본 경보를 보존합니다.

**목록과 판단의 범위를 확인하세요.** SBOM 생성기, 작성 범위와 시각, 그 대상이 이번 배포와 연결된다는 근거를 남깁니다. 의존 관계가 제공되면 직접 또는 전이 경로를 확인하세요. 올바른 생태계나 배포판의 권고에서 버전을 대조합니다. VEX의 식별자, 발행자, 개정 번호나 날짜, 취약점 식별자, 제품 범위, 상태와 사유를 봅니다. 조직의 서명 검증 또는 신뢰 채널 정책을 적용하세요. 신뢰하는 발행자가 서명했어도 다른 제품에 대한 문서라면 적용 범위 밖입니다.

**릴리스 뒤 예외가 여전히 적용되는지 살피세요.** 새 다이제스트에 연결된 SBOM이 없거나, 기존 VEX의 조건이 바뀌었거나, 같은 범위에서 신뢰하는 자료들이 충돌하면 검토 대상으로 표시합니다. 충돌하는 문서와 담당자를 기록하세요. 영향받는 빌드는 노출과 업무 영향을 바탕으로 우선순위를 정하고 승인된 완화나 수정을 적용한 뒤 배포 결과를 확인합니다. 이전 빌드가 남은 워크로드도 확인하세요. 판단 문서가 없거나 출처를 검증할 수 없다면 필요한 근거를 찾을 때까지 경보를 열어 둡니다.

## 5. 오프라인 실습 · 가상 경보 10건

[sbom-vex-cases.json]({{ '/assets/labs/sbom-vex-cases.json' | relative_url }})과 [sbom-vex-review.py]({{ '/assets/labs/sbom-vex-review.py' | relative_url }})를 같은 폴더에 받으세요. 먼저 S01과 S02를 직접 비교합니다. JSON은 자료를 단순화한 가상 기록입니다. 실제 CycloneDX나 OpenVEX 형식이 아니며 다이제스트도 가상 값입니다. `source_verified`는 실습에서 주어진 가정입니다. 검사기는 PURL을 문자열로 비교하고 예상 발행자 하나를 사용합니다. 실제 버전 범위, 서명 체인이나 운영 정책은 처리하지 않습니다.

~~~bash
python3 sbom-vex-review.py
~~~

| 사례 | 예상 판단 |
| --- | --- |
| S01 / S02 | S01은 근거를 확인해 범위가 제한된 예외를 검토. S02의 SBOM은 다른 빌드에 해당 |
| S03 / S04 | S03은 이름이 같지만 생태계가 다름. S04는 VEX가 다른 빌드에 해당 |
| S05 / S06 | S05는 출처 확인이 미완료. S06에는 실습이 확인하는 기계 판독용 사유가 없음 |
| S07 / S08 | S07은 검증된 상태가 서로 충돌. S08은 영향이 있어 수정 우선순위를 정함 |
| S09 / S10 | S09는 수정된 빌드의 배포 여부 확인 필요. S10은 조사 중 |

마지막에 `Reviewed: 10 synthetic cases`가 나옵니다. 파일을 찾지 못하면 두 파일을 원래 이름으로 같은 폴더에 두세요. 결과가 예상과 다르면 다이제스트와 PURL을 한 글자씩 대조하고 경보, 발행자, 출처 확인 값도 봅니다. VEX 형식에 따라 기계 판독용 사유 대신 영향 설명을 허용하기도 합니다. 실습은 사유 필드만 봅니다. 자가 소유 또는 승인 환경에서는 테스트 빌드의 SBOM과 배포 기록을 읽어 목록이 어디까지 해당하는지 확인할 수 있습니다. Python으로 가상 사례를 실행했습니다. 실제 레지스트리, 스캐너, SBOM 생성기와 서명 검증 서비스는 시험하지 않았습니다.

## 6. 확인 문제와 완료 기준

- **권고에 이름과 버전이 똑같이 나옵니다. 같은 패키지인가요?** 생태계, 배포판, 식별자와 권고의 적용 버전을 대조하세요.
- **공급자는 다이제스트 A가 영향받지 않는다고 했지만 배포는 B입니다. 어떻게 처리하나요?** 해당 배포의 경보를 열어 두고 B에 맞는 근거를 찾습니다.
- **공급자가 수정을 발표했지만 이전 다이제스트가 실행 중입니다. 대응이 끝났나요?** 실제로 실행 중인 빌드를 확인하고 남은 노출을 기록합니다.

S02, S05, S07이 왜 서로 다른 문제인지 설명하세요. 실제 배포 다이제스트와 플랫폼, PURL, 경보와 권고 범위, 출처 검증 결과, 다음 증거나 조치를 한 건의 조사 기록에 적으면 완료입니다.
