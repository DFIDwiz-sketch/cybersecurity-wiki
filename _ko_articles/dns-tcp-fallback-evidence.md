리졸버가 UDP로 받은 DNS 응답에 `TC=1`이 기록됐는데, 애플리케이션은 여전히 이름을 해석하지 못했다고 합니다. 전송 방식이 바뀌는 구간을 따라가며 어디까지 확인할 수 있는지 살펴보세요. 이 장은 요청자와 응답 서버 사이의 일반 DNS 한 구간을 다룹니다. 같은 이름에 대한 질의라도 단말의 스텁 리졸버와 재귀 리졸버 사이, 재귀 리졸버와 권한 서버 사이는 서로 다른 교환입니다.

## 1. DNS 메시지가 잘렸다는 신호

DNS 질문은 이름(QNAME), 레코드 유형(QTYPE), 클래스(QCLASS)로 구성됩니다. 헤더에는 16비트 트랜잭션 ID, 질의·응답 구분 비트(`QR`), 잘림 비트(`TC`), 응답 코드(`RCODE`)가 있습니다. 질의와 일치하는 유효한 `TC=1` 응답은 송신자가 DNS 메시지가 잘렸다고 표시했다는 뜻입니다. 일부 레코드가 포함될 수 있으므로 전체 내용은 후속 응답에서 확인합니다. 위임 응답이 잘린 경우에는 하위 존의 네임서버에 연락하는 데 필요한 주소인 글루(glue)가 빠졌을 수도 있습니다.

EDNS가 없을 때 원래 DNS 규격의 UDP 메시지 한도는 512옥텟입니다. EDNS(0)를 쓰는 요청자는 OPT 의사 레코드로 받을 수 있는 **UDP DNS 페이로드** 크기를 알립니다. 이 값에는 UDP·IP 헤더가 포함되지 않으며, 경로 MTU를 측정한 값도 아닙니다. 응답자는 더 작은 상한을 적용할 수 있습니다. 광고 크기 이하의 응답도 터널을 통과하거나 IP 단편이 유실되면 도착하지 않을 수 있습니다. RFC 9715가 소개하는 1232옥텟은 MTU와 헤더 오버헤드에 대한 가정을 둔 운영상 출발점입니다. 모든 경로에서 전송을 보장하는 값은 아닙니다.

| 관측 증거 | 확인할 수 있는 내용 | 다음 확인 |
| --- | --- | --- |
| 질의와 일치하는 UDP 응답의 `TC=1` | 이 응답자가 잘림을 표시했는가 | 요청자의 후속 재질의 |
| 질의의 EDNS OPT 크기 | 요청자가 어떤 UDP DNS 크기를 알렸는가 | 응답자 상한과 실제 경로 |
| TCP 연결 수립 또는 기존 스트림 | TCP 연결이 있는가 | 스트림을 재조립해 DNS 질의 확인 |
| 질의와 일치하는 TCP 응답의 `TC=0` | 이 응답자가 잘리지 않은 DNS 메시지를 보냈는가 | RCODE, 답변, 검증, 호출자 결과 |
| 프레임 길이보다 짧은 캡처 길이 | 센서가 프레임 일부만 저장했는가 | 캡처 길이 제한과 드롭 카운터 |

## 2. 정상 이름 해석 한 건 복원하기

가상 예시에서 재귀 리졸버 `192.0.2.20`은 권한 서버 `198.51.100.53`에 `example.test.`의 큰 TXT 응답을 요청합니다. 주소는 문서용이며 시각은 UTC입니다.

1. 14:02:01.110에 리졸버가 UDP 출발지 포트 53010에서 목적지 포트 53으로 `notes.example.test. IN TXT`를 질의합니다. EDNS 크기로 1232를 알립니다. 서버는 UDP 응답 크기를 제한하고 14:02:01.112에 `QR=1, TC=1`을 반환합니다.
2. 14:02:01.113에 리졸버가 다른 임시 출발지 포트에서 TCP 53으로 연결을 엽니다. 구현에 따라 기존 TCP 연결을 재사용할 수도 있습니다. 요청자와 서버, 질문, 시간, 제공된다면 리졸버 추적 ID를 대조하세요. UDP와 TCP 사이에 포트나 트랜잭션 ID가 같아야 하는 것은 아닙니다.
3. TCP 바이트 스트림에서는 DNS 메시지 앞의 2바이트가 메시지 길이입니다. 네트워크 바이트 순서를 쓰며 이 길이에 접두부 자체는 포함되지 않습니다. 한 번의 읽기에 접두부 일부분만 들어오거나 메시지 여러 개의 바이트가 같이 들어올 수 있습니다. 스트림 순서와 선언한 길이대로 재조립하세요. 같은 연결에 응답 대기 중인 질의가 여럿이면 ID와 질문 문맥을 대조합니다. 답이 질의 순서대로 도착한다고 가정하면 안 됩니다.
4. 14:02:01.119의 TCP 응답에서 `TC=0`, `NOERROR`, 예상한 TXT 레코드를 확인합니다. 상위 서버와의 교환은 완료됐습니다. 최종 앱 결과를 판단하려면 재귀 리졸버가 무엇을 검증해 스텁에 반환했는지, 호출자가 어떤 결과를 기록했는지 확인하세요.

운영 정책에 따라 처음부터 TCP를 사용할 수 있으므로 정상 TCP 교환 앞에 UDP가 없을 수 있습니다. UDP 타임아웃은 잘림 응답을 받은 경우와 다릅니다. 아무 응답도 없을 때의 재시도는 구현과 정책에 따라 달라집니다. TLS나 HTTPS 위의 DNS는 승인된 복호화·디코딩 지점의 관측이 필요합니다. 일반 DNS 포트 53 캡처의 가시성은 그 경로에서 제한됩니다.

## 3. 장애·오용과 관측 공백 조사하기

**같은 구간의 두 전송 방식을 수집합니다.** 시간대와 시계 상태, 인터페이스, 캡처 방향, 저장 길이 제한(snaplen), 드롭 카운터, 보존 기간을 기록하세요. 가능하다면 의심 경계의 양쪽에서 같은 요청자와 서버 사이의 UDP와 TCP를 수집합니다. TCP 연결 수립, 리셋과 DNS 질의·응답이 포함되도록 확인하세요. 질의 이름에는 민감한 정보가 들어갈 수 있으므로 승인 범위에서 수집·보존합니다. 리졸버나 권한 서버 로그에 설정된 질문, 전송 방식, 결과와 요청 ID를 보존하세요. 질의 로그에는 플래그나 응답이 빠질 수 있어 실제 스키마 확인이 필요합니다.

**어디서 멈췄는지 찾습니다.** 한 센서가 `TC=1` 이후 TCP 질의를 보지 못했다면 그 요청자, 경로, 기존 TCP 연결까지 볼 수 있는 지점인지 먼저 확인합니다. 리졸버 정책과 요청 제한 시간도 대조하세요. SYN이 요청자를 떠났지만 서버에 도착하지 않으면 방화벽·ACL의 판단과 경로를 비교합니다. 서버에 SYN이 도착한 뒤 리셋이 돌아오면 리스너와 리셋을 생성할 수 있는 중간 장비를 확인하세요. 연결 수립 후에도 응답을 해석할 수 없다면 스트림 재조립, 캡처 공백, 서버 로그와 요청 기한을 봅니다. TC 없이 UDP 응답이 사라지면 광고 크기, 응답 크기, 경로 MTU, 단편 관측 범위를 비교하세요. 포트 필터만 쓰면 UDP 헤더가 없는 후속 IP 단편을 놓칠 수 있습니다.

**평소 분포와 대조합니다.** 정상 DNSSEC 변경, 레코드 변화, UDP 상한을 낮춘 설정, 질의 유형 비율 변화로도 잘림이 늘 수 있습니다. 잘린 응답이 계속되고 해석이 끝나지 않으면 서비스가 저하될 수 있습니다. 예상하지 못한 응답자나 질문과 맞지 않는 응답은 통신 개입 가능성을 시사하지만, 동일 이름의 별도 질의, 주소 변환, 비대칭 캡처, 승인된 보조 서버도 설명이 될 수 있습니다. 원인을 단정하기 전에 단말·리졸버·정책 기록을 대조하세요.

**승인된 경로에서 복구를 확인합니다.** 같은 관측 범위에서 질문과 맞는 잘림 응답 중 TCP 교환 완료가 관측된 비율을 봅니다. 타임아웃, 리셋, DNS 부정 응답, 관측 공백은 따로 기록하세요. 리졸버, 상위 서버, QTYPE, 시간 구간별로 비교합니다. 승인된 엔드포인트의 UDP와 TCP 연결성을 각각 확인하고, 독립적인 애플리케이션 조회로 결과를 검증합니다. 타임아웃만 보고 TCP 53을 전역에서 열거나 UDP 페이로드 상한을 올리지 마세요.

python3 dns-tcp-fallback-lab.py
~~~

| 사례 | 예상 관측 | 확인할 수 있는 내용 |
| --- | --- | --- |
| UDP 완료 | UDP `TC=0`, 답변 있음 | TCP 재질의가 필요 없음 |
| UDP에서 TCP로 전환 | UDP `TC=1` 이후 TCP `TC=0` | 두 번째 교환에서 답변을 받음 |
| TCP 리스너 없음 | UDP `TC=1` 이후 TCP 연결 거부 | UDP 도달성과 TCP 가용성은 별개 |
| 처음부터 TCP | 길이 접두부가 붙은 TCP 질의·응답만 존재 | TCP로 시작할 수 있음 |

`PASS`가 네 줄 나와야 합니다. 전환 사례에서는 TCP 읽기를 작게 나누어 길이 접두부와 메시지를 복원합니다. 이 읽기 경계는 실습에서 정한 제약이므로 TCP 세그먼트 경계로 해석할 수 없습니다. 리스너가 없는 사례에서는 로컬 TCP 포트를 바인드하되 listen을 호출하지 않습니다. 방화벽 설정은 건드리지 않습니다. 바인드가 실패하면 환경에서 IPv4 루프백을 허용하는지 확인하세요. 검사가 실패하면 코드를 수정하기 전에 소켓 오류나 메시지 프레이밍 오류를 확인합니다. 실습 출력의 범위는 이 코드의 동작이며, 운영망 캡처나 특정 리졸버 재시도 동작까지 검증한 결과는 아닙니다.

## 5. 확인 문제와 완료 기준

1. **UDP `TC=1`과 TCP 핸드셰이크만 보이면 무엇을 보고할 수 있나요?** UDP 응답자가 잘림을 표시했고, TCP 연결이 수립됐습니다. DNS 완료를 판단하려면 질문과 맞는 DNS 응답이나 엔드포인트 증거가 필요합니다.
2. **1232바이트를 광고했는데도 실패할 수 있나요?** 받을 수 있다고 알린 크기로 경로 MTU나 단편 도착 여부를 알 수는 없습니다. 캡슐화나 경로의 특성이 실제 도착에 영향을 줄 수 있습니다.
3. **두 질의의 ID가 같으면 같은 조회인가요?** 연결 또는 데이터그램의 주소·포트, 질문, 시각과 엔드포인트 증거를 함께 대조하세요. ID는 범위가 제한되며 재사용될 수 있습니다.
4. **TCP 응답이 `TC=0`이면서 `SERVFAIL`이면 이름 해석에 성공했나요?** 잘리지 않은 DNS 오류 응답을 받은 것입니다. 실패 원인을 설명하려면 리졸버 문맥과 검증 증거를 확인하세요.

네 가지 결과를 재현하고 실패 사례에 대한 조사 메모를 한 건 쓰면 완료입니다. 관측 위치, 마지막으로 확인한 이벤트, 결론과 남은 불확실성을 줄일 자료 한 가지를 적으세요.
