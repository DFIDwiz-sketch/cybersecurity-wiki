**학습 목표.** Linux 연결이나 수신 대기 포트에서 시작해 수집 시점에 소켓을 보유한 프로세스를 찾습니다. 컨테이너에서 수집할 때 보이는 범위가 어떻게 달라지는지, 과거 연결을 조사하려면 어떤 기록이 필요한지도 설명합니다.

## 1. 같은 시스템을 세 가지 관점에서 보기

**소켓**은 커널이 관리하는 통신 종단입니다. **파일 디스크립터(FD)**는 프로세스가 열린 객체를 가리킬 때 사용하는 번호이며, 소켓도 그 객체 중 하나입니다. 수집기가 링크를 읽을 수 있다면 `/proc/842/fd/7 → socket:[31810]`은 PID 842의 FD 7이 현재 소켓 inode 31810을 참조한다는 뜻입니다. **PID**는 PID 네임스페이스 안에서 프로세스를 구분하는 번호입니다. 번호가 재사용될 수 있으므로 프로세스 시작 시각과 PID를 읽은 범위를 함께 기록하세요.

**네트워크 네임스페이스**는 인터페이스, 경로, 포트와 소켓 목록 등 네트워크 관측 범위를 나눕니다. `/proc/net`은 일반적으로 `/proc/self/net`을 가리킵니다. `/proc/842/net/tcp`는 PID 842의 네트워크 네임스페이스에 있는 IPv4 TCP 소켓 목록이며 같은 공간의 다른 프로세스가 보유한 소켓도 표시할 수 있습니다. 해당 프로세스가 실제로 보유한 디스크립터는 `/proc/842/fd`에서 확인합니다. 한 프로세스에 같은 소켓을 가리키는 디스크립터가 여러 개 있을 수 있고, 상속이나 디스크립터 전달로 여러 프로세스가 같은 소켓을 보유할 수도 있습니다.

## 2. 정상 TCP 연결 따라가기

가상 스냅샷에서 서비스가 `127.0.0.1:41802`에서 수신을 기다립니다. PID 842의 FD 7이 수신 소켓을 가리킵니다. 진단 프로세스 PID 1090은 같은 네트워크 네임스페이스에 있으므로 자기 경로인 `/proc/1090/net/tcp`에서도 해당 리스너를 볼 수 있습니다. 그러나 PID 1090의 디스크립터 중 그 inode를 가리키는 것은 없습니다. PID 1090이 클라이언트로 연결하면 서비스가 연결을 수락합니다. 리스너는 LISTEN을 유지하고, 클라이언트 소켓과 서버가 수락한 소켓은 각각 자기 inode와 로컬·상대 종단을 가집니다. 루프백이므로 두 소켓은 같은 네임스페이스의 목록에 함께 보입니다.

| 증거 | 알 수 있는 내용 | 추가 확인 |
| --- | --- | --- |
| `ss`의 로컬·상대 주소, 포트와 상태 | 수집 시점에 선택된 네트워크 네임스페이스에서 보인 소켓 | 읽을 수 있었던 PID 정보와 사건에 해당하는 주소·포트 조합 |
| `ss -e`의 inode와 `/proc/<pid>/fd/<n>` 링크 | 같은 inode가 있으면 현재 디스크립터 보유를 뒷받침 | 수집 시각, 프로세스 시작 시각과 공유 가능성 |
| `/proc/<pid>/net/tcp` | 해당 PID가 속한 네트워크 네임스페이스에서 보인 IPv4 TCP 소켓 | 실제 디스크립터를 보유한 프로세스 |
| 프록시·네트워크·엔드포인트 기록 | 사건 시간대에 저장한 관측 | 시계 정렬, NAT, 연결 방향과 수집 범위 |

Linux 커널 문서에서는 `/proc/net/tcp`와 `/proc/net/tcp6` 대신 소켓 진단 인터페이스를 사용하도록 안내합니다. 평소 조회는 `ss`로 하고, 보유 프로세스를 확인할 때 procfs 링크를 대조하세요. 실습에서는 네임스페이스의 범위를 분명하게 보여 주기 위해 기존 목록을 읽습니다. IPv4와 IPv6의 procfs 목록은 별도로 제공됩니다. 앞선 기록이 없다면 TCP 상태와 방향만으로 어느 프로세스가 교환을 시작했는지 단정하기 어렵습니다.

## 3. 범위를 정해 현재 상태 수집하기

필요한 호스트, PID, 네트워크 네임스페이스를 관측할 수 있는 승인된 수집기를 사용하세요. UTC 시각, 자산, 수집 지점, 네임스페이스 링크 값, 관련 로컬·상대 주소와 숫자 포트, 상태, 소켓 inode, PID와 시작 시각, 조사에 필요한 경로를 기록합니다. 프로세스 구분은 [Linux 프로세스 증거]({{ '/ko/wiki/linux-process-evidence/' | relative_url }})를 참고하세요. PID와 함께 `/proc/<pid>/stat` 22번째 필드 같은 시작 값을 확인합니다. 현대 Linux에서 이 값은 부팅 이후의 클록 틱입니다. 가능하면 부팅 식별자도 보존하세요. 소켓과 FD는 따로 읽으며 그 사이 프로세스가 종료되거나 번호가 재사용될 수 있으므로 관련 필드를 가능한 한 가까운 시각에 수집합니다.

iproute2가 있는 Linux에서 `PORT`를 조사할 숫자 포트, `PID`를 읽을 수 있는 프로세스 ID, `FD`를 후보 디스크립터 번호로 설정하세요. 아래 읽기 전용 명령은 수집기의 현재 네트워크 네임스페이스에서 실행합니다. 첫 필터는 로컬 포트, 두 번째 필터는 로컬 또는 상대 포트와 일치합니다. `-n`은 서비스 이름으로 변환하지 않고, `-p`는 프로세스 정보, `-e`는 inode 등 세부 정보를 요청합니다.

```sh
ss -Hltnep "sport = :$PORT"
ss -Htnpe state established "( sport = :$PORT or dport = :$PORT )"
readlink "/proc/$PID/ns/net"
readlink "/proc/$PID/ns/pid"
readlink "/proc/$PID/fd/$FD"
```

| 증상 | 해석하기 전에 확인할 점 |
| --- | --- |
| `/proc/net`이 없거나 읽히지 않음 | procfs 마운트, 네임스페이스, 수집 제한과 오류를 확인. 의도한 범위를 볼 수 있는 승인된 호스트 또는 워크로드 수집기 사용. |
| 소켓은 보이지만 `ss -p`에 프로세스가 없음 | PID 가시성, ptrace 접근 정책, 프로세스 종료 및 소켓 상태 확인. 일부 TCP 상태는 사용자 공간에서 FD를 닫은 뒤에도 커널에 남을 수 있음. |
| 호스트와 컨테이너에서 IP·포트 또는 PID가 다름 | 네트워크·PID 네임스페이스와 수집 지점을 대조. 당시 주소 변환이나 프록시 경로 확인. |
| 여러 PID나 디스크립터가 inode 하나를 공유 | 관측된 보유자들을 기록. 최초 프로세스를 고르기 전에 서비스 관리자, 상속, 워크로드 구성을 확인. |

## 4. 예상 밖 연결 조사하기

외부로 향하는 연결은 정상 에이전트의 상태 보고, 프록시가 전달한 다른 워크로드의 요청, 미승인 프로세스의 통신 등 여러 설명이 가능합니다. 로컬 리스너 역시 사이드카, 승인된 서비스 또는 원치 않는 접점일 수 있습니다. 리스너의 상태만으로 원격 접속이 도달했다고 판단하기는 어렵습니다. 주소·포트와 시각을 네트워크 로그와 대조한 뒤, 승인된 바인드 주소와 배포 상태, 부모 프로세스와 실행 파일을 확인하세요. 요청, 엔드포인트 또는 워크로드의 기록에서 행동을 뒷받침하는 근거를 찾습니다. 후속 수집 범위는 [엔드포인트 수집 증거]({{ '/ko/wiki/endpoint-collection-evidence/' | relative_url }})를 참고하세요. 관측한 사실과 남은 공백을 보존해 서비스 담당자나 사고 대응 책임자와 대응을 조율합니다.

센서는 NAT 뒤나 다른 프록시 구간에서 관측했고, 현재 프로세스 스냅샷은 나중에 내부 주소를 보여 줄 수 있습니다. IP와 포트만 맞으면 프로세스와 행위는 미확정입니다. PID와 inode의 연계는 그 시점에 디스크립터를 보유했다는 근거입니다. 최초로 소켓을 열었던 주체, 소켓을 사용한 요청 또는 이미 닫힌 연결의 내용을 확인하려면 별도 증거가 필요합니다. 명령 인수, 환경 변수, 페이로드는 조사에 필요한 승인 범위 안에서만 수집하세요.

## 5. 루프백에서 소켓 범위 재현하기

[linux-socket-scope-lab.py]({{ '/assets/labs/linux-socket-scope-lab.py' | relative_url }}){: download="linux-socket-scope-lab.py" }를 내려받습니다. 본인이 관리하는 Linux 환경에서 Python 3.12, procfs, IPv4 루프백과 iproute2 `ss`를 사용하세요. 프로그램은 `127.0.0.1`의 임시 포트에서 자식 프로세스를 띄워 로컬로 연결하고, 끝날 때 자식과 소켓을 정리합니다. 네임스페이스나 보안 설정을 변경하지 않으며 실습 연결의 확인 결과만 출력합니다.

```sh
python3 linux-socket-scope-lab.py
```

`PASS` 줄이 7개 나와야 합니다. 두 프로세스는 같은 네트워크 네임스페이스에 있고, 두 경로의 목록 모두 리스너를 보여 줍니다. 수신 대기 FD는 자식만 보유합니다. 연결된 클라이언트 소켓과 서버가 수락한 소켓은 inode가 다릅니다. 클라이언트 FD를 복제해도 inode는 같습니다. 마지막으로 `ss`에서 리스너의 PID와 연결 양쪽의 서로 다른 소켓 보유 프로세스를 확인합니다.

파일 조회에 실패하면 procfs가 마운트됐는지와 자식 프로세스의 디스크립터를 읽을 수 있는지 확인하세요. `ss`에 프로세스 필드가 없으면 샌드박스가 실습 PID를 노출하고 소켓 진단을 허용하는지 점검합니다. 해당 인터페이스를 제공하는 승인된 Linux에서 실행하면 권한 상승은 필요하지 않습니다. Linux 6.18.57, iproute2 6.15.0, Python 3.12.14에서 일반 사용자 권한으로 7개 검사를 재현했습니다. 네임스페이스 간 수집, IPv6, 운영 환경 수집은 실행 검증 범위에 포함되지 않습니다.

## 6. 확인 문제와 해설

1. **포트가 `/proc/1090/net/tcp`에 있습니다. PID 1090이 보유한 소켓인가요?** PID 1090의 네트워크 네임스페이스에서 보인다는 뜻입니다. 올바른 PID 범위에서 inode와 FD 증거를 대조하세요.
2. **디스크립터 두 개가 같은 inode를 가리킵니다. 연결이 두 개일까요?** 소켓 하나를 두 번 참조한 것일 수 있습니다. inode와 양쪽 종단을 대조하고 여러 PID가 보유한다면 모두 기록하세요.
3. **센서에서 어제 연결을 봤는데 오늘 스냅샷은 비어 있습니다. 당시 프로세스가 없었나요?** 스냅샷은 현재 소켓을 보여 줍니다. 어제의 엔드포인트, 프록시 또는 네트워크 기록을 확보해야 합니다.

**완료 기준.** 7개 결과를 재현합니다. 네임스페이스에서 본 소켓과 실제 디스크립터를 두 문장으로 설명한 뒤, 어제 연결을 프로세스에 연결하려면 어떤 근거가 더 필요한지 적어 보세요.
