## 1. 연결은 무엇을 입증하나요?

TCP는 두 엔드포인트 사이에서 순서가 보장되는 바이트 스트림을 제공합니다. 앱의 메시지 하나가 여러 TCP 세그먼트로 나뉘거나 반대로 합쳐질 수 있습니다. 네트워크에서 연결을 확인한 뒤에도 TLS 인증, HTTP 응답, 로그인 성공은 각각 해당 계층의 증거로 확인해야 합니다.

흐름을 찾을 때는 출발지 IP·포트, 목적지 IP·포트, 전송 프로토콜의 **5튜플**에 시간 범위와 센서 위치를 붙이세요. 포트가 재사용되고 NAT나 프록시에서 주소와 포트가 달라질 수 있습니다. 443번 포트는 서비스 후보를 찾는 단서입니다. 실제 앱 프로토콜은 별도 증거로 확인합니다.

## 2. SYN에서 ACK까지 직접 읽기

![클라이언트 SYN, 서버 SYN-ACK, 클라이언트 ACK 순서와 각 번호]({{ '/assets/diagrams/tcp-handshake-ko.svg' | relative_url }})

클라이언트가 SYN에 시퀀스 1000을 보내면 서버는 SYN+ACK에서 자신의 시퀀스 8000과 ACK 1001을 보냅니다. 이어 클라이언트가 시퀀스 1001과 ACK 8001로 답합니다. 양방향은 서로 독립적인 번호 공간을 사용합니다. ACK는 보통 **다음에 기대하는 바이트 번호**를 나타냅니다. SYN과 FIN은 각각 번호 하나를 소비하며, 데이터가 없는 일반 ACK는 소비하지 않습니다.

클라이언트가 시퀀스 1001부터 40바이트를 보냈다면 해당 데이터까지 받은 서버는 ACK 1041을 보낼 수 있습니다. 이 값은 TCP 계층이 받은 범위를 보여 줍니다. 앱의 처리 결과는 서버 로그와 응답에서 확인하세요. Wireshark의 상대 번호를 쓰는 화면에서는 처음 번호가 0으로 보일 수 있습니다.

## 3. 종료와 장애를 구분하기

| 관측 | 먼저 해석할 내용 | 함께 확인할 증거 |
| --- | --- | --- |
| SYN 반복, 응답 미관측 | 같은 연결 시도의 재전송 가능 | 방화벽 정책, 서버 도착 여부, 역방향 수집 |
| SYN 뒤 RST+ACK | 연결 시도에 대한 거절 후보 | 리스너 상태와 방화벽·중간 장비 로그 |
| 양쪽 방향의 FIN과 ACK | 양방향 스트림이 순차 종료 | 앱 응답·상태와 종료 시점 |
| RST로 기존 연결 종료 | 연결 중단 | 서버 재시작, 프록시 시간 제한, 양쪽 캡처 |
| 같은 시퀀스 범위 재등장 | 재전송 또는 중복 수집 후보 | ACK 진행, SPAN 중복, 시간 차이, 다른 센서 |

FIN은 보낸 방향의 전송을 닫습니다. 상대 방향은 잠시 데이터를 계속 보낼 수 있습니다. TCP 재전송은 손실뿐 아니라 지연이나 ACK 손실에서도 생길 수 있습니다. 단일 캡처로 실제 손실 위치를 찾기 어려울 때는 다른 관측 지점과 비교하세요.

## 4. 블루팀의 증거 수집 순서

1. 주장을 먼저 정하세요. 예를 들어 “해당 클라이언트의 TCP 연결이 완료됐는가?”와 “서버가 인증을 받아들였는가?”에는 다른 자료가 필요합니다.
2. 시간대, 센서, 인터페이스, 캡처 시작·끝, NAT·프록시 전후 위치를 기록합니다. 양방향이 보였는지 조사하세요.
3. Zeek에서 시간·5튜플로 후보를 찾고 UID를 기록합니다. `conn_state`, `history`, 바이트를 함께 읽으세요. 예를 들어 S0는 응답이 관측되지 않은 연결 시도를 뜻합니다. 관측 한계는 별도로 기록합니다.
4. 같은 지점의 원본 캡처에서 SYN·ACK·RST, 시퀀스와 ACK 번호를 확인합니다. Wireshark가 표시하는 TCP 분석 플래그는 관측된 패킷과 분석기 상태를 바탕으로 생성됩니다. 캡처 중간 시작, 누락과 순서 뒤바뀜을 고려하세요.
5. 방화벽의 허용·차단 결과와 서버 리스너·앱 로그, 엔드포인트 프로세스를 맞춰 봅니다. 지연·재전송이 많으면 장비 변경 시각이나 장애 기록도 대조합니다.

특정 목적지의 여러 포트에서 짧은 시도가 급증하면 서비스 탐색 가능성을 조사할 수 있습니다. 승인된 스캐너, 모니터링, 장애 시 재시도도 비교하세요. 경보 기준은 승인된 자가 소유 환경의 정상 연결·정상 거절로 먼저 확인합니다. 방화벽 차단 뒤에는 필요 서비스 영향과 로그 도착을 재검증하세요.

## 5. 오프라인 실습으로 네 흐름 읽기

두 파일을 같은 폴더에 저장하고 Python 3으로 실행하세요. CSV의 시간은 각 흐름 시작을 기준으로 한 밀리초입니다. C는 클라이언트, S는 서버입니다. 먼저 손으로 해석한 다음 분석기 결과를 비교하세요.

[tcp-evidence.csv]({{ '/assets/labs/tcp-evidence.csv' | relative_url }}) · [tcp-evidence.py]({{ '/assets/labs/tcp-evidence.py' | relative_url }})

```bash
python3 tcp-evidence.py
```

| 흐름 | 가상 기록에서 확인할 것 |
| --- | --- |
| A | 핸드셰이크 3단계, 40바이트에 대한 ACK 1041, 양쪽 FIN과 각각의 ACK |
| B | 같은 번호의 SYN 두 개, 관측된 응답 없음 |
| C | 원래 SYN을 ACK하는 RST, 거절 주체는 추가 증거로 확인 |
| D | 50바이트 구간이 두 번 관측됨, 캡처에는 핸드셰이크 없음 |

끝에 `PASS`와 16개 행이 표시되면 제공된 자료의 번호 관계가 맞습니다. 파일 오류가 나면 두 파일의 이름과 폴더를 확인하세요. 실습은 가상 CSV를 실행 검증했습니다. 실제 패킷 캡처, Zeek와 Wireshark의 동작은 공식 문서를 검토했습니다.

## 6. 확인 문제와 완료 기준

1. **ACK 1041이 앱의 정상 처리까지 보여 주나요?** TCP 수신 범위까지만 설명할 수 있습니다. 앱 응답과 서버 로그를 확인합니다.
2. **SYN 두 번이면 방화벽 차단인가요?** 먼저 응답이 관측되지 않았다고 기록합니다. 서버 도착 여부와 역방향 가시성, 방화벽 결정을 확인합니다.
3. **RST 출발지 IP로 장비를 확정할 수 있나요?** 주소는 단서입니다. 중간 장비와 양쪽 캡처를 대조하세요.

5튜플과 센서 위치를 기록하고, 네 흐름의 번호를 직접 계산한 뒤, 관측 사실과 아직 필요한 증거를 한 문장씩 적으면 완료입니다.
