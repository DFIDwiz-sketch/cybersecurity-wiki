## 1. ALPN은 무엇을 결정하나요?

**ALPN(Application-Layer Protocol Negotiation)**은 TLS 양쪽이 연결에서 사용할 애플리케이션 프로토콜을 고르는 기능입니다. 같은 포트에서 HTTP/1.1과 HTTP/2를 함께 제공할 때 유용합니다. 클라이언트가 **ClientHello**에 선호 순서대로 프로토콜 식별자를 넣습니다. 서버는 자신이 지원하는 항목을 제안 목록에서 정책에 따라 하나 고릅니다. 클라이언트가 맨 앞에 적은 값이 반드시 선택되지는 않습니다.

**애플리케이션 프로토콜**은 핸드셰이크 이후 양쪽이 메시지를 어떻게 해석할지 정합니다. `http/1.1`은 HTTP/1.1, `h2`는 TLS 위의 HTTP/2, `h3`는 QUIC 위의 HTTP/3를 협상할 때 쓰는 표준 식별자입니다. 예전 `h2c` 업그레이드 토큰은 RFC 9113에서 폐기됐으며 TLS에서 선택하는 식별자가 아닙니다. **SNI**는 서버가 리스너 정책을 고르는 데 쓸 수 있는 요청 이름입니다. 인증서의 신원, 선택된 ALPN, 요청 처리 결과는 각각 다른 사실을 보여줍니다.

## 2. 제안, 선택, 요청을 따라가세요

1. **제안.** 조사할 연결 구간의 ClientHello를 찾습니다. TLS 버전 제안, 관측 가능한 요청 이름, ALPN 목록을 확인하세요. 패킷 캡처를 늦게 시작했거나 조각이 빠졌다면 한계로 기록합니다. ECH(Encrypted Client Hello)를 쓰면 보이는 바깥쪽 ClientHello와 서버가 사용하는 안쪽 메시지가 다를 수 있습니다. 바깥쪽 목록을 안쪽 제안으로 해석하지 마세요.
2. **선택.** TLS 1.2에서는 ServerHello에 서버의 ALPN 선택이 들어갑니다. TLS 1.3에서는 핸드셰이크 키로 보호되는 **EncryptedExtensions**에 들어갑니다. ClientHello가 보이더라도 서버가 무엇을 골랐는지 수동 캡처에서 바로 읽을 수는 없습니다. 종단의 추적 출력은 복호화된 메시지를 보여줄 수 있습니다.
3. **완료 또는 실패.** RFC 7301에 따르면 ALPN에 참여하는 서버가 제안 중 공통 프로토콜을 찾지 못하면 치명적 경고 `no_application_protocol`을 보냅니다. ALPN을 제안하거나 선택하지 않고도 다른 TLS 조건이 맞으면 핸드셰이크 자체는 완료될 수 있습니다. 다음 동작은 애플리케이션과 리스너 정책에서 정합니다.
4. **사용 확인.** 선택값은 해당 TLS 연결에 적용됩니다. 요청이 어떻게 처리됐는지 확인하려면 요청 로그, HTTP 프레이밍 또는 애플리케이션 결과가 필요합니다. TLS를 종료하는 프록시가 다음 연결을 새로 열면 두 번째 구간에서 독립적으로 협상합니다.

**가상 정상 예시.** 브라우저가 엣지에 `h2,http/1.1`을 제안하고, 엣지는 TLS 1.3에서 `h2`를 고릅니다. 엣지가 원본 서버에 별도 TLS 연결을 열자 이번에는 `http/1.1`이 선택됩니다. 각 구간에서 해당 인증서 검증이 성공했습니다. 엣지와 원본 서버의 접근 로그에 같은 요청 ID `training-42`와 200 응답이 기록됐습니다. 두 값은 각 연결의 유효한 협상 결과이고, 로그는 요청 하나가 전달됐음을 뒷받침합니다. 엣지와 원본의 선택값을 비교하는 것만으로는 값이 다른 이유를 판단하기 어렵습니다.

## 3. 관측한 증거를 해석하세요

| 관측 | 확인 가능한 사실 | 다음 확인 |
|---|---|---|
| ClientHello에 `h2`가 있음 | 캡처한 메시지가 `h2`를 제안했습니다. | 해당 연결 구간과 종단에서 확인한 선택값을 찾습니다. |
| 완전한 TLS 1.2 캡처의 ServerHello에 `h2`가 있음 | 그 연결에서 서버가 `h2`를 골랐습니다. | 핸드셰이크 완료, 인증서 검증, 요청 자료를 따로 확인합니다. |
| TLS 1.3 수동 캡처에서 선택값이 안 보임 | 암호화됐거나 수집 범위에서 빠졌을 수 있습니다. | 선택이 없었다고 판단하기 전에 종단 또는 TLS 종료 지점의 기록을 봅니다. |
| 검증된 종단에서 ALPN 선택이 없다고 기록됨 | 이 핸드셰이크는 ALPN 선택 없이 완료됐습니다. | 확장 누락, 리스너 설정, 애플리케이션의 실제 기본값을 확인합니다. |
| 종단에 `no_application_protocol`이 기록됨 | 그 연결의 애플리케이션 프로토콜 협상이 실패했습니다. | 제안 목록과 해당 리스너·호스트·배포 버전의 정책을 대조합니다. |
| 프록시의 두 구간에서 각각 `h2`, `http/1.1` 사용 | 연결별로 다른 프로토콜을 협상했습니다. | 다운그레이드인지 판단하기 전에 두 구간에서 동일한 요청을 확인합니다. |

예상 밖의 리스너 정책, 잘못된 가상 호스트, 승인되지 않은 TLS 종료 지점 변경으로 기대한 프로토콜이 사라질 수 있습니다. 정상 프록시 설정이나 다른 클라이언트 빌드도 같은 관측을 만들 수 있습니다. 무엇이 바뀌었고 종단에서 무엇을 선택했는지 기록하세요. 사고 원인은 변경 이력과 요청 증거로 뒷받침한 뒤 판단합니다. 포트 443, 지문, 제안 한 건만으로는 침해를 입증할 수 없습니다.

## 4. 블루팀 수집·탐지·대응

- **수집.** UTC, 인터페이스와 캡처 위치, 전송 주소·포트, TLS 버전, 관측 가능한 요청 이름, ALPN 제안과 선택, 인증서 검증 및 핸드셰이크 결과를 따로 저장하세요. 엣지에서는 양쪽 구간의 연결 ID와 연결할 수 있는 요청 ID를 확보합니다. 패킷과 로그는 승인된 증거 처리 절차에 따라 보존합니다.
- **탐지.** 서비스, 리스너, 배포, 클라이언트 그룹별 정상 상태를 비교 기준으로 삼으세요. 새 협상 실패나 예상 밖의 선택값 변화가 애플리케이션 오류와 겹치는지 봅니다. TLS 1.3 수동 관측에서 선택 필드가 비어 있는 경우는 관측 범위의 한계입니다. 같은 구간과 유형의 관측자끼리 건수를 비교하세요.
- **대응.** 실패를 기록한 TLS 종단부터 조사합니다. 적용된 리스너·프록시 설정을 승인 기준과 실제 제안 목록에 대조하세요. 수정 뒤에는 같은 구간에서 통제된 핸드셰이크와 실제 애플리케이션 요청을 순서대로 확인합니다. 프록시가 있다면 원본 연결의 결과도 검증하세요.

Wireshark의 `tls.handshake.extensions_alpn_str`는 TLS 판독기가 해당 필드를 확인한 프레임을 찾습니다. 필요한 패킷을 충분히 수집하고 재조립할 수 있는 승인된 캡처에서 사용하세요. 값을 제안 또는 선택으로 표시하기 전에 TLS 트리에서 ClientHello, ServerHello, EncryptedExtensions 중 어디에 속하는지 확인합니다. 일반 수동 TLS 1.3 캡처에서는 승인된 핸드셰이크 비밀 정보 없이는 보호된 선택값을 읽을 수 없습니다. 이 실습은 종단의 추적 기능을 사용하며 패킷 복호화나 키 내보내기를 요구하지 않습니다.

## 5. 승인된 루프백 실습

본인 소유 또는 승인된 환경에서 Python 3과 OpenSSL 3.x로 실행하세요. 스크립트는 임시 포트를 골라 `127.0.0.1`에만 바인딩합니다. 클라이언트는 호스트 이름을 검증하고 시험용 임시 인증서만 신뢰합니다. `h2`를 선택해도 HTTP 요청을 보내지 않습니다. 정상 종료 시 임시 개인키가 삭제됩니다.

- <a href="{{ '/assets/downloads/tls-alpn-evidence/alpn_loopback.py' | relative_url }}" download>OpenSSL 루프백 실습 다운로드</a>

~~~sh
python3 alpn_loopback.py
python3 alpn_loopback.py --trace
~~~

| 조건 | 기대 결과 |
|---|---|
| TLS 1.3, `http/1.1,h2` 제안 | 실습 OpenSSL 서버가 공통 후보 중 선호하는 `h2`를 선택합니다. |
| TLS 1.3, `http/1.1`만 제안 | `http/1.1`이 선택됩니다. |
| TLS 1.3, ALPN 제안 생략 | 인증이 완료되고 선택된 ALPN은 없습니다. |
| TLS 1.3, 공통 후보 없음 | 클라이언트가 애플리케이션 프로토콜 협상 실패 경고를 받습니다. |
| TLS 1.2, 두 후보 제안 | `h2`가 선택됩니다. `--trace`에서 선택 위치는 ServerHello입니다. |

두 방식 모두 `5/5 ALPN controls passed.`가 나와야 합니다. 선택 사항인 추적 모드는 OpenSSL 종단 판독기로 ClientHello의 제안, TLS 1.2 ServerHello의 선택, TLS 1.3 EncryptedExtensions의 선택을 보여줍니다. CLI를 찾지 못하면 PATH를 확인하세요. 포트를 열 수 없다면 루프백 권한을 확인한 후 새 포트로 재시도합니다. 추적 모드만 실패하면 OpenSSL 빌드의 추적 기능과 출력 형식을 확인하세요. 인증서 검증 실패가 발생하면 결과를 따로 보존하고 이름과 신뢰 설정을 확인하세요.

**2026-11-27 실행 검증.** OpenSSL 3.5.9와 Python 3.12.14에서 두 방식 모두 다섯 사례가 통과했습니다. Wireshark 필드, ECH, 프록시와 HTTP/3는 문서로 검토했습니다. 루프백 실습의 실행 검증 범위는 TLS 협상이며 운영 종단, HTTP/2 요청, QUIC 전송은 별도 시험이 필요합니다.

## 6. 확인 문제와 완료 기준

- **`h2`를 제안했으면 HTTP/2를 사용한 건가요?** 제안 증거입니다. 서버 선택과 애플리케이션 증거를 확인하세요.
- **TLS 1.3 수동 캡처에서 왜 서버 선택이 보이지 않을 수 있나요?** 보호되는 EncryptedExtensions에 들어갑니다. 종단 증거나 승인된 복호화가 필요합니다.
- **엣지의 요청 하나가 구간마다 서로 다른 프로토콜을 사용할 수 있나요?** 가능합니다. 각 TLS 연결은 따로 협상합니다. 요청 식별자와 시각으로 전달을 대조하세요.

다섯 결과를 재현하고, 종단 추적에서 두 버전의 선택 위치를 확인하고, 실제 요청에서 프로토콜 사용을 입증할 증거를 설명하면 완료입니다.
