**학습 목표.** Linux 실행 파일에 선언된 의존성과 실행 중인 프로세스에 매핑된 파일을 비교합니다. 각 자료로 무엇을 확인할 수 있는지, 파일 출처와 실행 결과를 판단하려면 어떤 추가 증거가 필요한지 설명합니다.

## 1. 실행 파일과 프로세스를 왜 따로 보나요?

**ELF**는 Linux에서 실행 파일과 공유 라이브러리에 흔히 쓰는 파일 형식입니다. **공유 객체(shared object)**는 프로그램이 사용할 코드와 데이터를 제공하는 파일입니다. 동적으로 링크된 프로그램이 시작되면 **동적 로더**가 의존성을 찾아 공유 객체를 메모리에 매핑합니다. ELF 파일의 **직접 의존성**은 그 파일의 `DT_NEEDED` 항목에 기록됩니다. 각 라이브러리에도 자체 의존성이 있을 수 있습니다. 프로그램이 시작된 뒤 `dlopen()` 같은 인터페이스로 플러그인을 불러올 수도 있습니다.

**매핑**은 프로세스의 가상 주소 공간 안에 있는 구간입니다. 디스크 파일에 연결될 수도 있고, 연결된 파일이 없는 익명 구간일 수도 있습니다. Linux는 `/proc/PID/maps`에서 현재 매핑의 권한, 오프셋, 장치, inode와 가능한 경우 경로를 보여 줍니다. 예를 들어 `r-xp`에는 실행 권한이 있습니다. 메모리 매핑 목록은 어떤 함수가 호출됐는지 기록하지 않습니다.

| --- | --- | --- |
| ELF 프로그램 헤더 | 선언된 세그먼트와 인터프리터 | 실제 시작과 실행 상태 |
| ELF 동적 항목 | 직접 의존성 이름과 선언된 검색 설정 | 실제 선택 경로, 간접 의존성, 런타임 플러그인 |
| `/proc/PID/exe`와 프로세스 식별 정보 | 실행 파일 링크와 관측 대상 프로세스 | 각 라이브러리와 실제 동작 |

## 2. 정상 애플리케이션을 따라가기

보고서 앱이 C 라이브러리와 함께 시작하고, 사용자가 CSV 내보내기를 선택하면 공급자의 서식 플러그인을 불러온다고 가정합니다. 실행 파일의 동적 테이블에 C 라이브러리가 선언되어 있고 시작한 프로세스에서도 그 매핑을 볼 수 있습니다. 내보내기 기능이 초기화된 뒤의 스냅샷에서는 플러그인도 관측될 수 있습니다. 그 플러그인이 실행 파일의 `DT_NEEDED` 목록에 있을 필요는 없습니다. 실제 보고서가 생성됐는지는 해당 요청과 프로세스에 연결되는 앱의 내보내기 기록에서 확인합니다.

선언된 이름만으로 최종 경로를 알 수 없습니다. 예를 들어 glibc를 사용하는 GNU/Linux에서는 검색 경로, 로더 캐시, 기본 디렉터리 등이 이름 해석에 관여할 수 있습니다. `DT_RUNPATH`의 범위는 그 항목을 가진 객체의 직접 의존성입니다. 기존 `DT_RPATH`는 적용 우선순위와 하위 의존성으로의 전파 방식이 다릅니다. glibc에서 관찰한 순서를 다른 로더나 보안 실행 모드, 컨테이너에 그대로 적용하지 마세요. 조사 대상 버전과 마운트 네임스페이스를 기준으로 비교합니다.

## 3. 예상 밖의 매핑 조사하기

의존성의 출처가 불분명하거나 경로 권한이 느슨하면 서비스가 의도하지 않은 라이브러리를 불러올 수 있습니다. 낯선 경로, 디스크 파일 교체, 이름 불일치는 추가 조사가 필요한 단서입니다. 정상 업데이트 후에도 오래 실행된 서비스에 이전 파일이 매핑되어 있을 수 있습니다. `(deleted)` 표시는 파일이 연결 해제된 경우에 붙을 수 있으며, 경로 문자열 자체가 그 표시로 끝날 수도 있습니다. 업데이트 직후 같은 경로가 새 inode를 가리킬 수 있습니다. 익명 실행 구간은 코드를 생성하는 정상 런타임에서도 나타납니다. 경로, 매핑 하나, 공유 라이브러리 이름 하나로 침해를 확정할 수 없습니다.

1. **프로세스를 식별합니다.** 호스트와 부팅 식별값, PID 네임스페이스, 프로세스 시작 시각과 PID, `exe` 링크 대상, 확인 가능한 부모 또는 서비스, UTC 수집 범위를 기록합니다. PID가 재사용될 수 있으므로 여러 자료를 읽는 사이 같은 프로세스인지 확인합니다.
2. **범위를 정해 증거를 보존합니다.** 관련 매핑 줄과 장치·inode·권한·오프셋·이름을 보존합니다. 현재 경로의 파일 해시와 매핑된 파일의 식별 정보를 구분합니다. 같은 마운트 네임스페이스에서 경로를 비교하고 사고 절차에 따라 파일이나 패키지 증거를 보존합니다. 임의의 메모리 내용과 관련 없는 프로세스 환경 변수는 수집하지 않습니다.
3. **다른 설명도 확인합니다.** 패키지나 이미지 목록, 승인된 배포와 플러그인, 파일 소유권, 디렉터리 쓰기 권한, 업데이트 시각을 대조합니다. 로드 관측이나 애플리케이션 결과가 있다면 연결합니다. 버전·기능·컨테이너 이미지별로 정상 기준을 만듭니다. 예를 들어 쓰기 가능한 경로의 새 매핑, 예상 밖의 서비스 신원, 승인된 배포 시간 밖의 변경이 함께 나타나는지 확인할 수 있습니다.
4. **대응과 복구를 검증합니다.** 승인되지 않은 변경이라는 근거가 충분하면 가능한 범위에서 프로세스와 파일 증거를 보존한 뒤 담당자와 격리나 재시작을 조율합니다. 신뢰할 수 있는 패키지나 이미지를 복원하고 의도한 구성, 새 프로세스의 식별 정보와 매핑을 확인합니다. 실행이나 결과 증거가 없다면 그 부분은 미확인으로 남깁니다.

승인된 Linux 분석 환경에서는 GNU `readelf -l`로 프로그램 헤더를, `readelf -d`로 동적 섹션을 확인할 수 있습니다. 수상한 파일은 격리된 환경에서 최신 보안 패치가 적용된 분석 도구로 검사합니다. Linux 매뉴얼은 신뢰할 수 없는 실행 파일에 `ldd`를 사용하지 말라고 안내합니다. 실시간 프로세스의 `/proc/PID/maps`를 읽으려면 procfs 설정과 ptrace 접근 검사를 충족해야 합니다. 권한이 부족하면 승인된 수집 경로를 사용하고 공백을 기록합니다. 종료한 프로세스에서는 실시간 매핑 파일을 읽을 수 없습니다.

`cc`나 `readelf`가 없으면 컴파일러와 Binutils가 준비된 Linux 실습 환경을 사용하세요. 임시 디렉터리에서 실행이 실패하면 실행이 허용된 승인된 임시 작업 공간을 사용합니다. 실행 중 매핑 읽기에 실패한 경우 procfs와 환경의 접근 제한을 확인합니다. Linux의 GNU Binutils 2.44와 GCC 14.2.0에서 실행했습니다. 이 실습으로 확인한 것은 직접 빌드한 파일의 매핑이며, 운영 서비스의 동작은 검증하지 않았습니다.

## 5. 확인 문제와 완료 기준

- **플러그인이 실행 파일의 `DT_NEEDED`에 있어야 매핑되나요?** 시작 이후에 플러그인을 불러오는 경우에도 매핑될 수 있습니다.
- **`r-xp`로 특정 함수가 실행됐다고 볼 수 있나요?** 이 표시는 읽기·실행 권한이 있는 비공유 매핑을 나타냅니다. 실행 결과는 실행 관측이나 앱 기록으로 확인합니다.
- **업데이트 뒤 `(deleted)`가 보이면 변조인가요?** 매핑의 장치·inode, 패키지 업데이트와 프로세스 시작 시각을 비교합니다. 이전 파일이 매핑된 채 남아 있을 수 있습니다.

세 가지 검사를 통과하고, 실제 매핑된 파일을 식별하는 증거와 애플리케이션 결과를 확인하는 증거를 각각 설명하면 실습을 마친 것입니다.
