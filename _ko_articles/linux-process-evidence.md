**학습 목표.** 두 기록이 같은 Linux 프로세스의 수명에 속하는지 판단합니다. 현재 스냅샷으로 어디까지 알 수 있는지, PID만 같아서 연결을 보류해야 할 때는 언제인지 설명합니다.

## 1. PID는 특정 관점에서 보이는 번호입니다

**프로세스**는 프로그램을 실행하는 인스턴스입니다. **PID**는 Linux가 특정 PID 네임스페이스에서 프로세스를 가리키는 번호입니다. **PID 네임스페이스**는 번호가 쓰이는 범위를 나눕니다. 같은 프로세스가 컨테이너 안에서는 PID 7, 호스트에서는 PID 4200으로 보일 수 있습니다. 다른 컨테이너에도 PID 7이 있을 수 있습니다. 프로세스가 종료되면 재부팅 없이도 그 번호가 재사용될 수 있습니다.

**프로세스 수명**은 생성부터 종료까지입니다. 기존 프로세스가 `execve`를 호출하면 실행 중인 프로그램 이미지가 바뀌고 PID는 유지됩니다. 작업을 시작해 주는 래퍼가 다른 프로그램으로 넘어갈 때 새 프로세스를 만들지 않을 수 있는 이유입니다. **부모 PID**는 관측 시점의 부모 관계를 보여 줍니다. 부모가 종료되면 자식은 다른 부모에 연결될 수 있고, 기존 부모의 PID도 재사용됩니다. 이름과 PID·부모 PID는 이력을 조사하기 위한 단서입니다.

| 항목 | 어떤 질문에 답하나요? | 확인할 점 |
| --- | --- | --- |
| 호스트와 부팅 ID | 어느 장비의 어느 부팅에서 나온 기록인가요? | 수집기 이름이나 호스트 이름에만 의존하지 말고 원본 장비 식별자와 부팅 ID를 보존합니다. |
| PID 관점과 PID | 어떤 번호 범위에서 나온 PID인가요? | procfs나 센서가 PID를 어디서 읽었는지 적습니다. 호스트와 컨테이너 사이의 대응을 확인한 뒤에만 변환합니다. |
| 프로세스 시작 틱 | 부팅 이후 언제 시작했나요? | `/proc/<pid>/stat`의 22번째 필드 `starttime`을 읽습니다. 시간 단위를 바꿀 때는 틱 빈도도 남깁니다. |
| 현재 프로그램과 부모 | 관측 시점에 어느 프로그램과 부모가 보이나요? | 둘 다 바뀔 수 있습니다. 과거 관계를 주장하려면 기록된 실행·부모 이벤트를 찾습니다. |

**procfs**는 보통 `/proc`에 마운트되는 커널의 가상 파일시스템입니다. 프로세스별 파일을 읽으면 커널이 그 시점에 제공하는 상태가 나옵니다. 주기적으로 읽어 스냅샷을 남겨도 두 관측 사이에 시작했다가 끝난 프로세스는 놓칠 수 있습니다.

여기서 **틱**은 부팅 후 프로세스가 시작한 시점을 나타내는 단위입니다. Linux에서 `os.sysconf("SC_CLK_TCK")`로 초당 틱을 조회할 수 있습니다. 값이 100이면 12,000틱은 그 시계에서 120초입니다. UTC 시각이나 프로세스가 소비한 CPU 시간이 아닙니다. 대조에는 정수 원본을 쓰고, UTC 발생·수집 시각은 따로 보존하세요. 시간 네임스페이스를 지원하는 커널에서는 procfs가 읽는 쪽의 부팅 시계 오프셋을 적용할 수 있습니다. PID 관점이 같아도 시간 기준은 다를 수 있으므로 같은 시간 관점에서 대조하거나 먼저 변환 근거를 확보하세요. 저널의 단조 증가 수신 시각과 procfs 시작 틱은 용도와 단위가 다릅니다.

## 2. 같은 실행인지 확인하는 순서

![호스트·부팅·PID 관점부터 확인하고 PID와 시작 틱을 비교합니다. 키가 일치했는지, 달랐는지, 판단을 보류했는지 남깁니다.]({{ '/assets/diagrams/linux-process-identity-ko.svg' | relative_url }})

1. **원본 호스트와 부팅 구간을 확인합니다.** 접근 가능한 곳에서 커널 부팅 UUID는 `/proc/sys/kernel/random/boot_id`로 확인할 수 있습니다. 저널은 `_BOOT_ID`를 32자리 16진수 값으로 저장합니다. 원본을 보존한 뒤 두 값을 비교할 때만 UUID 표기를 통일하세요.
2. **출처가 PID를 어느 관점에서 기록했는지 확인합니다.** procfs 경로의 PID는 해당 procfs 인스턴스의 관점입니다. 지원되는 커널의 `/proc/<pid>/status`에서 `NStgid`는 보이는 네임스페이스별 프로세스 ID, `NSpid`는 스레드 ID를 나타냅니다. 스레드 그룹 리더에서는 각 관점의 두 값이 일치합니다. 프로세스가 살아 있을 때 관측한 대응 관계를 남기세요. 대상 프로세스가 속한 네임스페이스만 알아서는 이벤트의 PID가 어느 관점인지 알 수 없습니다.
3. **그 범위와 공통 시간 기준 안에서 PID와 시작 틱을 대조합니다.** 호스트·부팅·PID 관점·PID·시작 틱이 모두 같으면 PID만 같은 경우보다 근거가 강합니다. 틱의 시간 해상도에는 한계가 있고, 수집이 짧은 수명을 놓치거나 값을 잘못 변환할 수 있습니다. 같은 센서가 정의한 프로세스 인스턴스 ID가 있다면 문서에서 의미를 확인해 사용하고, 다른 센서끼리의 대응은 별도로 확인하세요.

**정상 예시.** 예약 작업이 보고서 래퍼를 실행합니다. 09:00:02 UTC에는 PID 4200, 시작 틱 12000인 래퍼가 보입니다. 09:00:04에는 같은 관점에서 PID와 시작 틱은 유지되고 실행 이미지가 Python으로 바뀝니다. 래퍼가 자신을 Python으로 교체한 정상 흐름에 들어맞습니다. 실제 실행 이벤트나 이미 확인한 시험 절차로 이를 뒷받침할 수 있습니다. 나중에 같은 호스트·부팅·관점에 PID 4200이 다시 나타나지만 시작 틱은 40000입니다. 다른 수명으로 보는 것이 타당합니다. 시작 틱이 없는 옛 보안 이벤트를 현재 보이는 PID 4200에 바로 붙이면 잘못된 실행을 지목할 수 있습니다.

## 3. 조사 질문에 맞는 출처를 고르세요

| 출처 | 확보할 수 있는 근거 | 수집 조건과 한계 |
| --- | --- | --- |
| 현재 `/proc` 스냅샷 | 상태, 시작 틱, 관측 시점의 부모, 네임스페이스 대응, 접근 가능할 때 실행 파일 링크 | Linux와 읽을 수 있는 procfs 필요. 관측 도중 프로세스가 종료되거나, 마운트·접근 정책으로 항목이 보이지 않을 수 있음 |
| systemd 저널 | 유닛과 메시지 문맥, 부팅 ID, PID, 메시지 출처에 관한 메타데이터 | systemd-journald가 메시지를 이미 수집했고 읽기 권한과 보존 기간이 확보돼야 함. 자식의 표준 출력·오류가 기존 스트림을 쓰면 스트림을 연 프로세스의 자격 정보가 남을 수 있음 |
| Linux Audit 또는 엔드포인트 센서 | 과거 실행과 연관 필드, 센서가 제공하는 프로세스 인스턴스 ID | 실행 시점 전에 커널·수집기, 해당 규칙과 보존이 마련돼 있어야 함. 필드 의미와 누락·필터링 여부 확인 |

PID로 저널을 좁힐 수 있습니다. Linux에서 systemd 저널을 읽을 수 있을 때, 원본의 저널 부팅 ID(16진수 32자리)와 짧은 UTC 구간을 씁니다. 승인 범위에 맞는 값을 `BOOT_ID`, `FROM_UTC`, `TO_UTC`에 넣고 실행하세요.

```sh
journalctl --utc --since "$FROM_UTC" --until "$TO_UTC" \
  "_BOOT_ID=$BOOT_ID" "_PID=4200" --output=json --no-pager
```

시각 입력 형식은 `2030-02-03 09:00:00 UTC`처럼 작성합니다. 가상 예시의 시각과 PID는 조사 범위에 맞게 바꾸세요. 이 명령은 필터와 맞는 저널 메시지를 반환합니다. 구간 안에서 번호가 재사용됐을 경우 여러 수명이 섞일 수 있습니다. 결과가 없으면 메시지가 전송되지 않았거나, 필드가 없었거나, 보존 기간이 지났을 수 있습니다. 아래 실습에는 systemd가 필요하지 않습니다.

**정상 설명과 오용 가능성.** 익숙한 프로세스 이름이 정상 작업으로 보이게 할 수 있고, PID만으로 연결하면 의심스러운 통신을 무관한 프로세스에 붙일 수 있습니다. 먼저 센서가 무엇을 기록했는지 확인하고, 실행 파일 출처, 서비스나 컨테이너, 실행 이력과 네트워크 기록을 독립적인 출처로 대조하세요. 서비스와 이름이 같다는 사실의 증거력은 낮습니다. 프로그램 변경은 정상 래퍼 교체일 수 있고, 부모나 의존 프로세스가 보이지 않는 것은 수집 공백일 수 있습니다. 승인된 방어 검증에서는 알려진 정상 프로세스로 시험해 관측값과 관측 범위가 수집 이후에도 유지되는지 확인할 수 있습니다.

대응할 때는 출처, 관측 시각, 원본 필드와 연결의 확실성을 남깁니다. 명령행에는 비밀이 포함될 수 있으므로 필요하고 승인된 경우에만 수집합니다. 프로세스를 격리하거나 종료하기로 했다면 승인된 도구로 실행 직전의 대상을 다시 확인하세요. 과거 이벤트의 PID만으로 대상을 고르면 재사용된 번호의 다른 프로세스에 영향을 줄 수 있습니다. 대응 대상을 뒷받침한 근거를 기록합니다.

## 4. 오프라인 연습과 읽기 전용 Linux 실습

[가상 관측 CSV]({{ '/assets/labs/linux-process-observations.csv' | relative_url }})와 [Python 분석기]({{ '/assets/labs/linux-process-evidence.py' | relative_url }})를 같은 폴더에 저장하세요. 식별자, 실행 경로, UTC 시각은 모두 가상입니다. 오프라인 연습에는 Python 3와 표준 라이브러리만 필요합니다.

```sh
python3 linux-process-evidence.py
```

가상 자료는 관측값의 시간 기준을 서로 비교할 수 있다고 가정합니다. 각 행을 `p01`과 비교합니다. 스크립트의 결과는 제공된 키의 일치 여부입니다. PID 관점이 다르면 직접 연결할 수 없지만, 신뢰할 수 있는 변환 관계가 나중에 확인되면 같은 실제 프로세스로 해석될 수 있습니다.

| 관측 행 | p01과 비교한 결과 | 이유 |
| --- | --- | --- |
| p02 | 키 일치 | 프로그램 이미지는 바뀌었지만 프로세스 키는 같음 |
| p03 | 키 불일치 | 같은 호스트·부팅·PID 관점에서 시작 틱이 달라짐 |
| p04 | 키 불일치 | 컨테이너 관점은 다른 PID 번호 범위를 사용 |
| p05 | 키 불일치 | 새 부팅에서 같은 번호와 시작 틱이 나타남 |
| p06 | 판단 보류 | 시작 틱을 확보하지 못함 |
| p07 | 키 불일치 | 기록의 원본 호스트가 다름 |
| p08 | 키 불일치 | 같은 호스트 관점에서 PID가 다름 |

**기대 결과.** 키 일치 1건, 불일치 5건, 보류 1건입니다. 파일을 열 수 없으면 이름, CSV 머리글, 첫 행에 키가 모두 있는지 확인하세요. 건수가 다르면 각 필드를 하나씩 비교하세요. 같은 시작 틱이 같은 관점의 여러 PID에 나타날 수 있습니다.

자가 소유하거나 명시적으로 승인된 Linux에서 procfs를 읽을 수 있고 Python의 PID와 procfs의 PID 관점이 같다면 다음 실습도 실행할 수 있습니다.

```sh
python3 linux-process-evidence.py --own-child
```

파이프 입력을 기다리는 Python 자식 하나를 시작합니다. 그 자식의 `stat`만 두 번 읽고 파이프를 닫은 뒤 종료를 기다립니다. 열린 proc 디렉터리를 기준으로 읽기 때문에 번호가 재사용되더라도 읽기 대상이 다른 프로세스로 바뀌지 않습니다. `stat`의 두 번째 필드 `comm`에는 공백이나 괄호가 들어갈 수 있어, 이름의 닫는 괄호 뒤에서부터 필드를 셉니다.

**실제 읽기에서 기대할 결과.** 두 번 읽은 시작 틱이 같고, 자식이 종료된 후 열린 디렉터리에서 `stat`을 더 이상 읽을 수 없습니다. 접근이 거부되거나 경로가 없으면 승인된 환경에서 운영체제, 마운트 정책과 PID 관점을 확인하세요. 관리형 컨테이너에서는 procfs 일부가 가려질 수 있습니다. 이 실습은 관리자 권한이나 PID 강제 재사용, 감사 설정 변경 없이 진행합니다. 게시 과정에서 가상 CSV와 클라우드 Linux의 자식 프로세스로 스크립트를 실행했습니다. 제품 텔레메트리와 저널 조회는 문서로 검토했습니다.

## 5. 확인 문제와 완료 기준

1. **재부팅 뒤 PID와 프로그램 이름이 모두 같습니다. 같은 실행인가요?** 부팅이 다르므로 수명이 다릅니다.
2. **키는 같고 실행 이미지만 바뀌었습니다. 침해 증거인가요?** 정상적인 `execve`로도 이미지가 달라집니다. 예상 업무 흐름과 실행 이력으로 대조합니다.
3. **두 컨테이너에 PID 7이 있습니다. 바로 연결할 수 있나요?** PID는 관점 안의 번호입니다. 네임스페이스 대응과 수명 근거를 확인해야 합니다.
4. **저널 검색 결과가 비어 있습니다. 프로세스가 실행됐나요?** 그 결과만으로 판단할 수 없습니다. 수집 범위를 확인하고 다른 출처에서 과거 실행 기록을 찾습니다.

p02·p03·p06의 차이를 설명하고, p04에 관점 변환이 필요한 이유와 Linux 실습에서 관측한 범위를 정리하면 완료입니다.
