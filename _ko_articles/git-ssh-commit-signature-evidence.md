Git 커밋의 서명 검증이 성공해도 저장소의 릴리스 정책을 통과하지 못할 수 있습니다. 어떤 커밋 객체에 서명했는지, 검증기가 어느 키를 신뢰했는지, 그 서명자가 변경을 승인할 권한이 있었는지 따로 확인하세요.

## 1. 서명은 어디까지 보호하나요?

**커밋 객체**는 트리, 부모 커밋 참조, 작성자·커미터 정보와 메시지를 담습니다. **트리**는 커밋에 포함된 파일의 스냅샷을 가리킵니다. Git은 SSH로 서명한 커밋에 커밋의 내용을 보호하는 서명을 넣습니다. 이 장에서는 OpenSSH를 사용하는 **SSH 서명 형식**을 다룹니다. 서명과 검증은 오프라인에서도 가능하며 SSH 로그인이나 Git 호스트 연결이 필요하지 않습니다.

서명자는 개인키를 보유하고 검증자는 신뢰하는 공개키 자료를 사용합니다. Git의 SSH 설정에서 **허용 서명자 파일**은 공개키와 하나 이상의 **프린시펄(principal)** 표기를 연결합니다. 이 표기는 일치한 키를 식별하는 데 쓰입니다. Git은 이를 작성자 이메일과 대조해 작성자를 인증하지 않습니다. **키 지문**은 공개키에서 계산한 짧은 식별자입니다. 새 키를 수락하기 전에 신뢰할 수 있는 등록 자료와 대조하세요.

## 2. 정상적인 서명 변경 한 건을 따라가세요

가상의 유지보수 담당자가 릴리스 노트를 바꾸고 커밋에 서명합니다. 검토자는 리뷰 기록에서 정확한 전체 커밋 ID를 기록하고, 조직에서 관리하는 출처에서 승인된 서명자 파일을 받습니다. 승인된 키와 폐기 자료로 커밋을 검증한 뒤 지문이 유지보수 담당자의 등록 키와 같은지 확인합니다. 이력을 다시 작성한 경우에도 리뷰가 동일 커밋 또는 의도한 변경 범위를 포함했는지 확인합니다. 이 코드에서 만들어진 빌드에는 별도의 출처 증명과 산출물 검증이 필요합니다.

| 증거 | 확인할 수 있는 범위 |
| --- | --- |
| 전체 커밋 ID와 검증된 서명 | 그 키가 서명한 객체의 무결성입니다. 판단 범위는 해당 객체입니다. |
| 허용 프린시펄과 키 지문 | 검증 파일의 어떤 공개키가 일치했고 어떤 표기가 연결됐는지 알려 줍니다. |
| 작성자·커미터 필드 | 커밋에 담긴 신원 표기입니다. 두 사람이 다를 수 있고 이 필드만으로 키 소유자를 확인할 수 없습니다. |
| PR 승인과 브랜치 제어 | 해당 객체나 변경 범위가 저장소의 검토·정책 조건을 충족했는지 확인합니다. |
| 빌드 출처 증명과 산출물 다이제스트 | 적절한 정책으로 검증하면 어느 워크플로에서 산출물을 만들었는지, 바이트가 증명과 일치하는지 확인합니다. |

커밋을 amend하거나 rebase하면 파일 결과가 같아 보여도 ID가 다른 객체가 만들어질 수 있습니다. 실제 릴리스에 쓸 객체를 검증하세요. 브랜치 끝 커밋의 서명에 성공해도 이전 커밋들의 서명 상태는 별도로 확인해야 합니다. 모든 커밋에 서명을 요구하는 정책은 그 정책이 정의한 범위를 검사합니다.

## 3. 실패와 오용 가능성을 조사하세요

알 수 없는 키는 개발자의 정상 키 교체가 검증 파일에 아직 반영되지 않았거나 승인되지 않은 신원에서 서명해서 나타날 수 있습니다. 별도의 승인 경로에서 지문과 키 수명주기 기록을 확인하세요. 개인키가 노출되면 승인되지 않은 커밋도 기존 승인 키의 서명으로 검증을 통과할 수 있습니다. 서명 키와 커밋 객체, PR 검토, 푸시·CI 활동을 대조해 범위를 정하세요. 조사하는 변경에 새 키가 포함됐다는 이유만으로 등록하지 마세요. 신뢰 정책의 변경은 이미 신뢰하는 승인 절차로 검증합니다.

현재 로컬 판정과 호스팅 서비스의 배지가 다를 수 있습니다. GitHub는 과거의 검증 성공 기록이 저장소 네트워크에서 키 교체·만료·폐기 뒤에도 남을 수 있다고 설명합니다. 배지를 본 시각과 어떤 검증 기록이 표시된 것인지 남기세요. 현재 사고 대응에서는 승인된 별도 출처의 신뢰·폐기 정보를 사용합니다. 커밋에 담긴 시각이나 로컬 키 유효 기간 검사만으로 신뢰할 수 있는 서명 시각을 확정할 수 없습니다.

## 4. 수집하고 검증한 뒤 대응하세요

1. 전체 커밋 ID, 참조, 관측 시각, 예상 병합·릴리스 커밋과 관련 리뷰·CI 기록을 보존하세요. Git과 OpenSSH 버전, 정책 파일의 출처와 버전을 기록합니다.
2. 승인된 허용 서명자 파일과 가능한 경우 폐기 파일을 명시적으로 지정하세요. 문제를 좁힐 때는 `git config --show-origin`으로 설정 출처를 확인합니다. 검증하려는 변경과 독립된 경로에서 신뢰 설정을 확보하세요.
3. 미서명, 검증 불가, 신뢰되지 않은 키, 폐기된 키를 구분하고 도구의 출력과 종료 상태를 확인하세요. 자동 검증은 서명 성공과 별도의 승인 조건을 모두 확인해야 합니다. 실패가 반복되면 저장소, 서명 키와 최근 정책 변경을 대조합니다.
4. 키 노출이 의심되면 커밋과 검증 근거를 보존하고 소유자와 키 교체·폐기를 조율하세요. 영향받은 참조, 빌드, 배포 범위를 정하고 사고 대응 정책으로 해당 구간을 다시 검사합니다.

대상 객체가 들어 있는 신뢰할 수 있는 로컬 체크아웃에서 `commit`에 전체 커밋 ID를, `allow`와 `revoked`에는 승인된 정책 파일의 절대 경로를 지정하세요. 폐기 파일은 OpenSSH KRL(키 폐기 목록) 또는 폐기된 공개키를 담은 텍스트 목록을 사용할 수 있습니다. 이 조회는 저장소 설정을 수정하지 않습니다. 승인된 폐기 파일이 없다면 조직 정책이 허용할 때만 해당 옵션을 빼고 검증 범위를 기록하세요.

```bash
git -c gpg.ssh.allowedSignersFile="$allow" -c gpg.ssh.revocationFile="$revoked" \
  verify-commit "$commit"
git -c gpg.ssh.allowedSignersFile="$allow" -c gpg.ssh.revocationFile="$revoked" \
  show -s --format='%H %G? %GS %GF %GT %ae %ce' "$commit"
```

서명 통과 여부는 `verify-commit` 종료 상태로 판단하고 진단 출력도 보존하세요. 두 번째 명령은 커밋 ID, 서명 상태, 서명자, 지문, 신뢰 수준, 작성자 이메일, 커미터 이메일 순으로 표시합니다. 검증 성공 여부는 첫 번째 명령에서 확인합니다. 신뢰할 것으로 예상한 서명이 실패하면 객체, 도구, 파일 읽기 권한과 키 지문을 확인하세요. 수집 도중 신뢰 정책을 바꾸기 전에 실패 출력 원본을 확보합니다.

## 5. 실제 서명으로 오프라인 실습하기

Python 3, SSH 서명을 지원하는 Git 2.34 이상과 유지보수 중인 OpenSSH `ssh-keygen`이 필요합니다. 실습은 접근이 제한된 임시 디렉터리에 암호 문구 없는 일회용 Ed25519 키 쌍 두 개와 별도 저장소를 만들고 종료할 때 정리합니다. 서버에 접속하거나 기존 키와 Git 설정을 사용하지 않습니다.

```bash
python3 git-ssh-commit-signature-evidence.py
```

```text
trusted: accepted
untrusted_key: rejected
unsigned: rejected
revoked_key: rejected
different_author: accepted
```

첫째, 둘째, 넷째 검사는 **같은 서명 커밋**에 다른 신뢰 자료를 적용합니다. 다섯째는 다른 작성자를 기록한 별도 커밋에 신뢰 키로 서명하며 작성자 필드가 실제로 다른지도 확인합니다. 준비 단계가 실패하면 `git`과 `ssh-keygen`의 PATH, SSH 서명 지원, 임시 폴더 쓰기 권한을 확인하세요. Git 2.56.1과 OpenSSH 10.0p2로 실제 검증을 실행했습니다. 호스팅 배지와 브랜치 규칙, CI 동작은 문서로 검토했습니다.

## 6. 확인 문제와 완료 기준

- **같은 서명 커밋이 다른 허용 목록에서 왜 실패했나요?** 검증자가 신뢰하는 키가 달라졌습니다. 커밋과 서명 데이터는 그대로입니다.
- **서명 검증에 성공하면 작성자가 직접 승인했나요?** 검증은 확인된 키가 커밋 내용에 서명했음을 보여 줍니다. 변경 승인은 리뷰 기록과 정책에서 확인하세요.
- **과거 호스팅 배지만으로 지금의 키 노출 의혹을 판단할 수 있나요?** 배지의 검증 기록을 수집하고 해당 객체를 사고 대응 신뢰 정책으로 평가하세요.

결과 다섯 줄을 맞추고, 승인된 키, 현재 폐기 정책, 변경 승인 사이의 차이를 각각 설명하면 완료입니다.
