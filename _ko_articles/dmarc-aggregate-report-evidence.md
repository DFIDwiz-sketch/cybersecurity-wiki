청구 메일 발송 서비스를 바꾼 뒤 DMARC 실패가 늘었습니다. 그런데 수신기의 일일 보고서를 보니 그중 일부는 SPF를 통과했습니다. DNS를 바꾸기 전에 어느 도메인이 SPF를 통과했는지, 고객에게 표시된 도메인은 무엇인지, 수신기가 어떻게 처리했는지부터 확인해 보세요. 집계 보고서를 읽으면 정렬이 어긋난 외부 발송 서비스, 예상된 전달 경로, 사고 조사가 필요한 트래픽을 가려낼 수 있습니다.

## 1. 집계 보고서는 무엇을 측정할까요?

DMARC는 SPF 또는 DKIM으로 인증한 도메인이 메일에 표시된 `From` 도메인과 **정렬**되는지 확인합니다. SMTP의 반송 주소가 비어 있지 않은 일반 메일에서 SPF는 수신기에 접속한 IP가 봉투 발신자 도메인에서 허용되는지 평가합니다. DKIM은 서명을 검증하며, 서명 도메인은 `d=` 값에 들어 있습니다. 엄격 정렬은 도메인 이름이 같아야 하고, 완화 정렬은 수신기가 적용하는 탐색 규칙에 따라 두 도메인의 조직 도메인이 같으면 됩니다. 두 방식 중 어느 하나라도 인증과 정렬을 모두 통과하면 DMARC를 통과할 수 있습니다.

**메일 수신기**는 들어온 메시지를 평가하고 집계 보고서를 보낼 수 있는 서비스입니다. **도메인 소유자**는 DMARC DNS 레코드의 `rua`로 집계 보고서 수신을 요청할 수 있습니다. **작성자 도메인(Author Domain)**은 화면에 표시되는 From 도메인입니다. **정책 도메인(Policy Domain)**은 수신기가 적용한 정책을 찾은 도메인으로, 작성자 도메인의 상위 도메인일 수도 있습니다. 보고서 한 건은 정책 도메인 하나를 기준으로 하며, 같은 정책을 적용받는 여러 From 도메인이 들어갈 수 있습니다.

## 2. 보고서 하나를 순서대로 읽기

1. `report_metadata`에서 보고 기관, 보고서 ID, UTC 시간 범위를 확인합니다. `date_range.begin`과 `date_range.end`는 유닉스 초이며 수집 기간을 나타냅니다. 개별 메시지가 도착한 정확한 시각은 이 값으로 알 수 없습니다.
2. `policy_published`는 해당 수신기가 관측한 정책입니다. 정책 도메인과 관련 `p`, `sp`, 정렬 모드, 테스트 여부를 확인합니다. 사건 당시 변경 이력과 DNS 응답을 대조하세요. 지금 조회한 TXT 레코드는 현재 값을 보여 줍니다.
3. 각 `record`를 읽습니다. `row.count`는 그 행에 포함된 메시지 수이고, `row.source_ip`는 그 수신기에 접속한 메일 서버의 IP입니다. 한 IP가 여러 행에 나와도 From 도메인이나 평가 결과가 서로 다를 수 있습니다.
4. 식별자와 인증 결과를 비교한 뒤 수신기가 보고한 정렬 및 처분을 읽습니다. 보고서를 분석할 때는 기록된 정렬 결과를 사용하세요. 과거의 판단을 독립적으로 재현하려면 당시의 DNS 증거와 수신기가 적용한 도메인 탐색 규칙이 추가로 필요합니다.

| XML 필드 | 알 수 있는 내용 | 이어서 확인할 곳 |
| --- | --- | --- |
| `identifiers.header_from` | 평가 대상인 화면의 From 도메인 | 도메인·하위 도메인 목록 |
| `auth_results.spf`, `auth_results.dkim` | DMARC 정렬을 따지기 전의 인증 도메인과 결과. DKIM 서명은 여러 개일 수 있음 | 발송 서비스 설정의 봉투 발신자 도메인, DKIM 서명 도메인 또는 셀렉터 |
| `row.policy_evaluated.spf`, `.dkim` | 수신기가 기록한 두 가지 DMARC 정렬 결과 | 어느 방법이 인증과 정렬을 함께 통과했는지 |
| `row.policy_evaluated.disposition`, `.reason` | 보고된 DMARC 처리와 기록된 예외 사유 | 수신 측 메시지 추적의 SMTP 수락, 필터링, 배달 위치 |
| `row.source_ip`, `.count` | 접속한 메일 서버와 해당 행의 메시지 수 | 승인된 발송 경로, 릴레이 로그, 알려진 전달 경로 |

## 3. 정상 보고서 안에서 살펴볼 행 고르기

내려받을 수 있는 가상 보고서는 수신기 하나가 2026년 11월 26일 UTC에 관측한 결과입니다. 정책 도메인은 `example.com`, 작성자 도메인은 `orders.example.com`이며 보고된 정책은 `p=reject`입니다.

| 접속 IP | 건수 | 정렬 전 인증 증거 | 정렬과 보고된 처리 |
| --- | ---: | --- | --- |
| `192.0.2.10` | 240 | 외부 발송 서비스의 `bounce.vendor.example.net`이 SPF 통과. `orders.example.com`이 DKIM 통과. | SPF 정렬 실패. DKIM 정렬 통과로 DMARC 통과. |
| `198.51.100.20` | 12 | 전달 서버의 `forward.example.org`가 SPF 통과. 원래 DKIM은 실패. | 두 방식 모두 정렬 통과 없음. 처분은 `none`, 예외 사유는 `mailing_list`. |
| `203.0.113.30` | 5 | 관련 없는 봉투 발신자 도메인이 SPF를 통과하고, 관련 없는 서명도 DKIM 통과. | 두 방식 모두 `orders.example.com`과 정렬 실패. 처분은 `reject`. |
| `192.0.2.11` | 3 | `orders.example.com`이 SPF 통과. DKIM은 실패. | SPF 정렬 통과로 DMARC 통과. |

이 보고서의 정렬 통과 비율은 **243 ÷ 260 = 93.46%**입니다. 정렬 통과가 없는 17건에는 12건과 5건이 모두 들어갑니다. 보고된 DMARC 처분이 `reject`인 건수는 5건입니다. 12건은 메일링 리스트에 대한 정책 예외와 들어맞을 수 있습니다. 예외 사유는 수신기가 어떤 판단을 보고했는지 알려 주며, 실제 ARC 평가와 배달 위치를 확인하려면 그 수신기의 자료가 필요합니다.

5건은 확인할 가치가 있습니다. 발신자는 자신이 관리하는 도메인으로 인증을 통과시키면서 화면의 From에 다른 도메인을 표시할 수 있습니다. 정상 발송 서비스의 설정이 잘못되어도 비슷한 결과가 발생합니다. 이미 허가받은 발송 경로나 철자가 비슷한 도메인에서 보낸 유해 메일은 실제 평가 대상 도메인의 DMARC를 통과할 수도 있습니다. 사칭이나 계정 침해를 단정하기 전에 메시지 내용과 업무 요청의 진위를 확인하고 신뢰할 수 있는 수신 기록을 대조하세요.

## 4. 블루팀의 수집, 탐지, 대응

- **승인된 `rua` 경로로 수집합니다.** 참여 수신기가 보고서를 사서함이나 수집 서비스로 보낼 수 있는지 확인하세요. 정책 도메인과 조직 도메인이 다른 목적지는 RFC 9990 §4에 따른 외부 목적지 승인이 필요합니다. 보고 기관별 수신 상태, 파싱 오류, 비어 있는 기간을 감시합니다. 압축 전송물과 압축 해제 결과에 모두 크기 제한을 적용하고, 외부 리소스 및 문서 유형 선언을 제한한 파서를 사용하세요. 원본 XML과 발송 인프라 정보에 접근할 수 있는 사람을 제한합니다. 예상 밖의 보고서는 신뢰하는 수신 메일 기록으로 보고 출처를 확인한 후 정책 결정에 사용하세요.
- **중복을 빼고 합산합니다.** 보고 기관, 보고서 ID, 정책 도메인, 시간 범위와 파일 지문을 보존합니다. 검증된 보고 기관과 정책 도메인을 기준으로 재전송을 구분합니다. 같은 범위에서 본문이 다른 복사본이나 기간이 겹치는 보고서는 검토가 끝날 때까지 집계를 보류합니다. 초기 조사에서는 수신기별 집계를 따로 봅니다. XML 행 개수 대신 `count`를 합산하고, 비율을 인용할 때는 수집 범위와 분모를 적습니다.
- **평소와 달라진 발송 경로를 조사합니다.** 같은 보고 기관과 From 도메인의 과거 실패 건수와 비율을 비교하세요. 접속 서버, 서명 도메인이나 셀렉터, 정책 예외 사유로 나눠 봅니다. 새 IP 또는 셀렉터는 서비스 등록·DNS 변경 이력, 릴레이 로그, 신뢰하는 `Authentication-Results` 표본과 대조합니다. 공유 IP 하나로 발송 주체를 특정하기 어렵습니다. 보고서가 빠졌다면 수신기의 미참여, 지연, DNS 목적지 승인, 수집 오류를 확인하세요.
- **확인된 영향에 맞춰 대응합니다.** 외부 발송 서비스가 자체 도메인으로만 인증을 통과한다면 발송 담당자와 협의해 정렬된 DKIM 또는 서비스가 지원하는 정렬된 봉투 발신자 도메인을 설정합니다. 무단 사용 정황이 있으면 대표 메시지와 수신 결정을 보존해 메일 악용 대응팀과 협업하세요. 정책 변경 전후로 정상 발송 서비스와 배달 영향도 비교합니다. 보고서 한 건으로 도메인 전체의 정책 변경을 결정하기는 어렵습니다.

2026년 5월 RFC 9989는 RFC 7489를 대체하고 `pct`를 제거했습니다. 새 `t`는 테스트 여부이며 백분율을 표현하지 않습니다. RFC 9990은 XML 네임스페이스를 지정하고, `discovery_method`에 `psl` 또는 `treewalk`를 보고할 수 있게 합니다. 수신기 전환 기간에는 여러 형식이 섞일 수 있으므로 새 태그에 의존하기 전에 실제 보고서와 공급자 동작을 확인하세요. 예를 들어 Gmail의 공개 지침은 모니터링에 집계 보고서를 권장하며, 대량 발송 요건 중 DMARC 정책 항목은 `none`으로도 충족할 수 있다고 안내합니다. Gmail의 다른 인증 요건과 배달 요건은 별도로 적용됩니다.

## 5. 오프라인 실습 · 세고 검증하기

본인이 관리하는 디렉터리에서 Python 3.9 이상을 사용하세요. 내려받은 파일은 표시된 이름으로 저장합니다. 입력은 전부 가상 자료입니다. 스크립트는 UTF-8 XML만 읽으며 DNS나 SMTP에 요청을 보내지 않습니다. RFC 9990 네임스페이스와 네임스페이스가 없는 이전 형식 한 가지를 받아 이 장에서 쓰는 필드를 확인합니다. 전체 XML 스키마 검사와 수신 메일 출처 검증은 운영 수집기에서 별도로 해야 합니다.

- <a href="{{ '/assets/labs/dmarc-aggregate-report-evidence/review.py' | relative_url }}" download="review.py">review.py 다운로드</a>
- <a href="{{ '/assets/labs/dmarc-aggregate-report-evidence/daily.xml' | relative_url }}" download="daily.xml">daily.xml 다운로드</a>
- <a href="{{ '/assets/labs/dmarc-aggregate-report-evidence/legacy.xml' | relative_url }}" download="legacy.xml">legacy.xml 다운로드</a>

```sh
python3 review.py daily.xml daily.xml legacy.xml
```

`daily.xml`은 260건 중 정렬 통과 243건, 어느 방식도 정렬을 통과하지 못한 건 17건, 보고된 거부 5건을 보여 줍니다. 정렬 전 인증을 한 가지 이상 통과하고도 정렬 통과가 없는 행은 두 개입니다. 완전히 같은 보고서를 다시 입력해도 집계는 한 번만 출력됩니다. 별도의 이전 형식 보고서에는 정렬 통과 20건, 거부 0건이 표시됩니다.

실패 사례를 확인하려면 `daily.xml`을 `changed.xml`로 복사한 뒤 첫 행의 건수 `240`을 `241`로 바꾸세요. `python3 review.py daily.xml changed.xml`을 실행하면 충돌이 표시되고 종료 코드는 1입니다. 이어서 수정본의 보고서 ID도 바꾸면 기간이 겹친다고 표시합니다. 원본 실행부터 실패하면 파일이 예상한 네임스페이스의 일반 XML인지, 세 파일이 현재 디렉터리에 있는지 확인하세요.

클라우드 실행 환경에서 원본 자료, 중복 처리, 동일 ID의 내용 충돌, 기간 겹침을 검증했습니다. 공급자 동작은 공개 문서로 확인했습니다.

## 6. 확인 문제와 해설

1. **외부 발송 서비스의 SPF는 통과했는데 SPF 정렬은 실패했습니다. DMARC를 통과할 수 있을까요?** 검증된 DKIM 서명의 도메인이 From과 정렬되면 통과할 수 있습니다. 가상 자료의 240건이 이에 해당합니다.
2. **실패 12건의 처분이 `none`입니다. 12건 모두 받은편지함에 도착했나요?** 보고서에 적힌 것은 DMARC에 따른 처분이 없었다는 내용입니다. SMTP 수락과 배달 위치는 메시지 추적에서 확인하세요.
3. **낯선 IP에서 거부가 여러 건 나왔습니다. 메일을 최초로 보낸 서버나 사람인가요?** 보고 기관에 직접 접속한 서버의 IP입니다. 로그로 서버의 역할을 확인하고, 개별 메시지는 신뢰하는 헤더와 추적 자료를 사용해 조사하세요.

건수와 분모를 재현하고, 중복을 세면 어떤 수치가 달라지는지 설명해 보세요. 인증, 정렬, 정책 처리, 배달에 대해 각각 어디까지 확인할 수 있는지 적으면 완료입니다. `rua`는 여러 관측을 묶은 보고입니다. 선택 사항인 `ruf` 실패 보고는 개인정보 고려 사항이 다르고, 요청하더라도 받지 못할 수 있습니다.

- IETF [RFC 9989 §4.4 · 도메인 정렬](https://www.rfc-editor.org/rfc/rfc9989.html#section-4.4), [부록 A.6 · 백분율 기반 테스트의 변경](https://www.rfc-editor.org/rfc/rfc9989.html#appendix-A.6).
- IETF [RFC 9990 · 집계 보고서 필드, 식별자, 외부 목적지와 보안](https://www.rfc-editor.org/rfc/rfc9990.html), [RFC 9991 · 실패 보고](https://www.rfc-editor.org/rfc/rfc9991.html).
- IETF [RFC 7489 · 이전 DMARC 보고 형식](https://www.rfc-editor.org/rfc/rfc7489.html#appendix-C).
- Google [Gmail 발신자 지침 · 인증과 DMARC](https://support.google.com/mail/answer/81126).
