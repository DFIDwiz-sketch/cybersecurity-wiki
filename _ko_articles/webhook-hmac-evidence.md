**학습 목표.** 웹훅 수신기가 2xx를 반환했을 때 메시지가 검증됐는지, 전송을 받아들였는지, 업무 작업이 끝났는지 각각 어떤 증거로 확인할지 배웁니다.

## 1. 웹훅을 받을 때 확인할 것

**웹훅**은 외부 시스템에서 이벤트가 생겼을 때 발신자가 보내는 HTTP 요청입니다. **이벤트**는 발생한 일이고, **전송**은 그 일을 알리는 한 번의 시도입니다. **작업자(worker)**는 수신기가 응답한 뒤 대기열에 있는 작업을 처리할 수 있습니다. 2xx가 영속 수신만 뜻한다면 후속 작업은 아직 시작하지 않았을 수도 있습니다.

**메시지 인증 코드(MAC)**는 메시지와 공유 비밀로 계산한 태그입니다. **HMAC**은 암호학적 해시로 MAC을 구성하는 방식입니다. HMAC-SHA256은 프로토콜이 정한 정확한 바이트를 인증합니다. 태그가 맞으면 검증 대상 바이트가 그대로이며 비밀을 가진 쪽이 태그를 만들었다는 근거가 됩니다. 두 쪽 모두 계산할 수 있으므로 비밀 보유자 중 누구의 태그인지 제3자에게 독립적으로 증명하기는 어렵습니다. 태그는 본문을 암호화하지 않습니다. 전자서명과의 차이는 [공개키 암호학 기초]({{ '/ko/wiki/public-key-cryptography/' | relative_url }})에서 이어서 읽을 수 있습니다.

| 통제 | 답하는 질문 | 확인할 증거 |
| --- | --- | --- |
| HTTPS | 발신자가 암호화된 연결로 의도한 수신기에 접속했나요? | 필요한 경우 인증서 검증과 전송 기록 |
| HMAC | 검증 대상 바이트가 비밀 보유자가 만든 태그와 일치하나요? | 검증 결과, 엔드포인트 범위와 키 버전 |
| 신선도와 인가 | 인증된 전송 시각이 있다면 허용 범위에 드나요? 이 이벤트와 리소스를 처리해도 되나요? | 시간 정책과 시계 오차, 인증된 이벤트 범위 |
| 멱등 처리 | 이 이벤트나 업무 작업이 이미 반영됐나요? | 영속 수신 기록, 작업자 결과와 기준 시스템 상태 |

## 2. 정상 전송 한 건 따라가기

가상의 학습 서비스가 수업 완료 이벤트 `evt-a`를 보냅니다. 수신기는 본문에서 읽은 값을 신뢰하기 전에 원본 요청 바이트로 태그를 확인합니다. 공급자가 인증된 전송 시각을 제공한다면 시간 정책을 적용합니다. 유형과 리소스가 승인된 범위인지 확인한 뒤 재시작해도 남는 곳에 처리 대상을 기록합니다. 작업자가 수업 완료 상태를 반영해 결과를 남깁니다. 발신자가 수신 확인을 못 받아 다시 보내더라도 완료 작업을 한 번 더 반영할 필요는 없습니다.

JSON은 공백이나 이스케이프가 달라도 같은 값으로 읽힐 수 있습니다. 그러나 인증 대상 바이트는 서로 다릅니다. 미들웨어가 본문을 바꾸기 전에 공급자가 정한 입력으로 검증하세요. 공급자 라이브러리를 사용하거나, 정해진 형식으로 파싱한 같은 유형의 값을 Python의 `hmac.compare_digest` 같은 API로 비교하세요. 비밀은 승인된 비밀 저장소에 엔드포인트별로 보관하고 운영과 테스트 키를 구분합니다.

| 공급자 | 검증 | 전송 추적 정보 |
| --- | --- | --- |
| 비밀을 설정한 GitHub 웹훅 | `X-Hub-Signature-256`의 HMAC-SHA256으로 본문 검증. SHA-1 헤더는 레거시 | 요청한 재전송에서는 `X-GitHub-Delivery`가 유지됨. 본문 MAC이 임의의 요청 헤더까지 인증하거나 서명된 시각을 제공하지는 않음 |
| Stripe HTTPS 웹훅 | 원본 본문, `Stripe-Signature`, 엔드포인트 비밀을 공급자 라이브러리에 전달 | 인증된 시각을 사용하며 라이브러리 문서의 기본 허용 시간은 5분. 재시도마다 시각과 태그가 새로 생성되므로 이벤트 ID를 별도로 추적 |

## 3. 오래되거나 중복되거나 변경된 전송 구분하기

이전에 인증된 전송은 정상 재시도, 요청한 재전송, 혹은 이전 입력의 오용으로 다시 나타날 수 있습니다. 인증된 시각은 메시지의 허용 나이를 제한하지만 그 안의 중복까지 판별하지는 못합니다. 최근에 도착한 재시도도 오래된 이벤트를 설명할 수 있습니다. 공급자 이력과 수신기 시계를 함께 확인하세요.

**중복 판별**은 같은 입력을 찾는 것이고, **멱등성**은 반복해도 효과가 더 생기지 않는 성질입니다. 공급자 계약과 계정·환경·엔드포인트 범위에 맞는 키를 영속 저장소의 유일성 제약으로 관리하세요. 업무 판단에는 인증된 본문 필드를 적용합니다. 다른 이벤트가 같은 상태 변경을 요청한다면 업무 작업 식별자에도 멱등 처리가 필요합니다. 메모리 기록은 재시작 때 사라지고, 먼저 읽고 나중에 별도로 쓰면 작업자 두 명이 같은 이벤트를 처리할 수 있습니다. 수신 기록과 효과가 같은 DB에 있다면 한 트랜잭션으로 커밋할 수 있습니다. 외부 시스템에 영향을 주는 작업이라면 전달 상태를 영속적으로 기록하고, 상대 시스템의 멱등 처리나 결과 대조를 사용합니다. DB 한 곳의 커밋으로 외부 전달까지 한 번으로 보장할 수는 없습니다.

| 관측 | 원인을 판단하기 전에 확인할 자료 |
| --- | --- |
| 배포 직후 태그 실패 | 엔드포인트와 키 버전, 원본 바이트, 미들웨어 순서와 공급자 전송 진단 |
| 태그는 통과했지만 시각 거부 | 인증된 시각, 수신 UTC와 오차, 지연과 공급자 이력 |
| 이미 처리된 이벤트 | 공급자 재시도·재전송 이력과 동일 범위에서 이미 반영한 결과 |
| 2xx 뒤 업무 변경이 없음 | 수신 기록, 큐에 머문 시간, 작업자 재시도와 기준 시스템 상태 |

## 4. 증거를 수집하고 대응하기

1. 환경, 엔드포인트, ID와 UTC로 발신 이력과 수신 로그를 연결합니다. 어느 필드가 인증됐는지, 수신기 시계 오차는 얼마인지 확인하세요. 검증 결과, 실패 사유와 안전한 키 버전 식별자를 남깁니다. 공유 비밀, 태그 전체와 민감한 원본 본문은 일반 로그에 저장하지 않습니다.
2. 태그 오류·누락, 시각 거부, 미지원 유형, 영속 수신, 중복, 작업자 재시도와 커밋을 별도로 기록합니다. 배포 이후 오류가 지속적으로 늘거나 유효한 수신 대비 작업 완료가 줄어드는 등 기준선에서 벗어난 흐름을 탐지하세요.
3. 재전송을 요청하기 전에 영속 처리 기록 또는 애플리케이션 감사 로그를 확인합니다. 승인된 테스트 환경에서는 정상 전송과 같은 이벤트의 반복 전송을 비교해 최종 상태를 확인하세요. 키 노출이 의심되면 통합 담당자와 키 교체를 조율하고, 관련 수신 기록을 보존한 뒤 수용된 이벤트와 기준 시스템 상태를 대조합니다.

## 5. 오프라인 실습 · 판단과 반영 횟수 확인

<a href="{{ '/assets/labs/webhook-hmac-lab.py' | relative_url }}" download>Python HMAC 실습</a>을 내려받으세요. Python 3.8 이상과 SQLite 3.24 이상에 연결된 `sqlite3` 모듈이 있는 승인된 환경에서 `python3 webhook-hmac-lab.py`를 실행합니다. 생성한 테스트 키, 고정 시각, 메모리 DB를 사용합니다. 실습 자체 형식은 원본 본문과 시각을 인증하며, 과거 300초부터 미래 30초까지 허용합니다. 공급자 HTTP 헤더를 파싱하거나 외부 서비스에 접속하지 않습니다.

| 사례 | 기대 결과 |
| --- | --- |
| A | 정상 이벤트 한 건을 처리해 1회 반영 |
| B / C | 공백만 달라지거나 다른 테스트 키를 쓰면 태그 거부. 반영 횟수 1회 유지 |
| D / E | 올바른 태그여도 과거·미래 허용 범위를 벗어나면 시간 정책에서 거부. 1회 유지 |
| F / G | 최신 시각으로 다시 온 같은 이벤트는 중복. 인증된 다른 이벤트라도 유형이 허용되지 않으면 거부 |
| H / I | 실패를 넣으면 수신 기록과 효과가 모두 롤백돼 1회 유지. 재시도가 한 번 성공해 2회가 됨 |
| J | 태그가 없어 거부. 2회 유지 |

예상 결과를 적고 실행해 보세요. 마지막에 `10/10 webhook controls matched.`가 표시됩니다. `sqlite3`를 가져올 수 없다면 모듈이 있는 Python 설치를 확인하세요. B와 A가 같아 보인다면 파싱 결과가 아닌 바이트를 비교해 보세요. F는 시각과 태그가 바뀌어도 이벤트 ID가 같은 예입니다. H와 I는 로컬 DB의 롤백과 재시도를 보여 줍니다. 이 Python 실습은 클라우드에서 실행했습니다. 공급자 SDK, 실제 HTTP 전송, 동시 작업자 처리는 설계 설명에 포함했으며 실행 범위에는 들어가지 않습니다.

## 6. 확인 문제와 완료 기준

1. **태그가 맞으면 본문도 비밀인가요?** 태그는 대상 바이트를 인증합니다. 내용의 기밀성은 별도 수단으로 보호합니다.
2. **최신 전송이 과거 이벤트를 담을 수 있나요?** 정상 재시도에서도 가능합니다. 이벤트 ID와 이미 반영된 결과를 확인합니다.
3. **발신자가 200 응답을 봤다면 어디에서 업무 결과를 확인하나요?** 인증되고 범위가 맞는 작업 식별자로 작업자 또는 기준 시스템 기록을 대조합니다.
4. **키 버전을 왜 기록하나요?** 비밀을 공개하지 않고도 키 교체 때 설정 불일치를 찾을 수 있습니다.

**완료 기준.** 열 사례의 판정과 반영 횟수를 예측하세요. 어떤 통제가 중복 효과를 막는지 설명하고 실제 반영을 확인할 별도 자료 한 가지를 제시하면 됩니다. HTTP 상태의 의미는 [HTTP 요청과 응답 증거]({{ '/ko/wiki/http-evidence/' | relative_url }})에서 확인할 수 있습니다.
