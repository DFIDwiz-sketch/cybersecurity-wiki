배포 도구가 `app.conf`를 같은 이름의 새 파일로 교체했습니다. 파일 무결성 감시기는 변경을 보고한 뒤 조용해졌습니다. 이후에 변화가 없었던 걸까요, 아니면 기존 감시가 끝난 걸까요? Linux의 inotify는 감시에 들어온 이벤트를 보여 줍니다. 사고 조사에서는 감시 상태, 현재 파일시스템, 어떤 프로세스가 변경했는지 확인할 독립적인 기록도 함께 필요합니다.

## 1. 경로와 감시 대상은 달라질 수 있습니다

**경로명**은 프로그램이 파일시스템에서 객체를 찾을 때 사용하는 이름입니다. **디렉터리 항목**은 이름과 객체를 연결합니다. **inode**는 객체가 존재하는 동안 해당 파일시스템 안에서 그 객체를 식별합니다. 조사 기록에는 inode 번호와 장치 ID를 함께 남기고 관측 시각과 마운트 네임스페이스를 보존하세요. inode 번호는 재사용될 수 있고, 같은 번호도 파일시스템이 다르면 다른 객체일 수 있습니다.

**inotify 인스턴스**는 커널의 알림 큐와 그 큐에 연결된 감시 목록입니다. 프로그램은 인스턴스를 열고 비트 마스크로 각 감시가 받을 이벤트를 정한 뒤, 인스턴스의 파일 디스크립터에서 알림을 읽습니다. 커널은 감시마다 **감시 디스크립터**(`wd`)를 반환합니다. 이 값은 인스턴스 내부의 감시를 식별하는 번호입니다. 프로세스 ID나 알림을 읽는 파일 디스크립터와는 쓰임이 다릅니다.

| 범위 또는 필드 | 식별 대상 | 관측할 수 있는 것 |
| --- | --- | --- |
| `app.conf` 파일 감시 | 감시를 추가할 때 경로가 가리킨 inode | 해당 객체의 활동. 같은 객체의 다른 하드 링크를 통해 일어난 활동도 포함될 수 있습니다. |
| 상위 디렉터리 감시 | 디렉터리 객체와 마스크에 포함된 바로 아래 항목 | `app.conf`라는 이름으로 들어온 파일이나 해당 디렉터리 안의 이름을 통해 발생한 쓰기. 하위 디렉터리는 별도 감시가 필요합니다. |
| `name` | 감시 중인 디렉터리 항목에 대한 이벤트의 이름 | 상위 감시의 경로와 마운트 환경을 기준으로 해석합니다. 수집기가 읽기 전에 해당 항목이 이미 달라졌을 수 있습니다. |
| 이름 변경 `cookie` | 하나의 이름 변경에서 수집기가 관측할 수 있는 양쪽 알림이 공유하는 커널 값 | 같은 인스턴스의 짧은 시간 범위에서 `IN_MOVED_FROM`과 `IN_MOVED_TO`를 연결합니다. 감시 경계를 넘으면 한쪽만 기록될 수 있습니다. |

## 2. 정상 배포에서 inode가 바뀌는 과정

1. 서비스가 사용하는 `app.conf`의 inode는 A입니다. 배포 도구는 같은 디렉터리에 새 파일 `app.conf.next`를 만들고 내용을 쓴 뒤 닫습니다. 이 파일의 inode는 B입니다.
2. 배포 도구는 `rename`으로 기존 `app.conf`라는 이름이 B를 가리키게 합니다. 같은 파일시스템에서 대상 이름은 원자적으로 교체됩니다. 이후 해당 경로를 다시 열면 B를 찾게 됩니다. 이전부터 A를 열어 둔 프로세스는 A를 계속 사용할 수 있습니다.
3. 상위 디렉터리 감시는 `app.conf.next`가 나가고 `app.conf`로 들어오는 이벤트를 같은 쿠키 값으로 보고할 수 있습니다. 기존 객체가 제거되면 파일 감시에 `IN_DELETE_SELF`와 뒤이은 `IN_IGNORED`가 남을 수 있습니다. `IN_IGNORED`는 감시가 제거됐다는 뜻이며 명시적으로 해제하거나 파일시스템이 마운트 해제될 때도 발생합니다. 기존 객체가 언제 사라지는지는 그 객체를 참조하는 항목과 열린 파일의 상태에 따라 달라집니다.
4. 경로 항목에 대한 감시 외에 inode 자체의 감시가 계속 필요하다면, 현재 경로를 다시 조회해 대상을 확인하고 새로 등록합니다. 기존 감시 번호를 캐시에 보관해도 B에 대한 감시가 생기지는 않습니다.

기존 파일의 **내용을 제자리에서 수정**하면 inode가 유지되면서 `IN_MODIFY`나 `IN_CLOSE_WRITE`가 나타날 수 있습니다. 닫기 이벤트는 쓰기 가능한 파일 디스크립터가 닫혔음을 알려 줍니다. 실제로 내용이 달라졌는지는 현재 메타데이터와 승인된 기준 파일 또는 해시를 확인하세요. 파일이 교체돼도 내용은 같을 수 있으므로 객체의 식별 정보와 해시를 모두 비교합니다.

## 3. 알림이 끊겼을 때 수집하고 대응하기

| 관측 내용 | 이어서 할 일 | 확인할 수 있는 범위 |
| --- | --- | --- |
| 쿠키가 같은 이름 변경 두 건, 현재 경로는 B | 감시 범위, 배포 기록, 현재 메타데이터, 서명된 배포본이나 정상 해시를 비교 | 감시 범위 안의 이름 변경을 봤습니다. 정상 변경 여부는 배포와 무결성 증거를 함께 보고 판단합니다. |
| 이름 변경의 한쪽만 보이거나 읽을 때 경로가 사라짐 | 여러 번의 읽기에 걸쳐 짧은 시간 동안 짝을 찾습니다. 양쪽 상위 경로의 감시 범위와 현재 디렉터리 상태를 확인합니다. | 관측한 쪽은 기록할 수 있습니다. 반대쪽 이름이나 최종 객체는 확인이 필요합니다. |
| 있어야 할 감시에서 `IN_IGNORED` 발생 | 로그에서 제거 사유를 살피고 현재 경로와 마운트 환경을 확인한 뒤 필요한 감시를 재등록 | 해당 감시는 끝났습니다. 새 객체를 직접 보려면 필요한 감시를 등록해야 합니다. |
| `wd=-1`인 `IN_Q_OVERFLOW` | 해당 인스턴스 캐시를 불확실로 표시합니다. 짝을 기다리던 이름 변경을 그대로 연결하지 말고 감시를 복구한 뒤 범위를 다시 스캔합니다. | 해당 인스턴스의 이벤트가 유실됐습니다. 재스캔은 그 시점의 상태를 보여 주며 유실된 변경 순서는 미확정입니다. |

**수집 범위부터 확인하세요.** 센서와 부팅 식별자, 수집기가 관리하는 인스턴스 세대 ID, 요청한 경로와 마스크, 등록 성공 여부, 서비스의 마운트 네임스페이스와 수집 시각을 남깁니다. 감시의 등록·종료와 등록 실패도 기록하세요. 예를 들어 `ENOSPC`는 사용자별 감시 한도 또는 자원 할당 문제에서 나올 수 있습니다. 인스턴스의 큐 한도는 생성할 때 결정됩니다. 큐 유실과 중앙 로그 전송 실패를 구분할 수 있도록 수집기 상태와 전송 상태를 따로 관찰합니다.

**유실 후 관측을 복구하세요.** 마지막으로 신뢰할 수 있는 스냅샷과 첫 이상 신호를 보존합니다. 감시 번호와 경로의 매핑을 믿기 어렵다면 인스턴스를 다시 만들고 감시를 등록한 뒤 목록을 수집합니다. 설정 중 발생한 변경도 다시 대조하세요. 새로 발견한 하위 디렉터리는 감시를 추가했을 때 이미 파일이 들어 있을 수 있으므로 곧바로 내용을 스캔합니다. 경보에 불확실한 시간 범위를 표시하고 당시 해당 범위에서 수집 중이던 Linux Audit, 엔드포인트, 배포 로그와 비교합니다.

**예상 밖의 변경을 조사하세요.** 관측한 객체를 검증된 버전과 비교한 뒤 시각과 경로를 신뢰하는 프로세스·계정 기록과 대조합니다. 정상 업데이트와 인가되지 않은 변경에서 같은 이름 변경 패턴이 나올 수 있습니다. 배포 시간대 밖에서 바뀐 해시, 사라진 감시, 비슷한 시기에 여러 호스트에서 생긴 감시 공백을 조사하세요. 차단이나 복구 전에 관련 기록을 보존합니다. 알림에는 변경 프로세스의 PID나 사용자 이름이 들어 있지 않습니다.

다른 관측 한계도 있습니다. 큐에 연달아 쌓인 같은 이벤트가 합쳐질 수 있고, 네트워크 파일시스템의 원격 변경이 로컬 inotify에 들어오지 않을 수 있습니다. 일부 메모리 매핑 I/O는 보고되지 않으며, 감시 중인 디렉터리 위에 새 파일시스템을 마운트하면 별도 알림 없이 보이는 트리가 달라질 수 있습니다. 큐 초과 기록이 없어도 마운트 환경과 실제 파일 목록을 확인하세요.

## 4. 승인된 실습 · 테스트 파일 교체 감시

glibc와 Python 3.9 이상이 있는 Linux에서, 본인이 관리하는 로컬 파일시스템 디렉터리에서 실행하세요. 프로그램은 현재 디렉터리에 임시 하위 디렉터리를 만들어 자기 실습 파일만 쓰고, 끝나면 그 디렉터리를 제거합니다. 관리자 권한, 운영 파일, 네트워크는 사용하지 않습니다.

- <a href="{{ '/assets/labs/linux-inotify-watch-evidence/watch_replace.py' | relative_url }}" download="watch_replace.py">watch_replace.py 다운로드</a>

```sh
python3 watch_replace.py
```

세 가지 결과를 확인하세요. 상위 감시에 0이 아닌 같은 쿠키의 이름 변경 짝이 남고 장치·inode 조합이 바뀝니다. 기존 파일의 직접 감시가 끝난 뒤 새 파일에 쓰면 상위 감시에 기록됩니다. 새 객체를 다시 직접 감시한 후 한 번 더 쓰면 직접 감시에도 기록됩니다. 감시 번호, inode 번호, 쿠키의 실제 값은 실행마다 달라질 수 있습니다. 실습은 이벤트 관계를 확인하며 고정된 순서에 의존하지 않습니다. 감시 시작 전에 실패하면 현재 디렉터리 권한, 로컬 파일시스템, glibc, 컨테이너의 시스템 호출 제한을 확인하세요. 이벤트 검사가 실패하면 출력된 기록과 파일시스템 종류를 보존한 뒤 기대 결과와 비교합니다.

다음은 Linux 6.18.57(`x86_64`), glibc 2.41, Python 3.12.14의 클라우드 실행에서 나온 실제 출력 일부입니다.

```text
replacement wd=1 flags=IN_MOVED_FROM cookie=74 name=app.conf.next
replacement wd=1 flags=IN_MOVED_TO cookie=74 name=app.conf
replacement wd=2 flags=IN_IGNORED cookie=0 name=-
write-before-reattach wd=1 flags=IN_CLOSE_WRITE cookie=0 name=app.conf
write-after-reattach wd=3 flags=IN_CLOSE_WRITE cookie=0 name=-
```

**큐 초과 가상 사례.** 수집기가 `IN_MOVED_FROM cookie=42`, `IN_Q_OVERFLOW wd=-1`을 차례로 읽고 재스캔에서 `app.conf`가 inode B를 가리키는 것을 봤다고 가정합니다. 관측 공백과 재스캔에서 확인한 B를 기록하세요. 쿠키 42는 공백을 넘어 이어 붙이지 말고 미확정으로 두고, 이전 짝짓기 상태를 버립니다. 실제 전환은 독립적으로 보존한 배포 또는 감사 로그에서 조사합니다. 실습에서는 정상 교체와 감시 재등록을 실제로 실행했습니다. 큐 초과 사례는 가상이며 공식 인터페이스 문서와 대조했습니다.

## 5. 확인 문제와 해설

1. **배포 후 파일 자체에 대한 감시가 조용합니다. 그 경로에는 변경이 없었나요?** 알림이 없다는 사실만으로 판단하기 어렵습니다. 감시 제거 여부를 보고 장치·inode를 비교한 뒤 상위 디렉터리 이벤트를 대조하세요.
2. **쿠키가 같은 이름 변경 이벤트인데 감시 번호가 다릅니다. 두 기록을 연결할 수 있나요?** 같은 인스턴스와 짧은 시간 범위에서 서로 맞는 양쪽 이벤트라면 가능합니다. 디렉터리 사이의 이동은 다른 두 감시에 기록될 수 있습니다.
3. **큐가 넘친 다음 재스캔에서 파일 해시가 바뀌었습니다. 누가 썼는지 알 수 있나요?** 재스캔에는 현재 내용 상태가 남습니다. 변경 주체를 확인하려면 독립적인 프로세스 또는 감사 증거가 필요합니다.

**완료 기준.** 실습에서 세 결과를 재현하고 경로에 연결된 객체의 교체와 같은 객체에 대한 쓰기를 구분하세요. 가상 사례에서는 유실된 것, 재스캔으로 확인한 것, 프로세스 확인에 필요한 자료를 각각 적습니다.
