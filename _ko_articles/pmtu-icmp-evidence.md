**학습 목표.** 연결이 정상적으로 시작된 뒤 큰 패킷부터 멈출 수 있는 이유를 설명합니다. 패킷 크기, ICMP 응답, 수집 위치, TCP ACK를 대조해 실제 크기 제한과 관측 공백을 구분합니다.

## 1. 무엇의 크기가 너무 큰가요?

**링크 MTU**는 한 링크가 전달할 수 있는 IP 패킷의 최대 크기입니다. **경로 MTU(PMTU)**는 한 방향의 경로를 구성하는 링크 MTU 중 가장 작은 값입니다. 돌아오는 방향의 경로와 제한은 다를 수 있습니다. 이 크기에는 IP 헤더가 들어갑니다. 이더넷 헤더와 트레일러는 다른 기준으로 셉니다. **TCP MSS**는 TCP 끝점이 상대에게 알리는 세그먼트당 TCP 데이터 한도입니다. TCP·IP 헤더, 옵션과 터널 캡슐화에는 공간이 따로 필요합니다. 상대가 알린 MSS 자체는 앞 방향의 경로를 측정한 값이 아닙니다.

| 값 | 값의 출처 | 말해 주는 범위 |
| --- | --- | --- |
| 인터페이스 MTU | 인터페이스 하나의 설정 | 로컬 제한. 이후 라우터나 터널의 제한이 더 작을 수 있음 |
| 통보된 다음 홉 MTU | 전달 노드의 ICMP 오류 | 해당 링크의 제한이라고 보고된 값. 인용 패킷과 관측한 안쪽·바깥쪽 계층 확인 필요 |
| PMTU 추정값 | 송신 장비의 탐색·패킷화 동작 | 송신자가 경로를 통과할 수 있다고 보는 크기. 경로가 바뀌면 달라질 수 있음 |
| TCP MSS | SYN 또는 SYN-ACK 옵션 | MSS를 보낸 상대가 받을 수 있는 TCP 데이터 한도. 경로와 헤더 제한도 적용됨 |

IP 패킷 한도가 1,400바이트이고 헤더가 최소 크기라면, IPv4에서는 TCP 데이터를 최대 1,360바이트까지 실을 수 있습니다. IPv4 헤더 20바이트와 TCP 헤더 20바이트를 뺀 값입니다. 확장 헤더가 없는 일반 IPv6에서는 기본 헤더가 40바이트이므로 1,340바이트입니다. 옵션, 확장 헤더, 캡슐화에 따라 실제 한도는 달라집니다. 터널의 바깥쪽 MTU를 안쪽 패킷을 캡처한 값에 바로 대입하지 마세요.

## 2. 정상적인 크기 조정을 따라가세요

가상의 IPv6 흐름에서 송신자가 **1,500바이트 IP 패킷**을 보냅니다. 한 라우터의 다음 링크는 **1,400바이트**까지만 전달할 수 있습니다. 라우터는 큰 패킷을 버린 뒤 링크 MTU를 담은 ICMPv6 **Packet Too Big** 메시지를 돌려보냅니다. 메시지에는 오류를 유발한 원래 패킷의 일부가 인용돼 있습니다. 송신자가 그 통보를 받아 유효하다고 판단하면 더 작은 패킷을 보낼 수 있습니다. 이 예시에서는 더 작게 재전송한 TCP 바이트 범위에 ACK가 돌아옵니다. 시퀀스와 ACK 번호로 원래 전송과 재전송을 연결할 수 있습니다.

![병목 라우터가 1,500바이트 패킷에 대해 ICMP 크기 제한을 돌려보냅니다. 더 작은 재전송은 1,400바이트 링크를 통과합니다.]({{ '/assets/diagrams/pmtu-feedback-ko.svg' | relative_url }})

*화살표는 단순화한 IPv6 예시입니다. 오른쪽 위는 다음 링크의 한도입니다. 큰 패킷은 그 링크로 전달되기 전에 버려집니다. ICMP 도착과 작은 재전송의 성공은 별도로 확인합니다.*

| IP 버전 | 관련 ICMP 응답 | 단편화 동작 |
| --- | --- | --- |
| IPv4, 단편화 금지(DF) 설정 | ICMP Destination Unreachable 유형 3 코드 4. 오래된 구현은 다음 홉 MTU를 0으로 돌려줄 수 있음 | 전달 중인 라우터는 DF 패킷을 단편화할 수 없음 |
| IPv6 | ICMPv6 Packet Too Big 유형 2 코드 0. 표준 PMTUD에서는 IPv6 링크의 최소 MTU인 1,280바이트보다 작은 통보를 버림 | 송신자만 Fragment 헤더를 추가할 수 있음. 전달 라우터는 단편화하지 않음 |

고전적인 경로 MTU 탐색(PMTUD)은 ICMP 통보를 활용합니다. 전송 계층에서 패킷을 구성하는 쪽이 여러 크기를 시험하고 전달 여부로 판단하는 방식도 있습니다. RFC 8899는 데이터그램 전송에서의 방법을 설명합니다. 장비나 프로토콜에 따라 지원 방식이 다르므로, ICMP가 보이지 않아도 다른 방식으로 크기가 조정됐을 수 있습니다.

## 3. 경로 MTU 블랙홀은 언제 의심하나요?

큰 패킷이 통과하지 못하고 송신자에게 유효한 크기 통보도 도착하지 않으면 **PMTU 블랙홀**이 생길 수 있습니다. 작은 ping과 TCP 연결 설정은 통과하는데 큰 데이터 전송은 멈추는 식입니다. 혼잡, 필터, 수신 장비 문제, 수집 누락도 재전송을 일으키거나 그렇게 보이게 할 수 있습니다. 같은 흐름을 적절한 위치에서 비교할 때까지 크기 제한은 조사 가설로 남깁니다.

잘못된 ICMP 메시지가 다른 흐름을 인용하거나 맞지 않는 MTU를 알려 줄 수 있습니다. 거짓 통보로 전송을 방해하려는 경우도 있습니다. 인용된 원래 패킷의 주소와 관측 가능한 전송 계층 식별자, 확인할 수 있는 시퀀스 번호, 방향과 시각을 대조하세요. ICMP의 발신 주소 하나로는 신뢰하기 어렵습니다. NAT, 터널, 잘린 인용, 재사용된 포트 때문에 단순 대조가 어려울 수 있습니다. 의도를 판단하기 전에 신뢰할 수 있는 게이트웨이·호스트 기록과 함께 확인하세요.

## 4. 블루팀 수집·탐지·대응

**수집 지점을 기록하세요.** 시각, 인터페이스, 방향, 캡처 길이, 확인 가능한 수집 누락 카운터를 보존합니다. 승인된 환경에서 송신자 쪽과 병목 라우터의 관련 인터페이스, 수신자 쪽이 유용합니다. 원래 흐름과 오류를 연결할 만큼 인용 데이터는 확보하고, 캡처 내용의 접근 범위는 제한하세요. 지점마다 NAT의 어느 쪽인지, 터널 안쪽 또는 바깥쪽인지 표시합니다.

**같은 계층의 길이를 읽으세요.** Wireshark의 IPv4 Total Length는 IPv4 헤더를 포함합니다. 일반 IPv6 패킷은 Payload Length에 기본 헤더 40바이트를 더합니다. 점보그램은 별도로 해석합니다. IP 길이와 캡처의 프레임 길이를 구분하고, 호스트에서 세그먼트 분할을 네트워크 카드에 맡기는 오프로딩도 고려하세요. 이 경우 선로에 실제로 나간 것보다 큰 패킷이 호스트 캡처에 보일 수 있습니다. 승인된 선로 관측이나 수집 방식으로 확인한 뒤 경로 크기의 증거로 사용하세요.

**ICMP를 찾은 뒤 인용 패킷을 대조하세요.** 다음은 IPv4 또는 IPv6가 해석된 기존 승인 캡처에서 후보를 찾는 Wireshark 표시 필터입니다. `icmp.mtu` 또는 `icmpv6.mtu`를 보고 인용된 원래 패킷을 펼칩니다. 확인한 흐름이 일치해야 해당 통보가 장애와 관련 있는지 판단할 수 있습니다. 표시 필터는 수집되지 않은 패킷을 복구할 수 없습니다. 필드 이름은 Wireshark 4.6.10 레퍼런스로 검토했습니다.

~~~text
(icmp.type == 3 && icmp.code == 4) || (icmpv6.type == 2 && icmpv6.code == 0)
~~~

**ACK 진행을 확인한 뒤 정책을 살펴보세요.** 수신 측이 큰 패킷의 바이트 범위에 ACK를 보냈는지, 더 작게 재전송한 뒤 ACK가 앞으로 이동했는지 봅니다. 큰 재전송에서 반복해서 진행이 없고, 라우터 쪽에서는 일치하는 통보가 보이지만 송신자 쪽에서는 보이지 않는다면 통보 경로를 조사하세요. 두 수집이 같은 경로와 시간대를 관측했는지 확인한 뒤 방화벽 결정 기록, 정책, 터널 MTU, 네트워크 변경 이력을 대조합니다. 잘못된 설정이 확인되면 담당자와 필요한 범위만 조정하고 승인된 시험으로 변경 전후 패킷 크기와 ACK 진행을 비교하세요.

## 5. 오프라인 실습 · 가상 관측 8건

[pmtu-cases.csv]({{ '/assets/labs/pmtu-cases.csv' | relative_url }})와 [pmtu-review.py]({{ '/assets/labs/pmtu-review.py' | relative_url }})를 같은 폴더에 받으세요. 먼저 관측값을 직접 읽습니다. CSV는 가상의 캡처를 본 분석자가 단순화해 정리했다고 가정합니다. `matched_quote`는 인용 내용과 원래 흐름을 대조한 결과이고 `coverage=both`는 가상 송신자와 라우터 쪽을 모두 관측했다는 뜻입니다. `large_ack`는 이후 누적 TCP ACK에 큰 패킷이 담았던 바이트 범위가 포함됐다는 뜻입니다. 어느 패킷으로 그 바이트가 전달됐는지는 추가 확인이 필요합니다. 미확인 값은 그대로 두세요. 스크립트는 이 CSV만 읽습니다.

~~~bash
python3 pmtu-review.py
~~~

| 사례 | 예상 판단 |
| --- | --- |
| P01 / P02 | 일치하는 IPv4·IPv6 통보가 송신자에게 도착했고 작은 재전송에 ACK가 돌아옴 |
| P03 | 라우터 쪽 통보는 일치하지만 송신자 쪽에서 보이지 않음. 통보 경로의 공백 조사 |
| P04 | 송신자 쪽 관측만 있음. 통보가 없다는 이유로 드롭 위치를 확정할 수 없음 |
| P05 | 유형 3 코드 4가 보이지만 다른 흐름의 패킷을 인용함 |
| P06 | 큰 데이터의 바이트 범위가 ACK됨. 처음 세운 장애 가설 재검토 |
| P07 | IPv4 통보는 일치하지만 값 0은 다음 홉 MTU 미지정을 의미 |
| P08 | 일치하는 통보가 도착했으나 복구를 뒷받침하는 진행은 확인되지 않음 |

마지막에 `Reviewed: 8 synthetic cases`가 나옵니다. 파일을 열지 못하면 이름을 바꾸지 않고 같은 폴더에 있는지 확인하세요. 결과가 다르면 열 이름이 원본 그대로인지, 빈 항목을 0으로 바꾸지 않았는지 살펴보세요. 자가 소유 또는 승인된 환경에서 선택 실습을 한다면, 정상 전송의 기존 양쪽 캡처를 비교하고 ICMP가 있을 때 인용 패킷을 어떤 값으로 연결할지 기록하세요. Python 실습은 실행했고 Wireshark 필터와 프로토콜 동작은 문서로 검토했습니다. 실제 터널, ICMP 주입, 공급자 방화벽은 시험하지 않았습니다.

## 6. 확인 문제와 완료 기준

- **ping과 TCP 연결 설정이 되는데 파일 전송만 멈춥니다. PMTU 문제인가요?** 작은 패킷이 통과해도 큰 패킷에서 제한에 걸릴 수 있습니다. 크기와 증상의 관계, 일치하는 통보, ACK 진행, 수집 범위를 확인하세요.
- **라우터가 1,400바이트를 통보했는데 인용된 주소가 다릅니다. 같은 흐름에 적용할 수 있나요?** 우선 관측한 계층과 NAT 등 변환 여부를 확인합니다. 연결 근거가 없으면 별도의 통보로 남깁니다.
- **송신자 근처에서 일치하는 ICMP가 보입니다. 애플리케이션이 복구됐나요?** 호스트가 그 통보를 받아들였는지, 크기를 줄인 전송과 ACK, 애플리케이션 기록에 진행이 있는지 확인하세요.

P03, P04, P08의 차이를 설명하고 한 사례에 대해 수집 지점, 관측 계층과 크기, 인용 내용의 일치 여부나 관측 공백, ACK와 다음 확인 자료를 기록하면 실습을 완료한 것입니다.
