**학습 목표.** 게이트웨이는 다이제스트가 맞지 않는다고 보고하는데 양쪽에서 보는 JSON은 똑같습니다. 각 필드가 가리키는 정확한 바이트를 찾고, 실제 바이트 차이와 캡처·검증 범위의 오류를 구분해 봅니다.

## 1. 바이트가 어느 계층에 있는지 확인하기

HTTP **표현**(representation)은 리소스를 전달하기 위해 선택한 형태입니다. 예를 들어 특정 방식으로 압축한 JSON입니다. **표현 데이터**에는 `Content-Encoding`에 표시된 인코딩이 적용돼 있습니다. **메시지 콘텐츠**는 해당 요청이나 응답이 실제로 담은 바이트입니다. 선택한 표현 전체, 일부 또는 빈 콘텐츠일 수 있습니다. HTTP/1.1의 `chunked` 같은 **전송 코딩**은 콘텐츠를 전송하기 위한 틀을 붙입니다. **다이제스트**는 바이트열에서 계산한 고정 크기 값입니다.

| 필드 또는 계층 | 무엇을 설명하나요? | 읽는 법 |
| --- | --- | --- |
| `Content-Type` | `application/json` 같은 미디어 유형 | 콘텐츠 인코딩을 풀고 나서 어떤 형식으로 해석할지 알려 줍니다. |
| `Content-Encoding` | `gzip`처럼 표현에 적용한 인코딩 | 같은 전체 gzip 응답에서 두 다이제스트의 입력에 압축된 바이트가 쓰일 수 있습니다. |
| HTTP/1.1 `Transfer-Encoding: chunked` | 청크 크기, 구분자와 선택적 트레일러를 담는 전송 틀 | 해시를 계산하기 전에 전송 틀을 제거합니다. 관련 트레일러는 별도로 보존합니다. |
| `Content-Digest` | 이 HTTP 메시지에 담긴 콘텐츠 | 전송 코딩을 벗긴 뒤 콘텐츠 인코딩을 풀기 전의 정확한 바이트를 씁니다. |
| `Repr-Digest` | 선택한 표현의 전체 데이터 | 콘텐츠 인코딩까지 맞는 전체 표현이 필요합니다. |
| `ETag` | 서버가 표현에 부여하는 검증자 | 캐시·범위 요청에서 검증자 규칙에 따라 해석합니다. 값에 다이제스트가 들어 있다고 가정할 수 없습니다. |

RFC 9530은 다이제스트 필드를 구조화 필드 사전으로 정의합니다. 항목 하나는 `sha-256=:BASE64_BYTES:` 형태입니다. 예시 자리에는 다이제스트의 원시 바이트를 Base64로 인코딩한 값이 콜론 사이에 들어갑니다. 실제 환경에서는 애플리케이션 정책에 따라 알고리즘을 선택하고 규격에 맞는 사전 파서와 관련 원본 필드를 확보하세요. 이전의 `Digest`와 `Want-Digest`는 정의가 다릅니다. RFC 9530은 RFC 3230과 이전 필드를 대체합니다.

## 2. 정상 응답 세 가지 비교하기

가상의 보고 서버에 작은 JSON 리소스가 있습니다. 일반적인 전체 GET에서 클라이언트가 gzip을 수용하고 서버도 그 표현을 선택합니다. HTTP/1.1 서버는 gzip 바이트를 청크로 보냅니다. 클라이언트가 청크의 틀을 제거하면 메시지가 표현 전체를 담고 있으므로 두 다이제스트가 같은 gzip 바이트와 일치할 수 있습니다. 화면에 표시하려고 압축을 풀면 해시 입력이 달라집니다. 같은 JSON을 다시 압축해도 gzip 메타데이터나 구현 차이로 바이트가 바뀔 수 있습니다.

| 응답 | Content-Digest 입력 | Repr-Digest 입력 |
| --- | --- | --- |
| gzip JSON을 보내는 전체 `200` GET | 전송 코딩을 벗긴 전체 gzip 바이트 | 같은 전체 gzip 표현 |
| 콘텐츠 인코딩이 없는 단일 범위 `206` GET | 이번에 받은 범위의 바이트 | 그 범위를 선택할 때 기준이 된 인코딩 없는 전체 표현 |
| gzip 표현을 선택한 `200` HEAD | 필드를 보낸다면 빈 콘텐츠 | HEAD 본문에는 실리지 않은 전체 gzip 표현 |

범위 예시는 이해를 위해 콘텐츠 인코딩을 적용하지 않았습니다. 인코딩이 적용돼 있다면 RFC 9110에서 바이트 범위는 **인코딩된** 바이트열을 기준으로 정합니다. 멀티파트 응답은 단일 범위와 메시지 콘텐츠가 다릅니다. 미디어 유형의 경계는 콘텐츠에 포함되고 청크의 전송 틀은 그 바깥에 있습니다. HEAD의 `Content-Length`가 대응하는 GET의 길이를 표시할 수 있지만 HEAD 자체의 콘텐츠는 비어 있습니다. 헤더의 숫자만 보고 전송된 본문 바이트를 판단하지 마세요. 실습의 전체 GET과 HEAD는 같은 gzip 바이트열을 선택하므로 HEAD의 표현 다이제스트를 별도로 대조할 수 있습니다.

## 3. 불일치와 오용의 원인 좁히기

| 관측 | 가능한 설명 | 확인할 자료 |
| --- | --- | --- |
| 브라우저 도구에 넣었을 때만 다이제스트가 다름 | 도구가 압축을 풀거나 변환한 사본을 저장함 | 캡처·내보내기 계층, 원래 인코딩, 수신 콘텐츠 |
| 일부 응답을 받아 전체 해시와 비교했더니 실패함 | 범위, 멀티파트 또는 수집 중 잘린 응답 | 상태 코드, `Content-Range`, 콘텐츠 길이, 전송 틀과 수집 완전성 |
| 압축을 풀면 같은 문서인데 인코딩 상태의 해시가 다름 | 재압축, 다른 인코딩 표현 또는 메타데이터 차이 | 바이트 비교, 인코딩, 캐시 선택, 프록시 변환 기록 |
| 다이제스트가 있고 검증도 성공함 | 바이트가 제공된 값과 일치함 | 출처와 정책이 요구하는 메타데이터를 별도로 인증합니다. |
| 필드가 없거나 지원하지 않는 알고리즘을 사용함 | 서비스 간 규약, 중간 장비 동작, 트레일러 누락 또는 수집 한계 | 적용 정책, 원본 헤더와 트레일러, 도구와 실제 경로 |

일반 다이제스트만으로 송신자를 확인할 수 없습니다. 신뢰하지 않는 주체가 콘텐츠와 기대 다이제스트를 둘 다 바꿀 수 있다면 서로 일치하는 응답이 만들어질 수 있습니다. 인증된 전송은 그 신뢰 범위 안에서 보호합니다. 출처에 대해 더 강한 근거가 필요하면 적용 정책에 따라 신뢰하는 서명이나 서명된 릴리스 매니페스트를 검증하세요. RFC 9421의 메시지 서명은 다이제스트 필드와 필요한 메타데이터를 서명 범위에 포함할 수 있습니다. 서명 키와 필수 서명 범위를 확인한 뒤 실제 바이트가 그 다이제스트와도 일치하는지 검증합니다.

## 4. 블루팀의 수집과 대응

1. **관측 지점을 기록합니다.** UTC, 확보 가능한 요청·추적 ID, HTTP 버전, 방향, 원본 서버·프록시·캐시 중 어느 지점인지, 승인된 TLS 종료 이후 바이트인지 남기세요. 암호화된 수동 캡처에서는 콘텐츠를 얻기 어려울 수 있습니다. 클라이언트가 전송 틀을 자동으로 벗겼는지, 콘텐츠 인코딩까지 풀었는지 확인합니다.
2. **바이트 범위와 메타데이터를 보존합니다.** 관측한 정확한 바이트, 관련 원본 헤더·트레일러, 메서드, 상태, `Content-Encoding`, `Content-Type`, 길이, 범위, 해당하는 `Vary`와 완전성 여부를 남깁니다. 전체 표현의 바이트를 실제로 확보했는지도 표시하세요. 캡처 해시를 보존하고 민감한 콘텐츠와 인증 정보를 보호합니다.
3. **필드에 맞는 입력을 검증합니다.** `Content-Digest`는 올바른 계층에서 받은 완전한 메시지 콘텐츠를 해시합니다. `Repr-Digest`는 정확히 선택된 표현을 확인한 뒤 인코딩된 전체 바이트를 검증합니다. 자료가 없거나 변환됐다면 미검증으로 남기세요. 범위만 대조한 결과로 전체 표현의 불일치를 판단하지 않습니다.
4. **반복되는 실패를 조사합니다.** 같은 경로의 정상 대조, 일부만 있거나 읽을 수 없는 캡처, 다른 표현, 실제 바이트 차이를 비교하세요. 발생 지점, 엔드포인트, 인코딩, 응답 유형별로 불일치를 나눠 봅니다. 변조로 판단하기 전에 프록시 변환이나 트레일러 수집이 달라졌는지 확인합니다. 무결성이나 서명 정책이 실제로 실패하면 승인된 거부·사고 대응 절차를 따라 원본 서버 또는 릴리스 기록을 대조합니다.

## 5. 승인된 루프백 실습

본인이 관리하는 디렉터리에 <a href="{{ '/assets/labs/http-digest-evidence.py' | relative_url }}" download>Python 3 루프백 실습</a>을 내려받으세요. `127.0.0.1`의 임시 포트를 열 수 있는 승인된 환경에서 실행합니다. 프로그램이 자체 HTTP/1.1 서버를 열고 닫습니다. 그 서버에 정해진 요청만 보내고 작은 가상 보고서만 처리합니다.

```sh
python3 http-digest-evidence.py
python3 http-digest-evidence.py --negative-control
```

| 항목 | 재현할 결과 |
| --- | --- |
| A–D | 전체 응답의 두 다이제스트는 인코딩된 gzip과 맞습니다. 압축을 푼 JSON과 청크 틀을 포함한 바이트에서 예상대로 불일치합니다. |
| E–G | 범위 다이제스트가 일치합니다. 그 범위만으로는 전체 표현을 검증할 수 없으며 정확한 전체 바이트를 주면 일치합니다. |
| H–I | HEAD의 콘텐츠는 비어 있습니다. HEAD 바깥에서 확보한 같은 전체 gzip 표현으로 표현 다이제스트를 검증합니다. |
| J–L | 동일 입력을 다른 gzip으로 인코딩하면 바이트가 달라집니다. 필드가 없으면 판정할 수 없고 길이가 잘못된 다이제스트는 도구가 거부합니다. |

일반 실행은 `12/12 HTTP digest checks matched.`를 출력합니다. 음성 대조는 A에 사용할 수신 바이트 하나를 메모리에서 바꿉니다. `A: mismatch`, 총 11개 기대 결과 일치, 종료 코드 1을 확인하세요. 루프백 포트를 열거나 연결할 수 없으면 승인된 환경의 로컬 통신 정책을 확인하세요. 일반 실행에서 불일치가 생기면 스크립트 버전과 전체 출력을 확인합니다.

클라우드에서 로컬 HTTP/1.1 GET, 범위, HEAD 응답과 gzip, SHA-256 및 바이트 변경 대조를 실제 실행했습니다. 파서는 실습용 SHA-256 항목 하나만 처리합니다. HTTP/2·3, 전체 구조화 필드 파싱, 트레일러 보존, 외부 프록시와 서명 검증은 실행 범위 밖이며 관련 RFC 동작은 별도로 검토했습니다.

## 6. 확인 문제와 해설

1. **청크로 전달한 gzip의 Content-Digest에는 무엇이 들어가나요?** 청크 틀을 제거하고 압축을 풀기 전 gzip 바이트를 해시합니다.
2. **206의 Content-Digest가 일치하면 전체 파일도 검증됐나요?** 이번 메시지에 담긴 범위 바이트가 일치한 것입니다. 전체 표현은 Repr-Digest로 별도 확인합니다.
3. **HEAD가 Repr-Digest를 보낼 수 있는 이유는 무엇인가요?** 선택된 표현을 본문으로 보내지 않아도 그 표현을 설명할 수 있습니다. 검증에는 별도로 확보한 정확한 전체 바이트가 필요합니다.
4. **다이제스트가 일치하면 게시자가 인증되나요?** 신뢰의 근거를 확인하고 적용되는 서명이나 인증된 전송을 별도로 검증합니다.

**완료 기준.** C·D·F·H·J를 설명하고 두 명령의 결과를 재현하세요. 실제 불일치에서 기록할 바이트 계층, HTTP 상태와 수집 지점을 제시합니다.
