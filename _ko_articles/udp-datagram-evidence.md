클라이언트는 메시지를 보냈다고 하고, 캡처에는 UDP 패킷이 있으며, 수신 앱은 메시지가 잘려 들어왔다고 합니다. 세 기록이 모두 맞을 수 있습니다. 송신 호출부터 실제 수신까지 따라가며 각 지점에서 무엇을 입증할 수 있는지 알아봅니다.

## 1. 데이터그램을 계층에 맞게 읽기

**UDP(User Datagram Protocol)**는 IP 위에서 메시지를 개별 단위로 전달합니다. **데이터그램** 한 건에는 UDP 헤더와 페이로드가 있습니다. 헤더에는 출발지·목적지 포트, 길이, 체크섬이 들어 있습니다. **포트**는 호스트의 전송 계층에서 통신 종단을 구분하는 번호입니다. 일반적인 UDP 길이는 8바이트 헤더와 페이로드의 합입니다. 길이가 28이면 페이로드는 20바이트입니다. 체크섬은 일부 전송 오류를 탐지할 수 있지만 발신자를 암호학적으로 인증하지는 않습니다.

UDP 자체는 연결을 맺기 위한 핸드셰이크를 수행하지 않으며 전달, 순서, 중복 제거를 보장하지 않습니다. 애플리케이션이 메시지 경계를 유지하거나 필요한 전송 기능을 직접 구현하려 할 때 사용할 수 있습니다. 예를 들어 일반 DNS 질의와 응답은 UDP로 오갈 수 있고, QUIC은 UDP 위에 자체 수신 확인 및 손실 복구를 구현합니다. UDP 소켓에서 `connect()`를 호출하면 기본 상대를 지정할 수 있으며, 이 호출로 UDP 핸드셰이크를 보내지는 않습니다.

| 증거 | 무엇을 보여 주나요? | 다음에 확인할 자료 |
| --- | --- | --- |
| `sendto()` 성공 | 로컬 송신 호출이 바이트를 받음 | 패킷 캡처나 수신 증거 |
| 센서에서 UDP 관측 | 해당 지점에서 패킷이 보였음 | 수집 범위와 방향, 다른 구간 |
| 대응 관계를 확인한 ICMP 오류 | 인용된 데이터그램에 대해 네트워크 또는 종단이 오류를 알림 | 원래 주소·포트, 유형·코드, NAT와 경로 |
| Linux 수신의 `MSG_TRUNC` | 소켓까지 도착했으나 해당 호출에 넘긴 버퍼가 작았음 | 원래 길이, 앱 버퍼와 파서 동작 |
| 애플리케이션 수신과 결과 | 앱이 기록한 메시지 및 처리 결과 | 신뢰할 수 있는 요청 식별자와 성공의 의미 |

## 2. 정상 요청과 다른 가능성 따라가기

가상 클라이언트 `192.0.2.10:53000`이 `192.0.2.20:9000`에 20바이트 메시지를 보내고 앱 요청 ID `A17`을 붙였다고 가정합니다. 송신 쪽 캡처에는 UDP 길이 28이 보입니다. 수신 앱은 `A17`을 기록하고 작업을 대기열에 넣은 뒤, 이 앱에서 정의한 수신 확인 메시지를 보냅니다. 작업 완료는 해당 응답과 작업 로그를 대조해 판단합니다. 일반 UDP 흐름 로그로 앱 처리 결과까지 알 수는 없습니다. 이 주소와 기록은 가상이며 실제로 실행하는 실습은 루프백만 사용합니다.

수신 호출에 8바이트 버퍼를 넘기면 Linux는 앞의 8바이트만 돌려주고 `MSG_TRUNC`를 설정할 수 있습니다. 그 호출에서 데이터그램의 나머지는 버려집니다. 다음 호출은 대기열에 있는 다음 데이터그램을 읽습니다. 반면 캡처의 최대 저장 길이 때문에 패킷이 잘리는 것은 별도의 관측 문제입니다. 저장된 길이와 원래 프레임 길이를 비교하세요. DNS의 `TC` 비트는 프로토콜 수준의 잘림 신호이며 앱에 넘긴 버퍼가 부족했다는 표시가 아닙니다.

목적지나 중간 장비가 ICMP 오류를 돌려줄 수 있습니다. 예를 들어 IPv4 Destination Unreachable 코드 3은 일반적으로 UDP 포트에 도달할 수 없음을 알립니다. 오류가 인용한 원래 패킷을 요청과 대조한 뒤 판단하세요. 방화벽이나 전송률 제한 때문에 오류 응답이 보이지 않을 수도 있습니다. 데이터그램 손실, 대기 중인 소켓 부재, 수신 대기열 압박, 앱의 무응답도 시간 초과로 보일 수 있습니다. 응답이 없다는 사실만으로 포트 상태를 확정할 수 없습니다.

## 3. 방어 관점으로 수집하고 조사하기

1. **요청을 특정합니다.** UTC 시각, 방향, 전송 프로토콜, 주소와 포트, 센서 위치, 인터페이스나 네임스페이스, 확보 가능한 앱 식별자를 기록합니다. 송신과 수신 관점을 비교하고 NAT를 확인하세요. 5튜플만으로 연결하면 재사용된 주소와 포트 때문에 관계없는 트래픽이 섞일 수 있습니다.
2. **캡처와 호스트의 한계를 확인합니다.** 캡처에 저장된 길이, 최대 저장 길이, 캡처 드롭 카운터를 보존합니다. 헤더와 길이를 해석할 때 관측 위치, 하드웨어 오프로딩, 단편화를 고려하세요. Linux 수신 앱이 기록한 길이와 플래그를 대기열 또는 드롭 자료와 비교합니다. 호출 하나에 넘긴 버퍼 크기와 소켓 수신 대기열 용량은 서로 다릅니다.
3. **정상과 의심스러운 활동을 대조합니다.** 받은 요청보다 훨씬 큰 응답을 보내는 서비스는 출발지가 위조된 요청을 통해 반사 공격에 악용될 수 있습니다. 서비스 노출 범위, 정상 요청·응답 크기, 방향, 앱 기록을 대조하세요. 전송량이나 포트 하나만으로 공격을 확정할 수 없습니다. 정상적인 대용량 응답, 제품 변경, 수집 공백도 비슷하게 보입니다.
4. **확인된 실패 지점에 대응합니다.** 패킷과 앱 증거를 보존합니다. 전달이 실패했다면 예상한 소켓 바인딩, 방화벽, 서비스 상태를 확인하세요. 수신 플래그가 잘림을 보여 주면 담당자와 버퍼 및 메시지 크기 처리를 검토합니다. 반사가 의심되면 노출 범위나 전송률을 바꾸기 전에 네트워크 담당자와 영향 범위를 확인하세요. 정상 요청을 다시 시험하고 수신 지점에서도 결과를 확인합니다.

## 4. Linux 루프백에서 검증하기

승인된 Linux 학습 환경에서 Python 3.8 이상으로 <a href="{{ '/assets/labs/udp-datagram-evidence.py' | relative_url }}" download="udp-datagram-evidence.py">루프백 실습 스크립트</a>를 실행하세요. 두 소켓은 `127.0.0.1`에만 바인딩하고 운영체제가 배정한 임시 포트를 씁니다. 외부 대상, 캡처 권한, 외부 패키지가 필요 없습니다. 별도의 해석 실습에는 <a href="{{ '/assets/labs/udp-datagram-worksheet.csv' | relative_url }}" download="udp-datagram-worksheet.csv">가상 증거 워크시트</a>를 사용합니다.

```bash
python3 udp-datagram-evidence.py
```

| 출력 | 확인할 결과 |
| --- | --- |
| `separate_datagrams: 3, 4 bytes` | 두 데이터그램의 경계가 각각 유지됨 |
| `truncation: sent=12 copied=5 flag=True` | 12바이트를 보냈고 수신 프로그램에는 5바이트만 전달됨 |
| `next_datagram: OK` | 앞서 버려진 부분이 두 번째 메시지로 나타나지 않음 |
| `empty_datagram: 0 bytes` | 길이가 0인 데이터그램도 받은 메시지 한 건임 |

바인딩에 실패하면 루프백 사용 가능 여부와 로컬 UDP를 허용하는 환경인지 확인하세요. `recvmsg()`나 `MSG_TRUNC`를 쓸 수 없다면 해당 기능을 제공하는 Linux 학습 호스트에서 실행합니다. 수신이 시간 초과되면 실습 실패입니다. Linux 6.18.57과 Python 3.12.14에서 IPv4 루프백의 네 결과를 모두 관측했습니다. 워크시트는 가상이며 캡처, 증거 누락, 원래 패킷을 인용한 오류 한 건을 다룹니다. 먼저 관측 열을 읽고 해석 열에서 답을 확인하세요. 외부 경로, 방화벽, 애플리케이션 프로토콜은 실행 범위에 포함하지 않았습니다.

## 5. 확인 문제와 완료 기준

1. **UDP 길이 28은 앱 페이로드 크기인가요?** 8바이트 헤더를 빼면 이 예에서 20바이트가 남습니다.
2. **센서 하나로 수신 프로그램이 데이터를 읽었는지 알 수 있나요?** 센서는 그 위치에서 패킷을 관측했다는 증거입니다. 프로그램 전달과 처리는 수신 쪽 자료와 앱 로그로 확인합니다.
3. **시간 초과면 서비스가 대기 중이 아니었다는 뜻인가요?** 여러 이유가 같은 관측으로 나타납니다. 송신, 경로, 수신, ICMP 맥락을 함께 확인하세요.
4. **5바이트로 잘린 수신과 길이 0인 데이터그램을 어떻게 구분하나요?** Linux는 버퍼가 작아 잘린 경우 `MSG_TRUNC`를 돌려줄 수 있습니다. 길이 0인 데이터그램은 그 플래그 없이 수신할 수 있습니다. 두 경우 모두 스트림 종료를 뜻하지 않습니다.

루프백의 네 관측을 설명하고 송신, 센서, 수신 소켓, 앱 사이에서 어떤 증거가 비어 있는지 구분할 수 있으면 완료입니다.
