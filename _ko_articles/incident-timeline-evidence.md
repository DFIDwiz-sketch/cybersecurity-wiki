**학습 목표.** 방화벽, 프록시, 호스트 기록에서 각각 무슨 시각을 보고 있는지 파악합니다. 원본을 보존한 채 UTC로 환산하고, 측정한 시계 오차를 적용한 뒤, 먼저 일어난 사건과 순서가 불확실한 사건을 구분합니다.

## 1. 타임라인은 날짜순 정렬 이상의 작업입니다

가령 방화벽의 허용 로그가 00:00:05이고 프록시 요청이 00:00:10일 때, 호스트의 00:00:17이라는 기록이 마지막일까요? 호스트 시계가 실제보다 8초 빠르다면 보정 중심값은 00:00:09입니다. 장비가 기록한 시각과 조사 시스템에 도착한 시각도 서로 다를 수 있습니다. 이 차이를 무시하면 결과가 원인보다 먼저 발생한 것처럼 보이거나 다른 세션을 같은 사건으로 연결하게 됩니다.

| 시각 | 뜻 | 확인할 자료 |
| --- | --- | --- |
| 원본 이벤트 시각 | 소스가 이벤트에 적은 시각 | 시간대, 형식, 시계 상태, 시각이 나타내는 단계 |
| 로그 생성·수신 시각 | 기록을 저장하거나 수집기가 받은 시각 | 버퍼링, 연결 복구, 전송 지연 |
| 색인 시각 | SIEM이 이벤트를 색인한 시각 | 처리·색인 지연, 재전송 |
| 보정 추정 시각 | 시계 차이를 반영한 비교용 값 | 측정 시점, 보정 근거, 불확실성 |

예를 들어 Zeek conn.log의 ts는 해당 연결에서 처음 관측한 패킷의 시각을 나타냅니다. 연결 요약이 수집기에 도착할 때는 그보다 늦을 수 있습니다. 프록시 로그의 시간도 설정에 따라 요청 시작이나 종료에 가까울 수 있으므로 필드 정의를 보세요.

## 2. UTC 변환과 장비 시계 보정은 다릅니다

**UTC**는 여러 장비의 기록을 같은 기준으로 표시하는 시간 기준입니다. RFC 3339 형식에서 끝의 Z는 UTC이고, +09:30은 UTC보다 9시간 30분 빠른 표시입니다. 가상 기록 **09:30:05+09:30**은 **00:00:05Z**로 바뀝니다. Unix epoch 숫자는 제품과 필드에 따라 초·밀리초·마이크로초일 수 있습니다. 단위를 먼저 확인하세요. 시간대가 없는 문자열에 조사자 PC의 시간대를 자동으로 붙이지 않습니다. 현장에서 확보한 시간대 설정을 확인합니다.

장비 시계가 기준보다 8초 빠르다는 별도 측정이 있으면 UTC로 변환한 기록에서 8초를 뺍니다. “빠름”을 양수로 정의했기 때문입니다. 보정 기준이 재부팅이나 동기화 변경 전후에도 유효한지 확인하세요. 보정 시점과 달라질 가능성이 크면 범위를 넓히거나 비교 불가로 남깁니다.

![호스트와 프록시의 시간 구간이 겹쳐 순서 미확정]({{ '/assets/diagrams/timeline-uncertainty-ko.svg' | relative_url }})

그림에서 방화벽은 **00:00:04–06**, 호스트는 **00:00:07–11**, 프록시는 **00:00:09–11**의 가능 구간입니다. 끝과 시작이 떨어진 방화벽·호스트의 순서는 이 가정 아래 정할 수 있습니다. 호스트·프록시 구간은 겹치므로 중심값이 09초와 10초여도 먼저 일어난 쪽은 판단할 수 없습니다. 시간 순서가 확정돼도 인과관계에는 별도의 증거가 필요합니다.

## 3. 실제 자료에서 먼저 적어 둘 항목

1. 원본 이벤트, 이벤트 ID, 호스트·센서·수집원과 원래 시간 문자열을 보존하세요. 정규화·보정은 파생 필드로 남깁니다.
2. 장비의 시간대, 시계 동기화 상태, 캡처 위치와 UTC 범위를 적습니다. 추정한 오차에는 관측 방법과 유효 기간을 남깁니다. 한 기준 장비의 오류가 여러 기록에 공통으로 전파될 수도 있습니다.
3. 같은 사건을 두 수집 경로에서 받은 경우 식별자와 내용, 생산자와 호스트 범위를 맞춥니다. ID가 다르거나 내용이 충돌하면 원본을 모두 보존합니다. 같은 초의 두 이벤트를 곧바로 중복으로 취급하지 않습니다.
4. SIEM 입력 설정이 어떤 값을 이벤트 시각으로 지정했는지 확인합니다. 필드가 없는 원본, 마이크로초 단위 누락, UTC 변환 오류, 재전송·보존 범위를 확인하세요.

Splunk의 **_time**은 시스템이 이벤트 시각으로 지정한 값이고 **_indextime**은 색인 시간입니다. 둘의 차이에는 전달 지연뿐 아니라 소스 시계와 파싱 오류도 섞일 수 있습니다. 예를 들어 정상 테스트의 원본 시각을 알고 있다면 검색 화면에서 두 값을 원본과 비교하세요. 운영 입수 경로의 시간 변환은 제품 문서와 실제 수집으로 확인합니다. systemd 저널의 **__REALTIME_TIMESTAMP**는 저널이 기록을 수신한 벽시계이고, **_SOURCE_REALTIME_TIMESTAMP**는 알려진 경우 소스 시각의 단서입니다. **__MONOTONIC_TIMESTAMP**는 부팅 범위를 함께 봐야 합니다.

## 4. 정상 지연과 조사해야 할 현상

| 관측 | 정상 가능성 | 다음 확인 |
| --- | --- | --- |
| 3분 전에 발생한 로그가 한꺼번에 도착 | 수집기 버퍼 재전송 | _time·색인 시각·수집기 상태·다른 소스 |
| 호스트만 갑자기 시각이 뒤로 감 | 재부팅, 동기화 또는 설정 변경 | 부팅 ID, 시간 서비스 기록, 변경 승인 |
| 경보 이후 한 소스가 비어 있음 | 보존 만료, 수집 오류, 보낸 경로 변경 | 원본과 중앙 기록, 로그 상태·감사 정책 |
| 같은 IP에서 연속 사건 관측 | 공유 NAT 또는 정상 배치 | NAT 매핑, 세션 식별자, 동일 호스트·프로세스 |

사고 중 기록이 지연되거나 빠진 구간은 조사 우선순위를 높일 수 있습니다. 변경 이력과 독립 센서를 먼저 대조하세요. 근거가 생기면 조직 절차로 증거를 보존하고 영향 자산을 좁힙니다. 시계를 변경해야 한다면 조치 전후 시간을 기록해 이후 조사에서 혼동을 줄이세요.

## 5. 오프라인 실습 · 가상 로그 8행

[time-correlation.json]({{ '/assets/labs/time-correlation.json' | relative_url }}) · [time-correlation.py]({{ '/assets/labs/time-correlation.py' | relative_url }})

두 파일을 같은 폴더에 두고 Python 3으로 실행하세요. 가상 JSON의 raw에는 RFC 3339 형식, Unix 초와 시간대 없는 문자열이 섞여 있습니다. clock_ahead_s와 uncertainty_s에는 별도 교정에서 얻었다고 가정한 값을 넣었습니다. 같은 source·host·id라도 이 실습에서 정한 내용 비교를 통과해야 중복으로 셉니다. 운영 로그에서는 안정적인 식별자의 범위와 재사용 가능성을 점검하세요.

~~~bash
python3 time-correlation.py
~~~

| 기록 | 확인할 결과 |
| --- | --- |
| f-01 / n-01 | 각각 오프셋 문자열과 Unix 초에서 00:00:05 UTC 산출 |
| h-01 | 원래 00:00:17에서 8초를 빼 00:00:09, 가능 구간 07–11초 |
| p-01 | 한 건이 중복 수집됐고 h-01과 시간 구간이 겹침 |
| h-02 | 보정 후 00:00:27, p-01보다 뒤라고 판단 가능 |
| u-01 / h-03 | 각각 시간대와 시계 보정치가 없어 순서 비교 대상에서 제외 |

마지막에 `PASS: 8 records, 1 duplicate, 2 unplaced, 3 ordering checks`가 출력돼야 합니다. 파일 오류가 있으면 두 이름과 저장 폴더를 확인하세요. 순서가 다르면 UTC 단위, 오프셋의 방향과 구간이 겹치는지 확인하세요. 이 분석기는 가상 자료만 비교합니다. 실제 Zeek·Splunk·저널의 수집 동작은 운영 버전과 구성에서 시험해야 합니다.

자가 소유·승인 환경에서는 정해진 테스트 서버에 정상 요청 한 건을 보내고 네트워크, 서비스, 수집기에서 해당 요청의 시간과 식별자를 비교할 수 있습니다. 예정한 시간에 한 건만 실행하고 시각과 응답을 기록하면 정렬 근거를 남길 수 있습니다.

## 6. 확인 문제와 완료 기준

- **색인된 시간이 늦으면 이벤트도 나중에 일어났나요?** 원본 이벤트 시각과 색인 시각을 각각 기록합니다. 소스 시계와 파싱, 수집 지연을 먼저 검토하세요.
- **호스트 09초, 프록시 10초면 호스트가 먼저인가요?** 불확실성 구간이 겹칩니다. 순서는 미확정입니다.
- **두 관측의 순서가 정해지면 같은 사건인가요?** 관련 요청 ID, NAT 매핑, 세션 또는 프로세스 계보를 추가로 확인합니다.

원본과 정규화 값, 보정 근거, 가능 구간을 두 기록에 적으세요. 확정 가능한 순서 한 개와 미확정 순서 한 개를 설명하면 실습을 완료한 것입니다.
