**학습 목표.** 관리하는 도메인의 인증서가 공개 로그에 나타났다는 알림을 받았다고 가정해 봅시다. 로그에 올라온 자료가 무엇인지, 예정된 발급이었는지, 실제 서비스가 그 인증서를 제시했는지 확인할 증거를 찾습니다.

## 1. 공개 인증서 발급을 관찰하는 이유

**인증서 투명성**(Certificate Transparency, CT)은 공개 TLS 인증서의 발급 흔적을 확인할 수 있게 합니다. 인증 기관(CA)은 공개 로그에 인증서나 **사전 인증서**(precertificate)를 제출할 수 있습니다. 사전 인증서는 로그 등록을 위한 발급 과정의 산출물입니다. 흔히 쓰이는 CT v1의 내장 SCT 흐름에서 사전 인증서는 일반 TLS 인증서 검증에 사용할 수 없습니다. CA는 로그가 돌려준 **서명된 인증서 타임스탬프**(SCT)를 최종 인증서에 넣을 수 있습니다. SCT는 로그가 **최대 병합 지연**(Maximum Merge Delay, MMD) 안에 해당 항목을 포함하겠다는 서명된 약속입니다.

로그는 항목의 해시를 **머클 트리**로 묶습니다. 루트 해시는 특정 항목 수에서 내용과 순서를 대표합니다. **서명된 트리 헤드**(STH)는 로그의 키로 서명한 스냅샷입니다. **모니터**는 로그를 읽어 관심 있는 이름이나 변경을 찾습니다. 모니터의 검색 색인이나 알림은 원본 로그보다 늦을 수 있습니다.

| 증거 | 답할 수 있는 질문 | 추가로 확인할 내용 |
| --- | --- | --- |
| SCT | 이 로그가 해당 항목을 넣겠다고 서명했나요? | 서명, 로그 식별자, 항목 유형과 시각 |
| 포함 증명과 인증된 트리 헤드 | 항목이 이 스냅샷의 해당 위치에 들어 있나요? | 로그 식별자, 트리 크기, 루트와 증명 |
| 인증된 두 헤드의 일관성 증명 | 나중 스냅샷이 이전 항목을 기존 순서대로 보존했나요? | 같은 로그의 두 크기를 비교합니다. 로그가 서로 다른 모습을 보여줬는지도 조사한다면 독립적인 관측 결과를 비교합니다 |
| 엔드포인트에서 관측한 최종 인증서 | 그 시각과 관측 지점에서 서비스가 어떤 인증서를 제시했나요? | TLS 맥락, 서비스 이름과 접속 지점. 신뢰 경로, 이름, 용도와 해지 검사는 별도로 확인합니다 |

## 2. 정상 갱신 따라가기

가상의 기업이 `reports.example`의 공개 인증서를 갱신합니다. CA는 09:00 UTC에 사전 인증서를 만들고 해당 로그에서 SCT를 받아옵니다. 얼마 뒤 모니터가 사전 인증서 항목을 발견하고, 승인된 배포 시스템은 09:30에 최종 인증서를 CDN에 적용합니다. 09:40의 TLS 관측은 특정 CDN 접속 지점에서 새 인증서가 제시됐음을 보여줍니다. 다른 지점에서 이전 인증서가 보인다면 배포가 진행 중일 수 있습니다. SCT 시각, 로그나 모니터에서 관측한 시각, 인증서 유효 기간 시작, 서비스 배포 시각은 서로 다른 사실을 나타냅니다.

포함 증명에는 항목에서 루트까지 올라가는 데 필요한 형제 노드의 해시가 들어갑니다. A, B, C, D 순서로 기록한 네 항목에서 B의 증명에는 A의 해시와 C·D를 묶은 해시가 있습니다. B를 해시한 뒤 왼쪽에 A를 놓아 부모 해시를 계산합니다. 그 결과 오른쪽에 C·D의 해시를 놓아 다시 계산하고, 크기 4인 트리에서 독립적으로 인증한 루트와 비교합니다. 리프 해시는 입력 앞에 `0x00`, 부모 해시는 순서대로 나열한 자식 해시 앞에 `0x01`을 붙입니다. 머리 바이트로 두 종류의 입력을 구분합니다. 실제 CT에서는 프로토콜이 정한 항목 구조를 해시하므로 최종 인증서의 DER 파일만 해시한 값과 CT 리프 해시가 다를 수 있습니다.

## 3. 예상 밖 발급과 로그 공백 해석하기

승인받지 않은 사람이 CA 계정이나 도메인 검증 경로를 통제하면 예상 밖 발급이 생길 수 있습니다. 계획된 CDN 이전, 관리형 갱신, 신규 CA 승인도 비슷한 알림으로 보일 수 있습니다. 공개 로그는 이런 발급을 검토할 기회를 제공합니다. 인증서 해지나 서비스를 운영한 주체의 확인은 별도 절차입니다. 기업의 사설 신뢰 체인으로 발급한 인증서도 공개 CT에 모두 나타나는 것은 아닙니다.

| 관측 결과 | 다음에 확인할 항목 |
| --- | --- |
| 관리 도메인에서 낯선 발급자가 보임 | CA 및 관리형 서비스 목록, 주문 감사 기록, 승인과 유효 기간 |
| 갱신 한 건에서 알림이 여러 번 옴 | 로그 식별자와 항목 유형, CA 기록을 대조합니다. 여러 로그가 같은 갱신을 기록하거나 사전 인증서와 최종 인증서 항목이 각각 들어갈 수 있습니다 |
| SCT는 있는데 검색 색인에서 찾을 수 없음 | 해당 로그, 최대 병합 지연, 트리 헤드, 수집 지연과 색인의 범위 |
| 와일드카드 항목이 보임 | SAN(주체 대체 이름)을 그대로 기록합니다. 각 하위 도메인이 실제로 그 인증서를 쓰는지는 별도 관측으로 확인합니다 |
| 사건 전후 발급자 목록이 바뀜 | 당시 DNS와 CA 계정 기록을 보존합니다. 현재 CAA는 향후 발급 제한을 검토하는 데 쓸 수 있습니다. 과거 승인 여부에는 당시 자료가 필요합니다 |

Chrome은 공개 신뢰 TLS 인증서에 자체 CT 정책을 적용합니다. SCT가 전달된 위치, 인증서 유효 기간, 로그 상태와 운영자의 다양성을 봅니다. Chrome 공식 정책에 따르면 버전 148 이전에만 스테이플된 OCSP 응답에서 받은 SCT를 CT 준수에 사용할 수 있습니다. Chrome의 로그 운영 정책은 RFC 6962 로그가 2026년 11월 1일부터 접수된 최종 인증서 제출을 거절할 수 있다고 명시합니다. 실제로 사용하는 로그의 API와 항목 유형을 확인하세요. C2SP 정적 CT API는 서명된 체크포인트와 여러 해시를 묶은 타일을 제공하며 RFC 6962의 암호 연산을 사용합니다. 실험 규격인 CT v2의 RFC 9162가 RFC 시리즈에서 RFC 6962를 대체했지만, 어떤 프로토콜을 쓰는지는 로그별로 확인해야 합니다.

## 4. 블루팀 수집·분류·대응

1. **알림과 원본을 보존합니다.** 모니터링한 이름, 관측 UTC 시각, 검색 색인, 로그 ID, 항목 유형과 SCT 시각을 적습니다. 있으면 리프 인덱스나 증명, 트리 크기도 함께 남기세요. 모니터링 대상은 승인된 도메인 목록으로 잡고 DNS 이름에서 점으로 구분된 레이블을 기준으로 대조합니다. 단순 부분 문자열이나 모니터의 중복 제거 키에만 의존하면 서로 다른 이름이 합쳐질 수 있습니다.
2. **발급 기록을 연결합니다.** 정확한 SAN, 발급자, 일련번호, 유효 기간을 변경 기록, CA 감사와 CDN 자산 목록에 대조합니다. 사전 인증서와 최종 인증서를 각각 보존하세요. 최종 인증서의 지문은 관측한 인코딩을 식별합니다.
3. **실제 제시 증거를 확인합니다.** 승인된 서비스에 대해 관측 시각, 서비스 이름, 접속 지점의 정보와 함께 최종 인증서를 보존합니다. 저장한 PEM 형식 인증서는 아래 명령으로 확인할 수 있습니다. 관측 시각과 지점에 한해 제시 여부를 기록하고 필요한 경우 관리하는 다른 CDN 접속 지점과 비교합니다.
4. **승인되지 않은 발급이 확인되면 대응합니다.** CA와 서비스 담당자가 주문 자료를 보존하고 필요에 따라 해지와 안전한 교체를 진행하도록 조율합니다. CA 계정 접근 이력과 도메인 검증 기록도 검토하세요. 모니터링을 이어가고 영향을 받은 서비스가 실제로 어떤 인증서를 제시하는지 다시 확인합니다.

아래 읽기 전용 명령은 OpenSSL과 저장된 PEM 최종 인증서가 필요합니다. 명령은 인증서의 메타데이터를 표시합니다. 신뢰 체인, CT 서명, 실제 엔드포인트의 신원은 각각의 증거로 검증합니다.

```bash
openssl x509 -in observed-leaf.pem -noout -issuer -serial -dates \
  -sha256 -fingerprint -ext subjectAltName
```

## 5. 오프라인 실습 · 네 항목의 포함 증명 검증하기

<a href="{{ '/assets/labs/ct-inclusion-lab.py' | relative_url }}" download>ct-inclusion-lab.py</a>를 내려받아 Python 3에서 `python3 ct-inclusion-lab.py`를 실행하세요. 가상의 짧은 문자열만 사용하며 네트워크 연결이나 인증서 제출이 없습니다. OpenSSL로 따로 계산한 크기 4 트리의 루트를 신뢰한다고 가정하고, Python 표준 라이브러리로 증명에서 루트가 복원되는지 시험합니다.

| 실습에서 바꾸는 조건 | 기대 결과 |
| --- | --- |
| 리프 인덱스 1의 B와 올바른 형제 해시 | 알려진 루트와 일치 |
| 바이트, 리프 위치 또는 형제 해시 순서를 바꿈 | 복원한 루트가 달라 검증 실패 |
| 형제 해시 하나를 빼거나 다른 루트를 제공 | 검증 실패 |
| 같은 자료에 항목이 다섯 개라고 표시 | 네 항목만 지원하는 실습의 범위 검사에서 거부 |

마지막 줄은 `7 synthetic checks passed.`입니다. 편집 후 정상 사례가 실패하면 정확한 바이트, 0부터 시작하는 리프 인덱스, 형제 해시의 순서와 고정 루트를 확인하세요. 실제 트리는 좌우 크기가 다를 수 있습니다. 실습의 형제 해시 두 개짜리 계산을 모든 운영 증명에 적용할 수는 없습니다. 실습은 SCT나 트리 헤드의 서명은 검증하지 않습니다. 조사에서는 올바른 로그 키의 서명으로 스냅샷을 인증하고 증명 메타데이터를 확인한 뒤 루트를 비교합니다. Python 3.12에서 실습을 실행했고, 위 명령은 OpenSSL 3.5.7과 일회용 자체 서명 인증서로 확인했습니다. 실제 로그와 브라우저 정책은 공식 문서로 검토했습니다.

## 6. 확인 문제와 완료 기준

- **유효한 SCT가 보이면 로그에 이미 포함됐나요?** 로그 키로 서명한 포함 약속을 확보한 상태입니다. 특정 스냅샷에 들어 있는지는 인증된 트리 헤드와 포함 증명으로 확인합니다.
- **예상 밖 사전 인증서가 공개 로그에 있습니다. 사용자가 봤나요?** 항목을 보존해 발급을 확인하세요. 실제 제시는 엔드포인트나 TLS 클라이언트 증거가 따로 필요합니다.
- **두 루트가 다르면 항목이 삭제된 것인가요?** 먼저 로그 식별자와 트리 크기를 비교하세요. 항목을 추가해도 루트가 바뀝니다. 같은 로그의 두 스냅샷을 검토할 수 있다면 일관성 증명으로 확인합니다.
- **같은 SCT라면 모든 클라이언트에서 통과하나요?** 관측 시점의 브라우저나 라이브러리, 적용 정책과 로그 목록을 확인합니다.

**완료 기준.** 알림 한 건에서 정확한 도메인 이름, 출처와 UTC 기준 증거, 발급 가설, 승인된 갱신과 미승인 발급을 구분할 다음 확인 항목을 기록하세요.
