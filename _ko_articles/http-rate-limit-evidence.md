트래픽이 많은 배포 시간대에 클라이언트가 HTTP 429를 받았습니다. 게이트웨이 정책, 원본 서버의 할당량, 원본이 호출한 다른 서비스가 모두 같은 상태를 낼 수 있습니다. 실패한 요청 한 건부터 찾아 응답을 만든 계층을 확인한 뒤 어느 한도에 걸렸는지 판단합니다.

## 1. 응답 결과와 정책을 따로 읽기

**요청률 제한**은 일정 시간 동안 허용되는 요청 활동을 제어합니다. **할당량(quota)**은 더 긴 기간의 사용량에 적용될 수 있습니다. **순간 요청 한도(burst limit)**가 있으면 평균 요청률이 낮아도 짧게 몰린 요청은 제한될 수 있습니다. 정책은 테넌트, 라우트, 클라이언트 신원, 계정 등 여러 기준을 사용할 수 있습니다. RFC 6585는 과도한 요청에 429를 정의하고 `Retry-After` 필드를 허용합니다. 사용자를 구분하는 방법과 요청 계산 기준은 구현에 맡깁니다. HTTP 캐시는 429 응답을 저장하면 안 됩니다. 제한기가 내부적으로 정책 판정을 캐시하는 동작은 별개입니다.

| 관측 자료 | 무엇을 확인할 수 있나요? | 더 필요한 근거 |
| --- | --- | --- |
| 클라이언트의 429 | 요청 제한이 응답으로 나타났음 | 응답 생성 지점, 정책 집계 키, 범위, 적용 조건과 규칙 판정 |
| 엣지 거부 기록과 업스트림 시도 없음 | 해당 요청에 대해 엣지가 기록된 결정을 적용함 | 적용된 정책 버전과 이 요청이 일치한 이유 |
| 클라이언트 429 및 대응하는 업스트림 429 | 프록시가 업스트림에서 429를 받음 | 그 서버가 직접 응답했는지 다른 서비스의 응답을 전달했는지 |
| `Retry-After`가 있는 503 | 일시적으로 서비스를 사용할 수 없으며 재시도 시점이 안내됨 | 용량, 유지보수, 업스트림 근거. 헤더만으로 할당량을 식별할 수 없음 |
| `Retry-After` 없음 또는 형식 오류 | 해당 필드에서 쓸 수 있는 시간 안내를 받지 못함 | 클라이언트에 설정된 대기 정책, 타임아웃과 재시도 한도 |

## 2. 정상 요청과 두 가지 제한 경로

가상 테넌트 Lab A의 인벤토리 조회 GET이 UTC 10:00:00에 게이트웨이에 도착합니다. 게이트웨이는 원본으로 요청을 전달하고 원본이 200을 보냅니다. 두 계층은 서로 연결할 수 있는 요청 ID를 기록합니다. 1분 뒤의 요청은 429와 `Retry-After: 30`을 받습니다. 게이트웨이 기록에는 로컬 정책의 제한 결정과 업스트림 시도 없음이 명시돼 있습니다. 이 요청이 게이트웨이에서 거부됐다는 근거입니다. 대신 업스트림에 요청했다는 기록이 있다면 원본 기록과 연결하고 업스트림 상태를 확인한 뒤 429를 귀속합니다.

30초는 응답을 받은 시점부터의 대기 시간입니다. `Retry-After`는 절대 HTTP 날짜일 수도 있습니다. 값이 `Fri, 27 Nov 2026 10:02:30 GMT`이고 클라이언트 시계가 UTC 10:02:00이라면 약 30초 남습니다. 시간이 맞지 않을 때는 응답의 `Date`와 양쪽 시계의 오차 범위를 함께 보존합니다. 과거 날짜는 추가로 기다릴 양의 시간을 제시하지 않습니다. 애플리케이션의 재시도 정책은 계속 적용됩니다. 클라이언트에 별도 처리 규칙이 문서화되어 있지 않으면 반복되거나 잘못된 값은 시간 안내로 사용하지 않습니다.

## 3. 가능한 원인과 재시도 오용을 구분하기

대량 작업, 배포, 같은 시각에 시작한 예약 작업, 공유 NAT 주소, 재시도 폭주에서도 429가 나타납니다. 자동화된 악용도 짧은 요청 폭주나 비용이 큰 라우트에 집중하는 양상을 보일 수 있습니다. 상태 코드, 공유 주소 또는 User-Agent 한 가지로 공격자를 특정할 수는 없습니다. 요청률과 테넌트 범위, 요청 구성, 배포 이력을 대조합니다. 게이트웨이 자체는 여유가 있어도 애플리케이션의 제한은 따로 걸릴 수 있습니다.

즉시 반복하면 과부하가 커질 수 있습니다. 승인된 클라이언트에서는 유효한 재시도 안내를 따르고, 대기 시간을 점차 늘리는 백오프에 작은 무작위 편차와 재시도 횟수·시간 한도를 적용합니다. 전체 작업의 제한 시간도 고려하세요. 여러 번 실행했을 때 결과가 달라질 수 있는 쓰기 요청은 첫 실행이 적용되지 않았다는 근거 또는 반복을 안전하게 만드는 애플리케이션 계약이 있어야 자동으로 재시도할 수 있습니다. 응답을 받지 못한 경우와 서버의 명시적 거부는 서로 다른 관측입니다. 일시적인 오류처럼 보인다는 이유만으로 쓰기를 반복해도 안전하다고 판단하지 않습니다.

## 4. 블루팀 수집·탐지·대응

1. **실패한 요청을 계층별로 보존합니다.** UTC 시각, 메서드, 라우트, 테넌트나 정책 범위, 상태, `Retry-After`, `Date`, 클라이언트 측과 업스트림 요청 ID, 관측한 전송 방식을 기록합니다. 신뢰할 수 있는 로그의 식별자를 사용합니다. 공유 자료에서는 자격 증명, 쿠키 값, 요청 본문을 제외합니다. 클라이언트가 보낸 ID와 원본 주소 헤더는 신뢰하는 인프라의 기록과 대조합니다.
2. **응답이 처음 나온 지점을 확인합니다.** 게이트웨이 결정과 정책 버전, 확인 가능한 카운터나 예산, 업스트림 시도와 상태, 원본 이벤트를 연결합니다. 업스트림 값이 비어 있다면 로그 필드가 빠졌을 수 있습니다. 가능하면 로컬 제한 판정과 명시적인 업스트림 미시도 기록을 함께 확인합니다. 프록시가 재시도했다면 최종 상태와 시도 순서를 모두 보존합니다.
3. **정책 범위별로 측정합니다.** 같은 범위·메서드·라우트의 전체 요청을 분모로 제한 건수와 비율을 추적합니다. 엣지와 원본의 판정을 나누고 정상적인 순간 요청과 반복 요청의 규모를 확인합니다. 예를 들어 AWS API Gateway HTTP API는 계정·리전의 요청률과 순간 요청 목표, 라우트별 제어를 문서화하고 있으며 제한은 최선형(best effort)입니다. 429 한 건으로 한도를 역산하기 전에 실제 배포 설정과 공급자 문서를 확인합니다.
4. **좁은 범위에서 수정 효과를 검증합니다.** 정책이 보호하는 의존 서비스가 있는지, 클라이언트 속도를 낮춰야 하는지, 잘못된 집계 키가 쓰였는지 구분합니다. 조정을 승인받았다면 확인 가능한 클라이언트와 가장 좁은 범위에서 허용 요청, 예상된 제한, 업스트림 상태를 모두 확인합니다. 수정 전후 표본을 보존하세요.

## 5. 승인된 루프백 실습

<a href="{{ '/assets/labs/http-rate-limit-evidence.py' | relative_url }}" download>Python 실습 파일</a>을 내려받아 소유하거나 사용 승인을 받은 환경에서 Python 3으로 실행합니다. 게이트웨이와 원본 서버는 `127.0.0.1`의 임시 포트 두 개만 사용합니다. 클라이언트는 GET 일곱 건을 한 번씩 보내고 재시도하지 않습니다. 각 라우트의 결과는 미리 정해져 있으므로 실제 처리 용량을 측정하는 실습과는 다릅니다. 요청 ID로 게이트웨이 응답과 원본 관측을 비교합니다. 헤더 실습의 시계는 고정합니다.

~~~bash
python3 http-rate-limit-evidence.py
~~~

| 라우트 | 기대 관측 |
| --- | --- |
| `/ok` | 200, 원본에서 요청 확인 |
| `/edge` | 게이트웨이 429, 원본 기록 없음, 30초 대기 |
| `/origin` | 원본 429 전달, 원본 기록 확인, 45초 대기 |
| `/maintenance` | 원본 503 전달, 절대 날짜까지 90초 |
| `/missing`, `/invalid`, `/repeat` | 값 없음, 잘못된 값, 반복 값을 각각 표시하며 대기 시간은 계산하지 않음 |

`7/7 observations matched.`가 나오면 됩니다. `--negative-control`을 주면 `/edge`의 안내 시간만 31초로 바뀝니다. 그 사례가 불일치하고 종료 코드 1이 나와야 합니다. 시작 단계에서 실패한다면 승인된 실습 환경에서 로컬 루프백 소켓을 사용할 수 있는지 확인하세요. 실습은 실제 루프백 HTTP를 이용하며 정책은 가상입니다. 관리형 게이트웨이는 연결하지 않고 공급자 문서로 검토했습니다.

## 6. 확인 문제와 완료 기준

1. **두 게이트웨이가 모두 429를 보내면 같은 제한인가요?** 상태는 결과를 보여 줍니다. 생성 지점별 실제 규칙과 집계 키, 라우트 및 범위를 비교합니다.
2. **429와 503의 `Retry-After`가 같으면 같은 문제인가요?** 이 필드는 시간만 안내합니다. 두 상태가 뒷받침하는 가설이 다르므로 어느 지점에서 각각 생성됐는지 확인합니다.
3. **클라이언트에서 실패한 쓰기를 바로 재시도해도 될까요?** 작업 계약이나 첫 시도 결과에 대한 근거를 통해 반복 실행이 안전한지 확인해야 합니다.
4. **초기에 요청이 몰린 것과 재시도 폭주는 어떻게 구분하나요?** 요청 ID 또는 문서화된 연결 정보, 최초·재시도 시각, 같은 논리적 클라이언트나 작업의 반복 호출을 비교합니다.

**완료 기준.** 일곱 관측과 대조 실험을 재현합니다. 429 한 건을 보고 생성 지점, 판정 근거, 클라이언트나 서비스 담당자의 다음 조치를 설명합니다. 이어서 [HTTP 증거]({{ '/ko/wiki/http-evidence/' | relative_url }})와 [리버스 프록시 응답 증거]({{ '/ko/wiki/http-proxy-response-evidence/' | relative_url }})를 읽어 보세요.
