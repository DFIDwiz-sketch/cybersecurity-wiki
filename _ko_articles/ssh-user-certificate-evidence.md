**학습 목표.** SSH 사용자 인증서와 접속 성공·실패 기록을 보고, 어느 쪽의 신원을 확인했는지, 어떤 로컬 계정에 접근하려 했는지, 해지가 대상 서버까지 전달됐는지 구분합니다. 서버 신원부터 익히려면 [SSH 호스트 키 증거]({{ '/ko/wiki/ssh-host-key-evidence/' | relative_url }})를 먼저 읽어 보세요.

## 1. 사용자 인증서에 무엇이 들어가나요?

**사용자 키 쌍**은 공개키와 개인키로 구성됩니다. 클라이언트는 인증 중에 해당 개인키를 사용할 수 있음을 증명합니다. **인증기관(CA)**은 사용자의 공개키와 특정 속성을 연결하는 내용에 서명합니다. OpenSSH **사용자 인증서**에는 principal, 유효기간, 제약 조건, 일련번호, 키 ID가 들어갈 수 있습니다. 서버는 해당 CA를 사용자 인증에 신뢰할 때 인증서 서명을 확인할 수 있습니다. 클라이언트가 개인키를 사용할 수 있는지도 별도로 확인합니다. OpenSSH 인증서는 SSH 전용 형식입니다. 브라우저의 X.509 인증서 저장소나 OCSP와는 적용 범위가 다릅니다.

| 항목 | 의미 | 조사에서의 한계 |
| --- | --- | --- |
| 서버 호스트 키 또는 호스트 인증서 | SSH 연결에서 클라이언트가 서버 신원을 확인 | 누가 로그인했는지는 별도 증거가 필요 |
| 사용자 인증서와 대응 개인키 | 서버가 CA의 서명과 사용자 키 사용 증거를 확인 | 개인키는 에이전트나 장치에서 사용할 수 있음. 직접 조작한 사람이 누군지는 별도 확인 |
| Principal | 접근 인가에 사용할 수 있는, 인증서에 서명된 이름 | 대상 서버가 요청한 운영체제 계정에 이 이름을 허용해야 함 |
| 일련번호와 키 ID | 일련번호는 발급 시 CA 범위에서 쓰는 식별자. 키 ID는 추적에 도움이 되는 서명된 이름표 | 다른 CA가 같은 일련번호를 쓸 수 있음. 키 ID가 유일하다는 보장은 없고 principal과 역할이 다름 |
| 키 해지 목록(KRL) | 해지할 키 또는 인증서를 지정한 OpenSSH 형식 파일 | 검증 서버가 해당 목록을 배포받아 적용해야 함. 로컬 조회는 지정한 파일만 확인 |

## 2. 정상 인증 한 건 따라가기

가상의 조직에서 `lab-auditor` 역할은 한 유지보수 호스트의 로컬 계정 `audituser`를 사용할 수 있습니다. 승인된 CA는 직원의 공개키에 이 역할을 담아 서명합니다. 짧은 유효기간을 둔 인증서의 일련번호는 43, 키 ID는 `lab-issued-43`입니다. 발급자는 CA 지문, 일련번호, 사용자 공개키 지문, principal과 승인 기록을 남깁니다.

1. 클라이언트는 이미 정해진 신뢰 기준으로 서버의 호스트 키 또는 호스트 인증서를 확인합니다.
2. 클라이언트는 `audituser`로 접근을 요청하고 인증서에 연결된 개인키를 사용할 수 있음을 증명합니다. 서버는 허용된 CA로 서명을 확인하고 인증서 유형, 유효기간, 제약, 해지 여부를 검사합니다.
3. **TrustedUserCAKeys**를 사용하는 인증 경로에서 서버는 요청한 로컬 계정이 해당 principal을 쓸 수 있는지 확인합니다. `AuthorizedPrincipalsFile`이나 `AuthorizedPrincipalsCommand`로 허용 이름을 제공할 수 있습니다. 이 예시가 작동하려면 `audituser`에 `lab-auditor`가 허용돼야 합니다. 별도 매핑을 설정하지 않은 일반 TrustedUserCAKeys 경로에서는 요청한 사용자 이름이 인증서 principal 목록에 있어야 합니다. Principal 파일 설정은 `authorized_keys`를 통해 CA를 신뢰하는 별도 경로에는 적용되지 않습니다.
4. 인증서 조건이 맞아도 계정 정책에 따라 거부되거나 추가 인증이 필요할 수 있습니다. 인증 성공 기록은 로그인 판정의 근거입니다. 이후 작업을 확인하려면 세션과 프로세스 자료를 대조하세요.

신뢰할 수 있는 관리 단말에서 승인된 인증서와 KRL 사본을 읽으려면 아래 명령을 사용할 수 있습니다. 원본 바이트를 보존하고 파일 버전과 출처를 적어 두세요. 서버에 연결하지 않는 조회입니다.

```bash
ssh-keygen -L -f sample-cert.pub
ssh-keygen -Q -f deployed-copy.krl sample-cert.pub
```

`-L`은 인증서 필드를 출력합니다. 대상 서버가 그 인증서를 신뢰하거나 허용했다는 의미는 아닙니다. `-Q`에서 목록에 없는 인증서는 만료됐어도 `ok`가 나올 수 있습니다. 종료 상태가 0이 아니면 출력의 진단을 함께 보고, 목록에 있다는 판정과 파일·입력 오류를 구분하세요.

## 3. 실패와 오용 가능성을 구분하기

| 관측 | 가능한 원인 | 비교할 증거 |
| --- | --- | --- |
| 배포 뒤 인증서 거부 | CA 불일치, 예상과 다른 계정 매핑, 대상 장치 정책이나 인증서 제약 | 해당 계정과 연결에 적용된 서버 정책, 발급 기록, 인증서 필드 |
| 승인된 사용자도 만료 즈음 거부됨 | 시계 오차, 이전 인증서를 제시함, 발급 장애 | 서버 UTC와 오차, 실제 제시한 인증서, 발급 타임라인 |
| 두 시스템에서 같은 일련번호 관측 | 발급 CA가 다르거나 같은 CA에서 번호가 중복 배정됨 | CA 지문과 일련번호를 먼저 대조하고, 사용자 공개키 지문·키 ID·시각 확인 |
| KRL을 만들었는데 어떤 호스트에서는 인증이 받아들여짐 | 이전 목록 또는 미적용, 다른 CA 범위, 인증서 없이 쓰는 공개키 경로, 기존 연결의 기록 | 당시 `RevokedKeys`, 배포 파일 내용, 인증 방식과 새 연결 증거 |

개인키가 유출되면 아직 쓸 수 있는 인증서와 함께 악용될 수 있습니다. 짧은 유효기간은 인증서를 다시 쓸 수 있는 기간을 줄입니다. CA가 침해됐거나 principal 매핑이 지나치게 넓다면 영향 범위가 더 커질 수 있습니다. 만료와 KRL 갱신은 그 뒤의 인증 판정에 적용됩니다. 기존 세션이 종료됐는지는 별도 확인이 필요합니다. 대응 범위를 판단할 때는 인증서 없이 허용된 공개키나 다른 인증 방식도 확인하세요.

## 4. 블루팀 수집·탐지·대응

1. **대상 서버 기록부터 확보합니다.** UTC와 시계 오차, 호스트, 요청한 로컬 계정, 출발지 정보, 실제 인증 방식과 확보 가능한 세션 식별자를 보존하세요. 로그에 있다면 CA·사용자 공개키 지문, 일련번호, 키 ID도 남깁니다. 수집 범위는 OpenSSH 버전, 로깅 설정, 전달 환경에 따라 달라집니다. [Linux 인증 로그 조사]({{ '/ko/wiki/linux-auth-evidence/' | relative_url }})에서 세션 기록을 이어서 확인할 수 있습니다. 클라이언트 오류만으로 서버 정책은 알기 어렵습니다.
2. **발급과 서버 정책을 대조합니다.** 기록된 일련번호가 0이 아니라면 CA 지문과 묶어서 검색하고, 사용자 공개키 지문, 키 ID, principal, 유효기간을 비교합니다. 사건 당시 서버 신뢰 목록, 허용 principal과 `RevokedKeys` 설정을 확보하세요. 조건부 설정이나 순차 배포 때문에 현재와 다를 수 있습니다. 공개 증거와 설정 해시는 보존하고 개인키는 일반 로그나 수집 자료에 포함하지 않습니다.
3. **해지 목록이 적용됐는지 확인합니다.** 해당 호스트에서 복사한 승인된 KRL로 오프라인 조회를 하고, 설정 경로와 배포 버전을 대조합니다. OpenSSH에서는 설정한 `RevokedKeys` 파일을 읽을 수 없으면 모든 사용자의 공개키 인증이 거부될 수 있습니다. 특정 인증서만 해지됐다고 결론 내리기 전에 파일과 설정 상태를 확인하세요.
4. **담당자와 대응 효과를 확인합니다.** 배포 뒤에는 승인된 테스트 호스트에 새 연결을 만들어 해지 대상과 영향받지 않아야 할 대조군을 확인합니다. 기존 세션과 그 안에서 실행한 명령·접근은 적절한 자료로 따로 조사합니다. 발급 CA가 침해됐다면 일련번호 하나만 처리하지 말고 CA 신뢰 변경과 재발급을 조율합니다.

## 5. 오프라인 실습 · KRL의 판정 범위 확인하기

<a href="{{ '/assets/labs/ssh-user-certificate-lab.py' | relative_url }}" download>OpenSSH 인증서 실습</a>을 내려받습니다. Python 3과 OpenSSH 클라이언트 도구가 PATH에 있는 승인된 환경에서 `python3 ssh-user-certificate-lab.py`로 실행하세요. 임시 폴더에서 일회용 CA 두 개, 사용자 키 하나, 실제 사용자 인증서 네 개를 만듭니다. 실습 키를 신뢰 설정에 추가하지 마세요. SSH 세션은 열지 않으며, 종료하면 임시 파일이 정리됩니다.

| 사례 | 대조 조건 | 기대 결과 |
| --- | --- | --- |
| A | 일련번호 42, 키 ID `lab-issued-42`, principal `lab-auditor`인 사용자 인증서 읽기 | 각 필드 확인 |
| B | CA A의 42번 해지 목록에 CA A의 42번 조회 | `REVOKED` |
| C | CA A의 43번 조회 | 이 목록에서 `ok` |
| D | CA B의 42번 조회 | 이 목록에서 `ok` |
| E | 만료된 CA A의 44번 조회 | 유효기간이 지났어도 이 목록에서 `ok` |

마지막에 `5/5 OpenSSH tool checks matched. No SSH session was attempted.`가 표시됩니다. `ssh-keygen`을 찾지 못하거나 환경 정책상 Ed25519를 사용할 수 없다면 설치 도구와 테스트 환경을 확인하세요. D가 해지돼야 한다고 생각했다면 목록의 범위를 지정한 CA 공개키를 확인하세요. E의 `ok`는 KRL 판정입니다. 서버의 유효기간·계정 인가 판정은 별개입니다. 대조 조건 5개는 Debian OpenSSH 10.0p2에서 실행했습니다. 서버 인증과 로그 수집은 공식 문서로 확인했으며 실행 범위에는 포함하지 않았습니다.

## 6. 확인 문제와 완료 기준

1. **인증서에 `lab-auditor`가 있으면 `audituser`로 로그인할 수 있나요?** 대상 서버의 CA 신뢰, 계정 매핑, 유효기간과 기타 정책을 함께 확인해야 합니다.
2. **CA A의 42번을 해지했다면 CA B의 42번은요?** CA A에 한정된 규칙이면 CA B에는 적용되지 않습니다. CA 지문과 일련번호를 함께 보세요.
3. **만료된 인증서의 KRL 결과가 `ok`입니다. 서버가 만료를 무시하나요?** 이 조회는 지정한 목록을 확인합니다. 서버의 유효기간 검사는 별도입니다.
4. **인증 성공 로그로 명령 실행도 확인할 수 있나요?** 세션·프로세스·애플리케이션 기록을 별도로 대조하세요.

**완료 기준.** 서버 신원, 사용자 개인키 사용 증거, 계정 인가를 설명하세요. 실습 결과 다섯 가지를 예측하고 서버가 어느 KRL을 적용했는지 확인할 자료 한 가지를 제시하면 됩니다.
