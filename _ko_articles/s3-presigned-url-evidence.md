고객은 비공개 보고서를 받았다고 말하고, CloudTrail에는 애플리케이션의 IAM 역할 세션이 기록되어 있습니다. 두 기록이 어떻게 동시에 맞을 수 있을까요? 이 장에서는 S3 범용 버킷의 사전 서명 GET을 따라가며 각 기록으로 답할 수 있는 질문을 살펴봅니다. 본문의 사례와 실습 자료는 가상입니다.

## 1. 링크로 무엇을 할 수 있을까요?

애플리케이션은 자신의 AWS 자격 증명을 사용해 특정 객체와 작업에 대한 요청을 미리 서명할 수 있습니다. 보고서를 읽는 `GetObject`가 한 예입니다. **사전 서명 URL**의 쿼리 문자열에는 서명과 인증에 필요한 매개변수가 들어 있습니다. 서명 버전 4(SigV4)는 HTTP 메서드와 객체 경로 등 요청의 세부 정보를 서명에 묶습니다. **서명 주체**는 앱이 자격 증명을 빌려 쓴 AWS 보안 주체나 역할 세션입니다. **링크 보유자**는 그 URL을 S3에 제시한 쪽으로, 브라우저나 서비스 또는 그 뒤의 사람일 수 있습니다.

이 방식으로 앱은 버킷을 비공개로 유지하고 AWS 자격 증명을 직접 배포하지 않으면서 다운로드를 허용할 수 있습니다. URL 전체는 **소지자 자격 증명**으로 취급하세요. 보유자의 요청이 서명·만료·권한 검사를 통과하면 유효 기간에 같은 URL을 여러 번 사용할 수 있습니다. 앱의 발급 기록은 누구에게 전달하려 했는지 보여 주고, S3는 실제로 들어온 서명 요청을 평가합니다.

## 2. 발급에서 응답까지

1. 앱은 요청자에게 보고서를 보낼 수 있는지 확인한 뒤 현재 역할 세션으로 객체 GET을 서명합니다. SDK가 앱에서 자체적으로 서명할 수 있으므로 URL이 만들어질 때 S3에 발급 이벤트가 생기지 않습니다. STS의 역할 수임 이벤트는 서명 세션이 시작된 시점을 파악하는 데 도움이 됩니다.
2. 링크 보유자가 서명된 요청을 S3에 보냅니다. S3는 요청이 시작될 때 서명과 만료를 확인하고 권한과 관련 정책 조건을 평가합니다. URL에 표시된 유효 시간이 남아 있어도 권한 검사에서 실패할 수 있습니다.
3. 사전에 수집을 설정해 해당 객체가 범위에 포함됐다면 CloudTrail에서 객체 요청과 서명 세션을 확인할 수 있습니다. S3 서버 액세스 로그에서는 HTTP 상태와 응답 바이트를 별도로 확인할 수 있습니다. 어떤 발급 건과 이어지는지 조사하려면 앱에서도 발급을 기록해야 합니다.

| 제한 | 의미 | 확인할 증거 |
| --- | --- | --- |
| URL 수명 | `X-Amz-Expires`는 서명 시점부터의 지속 시간을 초 단위로 나타냅니다. | 민감한 값을 제외한 앱의 서명 시각과 설정한 지속 시간 |
| 서명 자격 증명 | 임시 자격 증명은 URL의 예정 만료보다 먼저 끝날 수 있습니다. 자격 증명 취소·삭제·비활성화도 사용 가능 시간을 줄일 수 있습니다. | 서명 세션의 수명 또는 자격 증명의 상태 변경 기록 |
| 요청 정책 | 버킷 정책은 서명 후 경과 시간이 기준을 넘은 SigV4 요청을 거부할 수 있습니다. `s3:signatureAge`는 밀리초 단위입니다. | 요청 당시 실제 정책과 해당 작업·객체에 대한 조건의 적용 여부 |

**가상의 정상 흐름.** 앱이 10:00 UTC에 비공개 보고서 GET을 300초 동안 유효하도록 서명합니다. URL의 예정 만료는 10:05 UTC이고 서명에 사용한 역할 세션은 10:03 UTC에 만료됩니다. 10:02 UTC에 들어온 요청의 액세스 로그에는 HTTP `200`과 전송량 `8192`바이트가 남습니다. 10:03 UTC 이후 시작한 요청은 URL 자체의 유효 시간이 남았더라도 만료된 세션의 자격 증명으로는 허용되지 않습니다. 만료 전에 시작한 다운로드는 S3에서 계속 전송될 수 있습니다. 연결이 끊겨 다시 시도한 GET은 새 요청입니다. 이후 기록에 `403`만 보인다면 정책 거부인지, 세션 만료인지 등 정확한 원인은 추가로 확인해야 합니다.

## 3. 블루팀의 수집, 탐지, 대응

지원 티켓이나 로그에 유효한 링크가 노출되면 다른 보유자가 사용할 수 있습니다. 이때 CloudTrail에 정상 다운로드와 같은 서명 주체가 남을 수 있습니다. 평소에 보지 못한 객체 키, 짧은 시간에 몰린 성공 요청, 예상 전달 시간 이후 반복된 읽기, 앱 발급 기록과 맞지 않는 요청을 살펴보세요. 경보를 올리기 전에 정상 재시도, 범위 요청, 앱 배포로 달라진 동작과 비교합니다.

| 출처 | 수집하고 대조할 항목 | 뒷받침하는 판단 |
| --- | --- | --- |
| 앱 감사 로그 | 발급 ID, UTC 시각, 예정 수신자 참조값, 서명 세션 ARN, 대상 계정, 버킷, 키, 작업, 확인 가능한 URL·세션 만료 시각을 남깁니다. | 앱이 누구에게 권한을 주려 했고 어떤 발급 건이 해당 요청과 이어질 수 있는지 |
| CloudTrail S3 데이터 이벤트 | 해당 버킷과 접두사의 읽기 데이터 이벤트를 사전에 활성화합니다. `eventSource=s3.amazonaws.com`, `eventName=GetObject`, `additionalEventData.AuthenticationMethod=QueryString`, `requestParameters.X-Amz-Expires` 존재 여부를 확인합니다. `requestID`, `eventTime`, `userIdentity.arn`, 오류 코드도 보존합니다. | SigV4 사전 서명 GET일 가능성과 서명 세션. `userIdentity.sessionContext.sessionIssuer.arn`이 있으면 기본 IAM 역할을 확인할 수 있습니다. |
| S3 서버 액세스 로그 | 버킷의 서버 액세스 로깅을 미리 켭니다. `Request ID`와 CloudTrail `requestID`를 연결하고 버킷, 키, 작업, 계정 맥락, 시간을 대조합니다. `Authentication Type`, HTTP 상태, `Bytes Sent`를 확인합니다. | 해당 요청의 HTTP 결과와 기록된 응답 바이트. 액세스 로그는 수집이 보장되지 않으며 전달이 지연될 수 있습니다. |

CloudTrail의 `eventID`는 CloudTrail 이벤트 자체의 식별자입니다. 두 로그를 연결할 때는 S3 요청 ID를 사용하세요. `QueryString`만으로는 다른 쿼리 인증과 구분하기 어렵습니다. 제한된 환경에서 서버 액세스 로그를 추가 확인할 때는 `Authentication Type=QueryString`과 `Request-URI`에 만료 매개변수 이름이 있는지 함께 살펴보세요. 공유 조사 기록이나 경보에는 필요한 필드만 남기고 URL 전체, 서명, 보안 토큰은 제외합니다.

서명 세션, 대상 계정, 버킷, 키, 작업, 시각을 사용해 발급 후보를 찾습니다. 같은 조건에 들어오는 발급 건이 둘이면 후보를 모두 남기고 어느 링크였는지는 미확정으로 표시하세요. 출발지 IP와 User-Agent는 타임라인을 보강합니다. 공용 프록시, 링크 전달, 기기 공유가 있었다면 이 값으로 개인을 특정하기 어렵습니다.

노출이 의심되면 먼저 민감한 값을 제외한 증거를 보존하고 관련 객체 범위와 남은 유효 시간을 확인합니다. 서명 주체와 버킷 담당자와 협의해 추가 읽기를 제한하고 정상 사용자에게 미치는 영향을 파악한 뒤, 정책 변경의 효과를 검증하세요. 가능하면 거부 범위를 관련 객체나 보안 주체로 좁힙니다. 역할 권한을 점검하고 다운로드 흐름에 맞게 발급 수명을 짧게 잡으세요. 서비스 방식에 맞는 경우 서명 경과 시간과 출발지 네트워크 조건도 검토할 수 있습니다. 차단 뒤에는 대조가 끝난 성공 GET을 검토하고, 확인된 바이트와 결과가 불분명한 요청을 함께 기록합니다.

총 여덟 건의 검사를 통과해야 합니다. 실패 사례를 확인하려면 JSON을 복사해 첫 사례의 액세스 기록 `request_id`를 바꾼 후 다시 실행하세요. 기대했던 로그 연결이 실패하고 종료 코드는 1이 됩니다. 원본에서 실패하면 두 파일이 같은 실습용인지, JSON 형식이 유효한지, UTC 시각에 시간대가 들어 있는지 확인하세요. Python과 가상 자료는 클라우드 실행 환경에서 실험했습니다. AWS 로그와 정책 동작은 공식 문서로 확인했습니다.

## 5. 판단의 한계

비공개 버킷에서도 사전 서명 GET이 성공할 수 있습니다. HTTP `206`은 일부 범위에 대한 응답입니다. `Bytes Sent`는 서버가 보냈다고 기록한 응답 바이트이며 HTTP 프로토콜 오버헤드는 제외됩니다. 거부 요청의 바이트는 오류 응답일 수 있으므로 객체 데이터로 집계하지 않습니다. `200`과 바이트 수를 확인해도 보유자가 데이터를 저장했는지, 다른 곳으로 보냈는지, 누구였는지까지는 알 수 없습니다. 기록이 없다면 먼저 이벤트 선택 범위, 보존 기간, 전달 상태를 점검하세요.

<summary>확인 문제와 해설, 학습 완료 기준</summary>

1. **10:00 UTC에 300초 유효한 URL을 만들었고 서명 세션은 10:03 UTC에 만료됩니다. 10:04 UTC에 새 GET을 보내면 허용될까요?** 아니요. 서명에 사용한 임시 자격 증명이 이미 만료됐습니다.
2. **CloudTrail에 배포 서비스의 역할 세션이 있고 발급 기록 두 건이 일치합니다. 누가 파일을 내려받았을까요?** 서명 세션과 발급 후보 두 건까지 확인할 수 있습니다. 실제 보유자를 식별하려면 클라이언트나 앱의 독립적인 증거가 더 필요합니다.
3. **연결된 로그에 `206`과 `1024`바이트가 기록됐습니다. 조사 메모에는 무엇을 쓸 수 있나요?** S3가 해당 GET에 부분 응답을 보내고 응답 바이트 1024를 기록했습니다. 객체 전체를 받았는지는 확인되지 않았습니다.

두 가지 만료 시각의 차이를 설명하고 요청 ID로 S3 로그를 연결할 수 있는지 확인하세요. 마지막으로 서명 세션, 발급 후보, 관측된 객체 응답 바이트에 대해 각각 어떤 판단을 내릴 수 있는지 적으면 학습을 마칠 수 있습니다.
