**학습 목표.** SSH의 각 단계에서 누가 누구에게 신원을 증명하는지 설명합니다. 호스트 키가 바뀌었다는 경고를 받으면 정확한 목적지와 신뢰 규칙을 찾고, 독립적인 자료로 전체 지문을 대조해 접속을 승인할 수 있는지 기록합니다.

## 1. 호스트 키로 무엇을 증명하나요?

**SSH 호스트 키**는 SSH 서버의 키입니다. 공개키로 호스트를 인증하는 일반적인 흐름에서는, 최초 키 교환 중 서버가 교환 내용과 자신의 키를 연결하는 데이터에 서명합니다. 클라이언트는 서명이 유효한지와 제시된 키가 의도한 서버에 대해 신뢰할 수 있는지를 확인합니다. 두 질문을 따로 봐야 합니다. 다른 개인키를 가진 사람도 그 키로 유효한 서명을 만들 수 있습니다. 서버 이름과 공개키를 신뢰할 수 있는 방법으로 연결해야 서명을 서버 신원의 근거로 삼을 수 있습니다.

**지문(fingerprint)**은 공개키를 짧게 표시한 해시 값입니다. OpenSSH의 SHA-256 지문은 `SHA256:…` 형식으로 나옵니다. 같은 해시 형식의 전체 값을 비교하세요. 지문은 어떤 키인지 알려 주고, 별도의 신뢰할 수 있는 자료가 그 키의 소유자를 알려 줍니다. **known_hosts**는 클라이언트가 서버 이름과 키의 대응을 저장할 수 있는 파일입니다. **authorized_keys**는 서버가 사용자 계정에 허용한 공개키를 찾는 방법 중 하나입니다. 서버는 계정 정책, SSH 사용자 인증기관(CA), 다른 인가 수단도 사용할 수 있습니다.

| 확인하려는 것 | 보통 누가 키를 갖고 있나요? | 확인할 증거 |
| --- | --- | --- |
| 의도한 SSH 서버인가요? | 서버가 호스트 개인키를 보유 | 유효한 키 교환 서명과 독립적으로 신뢰할 수 있는 등록 키 또는 호스트 인증서 |
| 요청한 계정이 허용한 키를 사용할 수 있나요? | 클라이언트가 사용자 개인키를 보유하거나 허용된 서명 장치를 사용 | 유효한 사용자 인증 서명과 서버의 인가 정책 |
| 요청한 세션이나 권한이 열렸나요? | 서버와 운영체제가 판단 | 세션 시작, 명령 또는 권한 사용 기록. 키만으로는 판단할 수 없음 |

## 2. 정상 로그인 한 건을 따라가세요

운영자가 기본 SSH 포트의 `node.lab.example.test`에 연결한다고 가정합니다. 신뢰할 수 있는 프로비저닝 기록을 바탕으로 호스트 공개키를 이미 등록해 둔 상태입니다. 클라이언트와 서버는 알고리즘을 협상하고 세션 키를 설정합니다. 서버는 호스트 공개키를 제공하고 키 교환에 서명합니다. 클라이언트는 서명을 검증하고 그 키가 기대한 서버 신원과 일치하는지 확인합니다. 협상한 세션 키는 이후 전송을 보호합니다. 공개키로 사용자를 인증할 때는 클라이언트가 현재 세션에 묶인 사용자 인증 데이터에 서명하고, 서버가 요청한 계정에 그 키가 허용되는지 확인합니다. 사용자 개인키는 클라이언트나 서명 장치에 남습니다.

![서버는 호스트 키를 가지고 있음을 클라이언트에 증명합니다. 그 뒤 클라이언트가 사용자 키를 가지고 있음을 서버에 증명합니다.]({{ '/assets/diagrams/ssh-trust-directions-ko.svg' | relative_url }})

*화살표는 각 서명이 전달되는 방향입니다. 첫 번째 검증은 서버 신원을 확인하고, 두 번째는 계정 접근을 확인합니다. 서버 쪽 로그인과 세션 기록은 [Linux 인증 조사]({{ '/ko/wiki/linux-auth-evidence/' | relative_url }})에서 이어서 다룹니다.*

TCP 22번 통신 기록으로는 센서가 본 연결을 확인할 수 있습니다. SSH 배너를 교환한 사실만으로도 양쪽 신원은 확인할 수 없습니다. 호스트 키 검증에서 실패하면 사용자 인증에 들어가기 전에 클라이언트가 연결을 중단할 수 있습니다. 서버의 로그인 기록이 비어 있더라도 클라이언트의 호스트 검증 결과를 따로 확인하세요.

## 3. 첫 접속과 키 교체, 뜻밖의 변경

| 신뢰 방식 | 무엇을 근거로 삼나요? | 확인할 한계 |
| --- | --- | --- |
| 공개키 사전 등록 | 승인된 자산 목록이나 독립적으로 인증된 콘솔에서 받은 키 또는 지문 | 서로 다른 접속 대상은 구분해 등록하고, 검토된 변경 절차로 갱신 |
| 첫 사용 신뢰(TOFU) | 첫 접속에서 수락한 키와 이후 접속의 일치 여부 | 첫 접속 때 검증을 생략하면 자기 키를 내민 다른 장비가 기대한 서버로 기억될 수 있음 |
| SSH 호스트 인증서 | 해당 호스트 범위에 설정된 SSH CA, 허용 호스트 이름, 유효 기간 | CA와 이름의 적용 범위를 확인. SSH 호스트 CA는 브라우저의 TLS 신뢰 저장소와 별도 |
| DNSSEC로 검증되는 SSHFP | 검증된 DNS 응답과 SSHFP 검증을 사용하는 클라이언트 정책 | 검증되지 않은 답은 신뢰 근거가 약함. 검증 범위를 확인 |

업스트림 OpenSSH의 `StrictHostKeyChecking=yes`에서는 이미 신뢰할 수 있는 서버 신원이 필요합니다. 기본 `ask`는 처음 보는 키를 등록하기 전에 묻고, 기존 키가 바뀌면 접속을 거부합니다. `accept-new`는 새 키를 자동 등록하지만 이미 등록한 서버의 키가 바뀌면 거부합니다. 첫 접속 상대가 맞는지는 여전히 확인해야 합니다. 승인된 자산 목록으로 키를 사전 등록하거나 SSH 호스트 CA를 쓰면 첫 접속에서 받은 값에만 의존하는 상황을 줄일 수 있습니다. 자동화나 래퍼가 설정을 덮어쓸 수 있으므로 설치된 클라이언트에 실제 적용되는 정책을 확인하세요.

지문이 바뀐 원인으로는 서버 재설치, 승인된 키 교체, 주소 재할당, 다른 SSH 서비스로의 연결이 있습니다. 의도와 다른 서버로 유도되거나 중간에서 연결이 가로채진 경우에도 같은 경고가 날 수 있습니다. 반대로 호스트 개인키 자체가 복제되거나 유출되면 소유자가 달라져도 지문은 그대로일 수 있습니다. 원인을 판단하기 전에 정확한 접속 대상과 시점의 증거를 모으세요.

계획된 교체에서는 기존·새 키 지문, 적용 대상, 두 키를 함께 쓰는 기간이나 기존 키를 내리는 시점을 기록합니다. OpenSSH의 `UpdateHostKeys`는 조건에 맞으면 이미 인증된 서버에서 추가 키를 배울 수 있어 점진적 교체에 활용됩니다. 사용자 known_hosts로 일반 호스트 키를 신뢰한 경우 등 적용 조건을 매뉴얼에서 확인하세요. 설명되지 않은 경고에는 독립적인 검증이 필요합니다. 알고리즘 협상 실패는 별도로 살펴봅니다. 예를 들어 OpenSSH 8.8은 RSA/SHA-1 서명을 기본 비활성화했으며, 같은 RSA 키라도 SHA-2 서명을 사용할 수 있습니다. 오류 메시지의 의미는 설치 버전과 플랫폼 정책을 기준으로 해석하세요.

## 4. 신뢰 설정을 바꾸기 전에 수집·대응하세요

**원래 경고를 보존하세요.** UTC, 클라이언트 버전, 입력한 목적지, 실제 목적지, 포트, 호스트 키 알고리즘과 제시된 지문을 기록합니다. 경고에 파일 위치와 충돌한 줄 번호가 나오면 함께 보존하세요. 승인된 터미널이나 작업의 클라이언트 출력을 확보하고, 내부 호스트명이나 계정 정보가 담긴 진단 기록은 접근을 제한합니다. 승인된 변경 전에 기존 등록 파일을 보존하세요.

**클라이언트가 찾는 이름을 확인하세요.** 신뢰할 수 있는 설정에서 실제 연결 이름, 포트, `HostKeyAlias`, 사용자·시스템의 known_hosts 파일, 점프 서버 경로를 확인합니다. 점프 서버의 키와 최종 서버의 키는 각각 확인해야 합니다. 별칭은 키 검색과 호스트 인증서 검증에 쓰는 이름을 바꿀 수 있습니다. 기본값과 다른 포트는 흔히 `[node.lab.example.test]:2222`처럼 괄호와 포트를 포함해 찾습니다. 해시로 저장한 이름도 정확한 검색값을 알면 `ssh-keygen -F`로 찾을 수 있습니다. 단순 문자열 검색은 그 줄을 놓칠 수 있습니다.

**독립적인 기준을 확보하세요.** 승인된 자산 담당자, 프로비저닝 기록, 인증된 관리 콘솔, 신뢰하는 SSH CA 목록을 이용합니다. 서버 쪽 지문은 설정된 알고리즘의 공개키 파일에서 확인하고 개인키는 보호하세요. 같은 불확실한 네트워크 경로에서 새 키를 다시 보는 것만으로는 출처가 독립적으로 확인되지 않습니다. 재설치·교체·주소 변경 기록과 대조하고, 믿을 만한 일치 근거가 없으면 접속 차단을 유지한 채 담당자에게 알리세요. 새 키를 배포하기 전에 비슷한 경고의 영향 범위를 확인합니다.

**수집할 수 있는 증거를 연결하세요.** 승인된 환경에서 가능한 경우 클라이언트의 검증 결과, 서버 로그인 로그, 점프 서버 기록, DNS·자산 변경, 작업 승인 기록을 모읍니다. 접속 대상·클라이언트·시간 범위로 반복 시도를 묶은 뒤, 여러 관리 단말에서 발생한 예상 밖의 키 변경을 살펴보세요. 첫 등록과 기존 등록의 변경을 구분합니다. 이후 로그인이 있다면 같은 접속 대상과 계정인지 확인하세요. 경고는 조사 단서입니다. 지문이 일치해도 해당 서버가 안전한 상태인지까지 보장되지는 않습니다.

## 5. 오프라인 실습 · 등록 파일 읽기

[ssh-lab-known-hosts.txt]({{ '/assets/labs/ssh-lab-known-hosts.txt' | relative_url }})와 [ssh-lab-public-keys.txt]({{ '/assets/labs/ssh-lab-public-keys.txt' | relative_url }})를 같은 폴더에 저장하세요. 두 파일에는 실습용 공개 자료만 들어 있습니다. OpenSSH 클라이언트 도구가 설치된 자가 소유 환경에서 실행합니다. 명령은 로컬 파일만 읽으며 연결을 열지 않습니다. 공개키 세 개의 실습 이름은 A, B, C입니다. 출력에서 SHA-256 지문 전체를 대조하세요.

~~~bash
ssh-keygen -E sha256 -lf ssh-lab-public-keys.txt
ssh-keygen -F node.lab.example.test -l -f ssh-lab-known-hosts.txt
ssh-keygen -F '[node.lab.example.test]:2222' -l -f ssh-lab-known-hosts.txt
ssh-keygen -F db.lab.example.test -l -f ssh-lab-known-hosts.txt
ssh-keygen -F new.lab.example.test -l -f ssh-lab-known-hosts.txt
~~~

| 가정 | 예상 결과 | 판단 |
| --- | --- | --- |
| 기본 포트 서버가 A를 제시 | 등록 1번 줄이 A와 일치 | 등록 지문과 일치함. 실제 연결에서도 서명을 검증해야 함 |
| 기본 포트 서버가 B를 제시하고 독립 기록이 없음 | 기본 포트에는 A가 등록돼 있고 B는 2222 포트의 2번 줄에 있음 | 차단을 유지하고 접속 대상과 변경 기록을 확인 |
| 기본 포트 서버가 B를 제시하고, 해당 접속 대상의 승인된 교체를 독립 자료로 확인함 | 현재 등록 파일에서는 여전히 A가 나옴 | 확인한 승인 근거를 남기고 해당 접속 대상의 관리 절차로 등록을 갱신 |
| 2222 포트 서버가 B를 제시 | 괄호와 포트를 넣어 검색하면 2번 줄의 B와 일치 | 별개의 등록을 확인한 결과. 기본 포트의 신원 근거로 옮겨 쓰지 않음 |
| 데이터베이스 접속 대상이 C를 제시 | 저장 이름이 해시여도 3번 줄의 C를 찾음 | 등록이 존재함. 이름만 문자 검색하면 놓칠 수 있음 |
| 새 접속 대상이 C를 제시 | 이 파일에서 찾지 못하며 마지막 명령의 종료 코드는 1 | 연결 전에 승인된 신원 근거를 확보. 서버 쪽 오류 여부는 별도 확인 |

모든 조회가 실패하면 현재 폴더와 `-f` 뒤의 파일 경로를 확인하세요. 2222만 실패한다면 대괄호, 포트, 따옴표가 그대로 있는지 봅니다. 지문이 다르면 같은 키 유형에 대해 SHA-256 출력 전체를 비교하세요. 이 파일에 결과가 없어도 운영 클라이언트에는 다른 신뢰 자료가 설정돼 있을 수 있습니다. Linux의 OpenSSH 10.0p2에서 이 자료를 검증했습니다. 실제 서버 연결, 키 교체, SSH CA 배포는 실행 검증 범위에 포함되지 않았습니다.

## 6. 확인 문제와 완료 기준

- **클라이언트가 키 변경 경고를 냈는데 서버에 사용자 인증 로그가 없습니다. 서로 모순되나요?** 호스트 검증에서 멈추면 사용자 인증이 시작되지 않을 수 있습니다. 클라이언트 출력과 전송 연결을 받은 실제 서버를 확인하세요.
- **같은 이름인데 2222 포트의 키로 기본 포트를 확인할 수 없는 이유는 무엇인가요?** 이 실습에서 두 접속 대상은 별도 이름으로 등록돼 있으며 다른 SSH 서비스일 수 있습니다. 정확한 대상의 등록을 확인하세요.
- **자산 목록에 승인된 새 키가 있는데도 경고가 계속 뜹니다. 무엇부터 확인하나요?** 전체 지문과 알고리즘, 호스트·포트·별칭, 변경 기간을 비교한 다음 클라이언트가 실제로 어느 known_hosts 자료를 사용하는지 확인하세요.

등록된 세 키를 찾고, 등록되지 않은 결과의 의미를 설명해 보세요. 마지막으로 정확한 접속 대상, 제시된 지문과 등록 지문, 독립적인 근거, 차단 유지 여부를 짧은 조사 기록으로 남기면 완료입니다.
