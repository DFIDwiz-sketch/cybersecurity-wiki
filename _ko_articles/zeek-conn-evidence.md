## 1. 연결 로그 한 줄은 무엇을 보여 주나요?

**Zeek**는 관측한 네트워크 트래픽을 구조화된 로그로 남기는 도구입니다. `conn.log` 한 줄에는 Zeek가 추적한 연결 또는 흐름이 요약됩니다. **흐름**은 두 통신 지점 사이에서 하나의 교환에 속하는 패킷을 묶어 부르는 말입니다. 한 연결에는 앱 메시지가 여러 개 들어갈 수 있습니다. 예를 들어 HTTP 로그에는 한 연결에서 오간 요청이 각각 기록될 수 있습니다.

**시작 방향**(`orig`, originator)과 **응답 방향**(`resp`, responder)은 Zeek가 흐름에 부여한 양쪽 방향입니다. 일반적인 TCP 연결에서는 처음 SYN을 보내는 쪽이 `orig`입니다. 통신 일부만 보이거나 `history`에 방향을 뒤집었다는 표시인 `^`가 있다면 방향을 다시 확인합니다. 이 필드만으로 내부 단말, 사용자, 통신을 일으킨 프로세스를 식별하기는 어렵습니다.

| 필드 | 읽을 수 있는 내용 | 이어서 확인할 내용 |
| --- | --- | --- |
| `ts` | 해당 흐름에서 Zeek가 처음 본 패킷의 유닉스 타임스탬프 | UTC로 바꾸고, 센서 시각·수집 시스템 도착 시각·검색 범위를 구분합니다. |
| `id.orig_h`, `id.orig_p`, `id.resp_h`, `id.resp_p`, `proto` | Zeek가 판단한 양쪽 주소와 포트, 전송 프로토콜 | NAT, 프록시, 포트 재사용이 있다면 관측 위치와 시각을 대조합니다. |
| `uid` | Zeek가 부여한 연결 식별자 | 같은 데이터셋에서 UID로 로그를 연결합니다. 통합 저장소에서는 수집 출처도 남깁니다. |
| `conn_state`, `history` | 연결 성립·종료의 요약과 방향별 주요 관측 | TCP인지 UDP인지 먼저 확인하고, 필요하면 패킷과 대조합니다. |
| `service`, `duration` | 확인된 프로토콜 정보와 Zeek가 측정한 지속 시간 | 포트는 서비스의 단서입니다. `service` 누락에는 여러 원인이 있고, TCP 지속 시간은 마지막의 일부 비생산적 패킷을 제외할 수 있습니다. |

## 2. 상태, 방향별 기록, 바이트를 함께 읽기

| 상태와 전송 프로토콜 | 센서에서 먼저 읽을 내용 | 다음 확인 대상 |
| --- | --- | --- |
| TCP `S0` | 연결 시도는 보였으나 답은 관측되지 않음 | 응답 경로 수집, 방화벽 결정, 서비스 리스너 |
| TCP `REJ` | 연결 시도가 거절됨 | `Sr`이면 시작 방향의 SYN과 응답 방향의 RST가 보였습니다. 어느 장비가 RST를 보냈는지 확인합니다. |
| TCP `SF` | Zeek가 정상 성립과 종료로 분류 | HTTP 상태, 앱 처리 결과 또는 인증 결과 |
| TCP `S1` | 연결 성립을 관측했으며 종료는 관측되지 않음 | 캡처 종료 시점, 로그 시간 제한, 양방향 수집 범위 |
| TCP `RSTO` / `RSTR` | 성립된 연결을 각각 시작 방향 / 응답 방향에서 리셋 | 패킷 순서와 단말·프록시·방화벽 로그 |
| TCP `OTH` | SYN 없이 중간부터 패킷이 관측됨 | 캡처 시작 시점, 비대칭 경로, 포트 미러 설정 |
| UDP `SF`와 `Dd` | 이 UDP 예제에서는 양방향 페이로드 관측 | DNS라면 질의별 결과 확인 |

대문자는 **시작 방향**, 소문자는 **응답 방향**입니다. `ShADadFf`에서 `S`는 처음 SYN, `h`는 상대의 SYN+ACK, `A`는 시작 방향에서 보낸 순수 ACK입니다. `D`와 `d`는 데이터, `F`와 `f`는 FIN을 뜻합니다. `r`은 응답 방향의 RST, `g`는 응답 방향의 데이터 누락입니다. 일부 기호는 방향별로 한 번만 기록됩니다. 누락과 재전송 같은 기호는 1회·10회 이상·100회 이상처럼 로그 단위의 문턱에서 추가됩니다. 정확한 패킷 수와 순서를 확인하려면 패킷 캡처를 펼쳐 보세요.

| 바이트 필드 | 단위와 의미 | 해석할 때 주의할 점 |
| --- | --- | --- |
| `orig_bytes` / `resp_bytes` | 각 방향의 전송 계층 페이로드 바이트. TCP에서는 시퀀스 번호를 바탕으로 집계합니다. | 일부만 보이거나 시퀀스 동작이 비정상적이면 추정이 달라집니다. HTTP 본문 크기나 앱의 수신 성공은 따로 확인합니다. |
| `orig_ip_bytes` / `resp_ip_bytes` | 연결 크기 분석기가 제공하는 IP 계층 바이트 합계 | 관측된 IP와 전송 헤더 길이도 포함합니다. 다른 센서 수치와 비교할 때는 패킷과 수집 범위를 먼저 맞춥니다. |
| `missed_bytes` | Zeek가 인식한 데이터 누락 바이트 | 양수라면 누락의 근거입니다. 0은 Zeek가 인식해 기록한 누락이 0이라는 뜻입니다. 캡처 밖 트래픽과 프레임 손실은 별도로 확인합니다. |

JSON에서 키가 빠져 있거나 `null`이면 로그 작성기와 수집 설정에 따라 빠진 값으로 읽습니다. Zeek의 TSV는 탭으로 열을 구분하며, 파일 위쪽의 `#unset_field`와 `#empty_field` 헤더가 미설정 값과 빈 값을 어떻게 표시하는지 알려 줍니다. 숫자 0은 실제로 기록된 값이므로 집계 전에 누락을 일괄적으로 0으로 바꾸지 마세요. 실습에 쓰이는 JSONL은 한 줄에 JSON 객체 하나가 들어가는 형식입니다.

## 3. 정상 연결 예시를 한 줄씩 따라가기

가상 자료의 `C03`은 `edge-a.capture-01`에서 02:00:02 UTC에 시작한 TCP 흐름입니다. `SF`와 `ShADadFf`가 기록되어 TCP가 성립하고 양방향으로 데이터를 주고받은 뒤 종료되었음을 읽을 수 있습니다. 페이로드는 시작·응답 방향 각각 100·250바이트이고 IP 계층에서는 340·450바이트입니다. IP 계층 집계에는 헤더 등 페이로드 외의 바이트도 들어갑니다.

같은 출처에서 UID가 일치하는 HTTP 기록의 응답은 `503`입니다. TCP는 정상적으로 끝났고 HTTP는 서비스 이용 불가를 알렸습니다. 요청 시각을 기준으로 서버나 프록시 로그를 확인합니다. 실습 데이터에는 `edge-b.capture-02`에도 일부러 같은 UID와 HTTP `200`을 넣었습니다. 다른 데이터셋의 기록이므로 같은 연결의 HTTP 응답으로 붙이면 잘못된 결론을 내립니다. 다른 제품의 기록을 연결해야 한다면 시간·주소·포트 등을 바탕으로 별도로 상관 분석하고 불확실성을 기록하세요.

`C04`는 UDP `SF`와 `Dd`를 보여 줍니다. 같은 출처와 UID에서 A와 AAAA 질의를 각각 찾을 수 있습니다. 둘 다 `NOERROR`이며 답변에는 각각 `203.0.113.44`, `2001:db8::44`가 있습니다. 결과 코드와 답변 목록은 구분해서 읽으세요. `NOERROR`인데 주소 답변이 비어 있을 수도 있습니다. 단말이 그 주소를 실제로 사용했는지는 이후 연결 기록을 확인해야 합니다.

## 4. 이상 관측에서 결론과 대응까지

여러 주소나 포트를 향해 `S0`가 반복되면 연결 대상 탐색 가능성을 검토할 수 있습니다. 승인된 자산 조사, 모니터링, 공통 장애, 응답 경로 수집 누락도 비슷한 모습으로 나타납니다. 반대로 정상 응답이 있더라도 승인 범위를 벗어난 통신일 수 있습니다. 각 판단에 어떤 증거가 필요한지 먼저 정하세요.

1. **수집 범위부터 보존합니다.** UTC 시간 범위, 캡처와 수집기 ID, Zeek 버전과 스크립트, 미러 위치, 손실 여부와 시계 오차를 기록합니다. 원본 로그 행과 필터를 남기고 수집 공백, 드롭, 지연, 최근 경로 변경을 확인합니다.
2. **같은 조건끼리 비교합니다.** TCP 상태별로 출발지와 목적 서비스, 일정한 시간 구간을 기준 삼아 묶습니다. 건수뿐 아니라 전체 흐름 중 비율도 함께 보고, 단말 역할과 시간대가 비슷한 기준선을 고릅니다. 센서 간 비교에서는 NAT, 시계 오차, 중복 수집을 확인합니다.
3. **다른 설명도 검증합니다.** 여러 단말이 한 서비스로 향할 때 동시에 `S0`가 늘었다면 장애, 필터링, 수집 상태를 확인합니다. 한 단말이 서로 무관한 목적지 여러 곳에 접속했다면 승인된 작업 일정, 단말의 프로세스와 소켓 연결, 방화벽 결정을 대조합니다.
4. **실제 요청을 확인합니다.** 같은 출처와 UID로 `dns.log` 또는 `http.log`를 연결하되 일치하는 행은 모두 남깁니다. 암호화, 프로토콜 미인식, 로깅 설정, 수집 실패로 앱 기록이 빠질 수 있습니다. 앱 계층이 안 보이면 서버나 프록시 로그를 찾습니다. 실제 통신 손실과 수집 누락은 [캡처 가시성 안내]({{ '/ko/wiki/capture-visibility/' | relative_url }})의 절차로 대조해 보세요.
5. **근거에 맞춰 대응합니다.** 서비스 전반의 장애가 의심되면 서비스 담당자에게 로그와 변경 이력을 요청합니다. 여러 독립된 신호가 승인되지 않은 활동을 뒷받침한다면 사고 대응 절차로 올립니다. 필요한 패킷 구간을 정책에 따라 보존하고 단말, 시간, 관측 행동, 남은 불확실성, 추가로 필요한 자료를 남깁니다.

## 5. 가상 기록으로 하는 자체 실습

[실습 기록]({{ '/assets/labs/zeek-conn-cases.jsonl' | relative_url }})과 [Python 확인 스크립트]({{ '/assets/labs/zeek-conn-review.py' | relative_url }})를 받아 같은 폴더에 저장하세요. Python 3이면 인터넷 연결 없이 실행할 수 있습니다. 스크립트는 파일만 읽고 네트워크 통신을 만들거나 서버에 접속하지 않습니다. `source`와 `stream`은 Zeek 스타일의 일부 필드를 감싼 실습용 정보입니다. 실제 로그로 연습하려면 승인 범위와 조직의 수집 절차를 먼저 확인하세요.

1. JSONL을 텍스트 편집기로 열고 `conn` 기록부터 읽습니다. 연결별 상태와, 방향 기록 또는 카운터로 설명할 수 있는 관측 한 가지를 적습니다.
2. 출처와 UID가 모두 맞는 HTTP·DNS 기록을 찾습니다. `C04`의 DNS 기록 두 줄을 모두 남기고, `C03`의 다른 HTTP 기록을 왜 제외했는지 설명합니다.
3. 두 파일이 함께 있는 폴더에서 스크립트를 실행합니다.

```bash
python3 zeek-conn-review.py
```

| 사례 | 기대 결과와 다음 질문 |
| --- | --- |
| `C01` | SYN은 보였으나 답은 관측되지 않았습니다. 상대가 SYN을 받았나요? 돌아오는 경로도 수집했나요? |
| `C02` | SYN과 응답 방향 RST가 보였습니다. 어느 장비가 리셋을 보냈나요? |
| `C03` | 정상 TCP 성립·종료, 페이로드 `100/250`, HTTP `503`입니다. 앱과 프록시 중 어디에서 오류를 반환했나요? |
| `C04` | UDP 양방향 데이터와 `NOERROR`인 DNS 기록 두 개입니다. 리졸버는 어떤 주소를 반환했나요? |
| `C05` | 중간부터 관측되었고 페이로드 필드는 빠져 있으며 인식한 누락 바이트는 0입니다. 캡처는 어디서 시작했나요? |
| `C06` | TCP는 성립했고 응답 방향 누락이 있으며 페이로드 필드는 빠져 있습니다. 센서에서만 빠졌나요, 실제 경로에서도 손실이 있었나요? |
| `C07` | 정상 TCP 성립·종료와 명시적인 `0/0` 페이로드입니다. 제어 패킷 중 무엇이 IP 계층 바이트에 포함되나요? |

마지막에 `7 synthetic flows checked.`가 표시됩니다. 파일을 못 찾으면 다운로드한 파일 이름과 저장 위치를 확인합니다. JSON 읽기 오류가 나면 브라우저가 JSONL 대신 HTML을 저장했는지 살펴봅니다. 수동 해석에서 `503`과 `200`이 같이 나오면 연결 기준에 출처를 추가합니다. DNS가 한 줄만 나온다면 같은 UID에 행을 하나만 남기는 조건을 제거하세요.

**검증 범위.** 번들에 있는 가상 자료로 Python 실습을 실행했습니다. Zeek 필드 동작은 9.0.1 공식 문서에서 검토했습니다. 실제 Zeek 구동과 패킷 관측은 이 실습의 범위 밖입니다.

## 6. 확인 문제와 해설

1. **미러 설정을 바꾼 뒤 일주일 동안 `S0`가 늘었습니다. 차단 증거인가요?** 연결 시도와 응답 미관측을 뒷받침합니다. 필터링으로 결론 내리기 전에 미러에 역방향 트래픽이 들어오는지, 서비스에서는 어떤 패킷이 보이는지 확인합니다.
2. **한 흐름에 `SF`와 HTTP `503`이 있습니다. 어느 계층에서 문제가 드러났나요?** 실습에서 TCP 성립과 종료는 정상이었으며 HTTP가 서비스 오류를 보고했습니다. 원인은 서버 또는 프록시 자료로 좁힙니다.
3. **UID가 같은 DNS 기록 두 줄 중 하나를 지워도 되나요?** 같은 출처의 별도 트랜잭션이라면 둘 다 남깁니다. 중복 여부는 시각, 질의 이름과 유형, 트랜잭션 ID를 대조해 판단합니다.
4. **왜 `C07`은 0으로 저장하고 `C06`은 비워 두나요?** 앞의 사례는 숫자 0이 있고, 뒤의 사례는 페이로드 수치가 비어 있는 데다 누락 증거가 있습니다. 동일하게 저장하면 트래픽 규모를 잘못 집계할 수 있습니다.

**완료 기준.** 일곱 사례를 설명하고, 같은 출처의 HTTP 응답과 DNS 기록 두 줄을 올바르게 찾습니다. 관측 범위가 불완전한 흐름 하나를 골라 실제로 읽은 값, 가능한 다른 설명, 다음 확인에 필요한 자료를 하나씩 적습니다.
