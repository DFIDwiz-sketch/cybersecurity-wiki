**학습 목표.** “알림이 안 왔다”는 결과를 행위 발생, 로그 수집, 규칙 평가, 알림 전달로 나눠 조사합니다. 승인된 시험에서 기대 결과를 미리 정하고, 어떤 증거로 각 단계를 통과했다고 판단할지 기록합니다.

## 1. 탐지 가설부터 작성하세요

탐지 규칙은 관측 가능한 데이터를 조건과 비교합니다. 예를 들어 “시험 인덱스에서 특정 교육용 표식이 기록되면 테스트 알림을 보낸다”는 규칙은 결과를 분명하게 재현할 수 있습니다. 운영 규칙이라면 관측하려는 행위, 필요한 소스와 필드, 시간 창, 예외, 담당자 조치를 먼저 정하세요. 단순히 의심 주소나 User-Agent 하나가 보였다는 이유로 행위자나 침해를 확정할 수 없습니다.

**탐지 가설 예시.** 승인된 호스트가 남긴 표식이 수집돼 검색 가능한 상태로 들어왔다면 테스트 규칙이 한 번 일치하고, 그 결과가 시험 알림함에 도착합니다. 이 가설의 범위는 지정된 입력·필드·시간대·알림함입니다.

![원본 이벤트 생성 → 수집 및 필드 추출 → 시간 창과 규칙 일치 → 억제와 경보 생성 → 시험 수신처로 전달]({{ '/assets/diagrams/detection-validation-ko.svg' | relative_url }})

## 2. 단계별로 남겨야 할 증거

| 단계 | 먼저 물을 질문 | 남길 증거 |
| --- | --- | --- |
| 원본 생성 | 호스트나 센서에 이벤트가 생겼나? | 원본 시각·호스트·이벤트 ID·기록 |
| 수집·색인 | 검색할 위치까지 들어왔나? | 수집원·인덱스·도착 시각 |
| 필드 추출 | 규칙이 읽는 값이 생겼나? | 원본과 파싱된 필드, 매핑 버전 |
| 규칙 실행 | 해당 이벤트가 실행 시간 창 안에 있었나? | 실행 기록·시간 범위·조건 결과 |
| 경보 생성 | 일치 결과로 경보가 생겼나? | 경보 ID, 억제·중복 제거 정보 |
| 전달과 대응 | 담당자가 보는 곳에 도착했나? | 알림 작업 결과·테스트 수신 기록 |

예를 들어 08분 이벤트가 11분에 색인되면 10분에 실행된 검색에는 아직 없었습니다. 15분 검색이 10–15분 사건만 보면 그 이벤트는 다음에도 빠질 수 있습니다. 의도한 시간 창과 관측된 도착 지연을 함께 확인하세요. 시간 창을 겹치게 설정한다면 동일 사건이 여러 번 처리될 수 있으므로 중복 제거 기준도 검증합니다. 실제 예약·재실행·억제 동작은 제품과 설정에 따라 달라집니다.

## 3. 양성·음성·실패 대조를 준비하세요

| 대조 | 가상 입력 | 기대 결과 |
| --- | --- | --- |
| 양성 | 교육용 표식, 올바른 필드와 시간 | 규칙 일치 후 지정 알림 전달 |
| 음성 | 정상 표식, 같은 경로와 시간 | 원본과 색인은 확인되고 규칙에는 불일치 |
| 시간 경계 | 시작·끝 시각 또는 늦게 도착한 이벤트 | 문서화한 시간 정책대로 포함·제외 |
| 실패 | 소스·필드·전달 중 한 단계의 결손 | 처음 끊긴 단계에 맞는 설명과 수정 |
| 중복·억제 | 반복 일치와 승인된 억제 조건 | 일치 건수와 전달 건수가 정책대로 다름 |

음성 시험은 원본과 수집 성공을 확인해야 의미가 있습니다. 아무것도 수집되지 않았다면 규칙이 정상 트래픽을 제외했는지 판단할 수 없습니다. 양성이 한 번 통과해도 다른 OS·버전·사용자·네트워크에서 동일하다는 보장은 없습니다. 시험 버전과 범위를 기록하세요.

ATT&CK는 관측하려는 행위와 탐지 전략을 정리하는 데 도움이 됩니다. 태그를 붙인 뒤에는 실제 센서·필드·분석 조건을 각 환경에서 확인합니다. Sigma 규칙의 logsource와 detection은 데이터와 조건을 설명합니다. 백엔드 변환 후 필드 이름·대소문자·조건 의미가 유지되는지 별도로 확인하세요.

## 4. 알림이 안 오면 앞 단계부터 재현하세요

1. 승인된 시험 ID, 시간대, 기대 결과, 규칙과 파서 버전을 기록합니다.
2. 원본 호스트에서 동일 ID의 기록을 찾습니다. 없다면 이벤트 생성과 감사 설정을 확인합니다.
3. 원본이 있으면 수집기에 도착했는지, 올바른 인덱스·소스·시각에 배정됐는지 확인합니다.
4. 중앙에 들어온 원문과 파싱 결과를 비교합니다. 직접 조회에서 보이는 이벤트가 예약 검색 당시에도 색인됐는지 실행 내역을 확인합니다.
5. 규칙이 일치했으면 억제 상태와 알림 작업 결과를 검사합니다. 시험 수신함까지 도착했는지 확인합니다.
6. 조치한 단계와 근거를 기록하고 양성·음성 대조를 다시 실행합니다. 운영 규칙을 넓히거나 예외를 추가할 때는 오탐과 누락의 영향을 함께 검토합니다.

승인된 Linux 시험 호스트에서는 로컬 로깅에 표식 한 건을 남길 수 있습니다. 다음은 util-linux logger 예제입니다. 이 명령은 로컬 로깅 경로로 메시지를 보내며, 중앙 수집과 필드 추출은 별도의 설정이 필요합니다. 기존 운영 알림이 연결돼 있으면 시험 수신처가 지정된 환경에서만 실행하세요.

~~~bash
logger -t wiki-test -- 'wiki-canary validation_id=LAB-01'
~~~

제품에서 확인할 때는 원문에 LAB-01이 있는지 먼저 확인하고, 파싱 규칙이 표식을 별도 필드로 추출했는지 봅니다. 가상 분석기가 이 명령이나 실제 SIEM 연결을 수행하지는 않습니다.

## 5. 오프라인 실습 · 가상 사례 9건

[detection-validation.json]({{ '/assets/labs/detection-validation.json' | relative_url }}) · [detection-validation.py]({{ '/assets/labs/detection-validation.py' | relative_url }})

두 파일을 한 폴더에 넣고 Python 3에서 실행하세요. 시간은 가상 시작점부터의 분입니다. 규칙은 10분에 한 번 실행해 사건 시각 **5분 이상, 10분 미만**을 읽습니다. 이 모델에서 suppressed는 일치 후 억제, notification은 시험 알림 도착 여부입니다.

~~~bash
python3 detection-validation.py
~~~

| 사례 | 확인할 결과 |
| --- | --- |
| lab-01 / lab-02 | 양성은 전달, 정상 음성은 불일치 |
| lab-03 / lab-04 | 원본 미생성 / 원본은 있으나 색인 누락 |
| lab-05 | 색인은 됐지만 필드 누락 |
| lab-06 / lab-09 | 실행 뒤 늦게 도착 / 사건 시간 창 밖 |
| lab-07 / lab-08 | 억제 설정이 적용됨 / 일치했으나 알림 미도착 |

마지막에 `PASS: nine detection pipeline cases`가 나오면 기대 분류와 일치합니다. 파일 오류는 이름과 위치부터 확인하세요. 결과가 다르면 실행 분, 사건 시각, 색인 시각, 필드와 억제를 차례로 점검합니다. 게시 과정에서 가상 분석기를 실행 검증했습니다. 실제 로그 생성·색인·알림 전달은 해당 환경에서 별도로 검증합니다.

## 6. 확인 문제와 완료 기준

- **조회 화면에는 이벤트가 있는데 알림이 없었나요?** 예약 검색이 실행된 시각과 당시 색인 상태, 시간 창, 파싱값, 억제와 전달 결과를 확인합니다.
- **정상 대조에서 알림이 없으면 통과인가요?** 원본과 색인까지 확인하고 규칙 불일치를 입증해야 합니다.
- **일치했는데 알림이 없으면 규칙을 바꾸나요?** 억제·전달 상태부터 확인합니다. 규칙이 바뀌면 중복·오탐·누락에 대한 대조를 다시 실행합니다.

가상 사례 3건을 골라 첫 실패 단계와 증거를 각각 한 줄로 적으세요. 운영에 적용할 때는 생성부터 전달까지 같은 시험 ID로 추적하고 적용 버전과 범위를 남깁니다.
