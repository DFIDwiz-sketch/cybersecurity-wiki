14:22 UTC의 DNS 서버 로그에 IPv6 출발지 주소가 보입니다. DHCPv6 기록에는 그 주소와 라우터의 프리픽스 요청이 함께 들어 있습니다. 어느 단말이 그 주소를 사용했는지 알 수 있을까요? DHCPv6 바인딩으로는 어느 범위에서 언제 서버가 무엇을 할당했는지 확인할 수 있습니다. 실제 사용 단말을 알아내려면 별도의 증거가 필요합니다.

## 1. 설정 방식과 식별자를 따로 읽기

DHCPv6는 IPv6 주소, 위임 프리픽스 또는 DNS 리졸버 같은 설정을 제공할 수 있습니다. 클라이언트는 여러 설정 방식을 함께 쓸 수 있습니다. 일반 IPv6 호스트의 기본 경로는 Router Advertisement(RA)나 호스트의 명시적 설정에서 확인하세요. 자동 주소 설정인 SLAAC는 DHCPv6와 함께 쓰일 수 있고, 임시 주소를 비롯한 추가 주소를 만들 수도 있습니다.

| 필드 또는 교환 | 의미 | 대조할 범위 |
| --- | --- | --- |
| 클라이언트·서버 **DUID** | 해당 장비의 DHCP 식별자. 각 식별자 옵션에 포함되는 경우 확인할 수 있습니다. | 전체 값을 보존하세요. 유형에 따라 링크 계층 주소가 들어 있지만, 현재 인터페이스의 MAC이나 사람의 신원이라고 볼 수는 없습니다. |
| **IAID** | 할당 묶음인 Identity Association을 구분하도록 클라이언트가 정한 식별자 | 클라이언트 DUID와 **IA 유형**을 함께 비교하세요. 한 클라이언트의 IA_NA와 IA_PD에 숫자가 같은 IAID가 있을 수 있습니다. |
| **IA_NA** | 비임시 주소의 할당 묶음. 내부 IA Address 옵션으로 주소와 수명을 전달할 수 있습니다. | 전체 IPv6 주소와 링크 범위, 시각을 대조합니다. 비임시 주소에도 수명이 있습니다. |
| **IA_PD** | 프리픽스 위임을 위한 할당 묶음. 요청 라우터는 위임받은 주소 공간을 하위 네트워크에 사용할 수 있습니다. | 프리픽스 길이와 요청 라우터의 범위를 남깁니다. 주소가 프리픽스에 포함돼도 어느 하위 단말이 썼는지는 별도로 확인합니다. |
| **Information-request / Reply** | 해당 교환에서 주소나 프리픽스를 할당하지 않고 설정을 제공하는 방식 | 요청과 응답을 연결하고 호스트에 적용된 설정을 확인합니다. 이 교환에서는 주소 바인딩을 기대하지 않습니다. |

## 2. 릴레이를 거친 정상 임대 따라가기

1. 실습 네트워크의 클라이언트가 **Solicit**을 보냅니다. 서버는 할당 가능성을 알리는 **Advertise**로 응답할 수 있습니다. 클라이언트가 서버를 선택해 **Request**를 보내면 서버가 **Reply**를 보냅니다. 양쪽에서 Rapid Commit을 지원하고 사용하는 경우에는 Rapid Commit 옵션을 담은 Solicit과 Reply 두 메시지로 진행합니다. Advertise만 관측했다면 아직 확정된 임대로 볼 수 없습니다.
2. 릴레이는 클라이언트 메시지를 **Relay-forward**에 넣고, 돌아온 **Relay-reply**에서 내부 응답을 꺼내 전달할 수 있습니다. 서버 쪽 캡처에서는 내부 메시지의 트랜잭션 ID와 클라이언트·서버 식별자를 확인하세요. 링크 범위는 릴레이 체인과 `link-address`, 제공되는 경우 Interface-Id 또는 검증한 회선 매핑으로 파악합니다. 여러 릴레이에 중첩되거나 `link-address`가 0이면 릴레이 맥락을 봐야 합니다. 바깥 IPv6 출발지와 릴레이의 peer 주소는 의미가 다릅니다.
3. 성공 Reply에는 IA_NA와 IA_PD가 함께 있을 수 있습니다. 해당 수준의 상태 코드를 살펴보고 각 할당 묶음의 실제 주소나 프리픽스, 수명을 확인하세요. Reply는 오류를 알리거나 설정만 제공하거나 반환 요청에 응답할 때도 쓰입니다. 할당 여부는 서버에서 임대가 확정된 기록으로 뒷받침하세요.
4. **T1**과 **T2**는 할당 묶음의 갱신과 재바인딩 타이머입니다. 선호 수명과 유효 수명은 각 주소 또는 프리픽스에 적용됩니다. T1에서 클라이언트는 할당 서버에 갱신을 시도합니다. T2가 지나면 사용 가능한 서버에 재바인딩을 시도할 수 있습니다. 주소의 선호 수명이 끝나면 해당 주소는 비선호 상태가 되며, 유효 수명이 남아 있는 동안은 기존 통신 등에서 계속 사용할 수 있습니다. 유효 수명이 끝나면 프로토콜상 그 할당을 사용해서는 안 됩니다.

**가상 예시.** 14:00 UTC에 서버가 `training-a` 링크에서 IA_NA의 IAID가 7인 클라이언트에 `2001:db8:10::25`를 할당합니다. 클라이언트가 받은 선호 수명은 1,200초, 유효 수명은 1,800초입니다. 갱신이나 조기 반환이 없다면 이 예에서는 14:20 UTC에 비선호 상태가 되고, 14:30 UTC에 유효 기간이 끝납니다. 14:22 UTC의 흐름은 서버의 임대 기록과 시간상 일치합니다. 실제 단말과 주소 사용은 독립적인 호스트나 네트워크 경계 증거로 확인하세요. `2001:db8:2200::/56` 같은 위임 프리픽스는 별도 바인딩입니다. 같은 라우터가 위임에도 IAID 7을 사용해도 주소 할당으로 합쳐서는 안 됩니다.

## 3. 범위를 지정할 수 있도록 증거 수집하기

| 출처 | 확보할 수 있는 경우 수집할 항목 | 확인 가능한 내용 |
| --- | --- | --- |
| DHCP 서버 또는 임대 이력 | 서버 식별자와 범위, DUID, IA 유형, IAID, 확정된 주소 또는 프리픽스, 유효 구간, 갱신·반환·만료·재할당 | 주소나 프리픽스와 시각을 어느 임대가 포함하는지 확인합니다. 현재 목록에는 이전 상태가 빠질 수 있습니다. |
| 패킷 캡처 또는 릴레이 기록 | 해당 링크나 승인된 릴레이·서버 관측 지점에서 방향, 내부 메시지 유형과 트랜잭션 ID, 식별자, 상태, 릴레이 맥락 | 어느 교환이 어디에서 관측됐는지 확인합니다. 트랜잭션 ID는 해당 교환의 값이므로 장기 식별자로 쓰기 어렵습니다. |
| 호스트와 접속 네트워크 | 인터페이스 주소, 경로와 리졸버, 접속 포트나 단말 세션, 스위치·라우터의 이웃 정보와 UTC 시각 | 어느 단말이 주소를 썼고 어떤 설정이 적용됐는지 좁힙니다. 이웃 및 흐름 기록은 오래됐거나 해당 관측 지점에 국한될 수 있습니다. |

RFC 9915에서 클라이언트로 전달할 때 UDP 목적지 포트는 546이고, 서버나 릴레이로 전달할 때는 일반적으로 547입니다. 출발지 포트는 권고이며, 릴레이 확장에 따라 달라질 수 있습니다. 문서화된 배포 구성으로 캡처 범위를 정하고, 승인된 관측으로 직접 연결과 릴레이 경로를 모두 확인하세요. 관측 지점 하나에서 패킷이 보이지 않았다는 사실만으로 해당 교환을 배제하기 어렵습니다.

원래 관측 시각과 IPv6 출발지, 사이트, 라우팅·링크 맥락부터 확인합니다. 유효한 IA_NA 이력에서 정확히 같은 주소를 찾으세요. 라우팅 맥락이 뒷받침되면 위임 프리픽스에도 속하는지 따로 확인하고 요청 라우터의 바인딩을 기록합니다. 주소가 재사용됐을 때는 최신 상태 대신 당시 이력을 봅니다. 시계 동기화 상태를 확인하고 기록이 겹치거나 충돌하면 다른 근거가 나올 때까지 미확정으로 둡니다. 일치하는 임대가 없다면 이상으로 판단하기 전에 SLAAC, 고정 설정, 로깅 범위, 실제 릴레이 경로를 확인하세요.

예상 밖의 서버나 릴레이가 응답하면 잘못된 주소나 리졸버 설정이 제공될 수 있습니다. 설정 오류나 승인된 장애 조치에서도 새 응답자가 나타날 수 있습니다. 승인된 서버·릴레이 목록을 대조하고 단말이 그 설정을 실제로 적용했는지 확인하세요. 관련이 없어 보이는 포트에서 DUID가 반복되는 상황은 조사 단서이며, 이미지 복제나 오래된 기록으로도 설명될 수 있습니다. 원본 관측과 영향을 받은 설정을 보존하고 네트워크 운영팀과 함께 무단 서비스를 차단하고 승인된 설정을 복구합니다. 지원되는 환경에서는 승인된 서버·릴레이 구성을 바탕으로 DHCPv6-Shield를 검토하세요. 이 통제는 승인되지 않은 DHCPv6 서버 트래픽을 다루며, RA 통제는 별도로 확인합니다.

ISC Kea 3.2.1의 선택 기능인 Legal Logging 훅을 사용하면 DHCPv6 임대 활동을 기록할 수 있습니다. 활성화된 경우 주소 또는 프리픽스, 지속 시간, DUID, 확보 가능한 릴레이 정보가 기록될 수 있습니다. 실제 훅과 서브넷 설정, 보존 기간, 시간 형식을 확인하세요. 기본 로그 형식이 IAID를 항상 제공한다고 가정하지 말고, 필요하면 임대 메타데이터나 패킷을 함께 대조합니다.

## 5. 확인 문제와 해설

1. **Reply에 DNS 리졸버만 있고 주소가 없습니다. 할당이 실패했나요?** Reply가 어느 요청에 대한 응답인지 확인하세요. Information-request는 설정을 요청하며 주소 바인딩을 요청하지 않습니다.
2. **주소가 고객의 위임 프리픽스에 포함됩니다. 어느 장비가 사용했나요?** 프리픽스 바인딩과 가능한 라우팅 범위까지 확인할 수 있습니다. 하위 주소 설정이나 호스트·접속 네트워크 증거로 단말을 확인하세요.
3. **같은 주소가 서로 다른 시각의 두 임대 기록에 나옵니다. 어느 기록이 관련 있나요?** 관측 시각과 당시 유효 구간, 링크 범위를 비교한 뒤 조기 반환, 갱신, 시계 오차, 독립적인 증거를 확인하세요.

**완료 기준.** 여덟 사례와 범위 불일치 검사를 재현하세요. 서버의 할당, 관측된 주소 사용, 아직 확인하지 못한 단말 신원을 각각 한 줄로 적습니다.
