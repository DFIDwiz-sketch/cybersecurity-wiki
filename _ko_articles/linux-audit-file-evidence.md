**학습 목표.** 여러 호스트의 감사 로그가 섞여 있어도 어느 호스트의 어떤 동작인지, 어떤 로그인 신원과 프로세스가 기록됐는지 찾아낼 수 있습니다. 그리고 남은 증거의 빈틈을 설명할 수 있습니다. 소유자, 그룹, 접근 권한 비트가 낯설다면 [Linux 파일 권한]({{ '/ko/wiki/linux-file-permissions-evidence/' | relative_url }})부터 읽어 보세요.

## 1. Linux Audit 로그가 왜 필요한가요?

파일 권한은 접근 제어 정책 아래에서 누가 어떤 동작을 할 수 있는지 보여 줍니다. 감사 이벤트에는 특정 시점에 감사 조건에 해당했던 동작이 남습니다. 서비스 설정 파일이 바뀌었다면 두 관점이 모두 필요합니다. 권한 정보로 접근이 가능했던 이유를 살펴보고, 감사 이벤트로 어떤 프로세스가 접근을 시도했는지, 커널에서 어떤 결과가 돌아왔는지, 어떤 파일이 관련됐는지 확인합니다.

**시스템 호출**은 파일 열기처럼 프로그램이 커널에 어떤 처리를 요청하는 통로입니다. 커널의 **Linux Audit** 서브시스템은 설정과 규칙에 따라 레코드를 만듭니다. 사용자 공간의 데몬 **auditd**는 레코드를 받아 디스크에 기록할 수 있습니다. 별도의 수집기는 이를 전달하거나 형식을 변환합니다. **레코드**는 이벤트를 구성하는 개별 기록입니다. 같은 이벤트 식별자가 붙은 여러 레코드가 한 동작을 설명할 수 있습니다. `training_config` 같은 **규칙 키**는 규칙을 정리하고 검색하기 위해 운영자가 붙이는 이름입니다.

## 2. 흩어진 로그를 이벤트로 묶는 순서

1. 원본 호스트를 확인합니다. 여러 호스트의 로그를 모을 때는 수집기가 인증한 출처와, 있다면 부팅 ID나 동등한 실행 맥락을 보존합니다. 실습에서는 `node=`가 출처를 나타냅니다. 실제 조사에서는 이 값과 수집기의 출처 정보가 일치하는지 확인하세요.
2. 같은 출처와 실행 맥락 안에서 `msg=audit(초.소수점이하:일련번호)` 전체가 같은 레코드를 묶습니다. 일련번호만으로는 여러 호스트를 구별할 수 없습니다. 여러 이벤트의 줄이 섞여 도착할 수 있어 바로 다음 줄이 같은 이벤트라는 보장도 없습니다.
3. **SYSCALL**에서 동작과 결과를 읽습니다. 숫자만 보고 호출 이름을 정하지 말고 아키텍처부터 확인하세요. `items`가 예고한 개수에 맞춰 **PATH**의 `item`이 0부터 빠짐없이 있는지 확인합니다. **CWD**는 작업 디렉터리를 알려 줍니다. 실제 로그에는 명령줄을 16진수로 담을 수 있는 **PROCTITLE** 등 다른 유형도 있을 수 있습니다.
4. 경로별 역할, 신원, 실행 맥락을 함께 해석합니다. `openat`의 상대 경로는 디렉터리 인자가 `AT_FDCWD`일 때 호출자의 작업 디렉터리를 기준으로 합니다. 다른 디렉터리 파일 디스크립터가 기준일 수도 있습니다. 네임스페이스와 심볼릭 링크도 보이는 경로에 영향을 줍니다. 원래 값을 보존하고 추론해서 만든 경로는 구분해 기록하세요.

| 필드 | 알 수 있는 것 | 해석할 때 주의할 점 |
| --- | --- | --- |
| `arch`, `syscall`, `success`, `exit` | 어떤 시스템 호출이 실행됐고 어떤 값을 돌려줬나요? | 호출 번호는 ABI(프로그램과 커널의 호출 규약)에 따라, 반환값은 해당 호출의 의미에 따라 해석합니다 |
| `auid`, `ses` | 프로세스에 기록된 로그인 신원과 감사 세션은 무엇인가요? | 로그인 맥락이 설정되지 않았을 수 있습니다. 특정 사람의 행동으로 판단하기 전에 세션을 확인합니다 |
| `uid`, `euid`, `pid`, `exe` | 프로세스의 실제·유효 사용자 ID와 실행 파일은 무엇인가요? | 유효 사용자 ID만으로 파일시스템 UID, 커널 권한(capability), 네임스페이스, 강제 접근 제어를 알 수 없습니다. PID는 재사용됩니다 |
| `items`, `PATH.item`, `name`, `nametype` | 경로 레코드가 몇 개여야 하고 각각 어떤 역할인가요? | 경로 하나만 보면 이름 변경의 반대편을 놓칠 수 있습니다. 경로만으로 성공 여부를 판단할 수 없습니다 |
| `dev`, `inode`, `cwd` | 어떤 파일 객체와 경로 맥락이 기록됐나요? | 장치·inode를 호스트·시각과 함께 봅니다. 파일 교체, inode 재사용, 마운트 네임스페이스를 고려합니다 |

## 3. 정상 파일 열기 한 건을 처음부터 읽기

내려받을 실습 파일의 **가상 사례**입니다. x86-64 ABI에서 `arch=c000003e syscall=257`은 `openat`입니다. 2026-11-21 04:00:00.110 UTC에 `lab-a`는 식별자가 `:40`으로 끝나는 레코드를 남겼습니다. SYSCALL에는 `a0=ffffff9c`(디렉터리 인자 `AT_FDCWD`의 32비트 표현), `a2=1`(이 사례의 쓰기 전용 열기 플래그), `success=yes exit=3`, `items=1`이 있습니다. PATH의 `item=0`은 `report.conf`, CWD는 `/srv/training`입니다. 이 파일을 쓰기 모드로 여는 데 성공한 것으로 해석할 수 있습니다. 반환값 3은 프로세스가 이후 파일 작업에 쓸 수 있는 핸들인 **파일 디스크립터**입니다.

`auid=1001`과 `euid=0`은 로그인 세션 `ses=7`에서 권한을 높인 유지보수 프로세스와 일치하는 단서입니다. 어떤 방식으로 권한을 얻었는지는 로그인·sudo·서비스 기록과 승인된 변경 내역을 연결해 확인합니다. 파일 내용 변경은 별도로 확인해야 합니다. 예를 들어 기준본과 보존한 해시나 차이를 비교할 수 있습니다. 이 사례에서 사용한 플래그로 파일을 열었다는 기록만으로 이후 바이트를 썼는지 알 수 없습니다.

같은 시각과 일련번호에 `lab-b`는 같은 이름의 파일을 열려다 `success=no exit=-13`(`EACCES`)을 기록했습니다. 다른 호스트에서 일어난 별도의 접근 거부입니다. 반환값만으로 파일 자체 권한, 상위 디렉터리 권한, 강제 접근 제어 중 어느 쪽에서 막혔는지 알 수 없습니다. 당시 권한 상태와 원본 호스트의 이벤트 맥락을 확인하고 SELinux 환경이면 관련 AVC 레코드도 찾아보세요.

## 4. 예상 밖 접근과 수집 누락 조사하기

권한 높은 프로세스가 예상치 못한 설정 변경을 시도할 수 있지만, 정상 배포나 유지보수도 같은 방식으로 파일을 엽니다. 서비스, 경로, 주체, 실행 파일, 승인된 변경 시각이 맞는지 확인하세요. 서비스에서 시작한 작업은 `auid=4294967295`(부호 없는 원시 값으로 표시된 미설정 상태)를 남길 수 있습니다. 서비스 유닛, 상위 프로세스, 배포 이력을 살펴보세요. 미설정 값 하나만으로 익명이나 악성 활동을 확정할 수 없습니다. 편집기나 배포 도구는 임시 파일에 쓴 뒤 이름을 바꿔 대상을 교체하기도 합니다. 열기 호출 하나나 최종 파일명만 수집하면 필요한 동작이 빠질 수 있으므로 실제 프로그램 동작과 규칙 범위를 함께 검증하세요.

| 관측 | 다음에 수집할 증거 | 가능한 판단과 대응 |
| --- | --- | --- |
| 예상 밖의 권한 높은 열기 | 감사 세션과 로그인·sudo 기록, 상위 프로세스, 승인된 배포 시각, 기준본과 현재 파일 상태 | 정상 유지보수인지 설명되지 않는 동작인지 구분. 다른 증거도 일치하면 원본을 보존하고 다른 파일과 호스트의 영향 범위를 조사 |
| 접근 거부 | 같은 이벤트의 레코드, 서비스 맥락, 접근 정책, 주체·대상별 반복 여부 | 지속적인 정책 문제인지 드물게 발생하는 예상된 거부인지 판단. 오용 여부는 독립 증거로 검증 |
| SYSCALL은 `items=1`인데 PATH 없음 | 원본과 회전된 로컬 로그, 수집기의 파싱·전달 상태, 필터와 중복 제거 | 호출 자체 결과는 알아도 어떤 파일인지 확정하기 어려움 |
| 로컬·중앙 모두 결과 없음 | 규칙 버전과 키, ABI, 네임스페이스, 시간 범위, 커널 상태, auditd 디스크 설정, 수집기 상태 | 그 동작이 원래 관측될 조건이었는지 확인. 검색 결과 0건만으로 실제 동작을 배제할 수 없음 |

아래는 커널 감사와 필요한 도구가 설치된 승인된 Linux 호스트에서 사용하는 **조회 전용** 명령입니다. 커널 Audit 상태를 조회할 수 있는 승인된 관리자 세션에서 처음 두 명령을 실행하고, 호스트·부팅 맥락·시각과 함께 결과를 기록합니다. 원시 로그 사본은 읽기 권한만 있는 별도의 분석 머신에서도 조사할 수 있습니다.

```sh
sudo auditctl -s
sudo auditctl -l
ausearch --input ./audit-export.log --key training_config --raw
```

마지막 명령은 실제 원시 로그 사본에 지정한 규칙 키가 들어 있을 때의 예입니다. 배포한 규칙 키로 바꾸고 관련 보존 구간을 모두 찾아 제한 사항을 기록합니다. 증거 사본에서는 숫자 ID를 보존하세요. 보강 정보가 없는 로그를 `--interpret`로 읽으면 분석 머신의 계정 정보로 이름을 해석할 수 있습니다. 현재 상태만으로 사건 당시 설정을 알 수 없습니다. 같은 부팅과 카운터 초기화 구간에서 `lost`가 증가했다면 그 사이 커널이 레코드를 버린 것입니다. `backlog`는 현재 대기 중인 레코드 수입니다. 디스크나 전달 과정의 손실은 별도로 확인하세요. 수치가 그대로여도 전체 수집 범위를 보장하지 않습니다.

지속적으로 수집 상태를 검증할 때는 현재 로드된 규칙과 부팅 시 로드하도록 준비된 파일을 따로 확인합니다. 규칙 순서와 제외 조건, 관련 ABI, 경로·디렉터리 범위, 파일시스템과 마운트 경계를 점검하세요. upstream `auditctl` 매뉴얼은 과거 예제의 `-w` 감시 구문 사용 중단을 권고하고 시스템 호출 형태의 규칙을 안내합니다. 본인 소유 또는 명시적 승인 환경에서 운영자가 승인한 좁은 범위의 규칙을 쓰고, 일회용 파일을 대상으로 예상된 허용·거부·범위 밖 동작을 대조하세요. 탐지에 의존하기 전에 로컬과 중앙에 의도한 레코드가 도착하는지 확인합니다. 이 장의 실습은 호스트 규칙을 로드하거나 변경하지 않습니다.

## 5. 오프라인 실습 · 로그 열 줄에서 이벤트 다섯 건 찾기

<a href="{{ '/assets/labs/linux-audit-file-sample.log' | relative_url }}" download="linux-audit-file-sample.log">가상 감사 로그</a>와 <a href="{{ '/assets/labs/linux-audit-file-review.py' | relative_url }}" download="linux-audit-file-review.py">Python 분석 스크립트</a>를 같은 디렉터리에 저장하세요. Python 3.10 이상과 표준 라이브러리만 사용합니다. 스크립트는 실습 파일을 읽고 터미널에 결과를 출력합니다. 관리자 권한, 인터넷, auditd, 예시 경로에 대한 접근 권한은 필요하지 않습니다. 실습의 단순한 필드를 읽는 도구로, 임의의 감사 로그 인코딩이나 여러 줄에 걸친 레코드까지 처리하지는 않습니다.

먼저 일련번호만 보고 묶으면 어디서 모순되는지 찾아보세요. 스크립트는 호스트와 전체 감사 이벤트 식별자 기준으로 묶고, PATH의 번호가 맞는지와 예상 결과가 나오는지 검사합니다.

```sh
python3 linux-audit-file-review.py linux-audit-file-sample.log --check
```

| 이벤트 | 예상 출력 | 근거 |
| --- | --- | --- |
| `lab-a:40` | `open-succeeded` · auid 1001, euid 0 | 상대 경로에 CWD 정보가 있고, 호출이 파일 디스크립터 3을 반환 |
| `lab-b:40` | `open-denied` · auid 1002, euid 1002 | 앞 이벤트와 시간·번호는 같지만 출처와 결과가 다름 |
| `lab-a:41` | `open-succeeded` · auid 미설정, euid 998 | 읽기 전용 열기가 파일 디스크립터 4를 반환. 로그인 ID는 미설정 |
| `lab-a:42` | `path-incomplete` | 호출은 성공했으나 있어야 할 경로 레코드가 빠짐 |
| `lab-b:43` | `syscall-unavailable` | 경로만 남고 이를 뒷받침할 SYSCALL이 없음 |

**실행 기록과 실패 점검.** 2026-11-21에 Python 3.12.14로 실행해 `5/5 event outcomes matched.`를 확인했습니다. 입력 로그는 가상입니다. 운영 명령과 수집 동작은 공식 문서로 확인했습니다. 파일을 찾을 수 없으면 두 파일명이 다운로드 과정에서 바뀌지 않았는지 살피고 같은 디렉터리에서 실행하세요. 로그를 수정해 볼 때는 `--check` 없이 바뀐 출력을 확인하고, 표의 결과를 재현할 때는 원본 파일을 사용합니다. 레코드를 비교할 때 출처와 감사 이벤트 식별자의 두 부분을 보존하세요.

## 6. 확인 문제와 완료 기준

1. **시간과 일련번호가 같은 두 레코드는 바로 합쳐도 될까요?** 같은 출처와 실행 맥락일 때만 합칩니다. 실습에서 호스트를 빼고 묶으면 성공과 거부가 한 이벤트에 섞입니다.
2. **`euid=0`, `auid=1001`이면 특정 관리자가 파일을 바꿨다는 뜻인가요?** 유효 ID가 0이고 기록된 로그인 신원이 1001이라는 뜻입니다. 세션과 권한을 얻은 경로를 확인하고, 실제 변경은 파일 상태로 뒷받침해야 합니다.
3. **`lab-a:42`의 대상이 `lab-a:40`과 같을 수 있나요?** 가능하지만 남은 CWD로 파일을 특정할 수 없습니다. 원시 PATH 레코드를 다시 확보하기 전에는 대상을 미확인으로 둡니다.
4. **`lost=0`인데 검색 결과가 없으면 그 동작이 없었다고 볼 수 있나요?** 당시 규칙이 그 동작에 맞았는지, 로그 파일과 전달 상태가 온전했는지 확인해야 합니다.

예상된 다섯 결과를 재현하고, 두 종류의 신원 값이 무엇을 뜻하는지, 실제 변경과 수집 누락을 확인할 다음 증거는 무엇인지 설명할 수 있으면 완료입니다. 이어서 [Linux 프로세스 증거]({{ '/ko/wiki/linux-process-evidence/' | relative_url }})에서 상위 프로세스를 확인하는 법을, [저널 수집 범위]({{ '/ko/wiki/linux-journal-coverage/' | relative_url }})에서 서비스 기록이 빠지는 이유를 살펴보세요.
