**학습 목표.** 침입 탐지 시스템(IDS)의 경보에서 출발해 연관 가능성이 있는 연결 기록을 찾습니다. 어떤 증거가 후보를 뒷받침하고 어디서부터 판단을 보류해야 하는지 설명합니다.

## 1. Community ID는 어떤 문제를 해결하나요?

IDS 경보에는 어떤 규칙이 일치했는지가 남습니다. 연결 로그는 지속 시간, 양쪽 주소와 포트, 관측된 통신을 알려줍니다. Suricata와 Zeek는 자체 식별자를 사용하기 때문에 같은 트래픽을 두 도구가 봤을 때 공통으로 검색할 값이 필요합니다. **Community ID**는 네트워크 플로의 메타데이터를 같은 방법으로 계산해 얻는 식별자입니다. 도구마다 사용하는 식별자를 서로 바꾸지 않고도 후보를 좁힐 수 있습니다.

TCP와 UDP의 **5-튜플**은 IP 프로토콜과 양쪽의 IP·포트 조합으로 이뤄집니다. Community ID는 양쪽의 순서를 정해, 관측 방향이 반대여도 같은 값이 나오게 합니다. v1에는 설정으로 선택하는 16비트 값인 **시드**도 들어갑니다. 일반적인 기본값은 0입니다. 이진 값을 SHA-1로 해시한 뒤 일반적으로 Base64로 표현하고 `1:`을 붙입니다. 이 값은 로그의 연결 후보를 찾기 위한 것입니다. 통신 내용을 암호화하거나 송신자를 인증하지 않습니다. 페이로드, 개시 방향, 시각, 자산, 테넌트는 원본 기록에서 확인하세요.

| 식별자 | 사용 범위 | 주의할 점 |
| --- | --- | --- |
| Zeek의 `uid` | 같은 UID가 담긴 다른 Zeek 로그를 따라갈 때 | 원본 센서와 데이터셋을 함께 남김 |
| Suricata의 `flow_id` | 같은 출처의 EVE 이벤트가 어느 플로에 속하는지 볼 때 | 센서와 실행 또는 데이터셋 범위를 함께 남김 |
| `community_id` | 여러 도구가 같은 튜플을 관측한 기록을 찾을 때 | 버전·인코딩·시드·관측 범위·시각을 대조 |
| 패킷 또는 주소 변환 증거 | 실제 통신과 NAT 매핑이 맞는지 확인할 때 | 해당 지점의 가시성과 수집 출처가 필요 |

## 2. 정상 조사 한 건을 따라가세요

![경보와 플로의 원본 식별자를 보존하고, 공통 ID·튜플·네트워크 범위·시각을 대조합니다. 패킷이나 센서 원본으로 후보를 더 확인합니다.]({{ '/assets/diagrams/community-id-review-ko.svg' | relative_url }})

가상 실습에서 센서가 12:00:04 UTC에 `192.0.2.24:51000`과 `198.51.100.20:443` 사이의 TCP 통신에 규칙 일치를 기록합니다. Zeek는 같은 네트워크 구간에서 양쪽 주소를 반대 순서로 기록합니다. v1과 시드 0에서 양쪽 순서를 바꿔도 `1:crL5jj4ZGIYJPT6Db5ghbtwA+DI=`가 나옵니다. Zeek가 관측한 구간에 경보 시각도 들어갑니다. 따라서 관련 연결의 후보로 보되, 한 세션으로 확정하기 전에 패킷이나 센서의 원본 연관 기록 등으로 더 확인합니다. 규칙 일치만으로 호스트 침해가 입증되는 것은 아닙니다.

1. **원본 경보를 확보합니다.** 센서, 인터페이스 또는 VLAN, 캡처·데이터셋 ID, 경보 시각, 규칙 메타데이터, 패킷에서 읽은 값과 원본 식별자를 보존합니다. 발생 시각과 수집 시각을 구분합니다.
2. **비교할 수 있는 관측인지 확인합니다.** 알고리즘 버전, 인코딩, 시드가 맞는지 봅니다. 원본 양쪽 IP·포트와 전송 프로토콜을 대조합니다. 비교용 데이터에서는 방향을 정규화하고, 원본에는 시작·응답 방향을 보존합니다.
3. **범위를 좁힙니다.** 필요한 사이트·테넌트·VRF·VLAN과 NAT 전후 구간을 확인합니다. 두 센서의 시계 오차와 관측 범위를 고려해 경보 시각이 플로 구간에 해당하는지 봅니다. 시간 여유 폭은 측정값에 근거해 정하세요.
4. **다른 증거로 확인합니다.** 같은 튜플이 재사용되면 다른 연결에서도 같은 해시가 나옵니다. 여러 후보가 허용 구간에 있다면 추가 증거가 필요합니다. 승인된 패킷에서 핸드셰이크나 연속된 패킷을 확인할 수 있습니다. Zeek는 해당 분석기가 기록을 남긴 경우 UID로 `ssl.log`, `http.log` 등으로 이어 볼 수 있습니다. 실제 호스트 동작을 말하려면 엔드포인트 증거도 따로 확인합니다.

| 상황 | 해석 |
| --- | --- |
| ID가 같고 방향이 반대 | TCP·UDP의 양방향 비교에서는 정상입니다. 방향은 원본 필드에서 확인합니다. |
| 시간대나 테넌트가 다른데 ID가 같음 | 같은 입력값이 다른 연결에도 나타납니다. 관측 범위와 시각이 맞아야 합니다. |
| NAT 전후 ID가 다름 | 주소나 포트가 바뀌면 해시가 달라집니다. 시각이 포함된 변환 전후 매핑을 봅니다. |
| ID는 같은데 원본 튜플이 다름 | 필드 매핑, 값 잘림, 프록시 주소 처리 또는 드문 충돌을 점검하고 차이를 기록합니다. |
| 한 로그에 ID가 없음 | 로거 설정, 이벤트 유형, 수집 필드를 확인합니다. 패킷이나 도구 자체 식별자로 이어 볼 수 있습니다. |

프록시는 한 전송 연결을 끝내고 별도의 연결을 열 수 있습니다. 목적지 서비스 이름이 같다는 이유로 두 연결을 하나로 합치지 않습니다. 미러링된 여러 센서의 일치 기록은 세션이 추가된 것이 아니라 같은 패킷을 반복해 본 결과일 수도 있습니다. 의심스러운 조합의 반복, 공유 프록시 주소, 후보 급증은 조사할 단서지만 그 자체로 의도를 입증하지 않습니다. 원본과 패킷 참조를 보존하고, 가시성과 시계 보정을 확인한 뒤 해소되지 않은 후보는 사건 기록에 남깁니다. 승인된 방어 검증에서는 정상 플로 한 건과 별도 시간대의 무관한 플로를 대조할 수 있습니다.

## 3. 두 도구의 수집 필드를 맞추세요

| 제품 | 확인할 점 |
| --- | --- |
| Zeek | `policy/protocols/conn/community-id-logging.zeek` 정책을 로드했는지, `conn.log`의 해당 행에 선택 필드 `community_id`가 있는지 확인합니다. `CommunityID::seed`와 Base64 출력을 대조합니다. `ts`는 첫 패킷 시각이며 지속 시간이 없는 행도 있습니다. |
| Suricata | 사용하는 EVE 로거의 `community-id`가 활성화되어 있고 `community-id-seed`가 호환되는지 확인합니다. `community_id`, `flow_id`, 이벤트 유형, 캡처·센서 범위, 시각을 보존합니다. 플로 이벤트에 `flow.start`와 `flow.end`가 있으면 관측 구간을 확인합니다. |
| SIEM 또는 내보내기 | ID 대소문자, 버전 접두사, Base64 패딩을 그대로 보존합니다. 원본 튜플과 시각, 센서, 테넌트·네트워크 구간, 도구 내부 ID가 어떻게 저장됐는지 확인합니다. 의미가 같은 필드만 이름을 통일합니다. |

승인된 실습 환경에서 정상 통신을 담은 기존 캡처를 두 도구로 분석해 볼 수 있습니다. 빈 출력 폴더에 같은 캡처와 링크 계층 관측값을 사용하고 시드를 맞춥니다. Zeek에서는 `zeek -r approved.pcap policy/protocols/conn/community-id-logging`으로 정책을 함께 로드할 수 있습니다. Suricata는 사용할 `eve-log` 설정을 확인한 뒤 TCP 또는 UDP 플로를 Zeek 연결과 대조합니다. 공통 ID의 일치를 확인하는 데 IDS 경보가 발생할 필요는 없습니다. 제품 절차는 공식 문서로 검토했습니다. 이번 게시 과정에서 Zeek나 Suricata로 실시간 수집 또는 PCAP 재생을 실행하지는 않았습니다.

## 4. 오프라인 실습 · 가상 플로 기록 8건

[가상 기록 자료]({{ '/assets/labs/community-id-cases.json' | relative_url }})와 [Python 검토기]({{ '/assets/labs/community-id-review.py' | relative_url }})를 한 폴더에 저장하고 Python 3.8 이상에서 실행하세요.

```sh
python3 community-id-review.py
```

자료에는 예시 전용 주소와 2030년의 가상 UTC 시각이 들어 있습니다. 검토기는 IPv4 TCP·UDP의 v1 ID를 다시 계산하고 원본 튜플을 비교한 뒤 경보 시각의 앞뒤 1초에 걸친 닫힌 구간으로 후보를 좁힙니다. 1초는 실습용 가정입니다. 실제 제품에서 IPv6·ICMP 등은 문서에 명시된 별도 처리를 사용합니다.

| 기록 | 기대 결과 | 이유 |
| --- | --- | --- |
| Z01 | 후보 | 튜플 방향은 반대지만 범위가 같고 구간에 경보 시각이 포함됨 |
| Z02 | 시간 범위 밖 | 같은 튜플과 ID가 11:45에 있었음 |
| Z03 | 관측 범위 불일치 | 다른 네트워크 구간에서 같은 값이 나옴 |
| Z04 | 튜플 불일치 | 주소와 포트가 변환됨. 매핑 기록을 찾아야 함 |
| Z05 | 시드 불일치 | 센서의 시드만 달라 ID도 달라짐 |
| Z06 | 로그의 ID 없음 | 실습에서 대조할 기록값이 없음 |
| Z07 | 후보 | 경보보다 1초 뒤에 시작해 허용 범위의 끝에 걸침 |
| Z08 | ID 불일치 | 원본 필드로 다시 계산한 값이 기록의 ID와 다름 |

예상 출력은 `Candidates: Z01, Z07`과 복수 후보 메시지입니다. 하나로 좁히려면 추가 근거가 필요합니다. 파일이 열리지 않으면 이름과 폴더를 확인하세요. 값이 예상과 다르면 주소 체계, 프로토콜, 포트, 시드와 UTC 오프셋을 확인하고 NAT의 어느 쪽을 봤는지 대조하세요. 가상 자료를 실행했고 해시 계산은 명세 게시자가 제공한 IPv4 TCP·UDP 기준값(시드 0과 1)과 비교했습니다. 검증 범위는 이 계산과 가상 사례 판정입니다.

## 5. 확인 문제와 완료 기준

1. **어느 쪽이 연결을 시작했나요?** 패킷 순서 또는 신뢰할 수 있는 시작점 메타데이터를 확인합니다. TCP·UDP의 공통 ID는 방향을 구분하지 않습니다.
2. **Z02는 ID가 맞는데 왜 제외되나요?** 이 실습의 허용 시각 범위 밖에서 같은 조합이 재등장했습니다.
3. **Z04를 연결할 가능성이 왜 남나요?** NAT를 지나면서 튜플과 ID가 바뀔 수 있습니다. 시각과 기록된 변환 매핑을 먼저 대조합니다.
4. **무엇으로 Z01과 Z07을 구분하나요?** 같은 실제 통신을 가리키는 패킷 참조나 센서 원본 기록을 찾아 대조합니다. 근거가 없으면 두 후보를 남깁니다.

Z01·Z02·Z07에 대해 원본 ID, 발생 시각, 관측 지점과 남은 불확실성을 포함한 조사 결론을 적으면 완료입니다.
