**학습 목표.** APT가 저장소의 상위 메타데이터에 있는 서명으로 개별 패키지 다운로드를 어떻게 검증하는지 설명합니다. 어느 검증에서 처음 실패했는지 찾고, 다운로드 차단과 실제 설치를 증거로 구분합니다.

## 1. 패키지 관리자는 무엇을 신뢰하나요?

**패키지**는 소프트웨어나 데이터와 함께 버전, 아키텍처, 의존성 같은 정보를 담은 묶음입니다. Debian 바이너리 패키지는 `.deb`로 끝납니다. **dpkg**는 로컬 패키지 데이터베이스와 Debian 패키지를 관리합니다. **APT**는 설정된 **저장소**에서 버전과 의존성을 찾고 패키지를 받아 dpkg와 함께 설치를 진행합니다. 저장소는 사용할 수 있는 패키지 목록과 실제 파일을 게시합니다. **미러**는 저장소의 복사본을 제공합니다.

**해시값** 또는 **다이제스트**는 파일의 바이트로 계산한 짧은 값입니다. SHA-256 값으로 받은 파일이 예상한 바이트와 일치하는지 확인할 수 있습니다. 이때 비교하는 예상값의 출처가 중요합니다. **저장소 서명 키**는 메타데이터의 출처를 확인하는 데 쓰입니다. 게시자가 개인키로 메타데이터에 서명하고, APT는 해당 저장소에 허용된 공개키로 OpenPGP 서명을 검증합니다. 키와 서명의 기초는 [공개키 암호학]({{ '/ko/wiki/public-key-cryptography/' | relative_url }})에서 살펴보세요.

## 2. 정상 업데이트와 다운로드 따라가기

가상의 조직에서 Debian 장치가 승인된 저장소의 배포 경로 `lab`과 구성 요소 `main`을 사용한다고 가정해 봅시다. **스위트(suite)**는 어느 배포 경로를 볼지 고르고, **구성 요소(component)**는 그 안에서 `main` 같은 하위 집합을 선택합니다. 아키텍처에 따라 필요한 인덱스도 달라집니다. 실제 Debian 저장소를 설정할 때는 해당 릴리스나 공급자가 안내한 값과 키를 확인합니다.

| 증거 | 담긴 정보 | 확인 방법 |
| --- | --- | --- |
| 저장소 설정과 키링 | 저장소 URI, 스위트, 구성 요소, 허용된 서명 키 | 해당 저장소에 승인된 설정과 공개키 전체 지문을 별도의 신뢰 경로로 확인 |
| `InRelease` 또는 `Release` + `Release.gpg` | 릴리스 식별 정보, 날짜, 인덱스 파일의 예상 해시와 크기 | APT가 평문과 서명이 함께 있는 파일 또는 분리된 서명을 검증. 상황에 맞는 유효기간·릴리스 정보 정책도 적용 |
| `Packages` 인덱스 | 패키지 이름, 버전, 아키텍처, 파일 경로, 크기와 해시 | 실제로 받은 바이트를 인증된 `Release`의 해당 항목과 대조. 압축 파일인 경우 그 압축 형식의 항목 사용 |
| `.deb` 파일 | 다운로드한 패키지 바이트 | APT가 패키지 인덱스와 대조. 설치나 이후 파일 상태는 별도의 증거로 확인 |

`apt-get update`는 로컬 패키지 목록을 갱신합니다. 이후 패키지를 받는 작업에서는 APT가 로컬 목록과 선택 정책으로 후보 버전을 고르고, 받은 파일을 확인합니다. 예를 들어 검증된 실습 저장소 인덱스에 `wiki-archive-lab` 버전 `1.0`과 해당 `.deb`의 SHA-256 값이 있다고 합시다. 미러가 같은 이름으로 다른 바이트를 제공하면 패키지 검사가 실패합니다. 해시가 일치하면 저장소가 게시한 정확한 파일인지 확인할 수 있습니다. Debian의 일반적인 저장소 검증은 내려받은 `.deb`마다 유지보수자 개인의 서명을 확인하는 방식과 다릅니다.

`Signed-By`로 저장소에 사용할 키 파일이나 내장 키를 지정할 수 있고, 키링에서 특정 지문을 선택할 수도 있습니다. Debian 13 문서에서는 deb822 `.sources` 안에 키를 포함하거나, 직접 관리하는 키는 `/etc/apt/keyrings`, 패키지가 관리하는 키는 `/usr/share/keyrings`의 파일을 참조하는 방식을 설명합니다. APT가 샌드박스 사용자로 읽는 환경에서는 해당 사용자가 키링을 읽을 수 있어야 합니다. 인증된 공급자 안내를 따르고, 전체 지문은 기존에 신뢰하던 경로에서 대조하세요. 다른 공개키로 서명이 맞더라도 의도한 저장소의 증거로 쓸 수 없습니다.

## 3. 오류와 오용 가능성을 구분하기

| 증상 | 가능한 설명 | 확인할 증거 |
| --- | --- | --- |
| 서명 키를 찾을 수 없거나 서명이 거부됨 | 승인된 키 교체 미반영, 잘못된 키링 또는 스위트, 예상 밖 서명자 | 저장소 설정, 실제 적용 키링, 독립적으로 확인한 키 지문, 원본 메타데이터, 오류 전문 |
| `Hash Sum mismatch` | 미러나 프록시에서 서로 다른 시점의 파일을 제공, 전송 중 손상, 승인되지 않은 변경 | 예상·실제 해시와 크기, URL, 인덱스 압축 형식, UTC 시각, 미러 상태 |
| Release 유효기간이 지났거나 아직 유효하지 않음 | 오래된 미러, 이전에 서명된 메타데이터의 재전송, 장치 시계 오류 | 서명에 포함된 `Date`와 `Valid-Until`이 있다면 해당 값, UTC와 시계 오차, 미러 게시 시각 |
| 서명과 해시는 통과했지만 패키지가 의심스러움 | 게시자·빌드 시스템·서명 키 침해 또는 정식으로 게시된 취약 버전 | 정확한 빌드와 해시, 공급자 공지, 별도로 수집한 설치·실행 증거 |

공격자가 미러의 파일을 바꾸거나 사용자의 요청 경로를 바꾸더라도, 내려받은 파일과 하위 해시만 수정해서는 검증을 통과할 수 없습니다. 허용된 키로 인증된 메타데이터와도 일치해야 합니다. 게시자나 신뢰된 서명 키가 침해된 경우에는 유해한 파일이 이 검증을 통과할 수 있습니다. HTTPS는 연결한 서버의 신원을 확인하고 전송 구간을 보호합니다. 저장소 서명은 미러가 파일을 전달할 때도 패키지와 메타데이터의 관계를 보호합니다. 설정된 두 검사를 모두 유지하세요.

시간 검사는 서명 검증과 다른 질문에 답합니다. 과거에 올바르게 서명된 목록도 수학적으로 유효한 서명을 갖습니다. APT에서 그 목록을 계속 사용할 수 있는지는 저장소 메타데이터에 기록된 날짜와 적용 정책에 달려 있습니다. 새 목록을 받지 못했을 때 예전 캐시가 남을 수 있으므로 로컬 목록을 조회한 결과에는 수집 시각과 목록의 신선도를 함께 기록하세요.

## 4. 블루팀 수집·판단·복구 확인

1. **갱신 전에 증거를 보존합니다.** 장애 장치, UTC와 시계 오차, OS·APT 버전, 명령과 전체 출력, 패키지 이름·버전 및 의도한 저장소를 기록합니다. 승인된 범위에서 저장소 설정과 키링, `/var/lib/apt/lists/`에 남은 목록, `/var/cache/apt/archives/`에 남은 파일, `/var/log/apt/history.log`, `/var/log/apt/term.log`, `/var/log/dpkg.log`와 관련 보관본을 확보합니다. 실제 경로와 보존 기간은 설정에 따라 다릅니다. 원본 바이트를 유지하고 자격 증명이 있는 URL은 접근을 제한합니다.
2. **독립된 기준과 대조합니다.** 관측된 URI, 스위트, 아키텍처, 공개키 지문을 정상 설정과 비교합니다. 미러나 프록시 로그가 있다면 한 장치, 한 경로, 여러 장치 중 어디에 오류가 나타났는지 확인합니다. 가장 먼저 어긋난 단계부터 좁힙니다. 해시 오류를 조사할 때는 압축 형식까지 같은 파일끼리 비교하세요. 동기화 오류만으로 침해를 확정할 수는 없습니다.
3. **다운로드, 설치, 실행을 구분합니다.** Debian 계열에서 `apt-cache policy openssh-server`는 로컬 목록 기준의 후보 버전과 출처 정보를 조회합니다. 목록이 오래됐거나 없으면 결과의 범위도 제한됩니다. `dpkg-query -W -f='${db:Status-Abbrev}\t${Package}\t${Version}\t${Architecture}\n' openssh-server`는 로컬 dpkg 상태를 읽습니다. `ii` 뒤에 공백이 있는 값은 일반적인 설치 상태입니다. 상태만으로 설치 당시의 출처를 확정하기는 어렵습니다. 남아 있는 작업 로그에서 시각·버전을 확인하고, 인증된 과거 메타데이터가 있다면 패키지 해시를 대조합니다. 실행은 서비스나 프로세스 증거에서 별도로 확인하세요.
4. **담당자와 함께 신뢰를 복구합니다.** 정기 키 교체라면 승인된 키와 설정으로 목록과 예상 버전이 정상 갱신되는지 확인합니다. 게시자나 키의 침해가 의심되면 해당 저장소 사용 중단을 담당자와 조율하고, 그 출처에서 설치한 장치와 버전을 찾아 공급자의 인증된 사고 대응 안내를 따릅니다. 조치 전 증거를 보존하고, 예상 지문·패키지 버전·서비스 상태로 복구를 판정하세요.

## 5. 오프라인 실습 · 처음 실패하는 단계 찾기

<a href="{{ '/assets/labs/apt-repository-integrity-lab.py' | relative_url }}" download>Python 실습 파일</a>을 내려받으세요. Python 3, `dpkg-deb`, Ed25519를 지원하는 OpenSSL 3.x가 있는 승인된 Debian 계열 테스트 환경에서 `python3 apt-repository-integrity-lab.py`를 실행합니다. 스크립트는 텍스트만 담은 실제 `.deb`, 한 건짜리 패키지 인덱스, Release 메타데이터와 임시 실습 키를 만듭니다. 패키지 설치, 네트워크 연결, 관리자 권한은 필요 없으며 임시 출력은 종료 시 정리됩니다.

실습의 `Release.sig`는 OpenSSL의 원시 Ed25519 서명입니다. 실제 APT는 `InRelease`, `Release.gpg` 형식의 OpenPGP 저장소 서명을 검증합니다. 실습에서는 실제 파일로 서명과 두 번의 SHA-256 검사를 수행합니다. APT 실행, Release의 날짜 정책, 다양한 저장소 형식은 실습 범위 밖입니다.

| 대조 조건 | 기대하는 첫 판정 |
| --- | --- |
| 원본 파일과 예상 공개키 | 서명과 인덱스·패키지 해시 모두 통과 |
| 원본 파일과 다른 공개키 | Release 서명 거부 |
| Release만 변경 | Release 서명 거부 |
| 인덱스만 변경 | Packages 인덱스 해시 또는 크기 불일치 |
| 패키지만 변경 | 패키지 해시 또는 크기 불일치 |

실행하기 전에 어느 단계에서 실패할지 예측하세요. 2번과 3번은 원인이 다르지만 같은 단계에서 실패합니다. 실제 조사에서는 신뢰할 수 있는 키 정보와 원본 파일을 둘 다 확보해야 합니다. 4번과 5번은 서명 검사 뒤에도 확인할 항목이 남는 이유를 보여 줍니다. 마지막에 `5/5 archive-integrity controls matched.`가 표시됩니다. 실행 파일을 찾지 못하면 테스트 환경의 도구를 확인하세요. 키 생성 오류가 나면 OpenSSL 버전과 사용 가능한 공급자(provider)를 확인합니다. 대조 실험 5건은 클라우드에서 OpenSSL 3.5.7과 dpkg-deb 1.22.22로 실행했습니다. 운영 APT 동작과 조사 명령은 Debian 공식 문서에서 검토했습니다.

## 6. 확인 문제와 완료 기준

1. **신뢰할 수 없는 서버에서 인덱스와 해시를 한꺼번에 받았습니다. 무엇이 빠졌나요?** 허용된 서명자가 이 해시를 게시했다는 증거입니다. 서명된 Release가 인덱스의 예상 해시를 인증합니다.
2. **서명은 유효한데 Release가 만료됐다고 나올 수 있나요?** 서명은 바이트를 검증합니다. 현재 사용하기에 충분히 최신인지는 시간 정책에서 따로 판단합니다.
3. **해시 불일치가 기록됐습니다. 설치를 뒷받침하는 자료는 무엇인가요?** 패키지 이름과 버전, 시각을 dpkg 상태와 설치 작업 기록에 대조합니다. 해시 불일치는 해당 검사 실패를 보여 줍니다.
4. **인증과 설치를 확인했다면 실행도 확인된 건가요?** 실제 실행 여부는 서비스, 프로세스 또는 애플리케이션 자료에서 확인합니다.

**완료 기준.** 검증 세 단계를 순서대로 설명하고 실습 5건을 분류하세요. 설치와 실행을 각각 확인할 증거를 설명할 수 있으면 됩니다. 다음은 [SBOM과 VEX]({{ '/ko/wiki/sbom-vex-evidence/' | relative_url }})에서 인증된 빌드에 취약점이 적용되는지 판단하는 방법을 살펴보세요.
