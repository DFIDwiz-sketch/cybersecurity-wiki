## 1. seccomp는 무엇을 판단하나요?

**시스템 호출**은 스레드가 리눅스 커널에 작업을 요청하는 통로입니다. 파일을 열거나 부모 프로세스 ID를 확인할 때 쓰입니다. **ABI**는 프로그램이 커널에 호출을 전달하는 규약입니다. 시스템 호출 번호도 이 규약에 속합니다. ABI가 다르면 같은 번호가 다른 호출을 가리킬 수 있습니다.

**seccomp**는 스레드에서 사용할 수 있는 커널 기능을 줄여 줍니다. 필터 모드에서는 커널이 호출 번호, 아키텍처, 인자 등으로 필터를 평가합니다. 전통적인 seccomp BPF 필터는 인자의 숫자 값과 포인터의 주소 값을 볼 수 있지만, 그 주소의 메모리 내용을 읽을 수는 없습니다. 예를 들어 `openat` 인자로 넘어온 포인터에서 경로 문자열을 꺼내 검사할 수 없습니다. 파일 권한, capability, 리눅스 보안 모듈은 별도의 통제입니다. seccomp에서 통과한 호출도 커널이 실제로 처리할 때 다른 검사에서 거부될 수 있습니다.

## 2. 호출에서 결과까지 따라가기

1. **호출자를 식별합니다.** 호스트, 부팅 구간, 프로세스와 스레드를 확인합니다. 컨테이너 안의 PID와 호스트 PID가 다를 수 있습니다. PID가 재사용될 수 있으므로 실행을 구분하고, 번호를 해석하기 전에 스레드의 ABI를 확인하세요.
2. **필터 적용 상태를 확인합니다.** 해당 스레드의 상태에서 `Seccomp: 0`은 비활성, `1`은 엄격 모드, `2`는 필터 모드입니다. 지원되는 커널에서 `Seccomp_filters`는 붙어 있는 필터 수입니다. `NoNewPrivs`는 프로그램 실행을 통한 새 권한 획득을 제한하는 별도 값입니다. 이 필드에는 개별 규칙 내용이 담기지 않습니다.
3. **필터 동작을 해석합니다.** 상속된 필터를 포함해 여러 필터가 적용될 수 있습니다. 커널은 각 필터가 반환한 동작 가운데 우선순위가 가장 높은 것을 적용합니다. 한 필터가 허용해도 다른 필터의 더 엄격한 동작이 우선합니다.
4. **호출 결과와 감사 범위를 대조합니다.** 프로그램은 반환값이나 신호를 받습니다. 감사 레코드 생성은 커널이 별도로 판단하고, 이후 수집 경로가 기록을 보존하고 전달해야 합니다.

| `ALLOW` | 커널에서 정상 처리 단계로 넘어갑니다. | 다음 권한 검사에서 실패할 수 있습니다. seccomp는 ALLOW 동작 자체를 감사 로그로 남기지 않습니다. |
| `LOG` | 감사 기록을 요청하고 정상 처리 단계로 넘어갑니다. | 로그가 있어도 호출이 진행됐을 수 있습니다. 로깅 설정과 수집 범위도 확인하세요. |
| `ERRNO` | 호출을 실행하지 않고 설정한 오류를 반환합니다. | 다른 원인도 같은 오류를 낼 수 있으므로 호출과 필터 동작을 대조하세요. |
| `TRAP` | 호출을 실행하지 않고 호출 스레드에 `SIGSYS`를 보냅니다. | 수집할 수 있다면 `SYS_SECCOMP` 같은 신호 세부 정보를 확인하세요. 프로그램이 신호를 처리할 수도 있습니다. |
| `KILL_PROCESS`, `KILL_THREAD` | 호출을 실행하지 않고 각각 프로세스 또는 호출 스레드를 종료합니다. | 종료 상태, 워커 재시작, 관련 감사 기록을 대조하세요. |

## 3. 정상 흐름과 차단 사례 비교하기

**정상 예시.** 한 서비스가 일상적인 파일·네트워크 호출을 허용하는 검토된 필터로 시작합니다. 상태는 `Seccomp: 2`이고 요청 하나가 완료됐습니다. 해당 요청에 필요한 흐름이 동작했다는 증거입니다. 허용되는 모든 호출을 확인한 것은 아닙니다.

**통제한 비교.** 일회용 프로세스에서 먼저 무해한 `getppid`를 실행합니다. 이어 해당 호출에 `EPERM`을 반환하는 필터를 하나 추가합니다. 이후 반환값이 바뀌고 필터가 하나 늘어나면 이 실험 안에서 필터와 결과를 연결할 수 있습니다. 운영 환경에서는 `EPERM`만으로 원인을 정할 수 없습니다. 이미지나 런타임 프로필 변경으로 호환성 문제가 생길 수 있고, 예상 밖의 시스템 호출이 확인되면 애플리케이션이 어떤 경로로 실행됐는지 살펴볼 수 있습니다.

필터가 지나치게 넓으면 침해된 워크로드가 사용할 수 있는 커널 호출 범위도 커집니다. 승인 기준과 달라진 부분을 조사하려면 어느 이미지와 프로필이 바뀌었고 어떤 통제가 실제 적용됐는지 확인하세요. 차단 한 건은 정상 코드의 호환성 문제에서도 발생할 수 있습니다.

Kubernetes의 `RuntimeDefault`는 해당 컨테이너 런타임의 기본 프로필입니다. 구현과 버전에 따라 달라질 수 있습니다. 매니페스트에서 요청한 프로필을 확인하고 실제 컨테이너, 런타임, 호출 스레드의 상태와 대조하세요. 명시된 프로필이 없으면 노드 설정과 적용 정책을 함께 봅니다. 프로필이 적용되지 않았거나 지나치게 넓어 보이면 승인된 워크로드 기준과 비교한 뒤 원인을 판단하세요.

## 4. 블루팀 수집·탐지·대응

승인된 리눅스 호스트에서 상태와 로그를 읽는 예시입니다. 숫자는 **호스트에서 보이는** 대상 PID와 TID로 바꾸세요. procfs 조회는 접근 권한의 영향을 받습니다. 감사 검색에는 Linux Audit 도구와 해당 로그의 읽기 권한이 필요합니다. ausearch의 `recent`는 짧은 상대 시간입니다. 과거 사건은 기록한 시작·종료 시간을 직접 지정하세요.

~~~sh
pid=1234
tid=1234
grep -E '^(Name|Pid|Tgid|NSpid|NoNewPrivs|Seccomp|Seccomp_filters):' \
  "/proc/$pid/task/$tid/status"
cat /proc/sys/kernel/seccomp/actions_logged
sudo auditctl -s
sudo ausearch -m SECCOMP -ts recent
~~~

- **수집.** 감사 원본, 시각과 일련번호, 아키텍처·호출 번호, 기록된 필터 동작, 애플리케이션 오류나 신호를 보존합니다. 실행 파일 식별자, 프로세스 시작 시각, 컨테이너·노드, 이미지와 런타임 버전, 실제 적용됐거나 적용이 기대된 프로필 자료를 확보하세요. 관측 위치가 호스트인지 컨테이너인지 기록하고 원본 접근을 제한합니다.
- **탐지.** 워크로드와 버전별로 평상시 동작을 정리합니다. 배포 직후 반복되는 차단이나 안정적으로 운영되던 워크로드에서 새롭게 거부된 호출을 우선 살펴봅니다. 차단 건수를 세기 전에 감사 원본의 동작 값을 확인하세요. 감사 이벤트 ID가 있으면 같은 호스트와 부팅 구간 안에서 레코드를 묶습니다. 기록이 없으면 감사 활성 상태, 대기열과 유실, 전달 경로, 보존 범위를 확인합니다.
- **대응.** 먼저 프로세스와 런타임 증거를 보존하세요. 배포된 프로필을 승인 버전과 변경 이력에 대조하고, 차단 동작을 새로운 요청이나 실패한 워커와 연결합니다. 서비스 담당자와 검토된 설정을 복구하고 정상 업무를 다시 실행하세요. 차단 문제와 로그 수집 공백을 따로 확인합니다.

## 5. 승인된 실습 · 프로세스 하나에서 호출 하나 제한하기

본인 소유 또는 명시적으로 승인된 일회용 리눅스 작업 공간을 사용하세요. Python 3, `libseccomp.so.2`, 그리고 `Seccomp_filters`가 있는 procfs가 필요합니다. 이 필드는 Linux 5.9부터 제공되며 배포판에서 이전 버전으로 이식했을 수도 있습니다. 환경에서 필터 설치를 허용하면 일반 권한으로 실행됩니다. 규칙은 스크립트를 실행한 Python 프로세스에 적용되고 프로세스를 종료하면 실습이 끝납니다. 서비스 설정과 감사 정책을 변경하지 않습니다.

- <a href="{{ '/assets/downloads/linux-seccomp-evidence/seccomp_getppid.py' | relative_url }}" download>시스템 호출 검증 스크립트 다운로드</a>

~~~sh
python3 seccomp_getppid.py
~~~

스크립트는 libseccomp로 실행 중인 ABI의 호출 번호를 알아내고 libc를 통해 직접 시스템 호출을 합니다. 처음에는 0 이상의 부모 PID가 나와야 합니다. 필터 설치 뒤에는 `getppid=-1`, `errno=1`(`EPERM`), `Seccomp: 2`, 필터 수 1 증가, `PASS`를 예상할 수 있습니다. 부모 PID와 초기 필터 수는 환경마다 다릅니다. 처음부터 호출이 차단되거나 라이브러리가 없거나 환경이 필터 설치를 막으면 진단 메시지와 함께 종료합니다. 실습에는 필터 설치가 가능한 일회용 환경을 사용하세요. 감사 기록 생성 여부는 실습 성공 조건에 포함하지 않습니다.

**2026-11-27 실제 실행 결과.** Linux 6.18.57 x86-64, Python 3.12.14, libseccomp 2.6.0에서 처음 반환값은 2였고 필터 적용 뒤에는 -1과 errno 1이 나왔습니다. 필터 수는 1에서 2가 됐고 별도 프로세스에서는 `getppid`가 계속 동작했습니다. 운영 감사 수집과 Kubernetes 런타임 동작은 공식 문서로 검토했습니다.

## 6. 확인 문제와 완료 기준

- **`Seccomp: 2`면 특정 호출이 차단된 건가요?** 조회한 스레드에 그 시점에 필터가 있다는 뜻입니다. 특정 호출 차단 여부는 규칙이나 호출 결과와 필터 동작을 연결해 확인하세요.
- **SECCOMP 감사 이벤트는 언제나 차단인가요?** `LOG`는 호출을 계속 진행시킬 수 있습니다. 필터 동작과 프로그램의 결과를 대조하세요.
- **워커 둘이 같은 `EPERM`을 보고했는데 원인이 다를 수 있나요?** 가능합니다. 필터, 커널의 다른 권한 검사, 애플리케이션이 같은 오류를 나타낼 수 있습니다. 호출자, 호출, 프로필, 별도 통제와 감사 범위를 확인하세요.

호출 하나의 전후 결과를 재현하고, 필터 수가 무엇을 뜻하는지 설명하고, 운영 장애의 원인을 판단하기 위해 필요한 추가 증거를 제시하면 실습을 완료한 것입니다.
