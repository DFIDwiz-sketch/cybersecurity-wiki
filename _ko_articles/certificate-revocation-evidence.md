**학습 목표.** CA가 인증서를 해지했다고 알렸을 때 실제 클라이언트나 게이트웨이에 이를 거부할 만한 증거가 있었는지 확인합니다. 체인과 서비스 이름 확인은 [인증서 검증 입문]({{ '/ko/wiki/certificate-validation/' | relative_url }})에서 먼저 익힐 수 있습니다. 이 장에서는 기존 실습의 다음 단계인 해지 확인을 다룹니다.

## 1. 만료와 해지는 왜 구분할까요?

**만료**는 인증서에 서명된 유효 기간이 끝날 때 일어납니다. **해지(revocation)**는 개인키 유출이 확인된 경우처럼 만료 전에 발급 기관이 내린 상태 판단을 배포하는 절차입니다. 인증서는 공개키와 신원의 관계에 서명한 자료입니다. 해지해도 발급된 인증서가 사라지거나 유출된 개인키가 작동을 멈추지는 않습니다. 서버를 확인하는 TLS 클라이언트나 클라이언트 인증서를 확인하는 mTLS 게이트웨이 같은 **검증자**가 확보한 증거에 정책을 적용해야 합니다.

조사할 때는 발급자와 인증서 일련번호를 함께 사용합니다. 일련번호는 발급자의 범위에서 부여됩니다. SHA-256 인증서 지문으로 실제 인증서 바이트를 식별할 수 있습니다. 여러 인증서와 키에서 같은 이름을 쓸 수 있으므로 인증서를 바꿨는지와 키도 바꿨는지를 따로 기록하세요.

| 출처 또는 검사 | 알 수 있는 것 | 해석의 한계 |
| --- | --- | --- |
| 인증서 경로·이름·용도·유효 기간 | 해당 조건을 만족하는 인증서인가요? | 이 검사에 성공해도 해지 확인 결과는 별도입니다 |
| **CRL**, 인증서 해지 목록 | 권한 있는 서명자가 해당 범위와 버전의 목록에 실은 인증서는 무엇인가요? | 목록이 만료됐거나 여러 조각으로 나뉘었거나 다른 발급자·사유만 포함할 수 있습니다 |
| **OCSP**, 온라인 인증서 상태 프로토콜 | 권한 있는 응답자가 특정 인증서 ID에 대해 어떤 상태에 서명했나요? | 상태값, 응답 오류, 신선도는 별개입니다. 서비스 이름을 검증하지 않으며 모든 프로필에서 발급 사실을 보장하지 않습니다 |
| 실제 검증 결과 | 이 검증자가 적용 정책과 상태 자료를 바탕으로 어떻게 판단했나요? | 다른 검증자, 연결 모드, 시각의 결과는 달라질 수 있습니다 |

## 2. 정상 해지 절차를 네 단계로 따라가기

가상의 보고 서비스에서 개인키 유출을 확인했습니다. CA는 09:06 UTC에 발급자 I, 일련번호 1000의 해지를 기록합니다. 09:08에 이 인증서를 포함한 CRL 74를 발행하고 다음 갱신 예정 시각을 10:08로 표시합니다. 09:12에 승인된 게이트웨이가 목록을 가져와 서명, 범위, 시각을 검사하고 정책에 따라 해당 인증서를 제시한 새 연결을 거부합니다. 아직 CRL 73을 쓰는 다른 게이트웨이는 다르게 판단할 수 있습니다. 목록 게시 시각만으로 각 게이트웨이가 이를 적용했는지는 알 수 없습니다.

1. **범위를 확인합니다.** 인증서 발급자와 일련번호, CRL 서명 검증에 필요한 체인, 배포 지점과 적용 범위를 대조합니다. 목록이 특정 인증서 종류나 해지 사유만 포함할 수 있습니다. 기본 목록과 변경분(delta CRL)을 함께 쓰는 환경이라면 어떤 기본 목록에 어느 변경분이 적용되는지 확인한 뒤 목록에서 보이지 않는 이유를 해석합니다.
2. **시각을 확인합니다.** CRL의 `thisUpdate`는 목록 발행 시각입니다. `nextUpdate`는 RFC 5280 프로필에서 다음 목록이 늦어도 언제까지 발행돼야 하는지를 표시합니다. OpenSSL의 출력 `lastUpdate`는 CRL의 `thisUpdate` 필드입니다. 가져온 시각과 검증자 시계는 따로 기록합니다. 사건 뒤에 받은 목록이 사건 당시 검증자가 쓴 목록과 같다고 가정하지 않습니다.
3. **목록에서 항목을 읽습니다.** 적용되는 목록에서 발급자와 인증서 일련번호를 맞춥니다. 항목에 해지 날짜와 사유가 있을 수 있습니다. 해지 날짜로 최초 오용이나 검증자가 알게 된 시점을 판단할 수는 없습니다.
4. **검증 결과를 확인합니다.** 제품 버전, 정책, 캐시 출처와 실제 제시된 인증서를 확인하고 새 연결의 결과를 봅니다. 기존 연결과 재개 세션은 별도로 평가합니다.

## 3. 해지, 상태 미확인, 목록 오류 구분하기

| 관측 | 기록할 사항 | 더 확인할 내용 |
| --- | --- | --- |
| 유효하며 범위가 맞는 CRL에 일련번호가 있음 | 발급자, 일련번호, 있을 경우 CRL 번호, 서명과 유효 시간 | 검증자가 실제로 이 목록을 가지고 적용했나요? |
| 확인한 목록에 일련번호가 없음 | 목록의 발급자, 범위, 시각, 전체 목록 또는 변경분 여부 | 적용 범위의 상태 확인에만 쓸 수 있습니다. 다른 조각이나 빠진 변경분, 다른 인증서 검증 항목은 별도입니다 |
| 필요한 목록이 없거나 오래됨 | 정확한 오류, 조회 경로, 검증자 시계 | 목록 확보 실패인지 실제 해지 결과인지 구분. 배포·캐시와 실패 처리 정책 확인 |
| OCSP `unknown` | 가능하다면 해당 인증서 ID와 일치하는 검증된 응답 | 응답자가 상태를 판단하지 못했습니다. HTTP 오류나 OCSP 프로토콜 오류는 다른 관측입니다 |
| 해지 검사 없이 성공 | 제품 설정과 수집한 증거 | 체인 검증이 성공해도 해지 상태는 검사하지 않은 경우입니다 |

OCSP의 `good`, `revoked`, `unknown`은 서명된 인증서 상태값입니다. 서명자의 권한, 인증서 ID의 일치 여부, 시간 정책을 확인하세요. `thisUpdate`는 상태를 확인한 시각, `producedAt`은 응답에 서명한 시각입니다. `nextUpdate`가 있으면 다음 정보 제공 예정 시점을 나타내며, 일부 프로필은 이 필드를 요구합니다. **스테이플링**은 TLS 상대방이 핸드셰이크 과정에서 OCSP 응답을 첨부하는 방식입니다. 응답이 첨부돼도 검증자가 서명, 적용 범위, 신선도를 확인한 뒤 최종 판단합니다.

공급자별 동작은 다릅니다. Let's Encrypt는 **2025-08-06**에 OCSP 서비스를 종료하고 CRL을 통해 해지 정보를 제공합니다. Mozilla는 Firefox 142에서 CRLite를 실제 적용한다고 발표했습니다. 두 사례의 적용 범위는 해당 공급자와 공개 웹 PKI입니다. 기업 CA, 브라우저, 게이트웨이는 실제 제품 버전과 적용 정책을 확인하세요. 인증서의 CRL 배포 지점이나 AIA URL은 위치를 알려 주지만 검증자가 그 주소에 접속했다는 증거는 아닙니다.

## 4. 수집과 대응에 필요한 증거

실제 제시된 최종 인증서와 확보 가능한 중간 인증서, 발급자·일련번호·지문, 서비스 이름, UTC 시각과 시계 오차, 검증자의 버전·정책·오류, 연결 모드를 기록합니다. 해지 상태를 담은 자료와 해시, 메타데이터, 서명된 범위와 캐시 관측을 보존하세요. 승인된 CA 기록으로 게시 이력을 확인합니다. 내부 인증서 현황을 확인하려고 관련 없는 응답자에게 정보를 보내지 않습니다.

| 신호 | 단정하기 전에 비교할 것 | 대응 |
| --- | --- | --- |
| 새 연결에서 해지된 최종 인증서가 계속 허용됨 | 실제 제시된 인증서·발급자·일련번호, 적용 정책, 목록 버전과 캐시 갱신, 검사 실행 여부 | TLS 종료 지점 전반에서 키와 인증서 교체를 조율. 정책을 적용한 상태의 새 연결을 영향받은 검증자에서 확인 |
| CRL 시간 경계 이후 여러 연결이 실패 | 검증자 시계, 목록의 신선도와 발급자 범위, 배포 상태 | 신뢰할 수 있는 상태 배포를 복구해 재시험하고 원래 오류와 목록을 보존 |
| 예상과 다른 키에 연결된 인증서가 사용됨 | 플랫폼과 CA 발급 기록, 독립적인 엔드포인트 증거, 상태 자료, 키 보관 이력 | 영향받은 검증자와 세션 범위를 확인하고 CA·서비스 소유자와 대응 |

유출된 개인키로도 검증자가 해당 인증서를 허용하는 동안에는 TLS에서 개인키 보유를 증명할 수 있습니다. 정상 교체나 배포 지연, 오래된 캐시로도 검증자별 결과가 달라집니다. 같은 유출 키로 인증서만 재발급해도 키 유출 위험은 남습니다. 해지 자체가 과거 통신 기록을 지우거나 기존 세션을 종료하지도 않습니다. 클라이언트 인증 결과와 게이트웨이 증거는 [mTLS 클라이언트 신원]({{ '/ko/wiki/mtls-client-identity-evidence/' | relative_url }})을 참고하세요.

## 5. 오프라인 실습 · OpenSSL 검증 여섯 가지

<a href="{{ '/assets/labs/certificate-revocation-lab.py' | relative_url }}" download="certificate-revocation-lab.py">Python 실습 파일</a>을 내려받으세요. 본인 소유의 호스트나 샌드박스에 Python 3.10 이상과 PATH에서 실행할 수 있는 OpenSSL 3.x가 필요합니다. 임시 폴더에 일회용 CA 하나, TLS 최종 인증서 두 개, 서명한 CRL 두 개를 만듭니다. 실습 CA를 명시해 검증하며 네트워크 요청이나 시스템 신뢰 저장소 변경은 없습니다. 정상 종료하면 생성 자료를 정리합니다. 키 유출 사유는 실제 사건과 무관한 실습 조건입니다.

```sh
python3 certificate-revocation-lab.py
```

| 대조 조건 | 실제 OpenSSL 결과와 해석 |
| --- | --- |
| 해지 전의 신선한 목록으로 서비스 인증서 검사 | `OK`. 목록에 서비스 인증서가 없음 |
| 같은 인증서를 해지했지만 체인과 이름만 검사 | `OK`. 해지 목록 검사를 켜지 않음 |
| 새 목록에서 같은 인증서 검사 | `certificate revoked` |
| CRL 검사를 켰지만 목록을 주지 않음 | `unable to get certificate CRL`. 해지 판정과 다른 실패 |
| 해지하지 않은 다른 인증서를 이틀 뒤 시각으로 검사 | `CRL has expired`. 목록은 하루만 유효하고 최종 인증서는 아직 유효 |
| 같은 CA의 일련번호가 다른 인증서를 현재 목록으로 검사 | `OK`. 지정한 인증서만 해지됨 |

스크립트는 최종 인증서의 해지를 확인하는 `openssl verify -crl_check -CRLfile`과 시스템 시간을 바꾸지 않고 미래 시각에 검사하는 `-attime`을 사용합니다. `-crl_check_all`로 체인 전체를 검사할 경우 필요한 목록이 늘어날 수 있습니다. 출력에서 발급자, 인증서 일련번호, CRL의 시간 범위와 번호를 확인하세요. 두 목록이 같은 초에 발행됐다면 CRL 번호로 버전을 구분할 수 있습니다.

2026-11-21에 Python 3.12.14와 OpenSSL 3.5.7로 실행해 `6/6 CRL controls matched.`를 확인했습니다. CRL과 검증 결과는 일회용 인증서에서 생성한 실제 출력이며, 서비스 타임라인은 가상입니다. OCSP, 브라우저 상태 확인, 운영 TLS 정책은 공식 문서로 검토했습니다. 실패하면 OpenSSL 버전과 PATH, 임시 폴더 쓰기 권한, 시스템 시각, 처음 실패한 조건을 확인하세요. 예상과 다른 결과가 나오면 스크립트가 오류로 종료합니다.

## 6. 확인 문제와 완료 기준

1. **CRL 옵션 없는 `OK`와 해지 판정은 모순인가요?** 적용한 검사가 다릅니다. 실습은 실행별 정책과 입력 자료를 구분합니다.
2. **다른 조각의 더 새 CRL에 일련번호가 없으면 원래 인증서가 해지되지 않았다는 뜻인가요?** 발급자, 범위, 서명, 대상, 시각이 먼저 일치해야 합니다.
3. **CRL 오류가 나지만 최종 인증서의 유효 기간은 남았습니다. 무엇을 더 보나요?** 오류를 보존하고 필요한 목록, 검증자의 시계와 조회 경로를 확인하세요. 목록과 인증서의 수명은 별개입니다.
4. **특정 게이트웨이가 해지를 적용했음을 어떻게 확인하나요?** 그 게이트웨이의 연결 조건, 제시한 인증서와 상태 자료, 적용 정책, 최종 결과를 서로 맞춰 봅니다.

여섯 결과를 재현하고 CA의 게시와 검증자의 판단이 어긋날 때 어떤 자료를 찾아야 하는지 설명하면 완료입니다. 발급 증거는 [인증서 투명성]({{ '/ko/wiki/certificate-transparency-evidence/' | relative_url }})에서, 체인·이름·용도 검증은 [인증서 검증 입문]({{ '/ko/wiki/certificate-validation/' | relative_url }})에서 이어서 학습하세요.
