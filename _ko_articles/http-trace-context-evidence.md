클라이언트는 `200`을 받았는데 애플리케이션 로그에는 `503`이 보입니다. 두 기록은 같은 트레이스에 들어 있습니다. 재시도가 있었다면 모두 맞는 기록일 수 있습니다. 이를 확인하려면 프록시의 어느 요청에서 각각의 업스트림 시도가 나왔는지, 어떤 서비스가 처리했는지, 프록시가 마지막에 무엇을 응답했는지 따로 대조해야 합니다.

## 1. 먼저 관측 단위를 구분합니다

**트레이스**는 여러 서비스에 걸쳐 함께 일어난 작업을 묶습니다. **스팬**은 요청 수신, 외부 서비스 호출, 백그라운드 작업 등 한 작업을 식별자와 시간 정보로 나타냅니다. **부모 스팬**은 현재 스팬이 어느 작업에서 이어졌는지를 나타냅니다. **스팬 링크**는 부모·자식 관계를 만들지 않고 다른 스팬과의 관련성을 남깁니다. 서로 다른 트레이스도 링크로 연결할 수 있습니다. 게이트웨이의 **요청 ID**는 배포 환경에서 정한 규칙에 따라 해당 게이트웨이에 들어온 한 요청을 식별합니다. 누가 그 값을 발급하고 어디까지 전달하는지 확인하세요. HTTP는 배포별 요청 ID 헤더의 의미를 공통으로 정하지 않습니다.

W3C Trace Context는 HTTP에서 추적 정보를 전달하는 필드를 정의합니다. 버전 `00`의 `traceparent` 예시는 다음과 같습니다.

```text
00-72af9c30ed854219816c57b32a09d4fe-0102030405060708-01
```

| 부분 또는 기록 | 의미 | 조사할 때 주의할 점 |
| --- | --- | --- |
| `00` | 헤더 형식 버전 | 버전에 맞는 규칙으로 읽습니다. 이 장과 실습은 버전 00을 사용합니다. |
| 16진수 32자리 | 16바이트 트레이스 ID | 서로 다른 HTTP 요청을 포함해 여러 작업을 한 트레이스로 묶을 수 있습니다. |
| 16진수 16자리 | 발신 측이 전달하는 8바이트 부모 ID | 계측된 발신 요청에서는 보통 보내는 쪽의 스팬 ID입니다. 수신 서비스의 서버 스팬은 별도 ID를 갖습니다. 헤더만 전달하는 중계점에서는 값이 그대로일 수 있습니다. |
| 16진수 두 자리 | 트레이스 플래그. 이 형식에서는 최하위 비트가 샘플링 플래그입니다. | 해당 구간에서 전달된 신호입니다. 스팬이 저장소까지 도달했는지는 별도로 확인합니다. |
| `tracestate` | 선택 사항인 공급자별 추적 정보 | 필요한 경우에만 사용하고 민감한 값은 넣지 마세요. 수집도 제한합니다. |

버전 00은 정해진 길이의 소문자 16진수와 구분자를 사용합니다. 트레이스 ID나 부모 ID 전체가 0이면 유효하지 않습니다. 형식이 맞는다는 사실만으로는 신뢰하지 않는 외부 요청의 발신자나 접근 권한을 확인할 수 없습니다.

## 2. 정상 요청에서 재시도 따라가기

가상 사례의 게이트웨이는 `GET /reports/summary`를 받고 요청 ID `R17`을 발급하며 내부 트레이스 `T17`을 시작합니다. 이 값은 설명용 약칭이며 실습은 전체 길이의 16진수 ID를 사용합니다. 게이트웨이는 정책에 따라 외부 추적 정보를 받아들이거나 새로 시작합니다. 첫 발신 스팬 `A1`은 `reports-a`를 향합니다. 애플리케이션은 부모가 `A1`인 서버 스팬 `B1`과 `503`을 기록합니다. 게이트웨이는 스팬 `A2`로 `reports-b`에 재시도하고, 두 번째 서버는 부모가 `A2`인 `B2`와 `200`을 기록합니다. 게이트웨이의 최종 응답 기록도 `200`입니다.

게이트웨이가 직접 기록한 요청과 시도 ID로 두 시도의 관계를 먼저 확인하세요. 다음으로 내부 트레이스 ID, 앱이 기록한 부모 스팬과 게이트웨이의 발신 스팬을 대조합니다. 같은 환경에서 같은 경로와 업스트림 대상이 맞는지, 시각이 서로 양립할 수 있는지도 확인합니다. 시계 오차나 수집 지연으로 정렬 순서가 달라질 수 있습니다. 트레이스 저장소에 `B2`만 보여도 독립적으로 남은 게이트웨이 로그로 두 시도를 확인할 수 있습니다. 응답 본문이 클라이언트에 도착했는지는 클라이언트 측 증거가 필요합니다.

OpenTelemetry는 계측이 지원될 때 각 발신 시도에 클라이언트 스팬을 만들도록 권장하고, 재전송에는 `http.request.resend_count`를 정의합니다. 리디렉션, 인증 처리, 네트워크 문제로도 다시 보낼 수 있습니다. 일부 계측은 내부 시도마다 기록하는 대신 논리적인 호출에 스팬 하나만 만듭니다. 스팬 누락이나 재시도 원인을 해석하기 전에 실제 라이브러리가 어떤 단위로 기록하는지 확인하세요.

## 3. 기록을 연결하기 전에 신뢰 범위와 수집 상태 확인

| 관측 지점 | 활성화된 경우 수집할 항목 | 해석과 한계 |
| --- | --- | --- |
| 게이트웨이 액세스·업스트림 로그 | UTC 시각, 환경과 게이트웨이, 자체 발급 요청 ID, 정규화한 경로, 응답 상태, 시도별 대상 서버, 가능한 경우 발신 스팬과 내부 트레이스 ID | 최종 응답과 각 시도의 결과를 구분합니다. 외부 추적 정보를 받아들였는지 새로 시작했는지도 남깁니다. |
| 애플리케이션 로그 | 서비스와 인스턴스, 경로, 요청 또는 내부 트레이스 ID, 계측된 경우 로컬 스팬과 부모 정보, 작업 결과 | 해당 애플리케이션이 기록한 처리를 확인합니다. OTel 로그에 `TraceId`, `SpanId`, `TraceFlags`가 있을 수 있습니다. 로그의 스팬 ID는 자기 스팬이며 부모 관계는 트레이스 데이터나 별도 로그에서 봅니다. |
| 트레이스 수집기와 저장소 | SDK 샘플링 정책, 수집기의 전송·드롭 지표, 테넌트와 보존 기간, 조회 시간 범위 | 스팬이 보이지 않는 이유를 좁힙니다. 헤드 샘플링은 일찍 결정하고, 테일 샘플링은 이후 수집된 스팬을 고려할 수 있습니다. 둘 다 도달하지 않은 데이터를 복구할 수 없습니다. |
| 앱 감사 또는 작업 로그 | 업무 이벤트 종류와 결과, 작업 ID, 필요한 경우 인증 주체, 큐 등록과 소비의 연결 기록 또는 스팬 링크 | 응답 이후 실제 작업이 끝났는지 확인합니다. HTTP `202`는 처리 요청을 수락했다는 뜻이고, 실행 여부는 작업 기록에서 확인합니다. |

**신뢰 경계를 확인하세요.** 호출자가 실수로 또는 의도적으로 같은 식별자를 여러 요청에 쓸 수 있습니다. 외부 샘플링 플래그를 그대로 따를 때는 수집 부하도 커질 수 있습니다. 어느 업스트림의 추적 정보를 이어받을지 정합니다. 공개 경계에서 외부 정보를 신뢰하기 어렵다면 자체 발급 요청 ID와 새 내부 트레이스로 기록을 분명히 할 수 있습니다. 검증한 외부 정보를 유지하는 설계라면 게이트웨이가 발급한 독립적인 요청 ID를 함께 사용하고, 서비스와 시도 범위를 좁혀 대조하세요. 샘플링 비율과 전송 한도는 내부 정책으로 정합니다. 추적 값은 인증이나 인가에 쓰지 않습니다. 경계 동작을 조사하는 데 필요한 필드만 보존하고 자격 증명 전체, 민감한 URL, 추적 상태는 기본 수집에서 제외하세요.

**맞지 않는 기록은 한 단계씩 확인하세요.** 게이트웨이의 요청 ID와 시도 기록부터 찾아 대응하는 서비스에서 부모 관계, 경로, 대상 서버, 시간, 배포 버전을 비교합니다. 가능하면 이벤트가 발생한 시각과 수집기가 관측한 시각을 구분하세요. 서로 관련 없어 보이는 요청에서 외부 트레이스 ID가 반복되면 경계 정책과 클라이언트 계측 오류, 오용 가능성을 함께 조사합니다. 업스트림과 앱 로그가 맞지 않는 이유로는 잘못된 연결, 일부 수집 누락, 큐 등록 이후 지연 처리가 있습니다. 보호 대상 작업이 실제로 일어났는지 확인하려면 앱 감사 기록까지 확인하세요.

**스팬 누락은 수집 범위부터 살펴보세요.** 먼저 해당 경로에 계측이 있는지 확인하고 SDK 샘플링, 전송, 수집기 상태, 필터, 보존 기간과 조회 범위를 순서대로 점검합니다. 샘플링 비트가 켜져도 내보낸 트레이스가 보이지 않을 수 있습니다. 스팬이 없어도 독립적인 앱 감사 기록이 작업을 확인해 줄 수 있습니다. 트레이스는 관측 기록의 관계를 보여 주며, 행위자 신원과 데이터 접근은 별도의 감사 증거가 필요합니다.

## 4. 오프라인 실습 · 요청 여섯 건과 두 가지 수집 신호 비교

본인이 관리하는 디렉터리에서 Python 3.9 이상을 사용하세요. 스크립트와 가상 JSON을 표시된 이름으로 저장합니다. 스크립트는 HTTP 요청을 보내거나 OpenTelemetry SDK를 사용하지 않습니다. 가상 게이트웨이는 기록된 환경과 게이트웨이 내에서 요청 ID를 한 번만 발급합니다. 앱 기록을 연결할 때 환경, 경로, 대상 서버, 내부 트레이스 ID, 부모 스팬 일치와 5초 범위를 확인합니다. 5초는 실습용 기준입니다. 백그라운드 작업은 별도의 60초 범위에서 범위가 지정된 작업 ID로 대조합니다.

- <a href="{{ '/assets/labs/http-trace-context-evidence/cases.json' | relative_url }}" download="cases.json">가상 관측 자료 다운로드</a>

```sh

```

| 사례 | 기대 결과 |
| --- | --- |
| 재시도 | 게이트웨이 최종 200. 별개의 두 시도에 앱 결과 503과 200이 각각 연결됩니다. |
| 재사용된 외부 추적 정보 A와 B | 두 요청의 클라이언트 트레이스 ID는 같습니다. 내부 트레이스와 앱 결과는 따로 유지됩니다. |
| 샘플링하지 않았으나 감사 기록 있음 | 저장된 스팬이 없고 샘플링하지 않았다는 신호가 있어도 앱 로그가 해당 시도에 연결됩니다. |
| 샘플링 신호는 있으나 일치 기록 없음 | 일치 기록을 찾지 못해 앱 결과는 미확정입니다. 다른 환경의 비슷한 기록은 연결에서 제외됩니다. |
| 수락한 백그라운드 작업 | 게이트웨이의 202와 발급된 작업 ID로 연결한 작업 완료를 구분합니다. |

실행하면 비교 여섯 건이 통과합니다. 실패 사례를 확인하려면 JSON 복사본에서 첫 앱 기록의 `parent_span_id`를 0으로만 구성되지 않은 다른 16자리 16진수 값으로 바꿔 실행하세요. 첫 재시도 사례에서 시도 1의 앱 연결이 끊기고 종료 코드는 1이 됩니다. 원본에서 실패하면 다운로드한 파일이 같은 실습용인지, 두 파일이 모두 있는지, 환경과 시간 필드가 달라지지 않았는지 확인하세요. 가상 증거 연결은 직접 실행했습니다. OpenTelemetry 제품 동작은 공식 문서로 검토했습니다.

## 5. 확인 문제와 해설

1. **들어온 트레이스 ID가 같은 두 기록은 요청 하나인가요?** 클라이언트나 상위 트랜잭션이 값을 재사용할 수 있습니다. 게이트웨이의 자체 발급 요청 ID와 시도 관계를 확인하세요.
2. **샘플링 비트가 켜져 있는데 앱 스팬이 없습니다. 원인을 알 수 있나요?** 비트만으로 전송, 샘플링, 저장, 조회 범위 중 어디에 원인이 있는지 판단하기 어렵습니다. 관련 로그와 수집 경로를 확인하세요.
3. **클라이언트가 `202`를 받았고, 작업 완료 기록에 다른 트레이스 ID가 있습니다. 같은 작업일 수 있나요?** 가능합니다. 범위가 같은 작업 ID로 등록·완료를 연결하거나 명시적 스팬 링크를 확인한 뒤 실제 처리 결과를 별도로 검증하세요.

**완료 기준.** 여섯 결과와 실패 사례를 재현하세요. 최종 응답, 각각의 시도, 백그라운드 작업 결과에 대해 근거가 되는 기록을 구분해 적습니다. 스팬이 누락됐을 때 원인을 좁힐 출처 두 가지를 말할 수 있으면 됩니다.

## 공식 참고자료
