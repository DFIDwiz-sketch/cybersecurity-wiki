**학습 목표.** 사고 대응 자료를 받은 뒤 원본, 작업 사본, 분석 결과물에 각각 무엇을 기록해야 하는지 익힙니다. SHA-256으로 같은 바이트인지 확인하고 그 결과를 조사 기록에 정확히 표현합니다.

## 1. 파일 한 개를 받았을 때 꼭 남길 정보

예를 들어 네트워크 담당자가 방화벽에서 00:00–00:15 UTC 구간의 로그를 내보내 전달했다고 가정합니다. 먼저 내보낸 계정과 장비, 조회 범위, 적용 필터, 내보내기 시각, 수집 방법을 기록하세요. 받은 파일은 그 조회 결과를 보존한 **수집 원본**입니다. 장비의 전체 이력이나 디스크 전체를 수집한 것으로 해석하면 안 됩니다. 같은 범위를 다시 내보내도 보존 정책, 새로 도착한 이벤트, 정렬 순서 때문에 내용이 달라질 수 있습니다.

![수집 범위·출처 기록 → 수집 원본과 기준 해시 보존 → 작업 사본 복사·검증 → 파생 자료와 변환 이력 기록 → 전달본 검증·인계 기록]({{ '/assets/diagrams/evidence-custody-ko.svg' | relative_url }})

| 항목 | 뜻 | 예 |
| --- | --- | --- |
| 출처 정보 | 누가 무엇을 어떻게 확보했나 | 장비·로그 종류·조회 시간·방법 |
| 수집 원본 | 보존하는 최초 확보 바이트 | 변경 제한 저장소의 JSONL |
| 작업 사본 | 분석하기 전에 동일성을 확인한 사본 | 분석용 폴더에 복사한 JSONL |
| 파생 자료 | 필터링·변환을 거쳐 만든 결과 | UTC 변환 CSV, 마스킹한 보고서 |
| 인계 기록 | 증거를 언제 누가 다뤘나 | 이관·검증 시각, 제공자·수령자, 목적 |

휘발성 자료 수집, 디스크 이미지, 클라우드 API 결과는 서로 방법과 영향이 다릅니다. 운영에서는 승인된 수집 절차를 따르고 라이브 수집으로 발생한 변경이나 한계를 기록합니다.

## 2. 해시가 말해 주는 것

SHA-256은 입력 바이트에 대해 256비트 요약을 계산합니다. 사람이 읽을 때는 보통 64개의 16진수 문자로 표시합니다. 보존한 기준 해시와 작업 사본 해시가 일치하면 두 파일의 내용 바이트가 같다는 강한 증거입니다. 경로·파일명·접근 권한·파일시스템 시각은 일반적인 파일 내용 해시에 포함되지 않습니다.

| 확인 결과 | 말할 수 있는 내용 | 따로 확인할 내용 |
| --- | --- | --- |
| SHA-256 일치 | 기준으로 삼은 바이트와 일치 | 최초 수집 전 상태, 출처, 누락 여부 |
| SHA-256 불일치 | 같은 방식으로 읽은 바이트가 다름 | 손상, 줄바꿈, 압축, 버전, 의도적 변경 중 무엇인지 |
| 서명 검증 성공 | 신뢰하는 키로 서명한 자료가 검증됨 | 키 소유·관리와 자료 수집의 신뢰성 |
| 인계 기록 존재 | 누가 언제 무엇을 했는지 추적 가능 | 각 단계의 검증 결과와 누락 |

파일과 해시 목록을 같은 사람이 함께 바꿀 수 있다면 일치만으로 변경을 알아차리기 어렵습니다. 기준 해시는 작성 시점과 담당자가 추적되도록 접근 제어된 인계 기록이나 별도 저장소에 보관하세요. 메타데이터가 중요하면 해시와 별도로 수집합니다.

## 3. 수집부터 인계까지 따라가기

1. **범위 기록.** 사건 ID, 자료 ID, 출처 시스템·구간, 필요 시간 범위, 사용 도구와 버전, 수행자, 승인 범위를 기록합니다. SIEM 내보내기에는 검색 조건과 시간대·페이지 제한도 함께 남깁니다.
2. **수집 원본 보존.** 확보한 바이트를 승인된 저장소에 두고, 가능한 첫 지점에서 크기와 SHA-256, UTC 시각을 기록합니다. 내보내기 전의 원본 데이터를 해시할 수 없었다면 해시가 적용되는 지점을 명시합니다.
3. **사본을 만들어 확인.** 작업 사본의 해시를 비교합니다. 불일치하면 분석을 잠시 멈추고 원본·사본 경로와 도구 설정을 대조합니다. 둘 다 보존하고 재복사·재검증 과정을 기록합니다.
4. **분석 결과 연결.** 필터링·정규화·민감정보 삭제로 만든 산출물에는 새 자료 ID와 해시를 부여합니다. 원래 자료 ID, 변환 도구와 옵션, 범위와 시각을 연결합니다.
5. **검증하고 인계.** 누가 누구에게 무엇을 어떤 이유로 넘겼는지와 UTC 시각, 도착 해시와 검증자를 남깁니다. ZIP의 해시와 안의 파일 해시는 서로 다른 확인에 사용합니다.

예시 인계 문장. **“E-07, edge-a 이벤트 00:00–00:15 UTC, 승인된 내보내기로 확보. 00:22 UTC에 담당자 A가 기준 SHA-256을 기록하고 00:30 UTC에 담당자 B가 인계받은 파일을 검증함. 앱 로그는 이 수집 범위에 포함되지 않음.”** 실제 저장에는 역할뿐 아니라 조직에서 요구하는 식별 정보와 저장 위치도 기록합니다.

## 4. 이상이나 오용을 의심할 때

| 관측 | 가능한 설명 | 조사할 다음 자료 |
| --- | --- | --- |
| ZIP과 안의 파일 해시가 다름 | 서로 다른 바이트에 대한 정상 결과 | 각각의 기존 기준 해시와 비교 |
| 텍스트가 같은데 해시가 바뀜 | 줄바꿈, 인코딩, 공백 변경 | 저장 전 파일과 변환 이력 |
| 보관 파일과 처음 해시가 다름 | 전송 오류, 잘못된 버전, 무단 변경 가능 | 보관·접근 감사, 파일 크기, 독립 사본 |
| 수집 범위가 기록되지 않음 | 필터나 페이지 한도가 빠졌을 수 있음 | 도구 출력, 쿼리, 시간 범위 및 누락 |
| 파일과 기준 해시가 같이 바뀜 | 승인 갱신 또는 증거 훼손의 후보 | 별도 인계 기록, 저장소 버전, 접근 감사 |

해시 불일치가 발견되면 새로운 값을 기준 해시로 덮어쓰지 마세요. 관측한 값과 경로를 별도로 기록하고 원본·로그·접근 기록을 보존합니다. 원래 수집과 다른 바이트가 전달된 것으로 확인되면 해당 사본을 표시하고, 근거가 확보될 때까지 영향을 받는 분석 결과를 검토합니다.

## 5. 오프라인 실습 · 같은 로그, 다른 바이트

[evidence-sample.jsonl]({{ '/assets/labs/evidence-sample.jsonl' | relative_url }}) · [evidence-hash-lab.py]({{ '/assets/labs/evidence-hash-lab.py' | relative_url }})

Python 3.11 이상에서 두 파일을 같은 폴더에 저장해 실행합니다. 제공 데이터는 가상 로그 두 줄입니다. 편집기로 다시 저장하면 줄바꿈이 달라질 수 있으니 다운로드 그대로 사용하세요. 스크립트는 임시 폴더에서만 사본을 변경하고 원본을 읽기 전용으로 엽니다.

~~~bash
python3 evidence-hash-lab.py
~~~

| 시험 | 기대 결과와 해석 |
| --- | --- |
| 그대로 복사 | 기준 SHA-256과 일치 |
| 사본 이름 변경 | 바이트가 같으므로 해시도 동일 |
| LF에서 CRLF로 줄바꿈 변경 | 눈으로 읽은 내용은 비슷해도 해시가 달라짐 |
| ZIP 생성·내부 파일 읽기 | ZIP은 별도 해시, 안의 파일은 기준과 일치 |

마지막에 `DONE: four checks passed; original fixture unchanged`가 나옵니다. 파일을 찾지 못하면 두 파일의 이름과 폴더를 확인합니다. 줄바꿈 확인 오류는 원본 파일을 다시 내려받아 점검하세요. ZIP 자체의 해시는 생성 시각 같은 메타데이터에 따라 재실행 때 달라질 수 있습니다. 각 전달본과 **그 전달본의 기준 해시**를 대조합니다. 게시 과정에서는 로컬 파일 읽기·복사·압축과 네 검사를 실행했습니다. 실제 사건 기록, 장비 수집 또는 법적 인계 절차를 검증한 것은 아닙니다.

## 6. 확인 문제와 완료 기준

- **해시가 같으면 자료가 진실이고 완전한가요?** 기준과 바이트가 일치합니다. 출처, 적용 필터, 누락 및 수집 전 내용은 별도 증거가 필요합니다.
- **민감정보를 가린 보고서의 해시가 원본과 달라도 되나요?** 파생 자료에는 별도 해시와 원본 ID, 변환 방법을 기록합니다.
- **ZIP의 해시가 내부 파일과 다르면 무조건 손상인가요?** ZIP과 내부 파일은 각각 자신의 기준 해시와 비교합니다.

작업 사본과 변환 사본의 기대 결과를 설명하고, 가상 자료 ID·출처·UTC·기준 해시·인계 대상을 한 줄에 기록하면 완료입니다.
