클라이언트가 서로 관련된 두 사이트를 엽니다. 한 요청은 성공하지만 다른 요청은 `421 Misdirected Request`를 받고, 재시도 뒤에 성공합니다. 첫 연결의 인증서도 두 이름에서 유효할 수 있습니다. 연결에서 협상한 정보와 각 요청의 대상, 서버가 실제로 처리한 결과를 비교해 원인을 좁혀 봅시다. SNI와 ALPN이 익숙하지 않다면 [TLS 핸드셰이크와 관측 증거]({{ '/ko/wiki/tls-handshake-evidence/' | relative_url }})부터 읽어 보세요.

## 1. 각 필드의 적용 범위를 확인하세요

**오리진**은 스킴, 호스트, 포트로 구분합니다. **연결**은 HTTP/2 프레임을 전달하며, **스트림**은 그 연결 안에서 번호가 붙은 프레임의 흐름입니다. 연결 하나에 여러 스트림을 동시에 열 수 있습니다. 일반적인 요청과 응답은 스트림 하나를 공유하며, 스트림 ID는 해당 연결 안에서만 의미가 있습니다.

| 관측값 | 범위 | 무엇을 알 수 있나요? |
| --- | --- | --- |
| TLS SNI | 연결 하나의 TLS 핸드셰이크 | TLS 설정 선택에 사용하는 요청 서버 이름. 재사용 조건이 맞으면 이후 HTTP 요청의 오리진이 달라질 수 있음 |
| 인증서와 호스트 이름 검사 | 클라이언트가 검증한 상대 신원 | 한 인증서가 여러 이름을 담을 수 있음. 재사용 후보마다 신뢰와 호스트 이름 검사, 상대가 해당 오리진을 맡는지 확인 |
| 선택된 ALPN `h2` | TLS 연결 하나에서 협상된 애플리케이션 프로토콜 | 양쪽에서 HTTP/2를 선택. 개별 요청과 결과에는 별도 증거가 필요 |
| HTTP/2 `:authority` | 요청 스트림 하나 | 대상 URI의 권한부. 이 필드가 있으면 `Host`로 요청 대상을 정하지 않음 |
| HTTP/2 `:status` | 응답 스트림 하나 | 해당 구간에서 그 요청이 받은 결과. 다른 스트림의 결과나 처음 응답을 만든 지점은 별도로 확인 |

**연결 재사용(coalescing)**은 서로 다른 권한부를 대상으로 한 연결을 공유하는 방식입니다. RFC 9113은 연결한 서버가 요청 대상 오리진을 맡는 경우 재사용을 허용합니다. HTTPS에서는 새 연결을 열 때 대상 호스트에 대해 수행할 인증서 검사를 통과해야 합니다. 공유 주소, 인증서, 적용되는 오리진 선택 정책은 각각 다른 정보를 줍니다. IP가 같거나 인증서의 SAN에 두 이름이 들어 있다고 해서 요청이 올바르게 라우팅된다고 판단하기는 어렵습니다. 조건을 만족해도 클라이언트는 연결을 재사용하지 않을 수 있습니다. 선택 기능인 HTTP/2 ORIGIN 프레임을 구현한 클라이언트는 서버가 알린 오리진 집합을 참고할 수 있습니다. 인증서 검사는 여전히 필요합니다.

## 2. 정상 요청과 잘못 전달된 요청을 따라가세요

가상 환경에서 `alpha.example.test`와 `beta.example.test`는 주소를 공유하고 인증서에도 두 이름이 있습니다. 클라이언트는 SNI `alpha.example.test`로 TLS를 시작하고 ALPN `h2`를 선택합니다. 스트림 1에서 `alpha.example.test`의 `GET /catalog`를 요청하면 alpha 서비스가 `200`을 반환합니다. 같은 연결에서 alpha로 보낸 다른 요청도 새 스트림 ID로 정상 처리될 수 있습니다.

이제 기존 연결의 다음 요청 대상이 beta라고 가정합니다. 연결된 서비스가 beta를 처리할 수 있고 클라이언트의 오리진 검사도 통과하면 재사용이 성공할 수 있습니다. 하지만 이 환경에서 alpha SNI가 선택한 리스너는 alpha만 처리합니다. 스트림 3으로 도착한 beta 요청은 `421`을 받습니다. 클라이언트가 beta SNI로 다른 TLS 연결을 열고 재시도하자 beta 리스너가 그 연결의 스트림 1에 `200`을 반환합니다. 두 스트림 1은 서로 다른 연결에 속합니다.

RFC 9110은 421을 받은 클라이언트가 멱등 여부와 관계없이 다른 연결에서 해당 요청을 재시도할 수 있다고 설명합니다. 이 실습은 GET 요청을 명시적으로 재시도합니다. 감사 또는 앱 로그를 읽을 때 최초 시도와 재시도를 각각 구분하세요. RFC 9110에 따르면 일반 프록시는 421을 생성하면 안 됩니다. 리버스 프록시라고 불리는 제품이 421을 보냈다면, 오리진을 대신하는 게이트웨이 역할로 응답을 만들었는지 업스트림 응답을 전달했는지 확인하세요. 제품 이름만으로 응답의 출처를 알 수는 없습니다.

## 3. 라우팅 장애와 오용을 구분하세요

인증서의 이름 범위를 넓히거나 가상 호스트를 바꾼 뒤, 또는 연결별 경로와 요청별 대상이 맞지 않을 때 정상적으로 421이 나올 수 있습니다. 배포 직후 응답 수가 늘었다면 변경 내역과 비교하세요. 예상 밖 권한부는 사전 탐색이나 다른 테넌트로 접근하려는 시도일 수도 있습니다. 승인된 리스너·테넌트 설정과 실제 대상을 비교하고 인증된 클라이언트 정보나 요청 기록, 경로 결정 결과로 의도를 판단하세요. 프로토콜 선택, 공유 인증서, 이름 차이는 단서입니다.

수동 패킷 캡처에서 연결 시각을 확인할 수 있고, 캡처 조건이 맞고 ClientHello가 암호화되지 않았다면 제안된 ALPN과 SNI도 볼 수 있습니다. ECH를 쓰면 관찰 가능한 이름과 확장의 범위가 달라집니다. TLS 1.3에서 선택된 ALPN은 암호화된 핸드셰이크에 들어 있고, TLS로 전송되는 HTTP/2 스트림 헤더 역시 암호화됩니다. 요청 권한부와 연결 이름을 구분하려면 승인된 클라이언트나 TLS 종료 지점의 자료를 확인하세요. 연결 하나에 여러 요청이 들어가므로 패킷 수나 다른 구간의 스트림 ID만으로 요청을 식별할 수 없습니다.

## 4. 블루팀 수집·탐지·대응

| 수집 위치 | 기록할 항목과 조건 |
| --- | --- |
| 클라이언트 또는 엣지 TLS 로그 | UTC 핸드셰이크 시각, 프로세스나 노드 범위의 연결 ID, 확인 가능한 SNI, 선택된 ALPN, 인증서 식별자나 검증 결과, 전송 상대 |
| 접근 가능한 구간의 HTTP 요청 로그 | 가능한 경우 그 구간의 연결·스트림 ID, 필요한 범위의 원본·정규화 권한부, 메서드, 상태, 경로 식별자, 업스트림 상대, 요청·추적 ID, 시각 |
| 오리진·게이트웨이·배포 기록 | 로컬에서 생성한 상태인지 업스트림에서 받은 상태인지, 당시 정책, 리스너와 인증서 배포 이력, 새 연결에서의 성공 여부 |

범위를 아는 식별자로 기록을 연결하세요. HTTP/2 연결과 스트림 ID는 보통 TLS·HTTP 종료 지점까지만 이어집니다. 게이트웨이가 업스트림 연결을 새로 연다면 신뢰할 수 있는 요청 ID나 추적 ID로 구간을 넘겨 연결하세요. 재시도 관계가 기록됐을 때는 그 정보로 시도를 묶습니다. 시각만으로 연결하면 동시에 처리된 요청을 혼동할 수 있습니다.

로컬 응답과 전달된 상태를 분리한 뒤 리스너, 요청 권한부, 경로별로 421을 집계하세요. 전체 요청 대비 비율과 배포 시점, 새 연결에서의 회복 여부를 비교합니다. 승인된 호스트 이름 두 개로 정상 동작을 확인할 수 있습니다. 승인 시점 밖에서 라우팅이 바뀌면 설정과 로그를 보존하고 오리진 집합, 인증서 범위, 가상 호스트 정책을 대조하세요. 승인된 절차로 경로를 수정한 뒤 정상 요청과 합법적 연결 재사용을 확인하세요. 421만으로 정보가 노출됐다고 판단하기는 어렵습니다. 다른 테넌트의 데이터가 실제로 반환됐다면 그 응답을 별도로 조사합니다.

## 5. 승인된 루프백 실습

<a href="{{ '/assets/labs/http2-connection-reuse-evidence.cjs' | relative_url }}" download>Node.js 실습 파일</a>을 내려받아 소유하거나 사용을 승인받은 환경에서 실행하세요. `127.0.0.1`의 임시 포트에서 두 시험용 이름을 담은 임시 인증서로 HTTP/2 오리진을 흉내 냅니다. 클라이언트는 이 실습에서만 해당 인증서를 신뢰하고 호스트 이름 검사도 유지합니다. 외부 네트워크에 접속하지 않습니다. HTTP/2를 지원하는 Node.js 22 이상과 인증서 생성용 OpenSSL 3.x가 필요합니다.

```bash
node http2-connection-reuse-evidence.cjs
```

실습은 같은 연결에서 두 요청을 명시적으로 보내고 별도 연결에서 재시도합니다. 브라우저의 오리진 선택이나 재시도 알고리즘은 구현하지 않습니다. 시험 서버는 해당 연결의 경로가 대상 호스트를 제공하지 않으면 421을 반환합니다.

| 기대 관측 | 확인할 점 |
| --- | --- |
| 두 연결에서 양쪽이 `h2`를 협상 | 실제 로컬 HTTP/2 over TLS 관측 |
| 첫 연결의 인증서 검사에서 시험용 이름 두 개가 일치 | 호스트 이름이 맞아도 요청 경로는 거부될 수 있음 |
| 연결 하나의 서로 다른 스트림에서 alpha는 200, beta는 421 | 요청마다 대상 권한부가 있음 |
| beta가 새 연결에서 200을 받고 스트림 번호가 다시 시작 | 연결 ID와 스트림 ID를 함께 봐야 함 |

기대 출력은 `4/4 HTTP/2 controls passed.`입니다. 포트 열기에 실패하면 실행 환경이 로컬 소켓을 허용하는지 확인하세요. 인증서 생성에는 PATH에서 찾을 수 있는 `openssl`이 필요하며, 클라이언트는 생성한 시험 인증서를 신뢰 자료로 사용합니다. 운영 리스너의 라우팅과 브라우저의 재시도는 실습 범위 밖입니다. 운영 관련 설명은 아래 공식 규격을 기준으로 검토했습니다.

## 6. 확인 문제와 완료 기준

1. **SNI는 alpha, `:authority`는 beta입니다. 공격이라고 판단해도 되나요?** 재사용 조건을 충족했는지, 리스너가 해당 스트림을 어떻게 처리하거나 거부했는지부터 확인하세요.
2. **인증서에 beta가 있는데 왜 421이 나올 수 있나요?** 인증서 검사는 통과해도 연결한 서비스가 해당 연결에서 beta를 처리하지 않을 수 있습니다. 리스너 경로 정책과 요청 오리진을 비교하세요.
3. **두 로그 모두 스트림 1을 보여 줍니다. 무엇이 더 필요한가요?** 스트림이 속한 연결과 관측 지점을 확인하세요. 종료 지점을 넘어 연결할 때는 전달된 요청 ID가 도움이 됩니다.

**완료 기준.** 421과 재시도를 재현하고 각 필드가 기록된 계층, 응답을 만든 곳을 확인하려면 필요한 자료를 설명하세요. 이어서 [HTTP 요청·응답 조사]({{ '/ko/wiki/http-evidence/' | relative_url }})나 [QUIC과 HTTP/3]({{ '/ko/wiki/quic-http3-evidence/' | relative_url }})를 살펴보세요.
