**학습 목표.** 저널에서 기록 한 줄이 보이지 않을 때 가능한 이유를 설명합니다. 로컬 기록과 중앙 수집본을 대조해 어느 단계의 증거가 더 필요한지 판단합니다. 이 장은 systemd-journald를 사용하는 호스트에 적용합니다.

## 1. 메시지가 조사자에게 오기까지 따라가세요

**유닛(unit)**은 서비스처럼 systemd가 관리하는 대상입니다. **journald**는 커널, syslog, 저널 API, 서비스의 표준 출력과 오류 출력 등에서 메시지를 받습니다. **저널**에는 본문과 함께 구조화된 메타데이터가 붙으며, 설정에 따라 저장됩니다. **journalctl**은 저널을 읽습니다. 중앙 전달 에이전트와 색인 시스템은 이 과정에서 필드를 바꾸거나 일부만 선택하거나 전송을 재시도할 수 있습니다.

![서비스 메시지가 journald에 도착하면 로컬 저널에서 확인할 수 있습니다. 설정된 전달 에이전트가 읽은 기록은 중앙에서 색인되며, 조사자는 두 지점의 자료를 대조합니다.]({{ '/assets/diagrams/journal-coverage-ko.svg' | relative_url }})

그림은 로컬 저널을 읽는 전달 방식을 보여 줍니다. syslog로 직접 전달하는 구성은 수집 지점이 다를 수 있습니다. **저널 네임스페이스(namespace)**는 한 호스트에서 로그 흐름과 저장소를 나누는 단위입니다. 이름이 붙은 네임스페이스로 기록하는 앱은 기본 보기에서 빠질 수 있습니다. 별도의 로그 드라이버를 쓰는 Linux 컨테이너도 수집 경로가 다를 수 있습니다.

| 자료 | 확인할 내용 | 한계 |
| --- | --- | --- |
| `_MACHINE_ID`, `_BOOT_ID` | 원본 호스트와 부팅을 구분. 자산 목록을 함께 확인 | 호스트명은 재사용될 수 있고 복제 이미지에서는 머신 ID가 중복될 수 있음 |
| `_SYSTEMD_UNIT`, `_PID` | 필드가 있을 때 유닛과 프로세스 문맥 확인 | PID는 재사용됨. 상속된 표준 출력·오류에는 스트림을 연 프로세스의 자격 정보가 붙을 수 있음 |
| `SYSLOG_IDENTIFIER`, `MESSAGE` | 앱의 식별자와 메시지 문맥 확인 | 클라이언트가 제공한 값이므로 실제 신원을 확인하려면 다른 근거가 필요 |
| `__CURSOR` | 보존된 경우 저널 내 엔트리 위치를 식별 | 내부 구조를 해석하거나 정렬하지 않음. 전달기가 값을 누락하거나 교체할 수 있음 |
| `__REALTIME_TIMESTAMP`, `__MONOTONIC_TIMESTAMP` | 벽시계 표시와 한 부팅 안의 수신 순서를 비교 | 둘 다 저널의 수신 시각. 앱 내부에서 발생한 시각과 차이가 날 수 있으며, 단조 시각은 부팅마다 새로 시작 |

밑줄 하나로 시작하는 필드는 기본 수집에서 저널이 붙입니다. 밑줄 두 개로 시작하는 위치 관련 메타데이터는 내보낼 때 표시됩니다. 중앙 JSON에 같은 필드가 있다고 해서 모두 같은 경로에서 만들어졌다고 가정하지 마세요. 원본 호스트와 내보낸 경로가 신뢰할 만한지 확인합니다.

## 2. 정상 수집과 시계가 뒤로 움직인 사례

`reports.service`가 정상 상태 메시지를 남긴다고 가정합니다. 로컬 내보내기에는 머신, 부팅, 커서가 들어 있습니다. 중앙 전달기는 원본 네임스페이스와 관련 필드를 보존했습니다. 두 자료에서 해당 범위의 커서와 본문이 일치하면 그 엔트리가 중앙에 수집됐다는 근거가 됩니다. 재시도 후 같은 기록이 두 번 도착할 수도 있습니다. 양쪽 원본은 보존하고, 중복임을 확인한 뒤 타임라인에서는 한 번만 셉니다.

같은 호스트·네임스페이스·부팅에서 두 메시지의 시각을 비교합니다. 아래 값은 가상 실습을 쉽게 읽도록 바꾼 것입니다.

| 엔트리 | UTC 벽시계 | 부팅 후 단조 시각 | 판단 |
| --- | --- | --- | --- |
| LAB-01 | 00:00:10 | 100초 | 저널이 먼저 수신 |
| LAB-02 | 00:00:06 | 102초 | 단조 시각 기준 2초 뒤에 수신. 그 사이 벽시계는 뒤로 이동 |

실제 내보내기 값의 단위는 마이크로초입니다. 같은 부팅 안에서 단조 시각으로 수신 순서를 비교하고, 벽시계가 움직인 구간은 따로 표시하세요. 다른 호스트나 부팅의 100초는 다른 기준에서 잰 값입니다. 중앙 색인 시각에는 버퍼링과 파싱, 대기 시간도 포함될 수 있습니다.

## 3. 이전 부팅이 빠진 원인을 좁혀 보세요

systemd 257에서 `Storage=volatile`은 `/run/log/journal`에 저장합니다. 그곳에만 남은 기록은 보통 재부팅 뒤 사라집니다. `Storage=persistent`는 `/var/log/journal`에 우선 저장하지만 초기 부팅이나 디스크를 쓸 수 없는 경우 런타임 저장소를 사용할 수 있습니다. 기본 네임스페이스의 `Storage=auto`는 영구 저장 디렉터리 존재 여부에 따릅니다. 설정 파일과 추가 설정을 함께 보고, 대상 네임스페이스에서 실제 적용된 값을 확인하세요. 용량과 보존 정책은 남아 있는 파일 범위를 바꿉니다. 서비스별 속도 제한에 걸리면 일부 메시지가 버려지고 억제 건수가 기록될 수 있습니다. 앱이 조용했거나 다른 곳에 로그를 썼을 가능성도 확인합니다.

권한을 얻은 사람이 수집을 방해하거나 로컬 증거를 바꿀 수도 있습니다. 설정 변경 기록, 유지보수 일정, 디스크 상태와 중앙 사본을 대조하세요. 이전 부팅이 중앙에만 남아 있다면 정상적인 보존 기간이나 휘발성 저장도 설명이 됩니다. 로컬에만 남아 있고 두 관측 범위가 같다면 전달과 검색 과정부터 좁혀 조사하세요. 이 단서만으로 누가 누락을 일으켰는지는 알 수 없습니다.

## 4. 블루팀 수집·탐지·대응

1. **조사 범위를 고정합니다.** 원본 호스트, 부팅 ID, 네임스페이스, 유닛, UTC 시간 범위와 읽기 권한을 기록합니다. 로컬과 중앙의 보존 범위를 각각 확인하세요. `--list-boots`의 시작과 끝은 보이는 첫 메시지와 마지막 메시지의 시각입니다. 전원 켜짐·꺼짐 시각이나 과거 부팅 전체 목록으로 쓰기에는 근거가 제한적입니다.
2. **원본을 보존하고 작업 사본을 조회합니다.** 증거 절차에 따라 저널 파일과 해시, 중앙 내보내기 결과, 시스템 식별 자료를 함께 남기세요. 비밀 값이 메시지나 메타데이터에 있을 수 있으므로 읽기 권한이 있는 계정으로 제한된 사본을 조회합니다. 아래는 복제한 저널 파일 디렉터리와 첫 명령에서 얻은 부팅 ID를 사용하는 예입니다. 경로와 ID는 승인된 값으로 바꾸세요.

   ```sh
   journal_copy='/path/to/copied-journal-files'
   boot_id='bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb'
   journalctl --directory="$journal_copy" --utc --list-boots --no-pager
   journalctl --directory="$journal_copy" --utc -o json --all --no-pager \
     "_BOOT_ID=$boot_id" "_SYSTEMD_UNIT=reports.service"
   ```

   두 번째 명령은 해당 유닛 메타데이터와 정확히 일치하는 메시지를 고릅니다. systemd 관리자가 그 유닛에 대해 남긴 메시지는 다른 필드에 있을 수 있습니다. 필요하면 지정한 범위를 넓히거나 `-u`가 어떤 필드를 검색하는지 문서를 확인하세요. JSON에서 반복 필드나 텍스트로 표현할 수 없는 바이트는 배열이 될 수 있습니다. systemd 257의 일반 JSON 출력에서 4,096바이트를 넘는 값은 `null`일 수 있고, `--all`을 쓰면 더 큰 값도 출력할 수 있습니다. 내보낸 자료와 함께 원본을 보존하세요.
3. **무결성과 전달을 각각 확인합니다.** 사본의 `journalctl --verify`로 내부 일관성을 검사할 수 있습니다. Forward Secure Sealing의 진위 검증에는 봉인된 파일과 해당 검증 키가 필요합니다. 두 검사 모두 과거 기록이 빠짐없이 저장됐음을 보장하지는 않습니다. 호스트·네임스페이스 매핑, 전달기 상태와 저장 위치, 대기열·재시도, 파싱 오류, 색인 지연, 보존 기간과 검색 권한을 단계별로 확인합니다. 중복을 제거하기 전에 값이 다른 행은 원본과 대조하세요.
4. **수집이 복구됐는지 검증합니다.** 승인된 테스트 호스트에서 민감 정보 없는 표식 한 줄을 `printf '%s\n' 'wiki-journal-check-01' | systemd-cat -t wiki-journal-check`로 남깁니다. 같은 호스트와 대상 네임스페이스에서 `journalctl --since '5 minutes ago' -t wiki-journal-check --no-pager`로 찾고, 평소 전달 시간이 지난 뒤 중앙에서도 확인하세요. 태그는 클라이언트가 넣은 값이므로 시각과 원본을 함께 확인합니다. 이 시험은 표식이 지나간 경로만 검증합니다. 운영 유닛은 그 유닛에 설정된 경로를 이용하는 승인된 시험으로 확인하세요.

## 5. 오프라인 실습 · 가상 기록 여덟 건 대조하기

[가상 기록 파일]({{ '/assets/labs/journal-coverage-cases.json' | relative_url }})과 [Python 검토 스크립트]({{ '/assets/labs/journal-coverage-review.py' | relative_url }})를 같은 폴더에 내려받고 `python3 journal-coverage-review.py`를 실행하세요. Python 3.8 이상과 표준 라이브러리를 사용합니다. 로컬·중앙 내보내기를 흉내 낸 자료이며, 네임스페이스를 별도로 표시했습니다. 커서도 학습용 문자열입니다. 스크립트는 이 파일만 읽고 실제 호스트 로그를 조회하지 않습니다.

| 사례 | 예상 결과 |
| --- | --- |
| LAB-01·02 | 두 건 모두 일치. 같은 부팅에서 벽시계가 뒤로 움직인 내용 표시 |
| LAB-03·04 | 현재 부팅의 로컬 단독 기록과 이전 부팅의 중앙 단독 기록 |
| LAB-05·06 | 같은 식별 범위에 서로 다른 본문. 별도 중앙 행에는 커서가 없음 |
| LAB-07·08 | 같은 기록이 중복 전달됨. LAB-08은 커서가 같아도 네임스페이스가 달라 두 행으로 구분 |

비교 결과 아홉 줄과 시계 관련 결과 한 줄이 나옵니다. 다르게 나오면 파일 이름부터 확인한 뒤 머신 ID, 부팅 ID, 네임스페이스, 커서를 대조하세요. 실습에서는 중앙 도구가 해당 원본 필드를 보존한다고 가정합니다. 운영 데이터에서 필드가 빠졌다면 추가 증거가 필요합니다. 시각과 본문만 같다는 이유로 동일 엔트리로 확정하지 마세요.

가상 실습은 클라우드에서 실행했습니다. systemd 257.13으로 빈 입력 디렉터리의 `journalctl --list-boots`도 실행해 기록이 없을 때의 동작을 확인했습니다. 실제 메시지 생성, 전달 및 저장 동작은 공식 문서로 검토했습니다.

## 6. 확인 문제와 완료 기준

- **이전 부팅이 로컬에서 안 보이면 무엇을 알 수 있나요?** 읽을 수 있는 파일 범위에 그 부팅 기록이 없다는 사실입니다. 저장 방식, 보존 범위와 중앙 사본을 확인하세요.
- **커서는 같은데 로컬과 중앙의 본문이 다르면 어느 쪽을 쓰나요?** 두 기록을 보존하고 원본 저널, 출처, 변환 규칙을 확인합니다.
- **서로 다른 부팅의 단조 시각을 비교해도 되나요?** 부팅별로 따로 해석합니다. 부팅을 넘는 순서는 벽시계나 외부 시간 근거가 필요합니다.
- **새 표식이 중앙에 도착했으면 과거 전달도 검증했나요?** 시험한 메시지, 시각과 경로의 전달을 확인한 것입니다.

**완료 기준.** LAB-03과 LAB-04에서 다음에 확보할 자료를 각각 적으세요. 시계 변화와 LAB-08에서 결과가 두 건 나온 이유를 설명하면 완료입니다.
