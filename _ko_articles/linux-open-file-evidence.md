서비스 로그의 이름을 지웠는데도 디스크 사용량이 줄지 않습니다. 예전 경로는 사라졌지만 서비스에는 열린 디스크립터가 남아 있습니다. 관측 시간 범위를 기록하고, 열린 파일 객체와 현재 경로, 해당 프로세스 인스턴스를 비교해 보세요.

## 1. 경로 이름과 열린 파일의 수명은 다릅니다

**경로 이름**을 조회하면 디렉터리 항목을 거쳐 파일 객체에 도달합니다. **inode**는 하드 링크 수 같은 메타데이터를 포함해 파일시스템 안의 파일을 나타냅니다. 서로 다른 디렉터리 항목이 같은 inode를 가리킬 수 있습니다. **장치와 inode 번호의 조합**은 특정 파일시스템 관점에서 살아 있는 객체를 식별하는 단서입니다. 마운트와 시각도 남기세요. inode 번호는 나중에 재사용될 수 있고 다른 장치에서 같은 번호를 볼 수 있습니다.

**파일 디스크립터(FD)**는 프로세스의 테이블에 있는 작은 정수입니다. FD가 가리키는 **열린 파일 기술(open file description)**에는 파일 내 위치와 상태 플래그가 저장됩니다. 복제된 FD는 같은 열린 파일 기술과 오프셋을 공유할 수 있습니다. 같은 inode를 독립적으로 열면 오프셋이 서로 다를 수 있습니다. FD 자체의 번호도 닫힌 뒤 다시 쓰일 수 있습니다.

`unlink`는 디렉터리 항목을 제거합니다. 해당 이름이 마지막 하드 링크였고 프로세스가 여전히 열어 둔 상태라면 그 참조를 통해 파일을 쓸 수 있습니다. 마지막 관련 참조가 해제되면 파일시스템이 공간을 회수할 수 있습니다. 이런 관측으로 누가 파일을 읽었는지 또는 어떤 바이트를 사용했는지 알 수는 없습니다.

| 증거 | 답할 수 있는 질문 | 함께 확인할 점 |
| --- | --- | --- |
| 현재 경로와 메타데이터 | 지금 그 이름이 어떤 객체를 가리키나요? | 장치, inode와 마운트 |
| `/proc/PID/fd/N` 링크 | 관측 시점에 FD N이 무엇을 가리켰나요? | 객체 유형, 프로세스 수명, 반복 관측 |
| `/proc/PID/fdinfo/N` | 오프셋, 8진수 플래그, 마운트 ID와 유형별 정보는 무엇인가요? | 해당 마운트의 관점과 FD 변경 여부 |
| 디스크립터를 통한 메타데이터 | 객체 유형, 장치·inode, 크기와 링크 수는 무엇인가요? | 읽기·쓰기 변화와 수집 시각 |
| 감사 또는 배포 기록 | 작업이 기록됐다면 누가 왜 했나요? | 작업 결과, 원래 객체의 식별 정보와 서비스 영향 |

## 2. 정상 로그 회전 한 건 따라가기

가상 Linux 호스트에서 서비스가 10:00 UTC에 `status.log`를 엽니다. FD 7은 로그 파일시스템의 inode 410을 가리킵니다.

1. 10:10에 로그 회전 서비스가 이름을 `status.log.1`로 바꾸고 같은 장치에 inode 422인 새 `status.log`를 만듭니다. 원래 FD는 계속 inode 410을 가리킵니다. 서비스가 로그를 다시 열기 전이라면 새 경로를 읽는 사람과 FD 7로 로그를 쓰는 서비스는 서로 다른 파일을 보고 있습니다.
2. 10:20에 보존 작업이 `status.log.1`을 연결 해제합니다. 원래 FD가 남아 있다면 proc 링크 끝에 `(deleted)`가 붙고 링크 수는 0일 수 있습니다. 디렉터리 목록으로 계산한 크기보다 디스크 사용량이 더 클 수 있습니다.
3. 10:22에 승인된 설정 다시 읽기로 서비스가 로그를 다시 엽니다. 프로세스와 FD를 다시 확인하세요. 같은 번호 7이 이제 inode 422를 가리킬 수 있습니다. 새 로그에 항목이 들어오는지와 저장 공간 지표를 확인하세요. 다른 FD, 메모리 매핑과 파일시스템 동작도 공간 회수에 영향을 줍니다.

경로 끝의 `(deleted)`는 화면상 단서입니다. 실제 파일명에도 같은 문구가 들어갈 수 있으므로 객체 유형과 링크 수를 확인하세요. 이름 없이 생성한 임시 파일처럼 링크가 0인 일반 파일을 의도적으로 만드는 경우도 있습니다. 정상 로그 회전, 임시 작업 파일과 업그레이드에서도 경로를 고의로 없앴을 때와 비슷한 관측이 나올 수 있습니다. proc 링크 하나로 행위자, 악의적 의도, 실행이나 전송을 확인할 수 없습니다.

## 3. 수집·탐지·대응

1. **어느 관점에서 봤는지 기록합니다.** 호스트, 부팅 식별자, UTC 수집 시각, PID·마운트 네임스페이스와 프로세스 시작 시각을 남기세요. `/proc/PID/stat`의 22번 필드는 부팅 이후의 시작 시각을 클럭 틱으로 나타냅니다. 원본을 보존하고 괄호로 둘러싼 프로세스 이름을 처리할 수 있는 파서를 사용하세요. 전체 줄을 공백으로만 나누면 필드 위치가 달라질 수 있습니다. 컨테이너에서 보이는 PID와 호스트의 PID는 다를 수 있습니다.
2. **먼저 메타데이터를 수집합니다.** FD 번호, 원본 링크, `fdinfo`와 대상 메타데이터를 남기세요. proc 링크는 일반 파일, 소켓, 파이프나 커널 객체를 가리킬 수 있습니다. 임의의 FD를 바이트 스트림으로 읽으면 파이프 데이터를 소비하거나 읽기가 멈출 수 있습니다. 파일 본문은 승인된 수집기가 실제 객체가 일반 파일인지 확인하고 크기를 제한하며 식별 정보·UTC 시각·해시를 남기는 경우에만 수집하세요. 열린 파일은 수집 중 바뀔 수 있으며 해시는 수집한 바이트에 대한 값입니다.
3. **프로세스와 마운트 식별 정보를 대조합니다.** 보이는 경우 `fdinfo`의 `mnt_id`를 같은 프로세스의 `mountinfo`에서 마운트 ID 열과 비교합니다. 대응 항목이 없으면 다른 뷰의 마운트나 이미 분리된 마운트의 FD일 수 있습니다. 대조할 수 없다는 점을 공백으로 남기세요. 오프셋은 그 시점의 파일 내 위치입니다. 해당 프로세스가 읽은 누적 바이트 수가 아닙니다. 수집 전후에 시작 시각과 메타데이터를 반복 확인하세요. 항목이 사라진 것은 정상적인 닫기나 종료일 수도 있습니다. 반복 관측으로 모호함을 줄일 수 있지만 여러 조회가 한 시점에 이뤄진 것은 아닙니다.
4. **평소 상태와 가능한 원인을 비교합니다.** 오래 유지되는 링크 0 일반 파일을 서비스, 마운트, 크기와 첫 관측 이후 경과 시간으로 비교하세요. 로그 회전, 패키지, 애플리케이션 기록을 연결합니다. 로그를 다시 열어야 할 시점 이후에도 링크 0 파일의 크기가 늘면 파일 관리 누락이나 서비스 장애일 수 있습니다. 민감한 파일이라면 누가 열었는지, 서비스 역할은 무엇인지, 해당 작업을 감사 규칙이 수집했는지 확인합니다. 이벤트 시각, 감사 결과, 객체 식별 정보가 중요합니다. 같은 inode를 여러 FD가 가리킬 때 공간을 중복 합산하지 않도록 주의하세요.
5. **판단 근거를 남깁니다.** 정상 로그 재열기는 새 앱 기록과 저장 공간 지표로 확인합니다. 독립된 증거가 의심을 뒷받침하면 가능할 때 재시작 전에 승인된 바이트와 메타데이터를 보존하세요. 재시작하면 유일하게 남은 참조가 닫힐 수 있습니다. 당시 감사 기록이 없다면 관측된 객체만 보고하고 누가 연결을 해제했는지나 바이트가 사용됐는지는 미확인으로 남깁니다.

### 승인된 Linux 호스트에서 메타데이터만 확인하기

승인된 자산 목록이나 수집기가 알려 준 PID와 FD를 사용하세요. 아래 숫자는 변수 사용을 보여 주는 예시입니다. GNU Coreutils와 procfs가 필요합니다. 승인된 읽기 권한으로 대상과 맞는 네임스페이스에서 실행하세요. 파일 본문을 복사하지 않고 현재 상태를 관측합니다.

~~~bash
pid=12015
fd=7
readlink -- "/proc/$pid/fd/$fd"
stat -L -c 'type=%F dev=%d inode=%i links=%h bytes=%s' -- "/proc/$pid/fd/$fd"
sed -n '/^pos:/p; /^flags:/p; /^mnt_id:/p; /^ino:/p' "/proc/$pid/fdinfo/$fd"
~~~

권한 오류는 수집 한계로 기록합니다. proc 링크를 읽거나 따라갈 수 있는지는 접근 검사 결과에 달려 있습니다. `hidepid`, 네임스페이스와 보안 정책이 가시성을 제한할 수 있습니다. 항목이 없다면 프로세스 수명, FD를 닫았는지, 관측 범위를 확인하세요. 거부되거나 빠진 값은 추정으로 채우지 않습니다.

## 5. 확인 문제와 완료 기준

1. **새 로그 경로와 이전 FD가 모두 보이면 프로세스가 로그를 다시 열었나요?** 장치와 inode를 대조하세요. 새 경로는 교체 파일에 이어지고 기존 FD는 여전히 예전 파일을 가리킬 수 있습니다.
2. **FD 두 개의 inode가 같으면 오프셋도 공유하나요?** 하나의 열린 파일 기술을 복제했다면 공유합니다. 독립적으로 두 번 연 경우 오프셋은 서로 다를 수 있습니다.
3. **`pos`가 크면 바이트가 전송됐나요?** 탐색으로 오프셋을 옮길 수 있고 다른 참조가 파일을 사용했을 수도 있습니다. 전송에는 네트워크나 서비스 증거가 필요합니다.
4. **오래 실행된 서비스에 링크 0 일반 파일이 있습니다. 정상 회전과 오용은 어떻게 구분하나요?** 보존 작업, 배포, 감사·프로세스 기록과 앱의 예상 동작을 비교하세요. 링크 수는 파일 객체의 상태를 설명합니다.

네 가지 관측을 재현하고, 관측 범위, PID와 시작 식별 정보, FD, 장치·inode, 링크 수, UTC 시각과 추가 증거가 필요한 질문 하나를 적으면 완료입니다.
