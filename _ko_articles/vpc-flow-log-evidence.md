클라이언트는 서비스에 연결하지 못했다고 합니다. 로그에는 나가는 트래픽의 `ACCEPT`와 해당 인터페이스의 `SKIPDATA`가 보입니다. 어디서 어느 방향을 언제 관측했는지, 로그가 무엇을 놓쳤을 수 있는지부터 구분하세요. 애플리케이션의 처리 결과는 별도 증거로 확인합니다.

## 1. 흐름 한 줄은 특정 지점에서 본 기록입니다

Amazon **VPC**는 논리적으로 격리된 클라우드 네트워크입니다. **서브넷**은 VPC 안의 주소 범위이고, **ENI**(탄력적 네트워크 인터페이스)는 가상의 네트워크 인터페이스입니다. VPC Flow Logs는 VPC, 서브넷 또는 네트워크 인터페이스 범위로 설정할 수 있습니다. **구독**은 관측 대상 리소스, 수집할 트래픽 유형, 전달 설정을 정합니다. VPC나 서브넷 전체로 설정해도 일반적인 ENI 흐름은 인터페이스별로 기록됩니다.

흐름 한 줄은 집계 구간에 관측한 한 방향의 IP 트래픽을 요약합니다. **5튜플**은 출발지·목적지 주소와 포트, 전송 프로토콜의 조합입니다. 조사할 때는 관측 지점, 계정, 리전, 시간도 함께 기록하세요. 다른 네트워크나 같은 ENI의 다른 시각에도 동일한 5튜플이 나올 수 있습니다. 패킷 순서나 요청 처리 결과는 패킷 캡처와 앱 로그에서 확인합니다.

| 필드 묶음 | 읽는 방법 | 해석 범위 |
| --- | --- | --- |
| `interface-id`, `flow-direction` | 관측 인터페이스로 들어오면 ingress, 나가면 egress입니다. | 인터페이스 기준입니다. 인터넷으로 들어오고 나가는 방향과는 다를 수 있습니다. |
| `srcaddr`, `dstaddr`, 포트, `protocol` | 관측점에서 기록된 5튜플입니다. 6은 TCP, 17은 UDP입니다. | 구독에 지정한 필드 순서로 읽습니다. 기본 형식에는 `flow-direction`과 `pkt-*` 주소가 없습니다. |
| `pkt-srcaddr`, `pkt-dstaddr` | 값이 제공된 경우 해당 관측의 패킷 수준 주소입니다. | NAT나 클라이언트 IP 보존 설정에 따라 다른 지점의 값과 다를 수 있습니다. 주소만으로 사람이나 프로세스를 식별할 수 없습니다. |
| `start`, `end`, `packets`, `bytes` | 유닉스 초 단위의 대략적인 시작·끝과 그 기록의 패킷·바이트 합계입니다. | 로그 도착 시각, 개별 패킷 시각, 앱 데이터 크기는 별도입니다. 여러 인터페이스에 보인 같은 트래픽을 중복 합산하지 않습니다. |
| `action`, `log-status` | 네트워크 처리 결과와 로그 수집 상태를 따로 읽습니다. | 대시(`-`)는 값이 적용되지 않거나 제공되지 않았다는 뜻입니다. 0과 구분합니다. |

AWS 문서에 따르면 최대 집계 구간은 1분이나 10분으로 설정할 수 있습니다. Nitro 기반 인스턴스에 연결된 ENI의 집계 구간은 1분 이하입니다. 로그 전달은 별도 과정이며 지연될 수 있습니다. 설정한 구간을 기록하고 UTC 기준으로 조회하세요. AWS는 일부 `start`·`end` 값이 실제 인터페이스 처리 시각과 최대 60초 차이 날 수 있다고 설명합니다. 초 단위로 정확히 일치하는 조건에만 의존하면 관련 기록을 놓칠 수 있습니다.

## 2. 허용·거부와 로그 상태 따로 읽기

| 관측 | 뒷받침하는 판단 | 다음 확인 |
| --- | --- | --- |
| `ACCEPT / OK` | 관측된 트래픽이 허용됐고 기록 상태는 정상입니다. | 역방향과 TCP·TLS·앱 증거를 순서대로 확인합니다. |
| `REJECT / OK` | 관측된 트래픽이 거부됐고 로그는 기록됐습니다. | 보안 그룹, 서브넷 네트워크 ACL, 시각을 확인합니다. 이 행에는 차단 규칙이 지정돼 있지 않습니다. |
| `NODATA` | AWS가 해당 인터페이스와 구간에서 트래픽이 없다고 보고했습니다. | 이 구독의 수집 조건과 제외 대상을 확인한 뒤 해석 범위를 정합니다. |
| `SKIPDATA` | 용량 제약 같은 내부 사유로 일부 기록이 빠졌습니다. | 수집 공백으로 남기고 다른 인터페이스·관측 도구와 전달 상태를 확인합니다. |
| 일치하는 행 없음 | 이번 검색에서 일치 항목을 찾지 못했습니다. | 범위, 형식, 시각, 수집 조건, 전달, 보존 기간, 제외 대상을 확인합니다. |

**TCP 플래그는 요약입니다.** 사용자 지정 `tcp-flags`에서 1은 FIN, 2는 SYN, 4는 RST, 18은 SYN+ACK입니다. 여러 패킷의 플래그를 합친 값이 들어갈 수 있습니다. 예를 들어 3은 해당 구간의 이 방향에서 SYN과 FIN 비트가 기록됐다는 뜻입니다. 그 순서는 알 수 없습니다. 0은 지원되는 플래그가 기록되지 않았다는 뜻이며, ACK만 있는 관측에서도 나올 수 있습니다. 대시는 값 미제공 등으로 나타날 수 있습니다. 전체 연결 성립은 패킷이나 연결 상태 자료로 확인하세요.

## 3. 직접 연결과 NAT 관측 따라가기

가상 행 `A01`에서 `eni-client`는 00:30:00 UTC부터 `10.10.1.25:52344` → `10.10.2.80:443` TCP egress를 봤습니다. `ACCEPT / OK`와 플래그 `2`가 기록됐습니다. `A02`는 같은 ENI에서 시간 범위가 겹치고 두 주소·포트가 뒤집힌 ingress입니다. 플래그 `18`이 있으므로 SYN+ACK를 포함한 응답 후보입니다. 양방향 관측이 있어도 전체 TCP 연결 성립, TLS 검증, HTTP 결과는 각각 확인해야 합니다. `A03`은 역방향 5튜플이 같지만 약 5분 이전입니다. `A04`는 다른 계정이고, `A05`는 서버 ENI에서 본 별도 관측입니다. 같은 ENI에서 응답을 찾는 조건에는 세 행 모두 맞지 않습니다.

가상 행 `C01`은 **가용 영역 단위 NAT 게이트웨이**의 ENI에서 기록됐습니다. ingress의 `dstaddr=10.10.0.9`는 게이트웨이 인터페이스의 사설 주소이고, `pkt-dstaddr=203.0.113.80`은 패킷 수준의 원격 목적지 후보입니다. `C02`에서는 게이트웨이를 출발지로 삼아 같은 원격 주소로 향하는 egress가 관측됩니다. 시간과 목적지 일치만으로 정확한 포트 변환을 확정할 수 없습니다. 워크로드 ENI, 게이트웨이 범위, 포트와 시간, 별도 증거를 대조합니다. AWS의 **리전 단위 NAT 게이트웨이** 예시에서는 `resource-id`가 게이트웨이를 식별하고 ENI 관련 필드는 적용되지 않습니다. 비교 전에 게이트웨이 유형과 로그 형식을 확인하세요.

## 4. 수집하고 탐지해 근거에 맞게 대응하기

1. **수집 범위를 파악합니다.** 계정, 리전, 관측 리소스, 구독 ID, 트래픽 유형(`ALL`, `ACCEPT`, `REJECT`), 형식, 수집 시작, 전달 대상, 조회 구간을 기록합니다. 원본 행, 도착 시각, 파티션이나 스트림 이름, 사용한 쿼리를 남기고 전달 오류와 파서를 확인하세요. 허용 트래픽만 받는 구독에서는 거부가 없었다고 판단하기 어렵습니다. AWS 제공 DNS로 향하는 일부 인스턴스 요청이나 인스턴스 메타데이터 트래픽 등은 제외됩니다. 해당 조사는 적절한 DNS 로그나 단말 자료를 확인합니다.
2. **같은 관측 지점부터 연결합니다.** 영향을 받은 ENI의 양방향을 살피고 5튜플과 시간을 대조합니다. 직접 경로에서는 같은 인터페이스에서 주소와 포트를 뒤집어 응답 후보를 찾습니다. NAT와 프록시는 구간을 나눠 조사하고, 같은 패킷이 겹치는 인터페이스 간 합계는 피합니다. 사건 당시의 자산 목록을 사용해 주소와 ENI 연결 대상의 변경도 확인하세요.
3. **평상시와 비교합니다.** 여러 목적지에서 거부가 반복되면 승인되지 않은 탐색, 새 배포, 자동 재시도, 정책 변경 가능성을 함께 봅니다. 역할이 비슷한 시스템끼리 기준선을 정해 거부 목적지 수와 트래픽 규모를 비교하세요. 새로 허용된 외부 경로와 전송량 증가도 조사할 단서입니다. 정상 업데이트, 백업, 프록시 변경을 먼저 대조하고 워크로드 식별자, 단말 활동, DNS 증거, 배포 이력으로 확인합니다.
4. **독립적인 근거로 조치합니다.** 보안 그룹은 연결 상태를 추적합니다. 네트워크 ACL은 연결 상태를 추적하지 않으므로 양방향 규칙을 확인합니다. 연결이 끝난 뒤 도착한 패킷도 `REJECT`로 남을 수 있습니다. 과거 설정과 수집된 [CloudTrail]({{ '/ko/wiki/cloudtrail-log-integrity/' | relative_url }}) 변경 이력을 대조하세요. Reachability Analyzer는 지원되는 네트워크 설정을 모델링해 차단 후보를 찾습니다. 실제 패킷을 보내거나 앱 요청이 처리됐는지 확인하는 도구는 아닙니다. 서비스 장애는 로드 밸런서·TLS·앱 자료와 맞춰 봅니다. 승인되지 않은 통신을 뒷받침하는 증거가 있다면 사고 대응으로 올리고, 가능한 경우 격리 전에 증거를 보존하며 복구 후 정상 통신과 수집을 확인합니다.

승인된 AWS 계정의 해당 리전에서 AWS CLI v2와 `ec2:DescribeFlowLogs` 권한이 있으면 구독 설정을 조회할 수 있습니다. 예시 리전과 리소스 ID는 승인된 범위로 바꾸세요. 로그 본문을 읽으려면 전달 대상에 대한 별도 읽기 권한이 필요합니다. 이 명령은 지정한 리소스의 구독 설정을 조회합니다. VPC 자체에 구독이 없다면 해당 서브넷이나 ENI에 별도 구독이 있는지도 확인하세요.

```bash
aws ec2 describe-flow-logs --region us-east-1 \
  --filter 'Name=resource-id,Values=vpc-0123456789abcdef0' \
  --query 'FlowLogs[].{Id:FlowLogId,Resource:ResourceId,Type:TrafficType,Format:LogFormat,Interval:MaxAggregationInterval,Created:CreationTime,State:FlowLogStatus,Destination:LogDestination,Delivery:DeliverLogsStatus}' \
  --output json
```

## 5. 오프라인 실습 · 기록 12줄로 여덟 가지 확인

[가상 CSV]({{ '/assets/labs/vpc-flow-log-records.csv' | relative_url }})와 [Python 확인 스크립트]({{ '/assets/labs/vpc-flow-log-review.py' | relative_url }})를 같은 폴더에 저장하세요. 행 ID와 계정·리전 이름은 실습용입니다. 실제 로그의 필드 순서와 제공 여부는 설정과 전달 형식에 따라 달라집니다. Python 3만 있으면 실행할 수 있으며 AWS나 외부 네트워크에 접속하지 않습니다.

1. 계정, 리전, 인터페이스, 프로토콜이 같고 주소·포트와 방향이 반대이며 시간 구간이 겹치는 행을 찾습니다. 왜 `A03`부터 `A05`까지는 `A01`의 조건에 맞지 않는지 설명하세요. 정확한 구간 겹침은 이 자료의 실습 조건입니다. 실제 환경에서는 시간 오차와 후보가 여러 개인 경우를 처리해야 합니다.
2. `B01`에서 처리 결과와 수집 상태를 구분하고 `B02`와 `B03`을 비교하세요. `C01`에서는 인터페이스 주소와 원격 목적지를 따로 적습니다.
3. 다음 명령의 마지막 줄이 `8 synthetic checks passed.`인지 확인합니다.

```bash
python3 vpc-flow-log-review.py
```

| 실습 행 | 기대 결과 |
| --- | --- |
| `A01`, `A02` | 같은 ENI의 유일한 역방향 후보는 `A02`입니다. 플래그 18은 SYN+ACK 관측을 뒷받침합니다. |
| `B01`, `B02`, `B03` | 각각 정상 기록된 거부, 데이터 없음 보고, 일부 기록 누락입니다. |
| `C01`, `C02` | NAT ingress의 인터페이스 주소와 패킷 목적지가 다릅니다. egress의 플래그 3은 FIN과 SYN 비트를 나타내며 순서를 알 수 없습니다. |
| `D01` | UDP 기록이므로 TCP 플래그가 제공되지 않습니다. |
| `E01` | egress는 허용됐고 가상 자료에는 일치하는 응답 행이 없습니다. 같은 ENI에서 `B03`이 겹치므로 응답을 보지 못한 이유는 더 불확실합니다. |

CSV를 찾지 못하면 파일 이름과 저장 위치를 확인합니다. 이전 시각이나 다른 ENI에 있는 행이 연결되면 스크립트를 수정하기 전에 시간, 출처, 방향을 점검하세요. `E01`처럼 응답 행이 없다면 관측 범위를 기록한 뒤 다른 관측 지점을 찾습니다.

**검증 범위.** 고정 가상 자료로 Python 실습을 실행했습니다. AWS 동작과 CLI 조건은 AWS 공식 문서를 검토했습니다. 실제 VPC 트래픽 수집이나 AWS 계정 내 실행은 이번 검증 범위에 포함되지 않았습니다.

## 6. 확인 문제와 해설

1. **양방향 모두 `ACCEPT`입니다. HTTP가 200을 반환했나요?** 앱의 응답을 찾아 확인합니다. 두 행은 지정된 인터페이스에서 본 네트워크 관측입니다.
2. **어떤 보안 그룹 규칙이 `REJECT`했는지 알 수 있나요?** 5튜플과 시각을 보존하고 실제 적용 규칙, 연결 상태, 독립적인 증거를 대조합니다. 흐름 행에는 처리 결과만 있고 규칙 ID는 없습니다.
3. **왜 `SKIPDATA`를 바이트 0으로 바꾸면 안 되나요?** 기록이 빠졌다는 증거입니다. 0을 대입하면 관측하지 못한 값을 측정한 것처럼 해석하게 됩니다.
4. **`C01`에서 어떤 주소가 게이트웨이 주소인가요?** 이 ingress의 `dstaddr`는 게이트웨이 ENI의 사설 주소입니다. 패킷 수준의 목적지는 `pkt-dstaddr`에서 읽고, 리소스마다 필드 정의를 확인합니다.

**완료 기준.** 올바른 역방향 후보를 찾고 정상 기록·데이터 없음·일부 기록 누락을 설명합니다. 관측된 처리 결과, 아직 확인하지 못한 앱 결과, 다음에 볼 증거를 한 가지씩 짧게 기록하세요.
