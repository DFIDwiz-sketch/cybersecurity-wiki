**학습 목표.** Windows 이벤트에서 행위자, 추가·제거된 멤버, 대상 그룹을 찾습니다. 어느 시스템이 그룹을 관리하는지 판단하고, 이후 세션에 그룹이 나타났는지와 자원을 실제로 사용했는지를 각각 확인할 수 있습니다.

## 1. 멤버십, 세션, 자원 접근

**보안 그룹**을 사용하면 여러 계정과 그룹에 권리나 권한을 묶어서 부여할 수 있습니다. **직접 멤버십**은 멤버와 그룹 사이에 기록된 관계입니다. **중첩 멤버십**은 멤버 자체가 또 다른 그룹인 경우입니다. 이때는 그룹을 하나 추가해도 그 아래 계정들이 영향을 받을 수 있습니다. **SID(보안 식별자)**는 계정이나 그룹 같은 보안 주체를 식별합니다. 이름은 바뀔 수 있으므로 대조할 때는 SID와 이를 관리하는 보안 범위를 함께 보세요. **액세스 토큰**은 접근을 검사할 때 사용하는 보안 문맥으로, 사용자와 그룹의 SID 및 속성을 담습니다.

| 증거 | 알 수 있는 것 | 다음에 볼 것 |
| --- | --- | --- |
| 도메인 컨트롤러 또는 멤버 호스트의 그룹 변경 | 특정 멤버십 관계가 추가·제거됐음 | 변경 승인, 복제, 같은 권한을 주는 다른 관계 |
| 자원 호스트의 4624와 그에 대응하는 4627 | 로그인이 있었고 해당 세션에 특정 그룹 SID가 기록됐음 | 분할된 기록을 모두 받았는지, 토큰 속성과 후속 작업 |
| 자원의 접근 증거 | 해당 감사 원본이 기록한 인가 결정 또는 작업 | 정확한 대상, 접근 종류, 계정, 세션과 감사 범위 |

로그인과 인가 검사는 별개의 단계입니다. 그룹을 바꿔도 이미 존재하는 세션이 그 변경을 반영했는지는 별도 확인이 필요합니다. 어느 도메인 컨트롤러를 사용했는지, 복제 상태, 티켓과 세션의 수명, 자원 정책에 따라 관측 결과가 달라질 수 있습니다. 이후 로그인에 SID가 기록돼도 그 SID가 활성화됐는지, 권한이 상승했는지, 특정 작업에 사용됐는지는 따로 확인합니다.

![그룹을 관리하는 시스템의 변경 기록, 이후 자원 호스트의 로그인, 해당 자원의 접근 기록을 차례로 대조합니다.]({{ '/assets/diagrams/ad-membership-evidence-ko.svg' | relative_url }})

*단계마다 답할 수 있는 질문이 다릅니다. 세션이나 접근 기록이 빠졌다면 해당 단계는 미확인으로 남겨 두세요.*

## 2. 정상적인 멤버 추가 한 건을 읽으세요

접근 관리팀이 보고서 읽기용 글로벌 보안 그룹에 테스트 계정 한 개를 추가하는 작업을 승인했다고 가정합니다. 성공한 보안 그룹 관리 작업을 감사하도록 설정했다면, 작업을 처리한 도메인 컨트롤러의 Security 로그에 **4728**이 기록됩니다. `SubjectUserSid`는 변경을 수행한 계정, `MemberSid`는 추가된 계정이나 그룹, `TargetSid`는 대상 그룹입니다. `SubjectLogonId`는 그 이벤트를 기록한 장비에서 **행위자**의 세션을 가리킵니다. 새로 추가된 멤버의 세션과 구분하세요.

가상 정상 사례에서 `DC01`은 10:12에 추가를 기록했습니다. 동일한 DC가 10:10에 기록한 4624의 `TargetUserSid`에는 같은 행위자 SID가, `TargetLogonId`에는 같은 로그인 ID가 들어 있습니다. 이 두 기록으로 행위자의 세션을 연결할 수 있고, 승인 여부는 작업 승인 기록으로 확인합니다. 그 뒤 추가된 멤버가 `FILE01`에 로그인하고 해당 호스트의 4627에 보고서 그룹 SID가 기록됩니다. 보고서를 실제로 읽었는지는 파일 또는 애플리케이션의 감사 기록을 확인해야 합니다. 제공되는 경우 자원에 기록된 세션 ID와 객체 식별자로 묶으세요.

| 그룹 종류 | 추가 / 제거 | 수집 위치 |
| --- | --- | --- |
| AD 글로벌 보안 그룹 | 4728 / 4729 | 작업을 기록한 도메인 컨트롤러의 Security 로그 |
| AD 유니버설 보안 그룹 | 4756 / 4757 | 해당 도메인 컨트롤러의 Security 로그 |
| AD 도메인 로컬 또는 Builtin Local 보안 그룹 | 4732 / 4733 | 해당 도메인 컨트롤러의 Security 로그 |
| 멤버 서버·워크스테이션의 로컬 보안 그룹 | 4732 / 4733 | 로컬 그룹을 관리하는 컴퓨터의 Security 로그 |

`S-1-5-32-544`에 대한 4732는 해당 보안 범위의 기본 제공 Administrators 그룹을 가리킵니다. 멤버 호스트 두 대에서 같은 잘 알려진 SID가 보일 수 있지만, 각 호스트는 별도 멤버십을 관리합니다. AD 그룹은 도메인과 그룹 SID를 함께 봅니다. 같은 도메인의 추가와 제거를 서로 다른 도메인 컨트롤러에서 기록할 수도 있습니다.

## 3. 예상 밖의 변경을 어떻게 해석하나요?

그룹을 관리할 권한이 과도하거나 관리 계정이 침해되면, 정상적인 관리 경로를 통해서도 승인되지 않은 멤버 추가가 일어날 수 있습니다. 입사자 등록, 자동 프로비저닝, 승인된 임시 권한도 같은 종류의 이벤트를 남깁니다. 민감한 시스템이나 권한을 실제로 제어하는 그룹의 변경부터 살펴보세요. 추가와 제거 모두 중요합니다. 짧은 시간 뒤 제거됐다면 예정된 만료나 시정 조치일 수 있습니다. 그사이에 접근이 없었는지는 별도의 증거가 필요합니다.

추가된 SID가 그룹으로 확인됐다면, 조사 대상 시점과 보안 범위에서 멤버십이 어떻게 이어지는지 확인하세요. 현재 디렉터리나 로컬 목록의 상태는 현재만 설명합니다. 확보할 수 있다면 시각이 기록된 디렉터리·구성 스냅샷과 대조하세요. 멤버 이름 필드가 비어 있거나 이름이 바뀌어도 원래 SID와 조회 출처는 보존합니다.

## 4. 블루팀 수집·탐지·대응

**그룹을 관리하는 시스템에서 수집하세요.** 승인된 구성에서 필요한 시스템의 **보안 그룹 관리 감사(Audit Security Group Management)** 성공 설정을 확인합니다. 관련 DC와 멤버 호스트의 Windows Security 채널을 수집하고, 이벤트를 만든 Computer, ID, 채널, 원본 시각, 레코드 ID와 원래 EventData를 보존하세요. 수집기 자체의 이름은 별도로 남깁니다. WEF를 쓴다면 구독, 필터, 보존과 파서에서 필요한 이벤트와 필드가 유지되는지 확인합니다. 보조 증거로 5136을 쓸 경우 **디렉터리 서비스 변경 감사**와 객체 또는 속성의 해당 SACL이 필요합니다. 기록된 경우 `AttributeLDAPDisplayName`, 작업 종류와 값을 확인합니다. 이는 그룹 관리 이벤트와 수집 조건이 다른 자료입니다.

**행위자의 세션은 같은 호스트에서 연결하세요.** 변경의 `SubjectUserSid`와 `SubjectLogonId`를 성공 로그인 4624의 `TargetUserSid`, `TargetLogonId`에 연결합니다. 이벤트가 생성된 **같은 컴퓨터**인지, 같은 부팅 범위와 타당한 시간 범위인지 확인하세요. 이벤트 ID와 로그인 ID는 의미가 다릅니다. 다른 호스트에서 같은 로그인 ID를 만들 수 있습니다. 이 연결로 기록된 계정의 세션을 확인할 수 있습니다. 실제 사람을 특정하려면 관리 경로, 자동화 실행, 변경 승인 같은 증거가 더 필요합니다.

**추가된 멤버의 자원 로그인을 별도로 확인하세요.** 4627을 보려면 자원 호스트에서 **그룹 멤버십 감사(Audit Group Membership)**와 **로그온 감사(Audit Logon)** 성공 설정이 필요합니다. 같은 자원 호스트의 4624와 4627을 대상 SID, 로그인 ID, 시각으로 대조합니다. 목록이 나뉘어 기록됐는지는 `EventIdx`와 `EventCountTotal`에서 확인하세요. 해당 세션에 그룹 SID가 없다고 판단하려면 목록을 모두 확보해야 합니다. 실제 접근 시도나 허용 여부는 자원 쪽 감사에서 확인합니다. 이벤트가 비어 있다면 감사 설정, 보존 기간, 수집 필터와 전달 상태를 먼저 점검하세요.

**영향 범위와 근거를 바탕으로 대응하세요.** 민감한 그룹 SID와 관리 범위를 인벤토리와 비교합니다. 예상 밖의 직접·중첩 추가를 조사할 때는 자동화, 승인 기록, 중복 수집 여부를 살펴보세요. 제거는 관리 범위·그룹 SID·멤버 SID로 묶습니다. 승인되지 않은 변경을 뒷받침하는 증거가 있으면 조치 전 상태를 보존하고 승인된 절차로 제거합니다. 영향을 받은 세션, 후속 활동과 다른 멤버십 경로도 확인하세요. 제거 직후 모든 기존 세션의 접근이 사라졌는지는 자원 쪽 근거로 검증해야 합니다.

## 5. 오프라인 실습 · 가상 조사 8건

[ad-membership-cases.json]({{ '/assets/labs/ad-membership-cases.json' | relative_url }})과 [ad-membership-review.py]({{ '/assets/labs/ad-membership-review.py' | relative_url }})를 같은 폴더에 받으세요. 자가 소유 환경의 Python 3에서 실행합니다. JSON은 가상 이벤트에서 필요한 값만 뽑아 정리한 자료입니다. `group_authority`와 상대 분 단위 시각은 실습용 메타데이터입니다. 각 사례에는 추가 한 건이 있고 컴퓨터마다 부팅 범위 하나를 가정합니다. 멤버 유형은 디렉터리에서 조회한 것으로 가정한 값입니다. 그룹 목록은 SID 배열로 표현했습니다. Windows 원본 이벤트의 필드명과 표현 방식은 다릅니다.

~~~bash
python3 ad-membership-review.py
~~~

| 사례 | 확인할 결과 |
| --- | --- |
| G01 / G02 | G01은 DC01에서 행위자 로그인을 찾음. G02의 ADMIN01에 SID와 로그인 ID가 같아도 동일 세션으로 연결할 수 없음 |
| G03 / G04 | G03은 같은 도메인의 다른 DC에서 5분 뒤 제거가 관측됨. G04는 기본 제공 그룹 SID가 같아도 멤버 호스트가 달라 제거가 일치하지 않음 |
| G05 | 추가된 주체가 그룹임. 중첩된 멤버와 자원 범위를 확인해야 하며, 실습 자료에는 자원 접근 근거가 없음 |
| G06 | 추가된 멤버의 자원 로그인에서 보고서 그룹 SID가 관측됨 |
| G07 / G08 | G07은 4627 목록 일부가 누락됨. G08은 전체 목록을 확보했으며 그 세션에는 그룹 SID가 없음 |

마지막에 `Reviewed: 8 synthetic cases`가 나옵니다. JSON을 찾지 못하면 두 파일이 원래 이름으로 같은 폴더에 있는지 확인하세요. 연결 결과가 다르면 이벤트를 생성한 컴퓨터, 행위자와 멤버의 구분, 시간 범위와 파싱한 필드를 점검합니다. 선택 실습은 승인된 격리 도메인이나 멤버 호스트에서 관리자·운영 권한이 없는 기존 테스트 그룹으로 진행하세요. 감사가 설정된 자원 호스트에서 새 로그인을 관측하고 로컬 Security 로그의 변경과 대조합니다. 각 기록이 어느 시스템에 남았는지 적으세요. Python 가상 자료는 실행했고, Windows 감사와 세션 동작은 Microsoft 문서로 검토했습니다.

## 6. 확인 문제와 완료 기준

- **두 워크스테이션에서 그룹 SID와 멤버가 같습니다. 한쪽의 제거가 다른 쪽의 추가를 취소하나요?** 각 호스트가 자기 로컬 그룹의 멤버십을 관리합니다. 그룹을 소유한 호스트별로 보세요.
- **새 멤버의 자원 로그인에 그룹 SID가 있습니다. 보고서를 열었나요?** 해당 자원의 접근 감사 기록을 확인하세요. 그룹 목록으로는 보고서의 인가 결과를 알 수 없습니다.
- **5분 만에 임시 권한이 제거됐습니다. 모든 세션과 중첩 권한도 사라졌나요?** 제거는 멤버십 관계 하나의 변경입니다. 기존 세션과 자원 증거, 다른 멤버십 경로를 확인하세요.

행위자, 멤버, 그룹과 관리 범위, 기록한 호스트, 관측 시간대, 연결 가능한 로그인과 실제 접근을 판단하는 데 필요한 다음 자료를 한 건의 조사 기록에 적으면 완료입니다.
