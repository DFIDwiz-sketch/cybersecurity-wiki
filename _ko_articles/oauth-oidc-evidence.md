**학습 목표.** 로그인에 성공했는데도 API 요청이 거부될 수 있는 이유를 설명합니다. 어떤 검사에서 거부됐는지 찾고, 앱이 실제로 어떤 작업을 했는지 기록으로 확인합니다.

## 1. 로그인과 API 접근은 서로 다른 질문입니다

보고서 포털에서 보고서 한 건을 읽는 상황을 떠올려 보세요. **사용자**는 로그인하는 사람입니다. **클라이언트**인 보고서 포털은 사용자를 대신해 요청을 보냅니다. **인가 서버**는 필요할 때 사용자를 인증하고 접근을 허용할지 판단한 뒤 자격 증명을 발급합니다. **리소스 서버**인 보고서 API는 들어온 API 요청을 받아들일지 결정합니다. OpenID Connect(OIDC)에서는 인가 서버가 **OpenID 제공자**, 클라이언트가 **신뢰 당사자** 역할을 합니다.

**OAuth 2.0**은 클라이언트가 보호된 서비스에 제한된 접근 권한을 얻도록 합니다. **OIDC**는 여기에 로그인한 사용자의 신원을 클라이언트가 확인할 수 있는 계층을 더합니다. **클레임**은 발급자나 대상처럼 토큰에 담긴 정보 항목입니다. **스코프**는 서비스가 정의하는 권한 이름입니다. 여기서는 가상 권한 `reports.read`를 씁니다. API는 여기에 더해 사용자가 **특정 보고서**를 읽어도 되는지 자체 규칙으로 판단할 수 있습니다.

| 자격 증명 | 누가 어디에 사용하나요? | 용도 |
| --- | --- | --- |
| 인가 코드 | 클라이언트가 인가 서버의 토큰 엔드포인트에 제출 | 수명이 짧고 한 번만 쓸 수 있는 중간 값. 토큰과 교환 |
| ID 토큰 | 클라이언트가 자신의 식별자를 대상으로 검증 | 해당 클라이언트에 전달된 사용자 인증 증거 |
| 액세스 토큰 | 클라이언트가 토큰의 대상 API에 전달 | API가 요청된 작업을 평가할 때 사용하는 자격 증명 |
| 갱신 토큰(발급된 경우) | 클라이언트가 인가 서버의 토큰 엔드포인트에 제출 | 서버 정책에 따라 새 액세스 토큰을 얻는 데 사용 |

**JWT**는 클레임을 담을 수 있는 형식입니다. ID 토큰은 JWT를 쓰고, 액세스 토큰은 JWT일 수도, 클라이언트가 내용을 해석할 수 없는 불투명 토큰일 수도 있습니다. **베어러 토큰**은 유효 기간과 API 정책이 허용하는 동안 소지자가 쓸 수 있습니다. 송신자 제약 토큰은 허가된 송신자와 연결된 별도 증명도 요구합니다. 토큰 값과 인가 코드는 자격 증명으로 다루세요.

## 2. 정상 요청 한 건을 따라가기

![클라이언트가 로그인을 시작하면 인가 서버가 코드를 반환합니다. 클라이언트가 코드를 토큰과 교환하고, API가 자격 증명과 권한을 확인하면 앱이 작업 결과를 기록합니다.]({{ '/assets/diagrams/oauth-oidc-flow-ko.svg' | relative_url }})

1. Ada가 보고서 포털을 엽니다. 클라이언트가 `openid` 스코프를 포함한 OIDC 인가 코드 요청을 시작합니다. 브라우저는 인가 서버로 이동합니다. 인가 서버는 Ada를 인증하고 정책이 요구하면 동의를 받습니다.
2. 브라우저는 코드를 가지고 클라이언트에 미리 등록된 콜백 주소로 돌아옵니다. 클라이언트는 응답을 자신이 시작한 요청과 대조합니다. **PKCE**를 쓰면 토큰 엔드포인트는 교환 단계에서 받은 검증값을 인가 요청에 연결된 챌린지와 비교합니다. 그 결과 코드를 요청한 쪽과 교환하는 쪽이 연결됩니다.
3. 클라이언트는 코드와 검증값을 토큰 엔드포인트에 제출합니다. ID 토큰을 검증하고 앱 세션을 만듭니다. 이때 예상 대상은 클라이언트 ID입니다. 액세스 토큰은 TLS 연결의 Authorization 헤더에 담아 보고서 API에 보냅니다.
4. 보고서 API는 자신의 식별자를 대상으로 액세스 토큰을 검증한 뒤 경로와 보고서에 대한 권한을 확인합니다. 정상 흐름에서는 앱에 읽기 작업도 기록됩니다. ID 제공자의 로그인 기록, API의 허용 결정, 보고서 감사는 서로 다른 사실에 대한 증거입니다.

예를 들어 보고서 포털의 클라이언트 ID를 `reports-portal`, API 식별자를 `reports-api`라고 해 봅시다. 이 구성에서 ID 토큰의 `aud`는 `reports-portal`이고 액세스 토큰의 `aud`는 `reports-api`입니다. 액세스 토큰에 `reports.read`가 있어도 별도 객체 정책이 해당 보고서를 허용해야 합니다. 이 이름들은 관계를 보여 주기 위한 예시이며, 실제 대상 값은 발급자와 API 설정에서 확인합니다.

2025년 1월 OAuth 보안 권고 RFC 9700은 이런 흐름에 인가 코드를 권고합니다. 공유 비밀을 안전하게 보관할 수 없는 공개 클라이언트에는 PKCE가 필수이고, 기밀 클라이언트에도 권고합니다. 오래된 그림에서 흔히 보이는 암시적 흐름은 일반적인 신규 설계의 기본값으로 삼지 않습니다. 이 권고에 따르면 사용자 비밀번호를 클라이언트에 전달하는 비밀번호 자격 증명 그랜트는 사용하면 안 됩니다.

## 3. 전자서명이 맞으면 어디까지 확인한 걸까요?

신뢰하는 키로 서명을 검증하면 무결성과 발급 출처를 확인하는 데 도움이 됩니다. 내용을 읽을 수 있다는 사실은 디코딩이 됐다는 뜻입니다. JWT 액세스 토큰을 받는 API는 유지보수되는 라이브러리와 발급자의 토큰 명세를 사용합니다. 예상 발급자, 신뢰하는 검증 키, 허용 알고리즘을 설정하고 **토큰 종류**, **발급자**(`iss`), **대상**(`aud`), **유효 시간**(`exp`, 해당 시 `nbf` 등)을 확인합니다. JWKS는 공개키의 집합입니다. 설정에 등록한 발급자가 제공하는 키를 사용하고 키 교체를 고려하세요. 토큰의 키 식별자 `kid`는 그 집합에서 검증 키를 고르는 단서입니다.

RFC 9068의 JWT 액세스 토큰 프로필은 헤더의 유형으로 `at+jwt` 또는 `application/at+jwt`를 지정합니다. 다른 프로필을 사용하는 발급자는 별도 명세를 따릅니다. 불투명 토큰을 받는 API는 허가된 토큰 인트로스펙션처럼 지원되는 검증 방법으로 상태를 조회하고 이후 권한을 확인합니다. OIDC 클라이언트는 따로 ID 토큰의 발급자, 자신의 대상 식별자, 만료 시각을 확인합니다. 요청에 **nonce**를 넣었다면 ID 토큰의 값과 대조해 어느 인증 요청의 응답인지 확인합니다.

| 질문 | 확인할 근거 |
| --- | --- |
| 이 API에서 받아도 되는 자격 증명인가요? | 토큰 검증 결과. 다른 서비스를 대상으로 발급된 토큰은 서명이 맞아도 여기서 실패할 수 있음 |
| 요청한 작업이 허용되나요? | 인가 결정. 스코프·역할·권한과 리소스 규칙은 경로나 신원 유형에 따라 달라짐 |
| 작업이 실제로 일어났나요? | 앱이나 작업자의 감사 기록. 허용 후 오류가 나거나 백그라운드에서 나중에 처리될 수 있음 |

### 오용이 의심될 때

디버그 로그에 유출된 베어러 토큰은 아직 유효하다면 다시 사용될 수 있습니다. API가 용도나 대상이 다른 토큰을 받아들이면 서비스 사이의 신뢰 경계가 무너집니다. 권한을 과하게 부여하면 올바른 클라이언트도 업무 범위를 넘는 작업을 할 수 있습니다. API와 앱의 검증·감사 기록, ID 제공자의 동의 및 클라이언트 설정 변경, 요청 추적기나 로그에서의 노출 여부를 함께 보세요. IP 주소 하나, 반복 요청 하나, 드문 시간대의 권한 부여만으로 오용을 확정하지 않습니다. 승인된 방어 검증에서는 출시 전에 시험 계정으로 예상된 거부 결과와 감사 기록 수집을 확인할 수 있습니다.

## 4. 결정의 근거를 수집하고 작업 결과를 확인하세요

| 출처 | 수집할 값 | 알 수 있는 범위 |
| --- | --- | --- |
| ID 제공자 | UTC 시각, 테넌트·클라이언트 ID, 로그인이나 권한 부여 결과, 세션·상관 ID, 동의나 스코프 변경 | 인증·권한 부여·관리 변경 문맥. 갱신이나 워크로드 인증에는 새 사용자 로그인이 없을 수 있음 |
| API 게이트웨이 또는 미들웨어 | 확인된 환경·서비스, 서버가 부여한 요청·트레이스 ID, 경로 템플릿, 상태 코드, 검증 분류와 인가 결정 | API가 어느 단계에서 판단했는지 파악. 검증 전 클레임은 신뢰할 수 없는 입력으로 취급 |
| 앱 또는 작업자 감사 | 범위를 확인한 요청·작업 ID, 허용된 가명 주체·객체 ID, 작업명과 결과 | 해당 감사 기록이 관측하는 시스템과 이벤트의 작업 결과 |

API 요청 한 건에서 출발해 UTC 시간대와 신뢰 가능한 ID로 범위를 넓힙니다. 서비스 사이에 ID가 이어지는지, 환경과 테넌트가 맞는지 확인하세요. 수집 활성화, 보존 기간, 해당 경로 포함 여부, 샘플링 여부도 남깁니다. 원본 감사 로그는 접근을 제한해 보존합니다. 로그·트레이스·티켓에서는 Authorization 헤더, 쿠키, 코드와 토큰 값을 가립니다. 외부에는 필요한 수준의 오류만 알리고 상세 거부 사유는 내부에서 제한적으로 사용합니다. 실제 자격 증명을 토큰 뷰어에 붙여넣지 않습니다.

RFC 6750은 베어러 토큰이 유효하지 않을 때 401, 스코프가 부족할 때 403을 권고합니다. 실제 응답은 프록시나 제품 정책에 따라 달라질 수 있으니 상태 코드와 미들웨어의 내부 사유를 함께 보세요. 만료 거부가 갑자기 늘면 오래된 토큰 사용과 서버 시계 오차를 모두 확인합니다. 배포 직후 키 선택이나 서명 오류가 늘면 발급자 메타데이터, 캐시, 키 교체 이력을 확인합니다. 정상 발생량과 차이를 비교하고 관련 배포 또는 권한 변경 기록을 찾으세요. 노출 근거를 확보했다면 조직 절차에 따라 권한·자격 증명·세션의 영향을 제한하고, 리소스 사용 이력과 차단이 실제 적용된 시점을 확인합니다. 폐기 범위와 적용 시각은 발급자·토큰·API 설계에 따라 달라집니다.

## 5. 오프라인 실습 · API 요청 8건 분석하기

[가상 이벤트 로그]({{ '/assets/labs/oauth-oidc-events.jsonl' | relative_url }})와 [Python 분석기]({{ '/assets/labs/oauth-oidc-evidence.py' | relative_url }})를 같은 폴더에 내려받고 Python 3에서 실행합니다. 이 자료의 2030년 UTC 시각과 값은 모두 가상입니다. 분석기는 토큰을 만들거나 검증하지 않으며, 네트워크도 사용하지 않습니다.

```sh
python3 oauth-oidc-evidence.py
```

실행 전에 어떤 사례에서 앱 작업까지 입증할 수 있는지 적어 보세요. 분석기는 **환경, 서비스, 요청 ID**가 모두 일치한 감사 기록을 찾습니다. 실습의 두 출처에는 같은 가상 식별자를 미리 넣었습니다. 실제 시스템에서는 트레이스나 작업 ID를 이어 주는 다른 기록이 필요할 수 있습니다.

| 요청 | API에서 보이는 결과 | 앱 기록까지 보고 내릴 판단 |
| --- | --- | --- |
| r-01 | 토큰 검증과 인가 통과, 200 | 범위가 맞는 감사 기록으로 시험 보고서 읽기 확인 |
| r-02 | 토큰 용도 불일치, 401 | 검증 단계에서 거부 |
| r-03 | 대상 불일치, 401 | 이 실습에서 다른 API를 대상으로 발급된 토큰 |
| r-04 | 만료, 401 | 실제 조사라면 갱신 여부와 시계도 점검 |
| r-05 | 필수 스코프 누락, 403 | 토큰 검증을 통과했으나 경로 인가에서 거부 |
| r-06 | 요청을 대기열에 등록, 202 | 같은 ID의 감사는 다른 환경에서 발생. 최종 결과는 미확인 |
| r-07 | 인가 통과, 503 | 범위가 맞는 오류 기록으로 후속 처리 실패 확인 |
| r-08 | 스코프 통과, 403 | 앱이 특정 객체에 대한 접근을 거부 |

**기대 결과.** API 판정 8건, 연결된 앱 감사 2건, 연결되지 않은 앱 감사 1건입니다. 연결된 감사 중 1건은 읽기 완료이고 1건은 처리 오류입니다. 파일을 열 수 없다면 이름과 작업 디렉터리를 확인하세요. 행 오류가 나면 출력된 줄 번호에서 줄마다 JSON 객체 하나가 있는지 봅니다. 연결 개수가 다르면 원본과 세 가지 연결 키를 비교하세요. 요청 ID만 대조하면 r-06에서 잘못 연결됩니다.

게시 과정에서 클라우드 환경의 Python으로 가상 로그 분석기를 실행했습니다. 프로토콜과 제품의 동작은 공식 문서로 검토했습니다. 실제 ID 제공자나 API의 동작은 별도 시험이 필요합니다. 자가 소유하거나 명시적으로 승인된 서비스에서는 시험 사용자와 시험 객체로 정상 동작을 확인하세요. 서비스 담당자가 필요한 스코프 또는 객체 권한을 뺀 별도 시험 계정을 준비하면 예상 거부 사유와 후속 감사 기록을 정상 사례와 비교할 수 있습니다. 시험 자격 증명은 승인된 클라이언트 안에서만 쓰고, 판정과 요청 식별자를 수집합니다.

## 6. 확인 문제와 완료 기준

1. **클라이언트가 ID 토큰을 받아들였습니다. API에도 같은 자격 증명을 보내면 될까요?** API는 자신의 검증 정책과 대상에 맞는 액세스 토큰을 요구합니다. ID 토큰의 수신자는 클라이언트입니다.
2. **액세스 토큰 검증에 성공해도 403이 날 수 있나요?** 네. 경로에 필요한 스코프, 역할, 객체 규칙을 봅니다. r-05와 r-08은 거부가 일어난 단계가 다릅니다.
3. **202이면 보고서를 읽었다고 결론 내려도 되나요?** 202는 처리를 위해 요청을 받았다는 뜻입니다. 실제 읽기는 작업자나 앱의 감사 기록으로 확인합니다.
4. **r-06에서 ID가 같다는 사실은 어느 정도의 근거인가요?** 범위와 전파가 확인되어야 연결 근거가 됩니다. 이 실습에서는 서로 다른 환경에 같은 값이 있습니다.

두 403의 거부 사유를 설명하고, 후속 처리 오류와 증거가 없는 경우를 구분하며, 확인한 앱 작업의 출처와 연결 필드를 적으면 완료입니다.
