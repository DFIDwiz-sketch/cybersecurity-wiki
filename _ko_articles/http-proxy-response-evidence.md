**학습 목표.** 브라우저에 504가 표시됐습니다. 지금 보고 있는 프록시에서 시간이 초과됐을까요? 뒤쪽 서버가 이미 504를 반환했을까요? 요청한 작업은 완료됐을까요? 각 지점의 증거로 세 질문에 따로 답하는 방법을 배웁니다. 상태 코드가 낯설다면 [HTTP 요청과 응답 증거]({{ '/ko/wiki/http-evidence/' | relative_url }})부터 읽어 보세요.

## 1. 상태 코드는 어디에서 기록됐나요?

**리버스 프록시**는 서비스 대신 클라이언트 연결을 받습니다. 직접 응답하거나 **업스트림**, 즉 뒤쪽 애플리케이션 서버나 다른 프록시에 요청을 전달합니다. **로드 밸런서**는 여러 백엔드 중에서 요청을 처리할 대상을 고를 수 있습니다. 이 장은 조사 기준으로 삼는 첫 프록시를 **엣지**라고 부릅니다. 그 앞에 CDN이나 다른 서비스가 있을 수도 있습니다.

**요청 ID**는 정해진 범위에서 요청 한 건에 붙는 식별자입니다. **시도 ID**는 그런 필드를 수집하도록 구성된 시스템에서 업스트림 연결이나 처리 시도를 구분합니다. **트레이스**는 여러 서비스에 걸친 작업을 연결한 기록입니다. 하나의 트레이스에 여러 요청과 스팬(작업 구간)이 있을 수 있으므로, 각각을 구분하려면 구간과 시도 정보도 봐야 합니다.

엣지 상태 코드는 해당 프록시가 클라이언트 방향 연결에 보냈거나 기록한 결과입니다. 엣지가 직접 생성했거나 받은 상태를 전달했거나 다른 응답으로 바꿨을 수 있습니다. 업스트림 상태는 프록시가 각 시도에 대해 남긴 값이며, 어떤 의미인지는 제품의 필드 정의에 달려 있습니다. 애플리케이션 감사 로그는 사용자가 성공 응답을 받지 못했더라도 작업이 시작됐거나 상태가 바뀌었음을 보여 줄 수 있습니다.

## 2. 정상 요청 한 건을 따라가기

가상 예제에서 엣지는 `GET /orders/summary`를 받은 뒤 `shop` 서비스 범위에서 `r1`을 부여합니다. 문서화된 로그 규칙에 따라 이 ID를 애플리케이션에 전달하고 주문 백엔드를 선택합니다. 백엔드는 조회를 마치고 200을 보냅니다. 엣지는 클라이언트 응답 200, 선택한 백엔드, 한 번의 업스트림 시도를 기록합니다. 가상 수집 예제에서 시도 ID는 `a1`입니다. 어느 구성 요소가 응답했는지는 양쪽 기록을 연결해 확인합니다.

| 관측 지점 | 가상 증거 | 뒷받침하는 판단 |
| --- | --- | --- |
| 프록시 접근 로그 | `shop / r1`, 최종 200, 주문 백엔드 선택, 시도 `a1` | 해당 프록시가 200과 업스트림 시도 한 번을 기록 |
| 애플리케이션 요청 로그 | `shop / r1 / a1`, 상태 200, 조회 처리 완료 | 주문 애플리케이션이 조회와 응답을 기록 |
| 사용할 수 있는 트레이스 또는 흐름 | 같은 요청이나 스팬, 예상 목적지와 시간 | 경로의 독립된 단서. 흐름 자료에 HTTP 상태가 없을 수 있음 |

클라이언트가 보낸 식별자는 입력값입니다. 조사에 쓸 ID를 어디서 생성하거나 검증하는지, 어느 프록시가 유지하는지, 애플리케이션이 어떻게 기록하는지를 확인하세요. W3C Trace Context의 `traceparent`는 여러 구간으로 일관되게 전달될 때 분산 추적에 도움이 됩니다. 사용자 인증은 별도입니다. 서비스나 신뢰 범위를 벗어난 같은 ID는 연결 근거가 약합니다. 서비스, 시각, 백엔드와 시도 ID 또는 스팬을 함께 비교합니다.

## 3. 비슷한 증상을 구분하기

| 클라이언트에서 본 결과 | 가능한 설명 | 원인을 좁히는 증거 |
| --- | --- | --- |
| 403 | 해당 프록시의 접근 정책이나 WAF가 차단했거나 백엔드가 거부함 | 어느 지점의 정책 결정인지, 전달 시도가 있었는지 확인. 같은 403이 애플리케이션에도 있는지 비교 |
| 502 | 게이트웨이가 유효한 업스트림 응답을 받지 못했거나 다른 게이트웨이의 502를 전달함 | 업스트림 선택·연결·응답 상세, 프록시 오류 로그, 다음 지점 기록 |
| 503 | 프록시나 애플리케이션의 용량 부족, 유지보수, 사용 가능한 대상 부재 | 업스트림 식별 정보, 응답을 만든 지점의 증거, 대상 상태와 작업 이력 |
| 504 | 현재 프록시가 필요한 업스트림 응답을 기다리다 시간 초과되거나 이미 생성된 504를 전달함 | 연결·응답 시간과 시간 초과 기록, 같은 요청의 애플리케이션 기록이나 업무 처리 기록 |
| 앞쪽 실패 뒤 최종 200 | 재시도 성공 또는 중계 지점의 대체 응답 | 시도별 백엔드와 시간, 최종 응답에 사용한 시도 확인 |

애플리케이션은 게이트웨이의 제한 시간 전에 쓰기 작업을 완료했을 수도 있고, 사용자가 시간 초과를 본 뒤 작업을 끝냈을 수도 있습니다. 쓰기 요청을 반복하기 전에 지속적으로 보관되는 처리 기록이나 서비스의 멱등성 처리 기록을 확인하세요. 멱등성은 같은 작업을 반복해도 의도한 최종 효과가 늘어나지 않는 성질입니다. 캐시도 백엔드를 새로 호출하지 않고 응답할 수 있습니다. [HTTP 캐시 조사]({{ '/ko/wiki/http-cache-evidence/' | relative_url }})에서 이어 읽을 수 있습니다.

오용과 정상 장애가 비슷해 보일 수 있습니다. 접근 정책을 벗어난 요청은 프록시에서 거부될 수 있습니다. 예상 밖의 요청량은 재시도나 시간 초과의 원인이 되기도 합니다. 배포나 정상적인 트래픽 증가 때도 같은 패턴이 생깁니다. 정책 판정, 인증된 신원, 시간대와 평소 요청량을 대조하세요. 5xx 급증이나 클라이언트가 보낸 User-Agent만으로 침해 또는 행위자를 확정할 수 없습니다.

## 4. 필드를 수집하고 각 지점을 조사하기

1. **증상부터 기록합니다.** UTC 시간 범위와 시계 오차, 클라이언트 응답, 호스트명·경로, 메서드와 요청 ID를 남깁니다. 해당 요청을 받은 프록시 인스턴스와 당시 설정 버전을 찾고 원본 기록을 보존합니다. 조사에 꼭 필요하고 접근이 통제되는 경우에만 토큰, 쿠키, 요청 본문을 수집하세요.
2. **요청을 시도별로 펼칩니다.** 최종 상태, 경로나 로컬 정책 판정, 업스트림 대상, 시도별 결과·시간, 관련 오류 로그를 확보합니다. 재시도 대상은 바뀔 수 있습니다. 타임스탬프가 처리 시작인지 끝인지, 시간 단위와 시간원이 무엇인지 확인하세요. 서로 다른 구간의 시간을 그대로 빼서 지연 지점을 단정하지 않습니다.
3. **애플리케이션 기록에 연결합니다.** 승인된 식별자와 서비스 범위를 사용합니다. 가능한 경우 백엔드 인스턴스, 시도 또는 스팬을 함께 맞춥니다. 애플리케이션 요청 로그, 오류 자료, 업무 처리 기록이 답하는 질문은 서로 다릅니다. 연결되지 않으면 애플리케이션이 받지 않았다고 결론 내리기 전에 계측, 샘플링, 로그 전달과 보존을 확인하세요.
4. **확인된 원인 지점에 대응합니다.** 연결 실패는 수신 포트, 라우팅, 대상 상태를 점검합니다. 정책 차단이 확인되면 적용 규칙과 승인된 변경 및 범위를 비교합니다. 백엔드 결과가 확인되면 일치한 시도와 오류를 담당자에게 전달합니다. 시간 초과와 쓰기 기록이 함께 있다면 재시도 전에 작업 상태를 확인하세요.

| 제품과 수집 전제 | 주요 필드 | 해석할 때 주의할 점 |
| --- | --- | --- |
| NGINX HTTP 프록시의 접근 로그에 해당 필드를 설정 | `$status`, `$request_id`, `$upstream_addr`, `$upstream_status`, `$upstream_connect_time`, `$upstream_header_time`, `$upstream_response_time` | 시도 목록과 그룹 구분자를 보존. 서버를 고르지 못한 경우에도 업스트림 502가 기록될 수 있어 애플리케이션 응답이라고 단정할 수 없음 |
| AWS Application Load Balancer 접근 로그 활성화 및 수집 가능 | `elb_status_code`, `target_status_code`, 대상 주소와 처리 시간 | `target_status_code`의 대시는 문서에 정해진 조건에서 대상 응답 코드가 기록되지 않았다는 뜻. 대상 쪽 작업이 없었다고 보기 전에 로그의 작업 유형과 대상 기록 확인 |
| 애플리케이션 요청·트레이스 로깅 활성화 | 서비스 범위와 인스턴스, 신뢰할 수 있는 요청 ID, 스팬이나 시도, 응답, 작업 결과 | 요청 시작은 완료를 증명하지 않음. 작업 완료도 클라이언트가 응답을 받았다는 증거와 다름 |

NGINX는 처리가 끝나는 위치의 설정을 기준으로 접근 로그를 남깁니다. 내부 리다이렉트가 있으면 처음 처리한 위치와 다를 수 있습니다. 업스트림 필드에 여러 값이 있으면 쉼표와 콜론을 포함한 원본 형식으로 보존하고 같은 요청의 오류 로그와 비교합니다. 위 NGINX 업스트림 시간은 초 단위이며 밀리초까지 기록할 수 있습니다. ALB는 처리 시간과 누락값을 별도로 정의합니다. 본문의 가상 필드를 운영 수집에 적용하기 전에 수집기의 실제 매핑을 확인하세요.

## 5. 오프라인 실습 · 지점별 증거로 일곱 건 판단하기

Python 3으로 스크립트 안의 가상 기록 두 묶음을 읽으며 네트워크 트래픽을 보내지 않습니다. 실습의 `decision`과 `attempt`는 가상 계측에서 명시적으로 제공한 필드입니다. NGINX나 ALB에 기본으로 제공되는 공통 필드가 아닙니다.

| 사례 | 비교할 기록 | 기대 해석 |
| --- | --- | --- |
| r1 | 프록시 200과 일치하는 애플리케이션 200 | 성공 응답 전달 |
| r2 | 프록시 403, 명시적 로컬 차단, 업스트림 시도 없음 | 이 실습 자료에서는 프록시 자체 차단 |
| r3 | 프록시가 전달로 기록한 503과 애플리케이션 503이 일치 | 애플리케이션 응답 전달 확인 |
| r4 | 시도 두 건, 최종 200, 마지막 시도에서 애플리케이션 200 | 여러 시도 끝에 성공. 이 자료만으로 첫 시도의 결과는 알 수 없음 |
| r5 | 프록시는 시간 초과와 504, 같은 시도의 애플리케이션은 쓰기 완료 기록만 있고 HTTP 응답 기록은 없음 | 게이트웨이 시간 초과와 작업 완료가 함께 가능. 쓰기를 재시도하기 전 처리 상태 확인 |
| r6 | 프록시 502, 애플리케이션 후보는 같은 ID이지만 서비스 범위가 다름 | 응답 출처 미확정. 후보를 같은 요청으로 연결할 근거가 없음 |
| r7 | 프록시는 504를 전달로 기록했고 백엔드 504도 일치 | 현재 프록시는 상태를 전달함. 근본 원인은 백엔드의 의존 서비스 쪽에서 추가 조사 |

마지막에 `7/7 evidence controls matched.`가 표시됩니다. r6을 같은 요청으로 묶었다면 서비스 범위를 연결 키에 추가하세요. r5와 r7이 같은 사례처럼 보이면 상태 코드 외에 프록시의 결정과 애플리케이션 기록을 다시 비교합니다. 실습은 클라우드에서 가상 데이터로 실행했습니다. NGINX와 AWS 필드는 공식 문서로 검토했으며 실제 배포 환경에서 실행하지 않았습니다.

## 6. 확인 문제와 완료 기준

1. **백엔드가 503을 보냈는지 어떻게 확인하나요?** 올바른 업스트림 시도에 해당하는 애플리케이션 응답 또는 그 지점의 동등한 증거를 찾습니다. 클라이언트가 본 503만으로는 누가 만들었는지 알 수 없습니다.
2. **쓰기 도중 504가 나왔습니다. 다시 보내기 전에 무엇을 보나요?** 같은 작업의 영속 상태나 서비스의 멱등성 처리 기록을 확인합니다.
3. **최종 200인데 앞선 재시도가 기록될 수 있나요?** 가능합니다. 최종 상태만 집계하지 말고 시도 목록을 확인하세요.
4. **서로 다른 서비스 범위에서 요청 ID가 같으면 바로 연결하나요?** 신뢰할 수 있는 전달 관계가 있는지 확인하고 관측 지점과 시각을 대조합니다.

**완료 기준.** 프록시·업스트림·애플리케이션 결과를 설명하고, 일곱 사례를 분류하세요. r6을 해결하기 위해 확보할 기록 한 가지를 제시하면 됩니다.
