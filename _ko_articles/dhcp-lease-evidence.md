**학습 목표.** 장치가 IPv4 설정을 받는 과정을 설명합니다. 통신 시각에 유효했던 임대 기록을 찾아 장치 후보를 좁히고, 증거가 부족하면 그 이유를 기록합니다.

## 1. DHCP 서버는 무엇을 빌려주나요?

**DHCP**는 장치가 네트워크 설정을 자동으로 받도록 하는 프로토콜입니다. DHCPv4 서버는 IPv4 주소를 일정 기간 할당할 수 있습니다. 이 기간의 주소 사용을 **임대**, 주소와 클라이언트 식별자를 일정 기간 연결한 기록을 **바인딩**이라고 합니다. **스코프**는 서버에서 특정 네트워크에 적용하는 주소 범위와 설정입니다. **예약**은 특정 클라이언트에 어떤 주소를 주도록 정한 규칙입니다. 예약만으로 사건 시점에 장치가 접속했는지는 알 수 없습니다.

서브넷 마스크는 장치가 어느 IPv4 주소까지 같은 네트워크에 있는지 판단할 때 사용합니다. 라우터 옵션은 기본 게이트웨이를, DNS 서버 옵션은 이름을 조회할 리졸버를 알려줄 수 있습니다. VPN이나 장치 자체 설정이 다른 값을 적용하기도 합니다. 이 장은 DHCPv4를 다룹니다. DHCPv6와 IPv6 라우터 광고에는 별도의 메시지와 설정 방식이 있습니다.

## 2. 첫 임대부터 갱신까지 따라가기

![DHCPv4의 첫 임대는 네 단계입니다. 클라이언트가 서버를 찾고, 서버가 설정을 제안하면, 클라이언트가 제안을 골라 요청하고, 선택된 서버가 임대를 확인합니다.]({{ '/assets/diagrams/dhcp-lease-flow-ko.svg' | relative_url }})

| 단계 | 오가는 메시지 | 기록에서 확인할 수 있는 것 |
| --- | --- | --- |
| Discover | 설정이 필요한 클라이언트가 자신의 링크에 DHCPDISCOVER를 브로드캐스트 | 설정 요청이 있었음 |
| Offer | 서버가 DHCPOFFER로 주소와 설정을 제안. 여러 서버가 응답할 수 있음 | 제안 단계. 주소를 잠시 확보해 둘 수 있으나 임대가 확정됐는지는 별도 확인 |
| Request | 클라이언트가 DHCPREQUEST를 브로드캐스트해 고른 제안을 알림 | 클라이언트의 선택. 다른 서버도 자신의 제안이 선택되지 않았음을 알 수 있음 |
| Acknowledge | 선택된 서버가 바인딩을 기록하고 DHCPACK로 응답. 클라이언트는 설정을 확인하고 주소가 이미 사용 중이면 거절할 수 있음 | 서버의 결정. 장치가 실제로 설정을 받고 사용했는지는 추가 대조 |

첫 임대의 네 단계를 **DORA**라고 부릅니다. 일반적인 설정에서 클라이언트는 UDP 68, 서버는 UDP 67을 사용합니다. **릴레이**는 다른 네트워크에 있는 DHCP 서버와 클라이언트 사이에서 메시지를 전달합니다. 서버는 릴레이 주소 필드 `giaddr`를 보고 서브넷을 고를 수 있습니다. 신뢰할 수 있는 릴레이에 설정이 되어 있다면 Option 82로 회선 또는 접속 지점의 단서를 얻을 수 있습니다. 회선 ID는 릴레이와 설정 범위 안에서 해석해야 합니다. 서버 쪽 센서에는 릴레이가 보이고 클라이언트 쪽에서는 장치가 보일 수 있습니다.

장치는 보통 T1 시점부터 기존 서버에 DHCPREQUEST를 보내 갱신합니다. 응답이 없으면 T2 시점부터 브로드캐스트로 재바인딩을 요청할 수 있습니다. 별도 값이 없으면 기본값은 임대 시간의 절반과 8분의 7입니다. ACK가 기존 임대를 연장할 수도 있습니다. 주소를 이미 아는 장치의 DHCPINFORM에도 주소 할당 없이 ACK가 오므로 앞선 메시지와 바인딩 상태를 읽어야 합니다. DHCPNAK로 설정을 다시 받아야 할 수 있고, DHCPRELEASE를 서버가 기록하면 만료 전에도 임대가 끝날 수 있습니다. 제안된 기간이나 예정 만료 시각만으로 실제 이력을 추정하지 말고 변경 기록을 확인하세요.

**정상 예시.** 노트북이 사무실 VLAN에 접속해 `192.0.2.40`을 한 시간 동안 받습니다. 서버가 임대를 확인하고 노트북이 주소를 점검합니다. 엔드포인트 자산 기록에서도 해당 VLAN 접속이 보입니다. 09:10의 사무실 통신은 이 임대 구간 안에 있습니다. 예시에서 10:00이 되면 앞선 바인딩이 끝나고 새 클라이언트가 주소를 받습니다. 게스트 네트워크도 별도의 라우팅 범위에서 같은 주소를 쓸 수 있습니다. 주소 문자열만으로는 장치를 고를 수 없습니다.

## 3. 할당 기록, 접속 지점, 시각을 모으세요

| 출처 | 수집할 값 | 해석할 때 확인할 점 |
| --- | --- | --- |
| DHCP 서버 또는 고가용성(HA) 쌍 | 스코프, IPv4 주소, 클라이언트 식별자나 하드웨어 주소, 바인딩 상태, 실제 시작·종료, 원본 서버와 발생 시각 | 서버가 무엇을 할당했는지 보여 줌. 현재 임대 표는 재사용 전 이력을 빠뜨릴 수 있으므로 보존 기간과 HA 양쪽 확인 |
| 릴레이 또는 네트워크 센서 | 시각, 관측 인터페이스·VLAN, 메시지 유형, 주소, 트랜잭션 ID, 관측된 릴레이·Option 82 | 해당 지점이 본 메시지를 보여 줌. 브로드캐스트와 갱신·응답 경로가 다를 수 있음. `xid`만으로 모든 장치나 긴 시간대를 구별할 수 없음 |
| 접속망과 엔드포인트 | 스위치·AP 접속 포트와 시각, 네트워크·자산 ID, 승인된 NAC·802.1X 기록, 필요한 경우 실제 게이트웨이·리졸버 | 물리적·논리적 접속을 뒷받침. MAC은 바뀌거나 무작위화될 수 있고 호스트 이름은 인증 증거가 아님 |
| 방화벽 또는 플로우 센서 | 변환 전 출발지 주소, 발생 시각, 관측 지점과 VLAN·라우팅 범위, 필요시 NAT 주소와 포트 | 그 지점에서 본 통신 기록. 주소가 변환됐다면 먼저 변환 전 주소를 찾음 |

DHCP 클라이언트 식별자(옵션 61)는 `chaddr`의 링크 계층 주소와 다를 수 있습니다. 가능하면 둘 다 보존하고 식별자 유형을 구분하세요. RFC 6842는 서버 응답의 클라이언트 식별자에 관한 RFC 2131의 예전 규칙을 갱신했습니다. 새 규칙에 맞는 서버는 클라이언트가 옵션을 보낸 경우 그 값을 응답에 그대로 담습니다. 부분 캡처나 정규화 로그에서 필드가 없으면 패킷 가시성과 변환부터 확인하세요.

Zeek 9.0.1의 `dhcp.log`는 DHCP 분석기가 메시지를 충분히 볼 때 `msg_types`, `requested_addr`, `assigned_addr`, `lease_time`, `server_addr` 등을 기록할 수 있습니다. 이 값은 대화 단위이며 일부는 선택 필드입니다. 바인딩의 시작·갱신·종료는 원본 패킷 또는 서버 이력으로 대조하세요. 대화 시작, ACK 관측, 서버의 바인딩 시작은 시각이 다를 수 있습니다. 대화 시작에 임대 시간을 더한 값을 실제 만료 시각으로 확정하지 마세요. Windows Server 2025 DHCP 서비스에 대해 DhcpServer 모듈과 승인된 읽기 권한이 있으면, 예시 서브넷을 실제 대상 스코프로 바꿔 `Get-DhcpServerv4Lease -ScopeId 192.0.2.0 -AllLeases`로 조회할 수 있습니다. 이 옵션은 활성 상태 외에도 서버에 아직 남아 있는 제안·거절·만료 등의 상태를 포함합니다. 전체 과거 이력이 필요하면 별도로 보존한 감사 로그를 확인합니다.

### 예상 밖의 설정이 발견되면

승인되지 않은 DHCP 서버가 예상 밖의 게이트웨이나 리졸버를 지정할 수 있습니다. 반대로 정적 IP를 쓴 장치는 DHCP 임대가 없어도 통신할 수 있습니다. 처음 보는 서버 주소가 승인된 HA 파트너나 장비 전환에서 나온 값일 수도 있습니다. 제안·승인된 설정을 승인 서버 목록과 장치의 실제 설정에 대조하세요. 검증된 기록으로 스위치나 AP와 VLAN을 찾고, 서버·릴레이 로그를 비교합니다. 패킷은 승인된 범위에서만 보존하세요. 낯선 OFFER 한 건이나 새 MAC 주소만으로 침해를 판단하지 않습니다.

지원되는 스위치의 DHCP 스누핑 기능은 승인된 경로에서만 서버 응답을 받도록 제한할 수 있습니다. 실제 제품 문서에 따라 서버·릴레이·HA 경로와 신뢰 경계를 확인하고, 통제된 변경에서 정상 임대·갱신·장애 조치를 검증하세요. 승인되지 않은 서버를 확인했다면 절차에 따라 해당 접속 경로를 격리하고 장치가 예상한 게이트웨이와 리졸버를 다시 받는지 점검합니다. 기록이 사라지기 전에 당시 증거를 확보하세요. 이미 다른 장치에 넘어갔을 수 있는 IP만으로 대응 대상을 고르지 않습니다.

## 4. 통신 시각을 임대 구간에 대조하세요

**네트워크 범위, 변환 전 IPv4 주소, 발생 시각 범위**를 함께 사용합니다. 네트워크 범위에는 필요한 사이트, VLAN, VRF나 테넌트가 반영돼야 합니다. 원본 시간대와 확인된 시계 오차를 남기세요. 로그가 도착한 시각과 사건 발생 시각은 다를 수 있습니다. 조기 반환, 만료, 갱신, 충돌하는 스냅샷은 서버의 실제 바인딩 변경 이력으로 확인합니다. 기록이 엇갈리면 시계, HA 동기화, 과거 보존 범위를 점검하세요. HA가 같은 바인딩을 복제해 두 기록이 생겼다면 서로 대조하고 양쪽 출처를 보존합니다.

오프라인 실습은 정규화된 임대 구간 **[시작, 종료)**를 사용합니다. 시작 시각은 포함하고 종료 시각은 제외합니다. 통신 시각의 오차 범위는 양 끝을 포함합니다. 실습에서는 임대 구간 경계가 정확하고 **통신 센서의 시계**만 앞뒤로 같은 폭의 오차가 있을 수 있다고 가정합니다. 실제 임대 구간에도 시각 오차가 있으면 별도로 반영해야 합니다. 한 임대가 통신 시각의 전체 범위를 덮으면 후보입니다. 여러 임대가 겹치거나 한 임대가 범위의 일부만 덮으면 추가 확인이 필요합니다.

## 5. 오프라인 실습 · 가상 통신 8건

[임대·통신 자료]({{ '/assets/labs/dhcp-lease-cases.json' | relative_url }})와 [Python 분석기]({{ '/assets/labs/dhcp-lease-evidence.py' | relative_url }})를 같은 폴더에 저장합니다. Python 3.7 이상이 필요합니다. 예시 전용 IPv4 주소와 2030년의 가상 시각을 사용했습니다. 분석기는 네트워크에 연결하지 않습니다.

```sh
python3 dhcp-lease-evidence.py
```

| 통신 | 기대 결과 | 근거 |
| --- | --- | --- |
| F01 | A 후보 | 09:10이 해당 주소의 사무실 임대 구간 안에 있음 |
| F02 | B 후보 | 정확히 10:00이고 이전 임대는 종료, 새 임대는 시작 |
| F03 | A·B 후보가 겹침 | 앞뒤 2초의 시계 오차 범위가 경계를 걸침 |
| F04 | G 후보 | F01과 주소·시각은 같고 네트워크는 게스트 |
| F05 | X·Y 후보가 겹침 | 동일 범위에서 두 서버의 임대 구간이 서로 겹침 |
| F06 | 판단 보류 | 주어진 이력에 교차하는 임대가 없음 |
| F07 | 판단 보류 | 네트워크 정보가 없어 IP만으로 연결할 수 없음 |
| F08 | 판단 보류 | B의 임대가 오차 범위 일부만 덮고 이후 증거가 없음 |

**기대 결과는 단일 후보 3건, 복수 후보 2건, 판단 보류 3건**입니다. 파일 오류가 나면 파일 이름, JSON 구조와 UTC 오프셋을 확인하세요. 결과가 예상과 다르면 장치 이름보다 먼저 네트워크와 시각 구간을 비교하세요. 실습의 후보는 임대 기록을 가리킵니다. 통신의 실제 송신 장치나 사용자를 확인하려면 별도 근거가 필요합니다.

선택 실습은 정상 DHCP 서버가 있는 격리된 승인 네트워크에서 시험 장치 한 대를 연결하는 방식입니다. 서버가 남긴 정상 임대와 클라이언트 쪽의 할당 시각·주소·설정을 비교합니다. 공유망에서 새 서버를 띄우거나 운영 임대 시간을 변경할 필요는 없습니다. 가상 분석기는 클라우드에서 실행했습니다. 실제 DHCP 서버와 센서 동작은 공식 문서로 검토했습니다.

## 6. 확인 문제와 완료 기준

1. **DHCPOFFER에 IP가 있습니다. 이후 통신과 바로 연결할 수 있나요?** 요청과 ACK의 맥락, 실제 바인딩 이력을 확인하고 장치가 주소를 사용했는지 대조해야 합니다.
2. **같은 IP가 두 네트워크에 있습니다. 무엇부터 확인하나요?** 변환 전 출발지 주소와 해당 라우팅 범위나 VLAN을 확인한 뒤 시각을 대조합니다.
3. **정확히 경계 시각에 통신했지만 시계가 2초 틀릴 수 있습니다. 어떤 장치가 보냈나요?** 두 후보를 남기고 접속망이나 엔드포인트에서 독립적인 증거를 찾습니다.
4. **임대가 없으면 승인되지 않은 장치인가요?** 정적 설정, 네트워크 범위 누락, 이력 공백으로도 설명할 수 있습니다.

F02·F03·F08을 손으로 대조해 결과를 확인하세요. 판단의 근거가 된 네트워크 범위, 시각, 기록 출처를 남기고 장치가 주소를 사용했는지 뒷받침할 두 번째 출처를 제시하면 완료입니다.
