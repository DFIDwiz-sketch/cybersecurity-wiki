애플리케이션 로그에는 테스트 요청이 성공했다고 나오는데 Suricata 경보는 보이지 않습니다. 이런 경우에는 센서가 해당 트래픽을 받았는지, 흐름을 재구성했는지, 로컬에 이벤트를 기록했는지, 그 기록이 수집기까지 도착했는지 순서대로 확인합니다. 이 장에서는 실제 통신 경로와 그 복사본을 관찰하는 Linux 패시브 센서의 관점을 구분합니다.

## 1. 패킷 복사본과 로그의 경로 따라가기

**TAP**은 통신 링크의 트래픽을 복사하는 장치입니다. 스위치의 **포트 미러링**으로도 트래픽 복사본을 받을 수 있습니다. 센서의 네트워크 인터페이스와 캡처 백엔드가 이 복사본을 Suricata에 전달합니다. Suricata는 패킷 헤더를 해석하고 TCP 스트림을 재조립해 탐지나 애플리케이션 메시지 분석에 활용합니다. **EVE**는 Suricata의 구조화된 이벤트 출력입니다. 로그 전달 에이전트가 이 이벤트를 별도의 분석 시스템으로 보낼 수 있습니다.

**누적 카운터**는 정해진 집계 기간에 발생한 횟수를 셉니다. 현재 메모리 사용량 같은 **게이지**는 샘플 시점의 값을 나타내므로 정상적으로 감소할 수 있습니다. 누적 카운터의 차이를 구하기 전에 센서, 프로세스 시작 시점, 캡처 방식, 인터페이스 범위, 전체 집계인지 스레드별 집계인지를 확인합니다. EVE 로거에서 `stats` 이벤트 유형의 `totals` 옵션은 스레드를 합산한 집계의 출력을 제어합니다. 출력된 JSON 이벤트에서는 `stats` 객체 아래에 값이 담깁니다.

| 관측 근거 | 무엇을 보여 주나요? | 이 자료만으로 판단하기 어려운 점 |
| --- | --- | --- |
| TAP 또는 포트 미러 설정과 포트 카운터 | 어떤 트래픽을 복사하도록 구성했는지, 관련 포트에 부하나 드롭이 있었는지 | 센서가 모든 패킷과 양방향을 다 받았는지 |
| `capture.kernel_drops` | 캡처 백엔드에서 보고한 드롭. 활성 캡처 모드와 카운터 정의를 먼저 확인합니다 | 통신 당사자 사이의 경로에서 또는 캡처 백엔드에 오기 전에 유실됐는지 |
| `tcp.reassembly_gap` | TCP 스트림을 재조립하는 중 빠진 데이터가 있었는지 | 집계에 포함된 구체적인 인터페이스, 패킷, 플로 또는 원인 |
| `detect.alert_queue_overflow` | 패킷별 경보 큐가 가득 차 버려진 경보의 수 | 전달 장애 여부, 빠진 서명 규칙, 모든 환경에서 통용되는 경보 손실률 |
| 로컬 EVE와 수집기 도착 기록 | 이벤트가 센서에서 출력됐는지, 수집기까지 도착했는지 | 수집 범위, 시간, 전달 상태를 대조하기 전에는 로컬 기록이 없어진 이유 |

## 2. 정상 구간을 먼저 읽고 변화 비교하기

가상의 UTC 10:00:00부터 10:00:10까지 같은 프로세스의 전체 집계에서 커널 드롭이 `200`으로 유지되고, 디코더 패킷 수는 `10,000`만큼 늘었습니다. 재조립 공백은 `15`로 그대로였습니다. 예정된 테스트 이벤트 하나가 로컬 EVE에 기록되고 수집기에도 도착했습니다. 이 구간에서는 그 이벤트의 전달을 확인했고 두 카운터의 증가도 관측되지 않았습니다.

다음 가상 구간에서 커널 드롭이 `200`에서 `320`으로, 재조립 공백은 `15`에서 `21`로 늘었습니다. 각각 `120`과 `6`이 증가했습니다. 이 경우에는 캡처 부하와 TCP 스트림 가시성을 함께 점검합니다. 두 숫자의 단위가 다르므로 공백 6건을 패킷 6개 손실로 읽을 수 없습니다. 두 변화의 인과관계나 특정 요청에 영향이 있었는지도 별도 확인이 필요합니다. 인터페이스와 미러 포트의 기록을 확인하고, 가능하면 승인을 받은 다른 관측 지점의 자료와 대조합니다.

초당 변화량은 확인된 증가분을 실제 샘플 간 초로 나눠 구합니다. 패킷 비율의 분모는 별도로 검토해야 합니다. AF_PACKET과 PF_RING에서 `capture.kernel_packets`의 의미가 다르므로 모든 백엔드에 하나의 드롭 비율 공식을 적용할 수 없습니다. 증가량 0은 해당 지표와 구간에 한정된 관측입니다. 값이 수집되지 않은 경우와 처리한 트래픽이 없던 경우도 별개로 기록합니다.

## 3. 어느 단계에서 근거가 끊겼는지 판단하기

미러가 특정 VLAN이나 한 방향을 누락할 수 있습니다. 포트나 큐가 처리할 수 있는 양보다 캡처 트래픽이 많을 수도 있습니다. 체크섬 처리 방식이나 스트림 추적에 할당된 자원 한도도 재조립 공백을 만들 수 있습니다. 사고 시간대 부하가 가시성을 낮출 수 있지만 정상 백업, 일시적 버스트, 유지보수도 비슷한 증상을 남깁니다. 카운터가 증가했다는 근거만으로 고의성을 판단할 수 없습니다.

암호화된 트래픽이 관측돼도 평문을 요구하는 탐지 규칙은 적용되지 않을 수 있습니다. 적용한 규칙 세트나 애플리케이션 이벤트 출력, 경보 임계값도 확인합니다. 기대한 이벤트가 로컬에 있으면 수집 입력 필터, 전달 에이전트의 읽기 위치와 큐, 파싱 오류, 인덱스 시간, 수집기 권한을 살펴봅니다. 로컬에 없으면 먼저 트래픽과 경보의 발생 조건을 확인합니다. 패킷별 경보 큐 오버플로는 수집기에 여유가 있어도 센서에서 발생할 수 있습니다.

프로세스 재시작이나 집계 대상 변경이 있으면 이전 값을 새 기준값과 바로 비교할 수 없습니다. 호스트 부팅 ID와 함께 프로세스 시작을 식별하는 값도 기록합니다. 경과 시간과 프로세스 가동 시간을 확인하고 감소한 누적값에는 연속성 문제가 있다고 표시합니다. 행이 없으면 실제 트래픽이 조용했던 것인지, 수집 공백·필터·파일 로테이션의 영향인지 구분합니다. 정상 전달에 걸리는 시간을 기다린 뒤 이벤트 발생 시각과 수집 시각을 모두 기준으로 검색합니다.

## 4. 블루팀 수집·탐지·복구

1. **관측 범위를 기록합니다.** 센서와 인터페이스, 방향, 캡처 모드, Suricata 버전, 프로세스 시작, EVE 파일 경로, 적용한 룰과 설정을 남깁니다. `suricata --build-info`는 빌드 시 지원되는 기능을 보여 줍니다. 실제로 활성화된 방식은 실행 서비스 설정과 시작 기록에서 확인합니다.
2. **계층별로 같은 시간대를 보존합니다.** 미러와 네트워크 인터페이스 카드(NIC)의 카운터, 같은 구간의 Suricata 기록을 확보합니다. 승인된 Linux 센서에서 `ethtool -S INTERFACE`를 사용하려면 도구와 드라이버 지원이 필요합니다. 인터페이스와 드라이버에 따라 필드 이름과 의미가 달라집니다. 스레드별 출력이나 파일 로테이션을 사용한다면 관련 파일 각각과 전달 범위를 확인합니다.
3. **원본 이벤트와 수집 결과를 대조합니다.** 승인된 환경에서 발생이 예상되는 무해한 트랜잭션을 고릅니다. 센서, 이벤트 유형, 발생 시각, 확인 가능한 플로 또는 트랜잭션 ID로 매칭합니다. 아래 읽기 전용 명령에는 `jq`와 `stats` 유형 및 전체 집계가 활성화된 상태에서 저장한 EVE JSON Lines 파일이 필요합니다. 스레드별 행이나 외부에서 계산한 증가량 대신 누적값을 대조합니다. 없는 필드는 `null`로 표시됩니다.

```bash
jq -c 'select(.event_type=="stats") | {
  timestamp, uptime:.stats.uptime, decoder_packets:.stats.decoder.pkts,
  kernel_drops:.stats.capture.kernel_drops, gaps:.stats.tcp.reassembly_gap,
  alert_overflow:.stats.detect.alert_queue_overflow
}' eve-snapshot.jsonl
```

4. **제한된 범위에서 탐지하고 복구를 확인합니다.** 처리 트래픽이 충분한 상태에서 비교 가능한 집계의 증가가 이어지거나, 로컬에서 확인된 이벤트가 약속된 시간 내 수집기에 도착하지 않으면 알립니다. 트래픽 의심 신호와 관측 장애 알림은 각각 해석합니다. 캡처 쪽은 조정에 앞서 미러 용량, NIC 오류, 활성 캡처 설정을 확인합니다. 전달 쪽은 라우팅, 적체와 로테이션을 점검합니다. 복구 후에는 승인된 테스트 이벤트를 로컬과 수집기에서 모두 확인합니다.

## 5. 승인된 오프라인 실습

<a href="{{ '/assets/labs/suricata-sensor-health-evidence.py' | relative_url }}" download>Python 검사기</a>와 <a href="{{ '/assets/labs/suricata-sensor-health-cases.json' | relative_url }}" download>가상 사례 JSON</a>을 같은 폴더에 저장하세요. 본인이 소유하거나 사용 승인을 받은 환경에서 Python 3으로 실행합니다. 검사기는 로컬 실습 파일에서 구간별 변화를 계산하거나 로컬 및 수집기 도착 기록을 분류합니다. 테스트의 프로세스 식별자와 전달 여부는 가상의 수집 메타데이터입니다. 패킷 생성이나 Suricata 조회 없이 실행할 수 있습니다.

```bash
python3 suricata-sensor-health-evidence.py
```

| 비교할 상황 | 기대 결과 |
| --- | --- |
| 트래픽이 있는 구간의 카운터 유지, 유휴 구간, 필드 누락 | 관측된 증가 없음, 디코더 처리 증가 없음, 판단 자료 부족을 각각 구분합니다 |
| 커널 드롭, TCP 공백, 경보 큐 오버플로 | 양의 증가분을 항목별로 분류합니다 |
| 프로세스 교체, 누적값 감소, 긴 샘플 공백 | 기준값을 다시 잡거나 비교를 보류합니다. 실습에서는 예상 간격의 두 배를 초과하면 공백으로 처리합니다 |
| 수집기에 없음, 로컬에 없음 | 원본 기록 존재 여부에 따라 점검 시작 지점이 달라집니다 |

정상 파일에서는 `12/12 evidence cases matched.`가 나옵니다. 실패하면 두 파일이 같은 판본인지 확인하고 출력에 나온 사례 ID를 살펴보세요. 사본의 B 사례에서 기대값을 유지한 채 `after.capture_drops`만 `320`에서 `200`으로 바꾸면 드롭 증가로 분류되지 않고 종료 코드 1이 나와야 합니다. 이 대조 실험으로 검사기가 두 기록의 차이를 구별하는지 확인할 수 있습니다. Suricata와 NIC 및 전달 에이전트 동작은 공식 문서로 검토했습니다. 실습은 실제 센서나 수집기의 동작을 검증하는 절차와 별개입니다.

## 6. 확인 문제와 완료 기준

1. **드롭은 0으로 유지됐지만 TCP 공백은 증가했습니다. 통신 경로에서 패킷이 유실됐다고 볼 수 있나요?** 다른 관측 지점과 인터페이스의 근거가 필요합니다. 비대칭 캡처, 체크섬, 스트림 자원 한도도 점검합니다.
2. **어제 320이던 값이 오늘 10입니다. 드롭이 310건 개선된 걸까요?** 프로세스 시작, 집계 범위와 카운터 연속성을 확인해야 합니다. 비교 가능한 누적값이라면 감소는 차이를 계산하기 위한 전제를 깨뜨립니다.
3. **로컬 EVE에서 찾은 이벤트가 시간을 기다려도 수집기에 없습니다. 어디를 보나요?** 원본 파일에서 전달 에이전트와 목적지까지 따라가며 조회 범위와 발생·수집 시간 기준을 확인합니다.

**완료 기준.** 사례 12개와 대조 실험 결과를 재현합니다. 테스트 이벤트가 빠졌을 때 어느 단계까지 근거로 확인할 수 있는지와 다음에 수집할 자료를 설명합니다. 이어서 [두 지점에서 패킷 캡처 비교]({{ '/ko/wiki/capture-visibility/' | relative_url }})와 [Suricata 트랜잭션 증거]({{ '/ko/wiki/suricata-eve-transaction-evidence/' | relative_url }})를 읽어 보세요.
