**학습 목표.** 패스키가 무엇을 증명하는지 설명하고, 로그인 시도가 어디에서 멈췄는지, 대상 앱이 세션을 만들었는지 기록에서 확인합니다.

## 1. 어떤 키를 누가 보관하나요?

**패스키**는 로그인에 사용하는 공개키 자격 증명입니다. **인증기**는 자격 증명의 키를 관리하고 필요하면 장치에서 사용자를 확인합니다. 휴대전화나 컴퓨터에 내장된 플랫폼 인증기를 쓰거나 외장 보안 키를 사용할 수 있습니다. **신뢰 당사자(RP, Relying Party)**는 자격 증명을 검증하는 서비스입니다. 통합 로그인에서는 ID 제공자가 RP일 수 있습니다. 브라우저와 운영체제는 웹사이트와 인증기 사이에서 요청을 전달합니다. **WebAuthn**은 브라우저 API와 등록·인증 절차를 정의합니다. **FIDO2**에는 WebAuthn과 지원되는 외장 인증기가 통신에 사용하는 CTAP가 포함됩니다.

| 용어 | 뜻 | 증거가 말해 주는 범위 |
| --- | --- | --- |
| 자격 증명 ID와 공개키 | 서비스가 ID로 이전에 등록한 공개키를 찾음 | ID만으로 사람이나 장치를 특정할 수 없음 |
| RP ID와 오리진 | RP ID는 자격 증명의 도메인 범위. 오리진은 스킴·호스트·포트로 웹 호출 출처를 나타냄 | 허용되는 RP ID와 예상 오리진은 별도 검사 |
| 사용자 존재(UP) | 사용자가 장치와 상호 작용했거나 존재를 나타냄 | 신원이나 구체적인 확인 방법을 판단하기에는 부족 |
| 사용자 검증(UV) | 인증기가 PIN·생체 인식 등으로 로컬 확인을 했다고 보고 | RP가 받는 것은 플래그. 그 값만으로 어떤 수단으로 확인했는지는 알 수 없음 |

**장치에 묶인 자격 증명**은 해당 인증기에 연결되도록 설계됩니다. **동기화 패스키**는 제공자를 통해 다른 장치에서도 사용할 수 있습니다. 장치에 묶였다는 표기만으로 인증 보증 수준을 정할 수는 없습니다. NIST SP 800-63B-4가 정의하는 AAL3은 내보낼 수 없는 개인키 등 별도 요건을 갖춰야 하므로 동기화 가능한 인증기는 사용할 수 없습니다. 패스키 창만 보고 보증 수준을 판단하지 말고 실제 정책, 등록·복구 통제, 자격 증명 유형을 확인하세요. 검증기에 WebAuthn Level 3의 백업 플래그가 보인다면 BE는 백업 가능 여부, BS는 인증기가 보고한 현재 백업 상태입니다. 동기화 제공자나 실제 로그인 장치, 상태 변경 이유는 이 값만으로 알 수 없습니다.

## 2. 정상 로그인 한 건을 따라가세요

![서비스가 등록 때 공개키를 보관합니다. 로그인 때 인증기가 새 챌린지에 서명하면 서비스가 응답을 검증하고 접근 정책과 앱 세션 기록을 따로 확인합니다.]({{ '/assets/diagrams/passkey-signin-flow-ko.svg' | relative_url }})

1. **등록합니다.** 승인된 계정 등록 절차에서 RP가 새 챌린지를 포함한 등록 옵션을 보냅니다. 인증기는 자격 증명을 만듭니다. 서비스는 등록 응답을 검증하고 해당 계정의 공개키와 자격 증명 ID를 저장합니다. 개인키는 RP에 전달되지 않습니다. 인증기 증명(attestation)을 쓰는 경우 신뢰 및 개인정보 보호 정책의 범위 안에서 인증기 정책을 적용하는 근거가 될 수 있습니다.
2. **인증을 요청합니다.** RP가 이번 거래에 연결된 예측하기 어려운 새 챌린지를 발급합니다. 브라우저는 지정된 RP ID로 자격 증명을 요청합니다. 일반적인 최상위 페이지 `https://login.example.test`에서는 `example.test`가 유효한 RP ID가 될 수 있습니다. 허용 오리진은 별도로 설정합니다.
3. **서명하고 검증합니다.** 인증기는 인증기 데이터와 클라이언트 데이터의 해시를 함께 서명합니다. 클라이언트 데이터는 챌린지와 오리진을 연결합니다. 인증기 데이터에는 RP ID 해시와 플래그가 있습니다. RP는 응답 유형, 챌린지, 오리진, RP ID 해시, 필요한 플래그, 계정과 자격 증명의 관계, 서명을 검증합니다. 실제 구현은 유지보수되는 WebAuthn 라이브러리와 최신 표준의 전체 요건을 따릅니다.
4. **접근 정책과 결과를 확인합니다.** 응답 검증을 통과하면 인증을 뒷받침합니다. 이후 접근 정책이나 통합 로그인 단계에서 거부될 수 있습니다. 앱이 세션을 만들거나, 거부하거나, 별도 기록을 남기지 않을 수 있습니다. 검증, 정책, 앱 결과를 구분해 확인합니다.

**정상 예시.** Ada가 훈련용 ID 서비스에 이미 등록한 패스키로 로그인합니다. 인증기가 필요한 UV를 보고하고 검증기는 응답을 받아들입니다. 접근 정책도 통과한 뒤, 동일한 범위의 앱 감사 이벤트에 세션 생성이 기록됩니다. 통합 로그인이라면 ID 제공자의 인증 결과와 앱의 자체 기록을 대조하세요. 브라우저 화면에서 패스키 확인이 끝났다는 표시만으로 두 결과를 확정할 수 없습니다.

## 3. 어디서 실패할 수 있고 어떻게 대응하나요?

WebAuthn은 인증을 예상 서비스에 묶어 자격 증명 피싱을 줄입니다. 정상 사이트를 흉내 낸 다른 오리진이 일반적으로 정상 사이트의 패스키를 자기 자격 증명처럼 요청할 수 없습니다. 하지만 등록·복구 경로, 더 약한 대체 로그인 수단, 침해된 클라이언트와 이미 인증된 세션의 위험은 남습니다. 대체 수단이나 복구 경로를 악용한 경우 패스키 응답 없이도 계정에 접근할 수 있으므로 실제 인증 방법을 확인합니다. 등록·복구·예외 허용을 제한하고 감사하며, 새 자격 증명은 승인된 경로로 계정 소유자에게 확인합니다.

| 관측 | 수집할 기록 | 신중한 해석 |
| --- | --- | --- |
| 브라우저가 취소됐고 검증기 기록이 없음 | 브라우저 오류 분류·시각, 서버 요청과 로그 가시성 | 시도는 보고됐으나 서버 검증기에 도착하기 전에 멈췄을 수 있음 |
| 오리진·RP ID·챌린지 거부 | 내부 사유, 신뢰 가능한 예상 설정, 요청 ID와 최근 변경 | 보안 검사가 실패함. 설정 변경, 만료 또는 의심스러운 시도에서도 비슷한 결과가 나올 수 있음 |
| 필수 UV가 없음 | 검증 정책, 허용 인증기와 기록된 플래그 결과 | 적용된 요구 조건을 충족하지 못함. PIN이나 생체 정보는 알 수 없음 |
| 서명 카운터 경고 | 확인 가능한 이전·현재 카운터, 인증기 특성, 중복 수신, 계정 활동 | 정책에 따라 검토할 신호. 일부 인증기는 0을 사용하며 증가하지 않았다는 것만으로 복제를 확정할 수 없음 |
| 검증을 통과했으나 접근 거부 또는 미확인 | 동일 범위의 정책 결과와 앱 세션 감사 | 인증 검증과 앱 결과는 각각 확인해야 함 |

UTC 시각, 가명화한 계정·자격 증명 참조, 조직 또는 RP 범위, 거래 ID, 인증 방법, 사유 분류, 릴리스나 정책 버전을 확보하세요. 보존 기간과 필드 출처를 확인합니다. 원본은 접근을 제한해 보존합니다. 공유 자료에는 원본 챌린지, 인증 응답, 세션 쿠키, 불필요한 장치 정보를 넣지 않습니다. 이 장의 내부 사유 이름은 설명용이며 실제 제품이 같은 필드를 제공할 필요는 없습니다.

Microsoft Entra에서는 로그인 기록의 Authentication Details에서 사용한 방법을 확인하고, 가능한 경우 조건부 액세스 및 앱 로그로 보강합니다. 해당 테넌트의 패스키 정책과 로그 세부 범위를 확인하세요. WebAuthn의 원시 검사 결과가 Entra 로그에 모두 나온다고 가정하지 않습니다. 승인되지 않은 등록이나 복구가 확인되면 사고 절차에 따라 계정을 보호하고 등록 수단과 세션을 확인합니다. 관련 세션이 앱에서 더 이상 허용되지 않는지도 확인하세요.

## 4. 오프라인 실습 · 가상 로그인 10건

[가상 감사 기록]({{ '/assets/labs/passkey-evidence-cases.json' | relative_url }})과 [Python 검토기]({{ '/assets/labs/passkey-evidence-review.py' | relative_url }})를 같은 폴더에 저장하고 Python 3로 실행합니다.

```sh
python3 passkey-evidence-review.py
```

자료는 가상 관측 결과를 정규화한 값입니다. 실제 인증기, 인증 응답, 자격 증명이나 시스템 로그는 포함하지 않습니다. 검토기는 암호 메시지를 생성하거나 검증하지 않고 네트워크에도 연결하지 않습니다. 검증을 통과한 건은 **관측 범위와 시도 ID가 모두 같은** 앱 세션 결과를 찾습니다.

| 시도 | 기대 결과 | 이유 |
| --- | --- | --- |
| A01 | 세션 생성 | 응답 검증을 통과했고 같은 범위의 세션 감사가 있음 |
| A02 | 검증 미확인 | 브라우저 취소 기록은 있지만 검증기 결과가 없음 |
| A03 | 검증 단계에서 거부 | 챌린지 검사 실패 |
| A04 | 검증 단계에서 거부 | 오리진이 예상 설정과 불일치 |
| A05 | 검증 단계에서 거부 | RP ID 해시 불일치 |
| A06 | 검증 단계에서 거부 | 필수 사용자 검증 없음 |
| A07 | 세션 생성, 추가 검토 신호 | 검증기가 카운터 신호를 기록했지만 정책상 응답을 허용 |
| A08 | 세션 거부 | 응답 검증 뒤 접근 정책이 세션을 거부 |
| A09 | 세션 미확인 | 같은 ID의 세션 기록이 있으나 다른 범위에 속함 |
| A10 | 대체 로그인 방식 | 세션은 생성됐으나 실제 방법은 WebAuthn이 아님 |

예상 마지막 줄은 `Reviewed: 10`입니다. 검증 단계에서 4건이 거부됐고, 패스키 검증 뒤 세션 생성이 확인된 것은 A07의 추가 신호를 포함해 2건입니다. 파일 오류가 나면 이름과 JSON 문법을 확인하세요. A09가 연결되면 두 출처의 범위 값을 비교합니다. A07과 A08을 해석하기 어렵다면 검증기가 받아들였는지와 앱이 세션을 허용했는지를 각각 살펴보세요.

**승인된 환경에서 선택 실습.** 시험 RP 또는 이미 설정된 승인 테넌트의 시험 계정으로 정상 패스키 로그인을 한 번 진행하고 실제 방법, 정책과 앱 세션을 확인합니다. 두 번째 로그인은 정상 브라우저 창에서 승인 전에 취소하고 브라우저와 서버가 각각 남긴 기록을 비교하세요. 운영 정책을 바꿀 필요는 없습니다. 오프라인 검토기는 클라우드에서 실행했습니다. 제품 절차는 문서로 검토했고, 실제 패스키나 테넌트 로그인 시험은 이번 게시의 검증 범위에 포함되지 않았습니다.

## 5. 확인 문제와 완료 기준

1. **서비스에 지문이 전송되나요?** 서비스에는 서명된 응답과 플래그가 전달됩니다. 로컬 확인은 인증기나 플랫폼이 담당합니다.
2. **사용자 인증이 성공해도 앱에 접속할 수 없는 경우가 있나요?** 네. 접근 정책, 통합 로그인, 앱 세션이 별도로 판단됩니다. A08이 그 예입니다.
3. **서명 카운터 경고는 복제의 확정 증거인가요?** 인증기 특성과 거래 문맥을 확인하고 다른 출처로 대조해야 합니다.
4. **A09의 판단을 왜 보류하나요?** 다른 범위에 있는 같은 식별자는 검증과 앱 세션의 연결 근거가 되지 않습니다.

A02·A07·A08·A09에 대해 출처, 확인된 사실, 추가로 필요한 증거를 한 문장씩 적으면 완료입니다.
