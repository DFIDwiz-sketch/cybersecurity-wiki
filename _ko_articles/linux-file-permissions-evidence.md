**학습 목표.** 읽을 수 있어 보이는 파일에서 서비스가 `Permission denied`를 받았다고 가정해 봅시다. 어떤 프로세스가 무슨 작업을 요청했고, 어느 디렉터리나 규칙이 그 결과를 설명하는지 찾아봅니다. 현재 권한으로는 지금 상태를 확인하고, 과거에 무슨 변경이 있었는지는 감사 기록으로 조사합니다.

## 1. 모드 비트 읽기

파일 **모드**의 기본 권한은 소유자, 그룹 권한 범위, 그 밖의 사용자로 나뉩니다. 각 숫자는 읽기(4), 쓰기(2), 실행 또는 탐색(1)을 더한 값입니다. 기본 ACL에서 `0640`은 소유자가 읽고 쓸 수 있고, 소유 그룹이 읽을 수 있으며, 나머지는 접근할 수 없다는 뜻입니다. **ACL**(접근 제어 목록)을 사용하면 특정 사용자나 그룹에 권한을 따로 지정할 수 있습니다. 확장 ACL에 **마스크**가 있으면 모드의 가운데 숫자는 소유 그룹 항목과 이름이 지정된 항목들의 권한 상한을 나타냅니다.

| 권한 | 일반 파일에서의 의미 | 디렉터리에서의 의미 |
| --- | --- | --- |
| `r` | 파일 내용 읽기 | 안에 있는 항목의 이름 나열 |
| `w` | 파일 내용 쓰기 | 보통 탐색 권한과 함께 항목 추가 또는 삭제 |
| `x` | 다른 조건이 허용할 때 파일 실행 | 디렉터리를 탐색해 이미 알고 있는 이름 조회 |

경로로 파일을 새로 열려면 요청한 프로세스에 경유하는 각 디렉터리의 탐색 권한이 있어야 합니다. 디렉터리를 읽을 수 있어 이름이 보이더라도 내부 파일에는 접근하지 못할 수 있습니다. 파일 이름을 제거하는 `unlink`는 부모 디렉터리의 항목을 바꿉니다. 따라서 부모 권한과 스티키 비트 같은 제한을 확인해야 합니다. 파일이 읽기 전용이라는 사실만으로 그 이름을 삭제할 수 있는지 판단하기는 어렵습니다.

## 2. 정상적인 서비스 읽기 따라가기

가상의 서비스에서 `/srv/reports`는 `root:reporting` 소유이며 모드는 `0750`입니다. 그 안의 `current.csv`는 `publisher:reporting` 소유이며 모드는 `0640`입니다. 앞선 경로를 탐색할 수 있고, 서비스 프로세스가 `reporting`에 속하며, 파일시스템 ID 매핑이 예상과 같고 추가 정책이 막지 않는다고 가정합시다. 프로세스는 `reports`의 그룹 탐색 권한으로 이름을 조회하고, `current.csv`의 그룹 읽기 권한으로 파일을 엽니다. 관리자 셸은 다른 자격 정보로 실행되므로 같은 경로를 열어도 결과가 다를 수 있습니다.

Linux 파일 권한 검사에 쓰는 파일시스템 UID와 GID는 보통 유효 UID 및 GID와 같습니다. 보조 그룹과 Linux capability에 따라 결과가 달라질 수 있습니다. 컨테이너에서는 같은 경로라도 다른 마운트, 객체 또는 숫자 ID 매핑이 보일 수 있습니다. SELinux나 AppArmor 같은 강제 접근 제어가 모드와 ACL이 허용한 작업을 거부할 수도 있습니다. 그림은 조사 순서를 보여줍니다. 커널 내부 호출 순서는 구현에 따릅니다.

## 3. ACL과 흔한 권한 변경 읽기

아래는 `publisher`가 소유한 파일의 **가상** 접근 ACL을 줄여 쓴 예시입니다. `svc-report`에 읽기와 쓰기가 표시되지만, 마스크가 읽기만 허용합니다.

```text
user::rw-
user:svc-report:rw-    #effective:r--
group::---
mask::r--
other::---
```

일반적인 임의 접근 제어에서는 먼저 소유자가 일치하는지 봅니다. 이름이 지정된 사용자와 일치하면 해당 항목에 마스크를 적용합니다. 그룹으로 비교할 때는 요청 권한을 부여하는 해당 그룹 항목이 있는지 확인한 뒤 마스크가 있으면 적용합니다. 소유자, 지정 사용자, 그룹 가운데 일치하는 항목이 없을 때만 `other`를 봅니다. 지정 사용자 항목에서 거부됐다면 더 관대한 그룹 항목을 찾아 넘어가지 않습니다. 예시의 `svc-report`는 경로와 다른 정책이 허용하면 지정 사용자 항목에 따라 읽을 수 있습니다.

| 발견한 변경 | 확인할 증거 |
| --- | --- |
| ACL 항목을 추가해 접근 범위가 넓어짐 | 숫자 사용자·그룹 ID, 유효 마스크, 승인 내역, 실제 프로세스 자격 정보 |
| 모드를 바꾼 뒤 ACL 유효 권한이 줄어듦 | 마스크가 있다면 모드의 가운데 숫자와 마스크가 함께 바뀝니다. 지정 항목 자체는 남을 수 있습니다 |
| 새 파일에 예상과 다른 권한이 붙음 | 부모의 기본 ACL이 없으면 요청 모드에서 프로세스의 `umask`에 해당하는 비트를 제거합니다. 기본 ACL이 있으면 이를 상속하고 요청 모드 범위로 제한합니다 |
| 배포 후 경로의 권한이 달라짐 | 장치와 inode, 마운트 관점, 변경 승인 내역을 비교합니다. 같은 경로에 다른 객체가 들어왔을 수 있습니다 |

민감한 데이터에 승인 없이 ACL 권한을 추가하거나 갑작스러운 모드 변경으로 서비스 접근을 막는 일이 있을 수 있습니다. 정상적인 패키지 갱신, 파일 교체, 지원 작업도 비슷한 모습으로 남습니다. 변경 전 상태와 실제 접근 범위를 확보한 뒤 의도를 판단하세요.

## 4. 블루팀의 수집·탐지·대응

1. **실패한 요청을 기록합니다.** 호스트, UTC 시각, 작업, 경로, 프로세스를 적습니다. 살아 있는 프로세스의 정보를 읽을 권한이 있다면 `/proc/PID/status`에서 `Uid`, `Gid`, `Groups`, `CapEff`를 보존합니다. 프로세스의 신원과 마운트 네임스페이스를 확인합니다. 관리자 셸에서 실행한 `id`는 그 셸의 정보입니다.
2. **상태를 변경하지 않고 수집합니다.** 승인된 계정과 올바른 파일시스템 관점에서 `namei -l -- /srv/reports/current.csv`로 경로 구성 요소를 봅니다. GNU `stat -c '%a %u:%g %d:%i %z %n' -- /srv/reports/current.csv`로 모드, 숫자 소유권, 장치와 inode, 상태 변경 시각, 이름을 확인하고, `getfacl -n -p -- /srv/reports /srv/reports/current.csv`로 숫자 ACL과 유효 권한을 확인합니다. ACL 도구와 파일시스템의 지원이 필요합니다. 다른 관련 상위 경로도 확인하세요. 상태 변경 시각만으로는 누가 바꿨는지 알 수 없습니다.
3. **감사 타임라인을 만듭니다.** 사고 당시 Linux Audit가 동작했고 일치하는 규칙에 `report_permissions` 키가 있었다면, 원본 호스트에서 `ausearch -k report_permissions -ts today --raw`로 오늘의 기록을 검색할 수 있습니다. 로그 읽기 권한이 필요합니다. 과거 사건은 호스트 시간 기준으로 시작·종료 시각을 지정하고 원본 레코드를 함께 남깁니다. 결과가 없을 때는 그 기간의 규칙, 유실 카운터, 보존 기간, 전달 상태부터 확인합니다. Linux Audit에는 대상 경로를 좁힌 파일시스템 규칙을 적용하고 필요에 따라 아키텍처를 지정합니다. 업스트림 `auditctl` 매뉴얼은 구형 `-w` 문법을 사용 중단 대상으로 표시합니다.
4. **기록을 연결하고 대응합니다.** 원본 호스트와 전체 `msg=audit(timestamp:serial)` 값으로 `SYSCALL`과 `PATH`를 묶습니다. 결과, `auid`(로그인 UID, 설정되지 않을 수 있음), 현재 UID 필드, 실행 파일, 경로와 inode를 확인합니다. 같은 이벤트 ID에 `SYSCALL success=yes auid=1001 euid=0`과 `PATH name="/srv/reports/current.csv" inode=41012`가 있다는 가상의 축약 예시를 생각해 보세요. 로그인 UID와 연결된 권한 있는 프로세스에서 감시 대상 작업이 성공했다는 증거입니다. 권한 변경이라고 결론 내리기 전에 시스템 호출과 인자를 확인합니다. 접근을 복구하기 전에 승인 기준과 증거를 보존하고, 대상 서비스의 자격 정보와 동일 경로로 재확인합니다. 노출 가능성이 있다면 별도로 수집된 읽기 증거를 찾습니다.

현재 파일 권한과 성공한 권한 변경 이벤트는 각각 다른 사실을 뒷받침합니다. 일반적인 로컬 Linux 임의 접근 제어에서 모드나 ACL을 변경해도 이미 열려 있는 파일 디스크립터의 접근이 자동으로 철회되지는 않습니다. 기존 핸들, 추가 정책, 원격 파일시스템의 동작은 따로 확인하세요. 이 장은 로컬 Linux의 POSIX 방식 ACL을 다룹니다. NFSv4 ACL이나 SMB 서버 권한은 해당 환경에서 별도로 분석해야 합니다.

## 5. 오프라인 실습 · 커널이 보여주는 여섯 가지 결과

POSIX ACL을 지원하는 Linux 파일시스템의 본인 전용 폴더에 <a href="{{ '/assets/labs/linux-file-permissions-lab.py' | relative_url }}" download>linux-file-permissions-lab.py</a>를 내려받으세요. Python 3, 시스템 `libacl` 라이브러리, 일반 사용자 계정이 필요합니다. 스크립트는 임시 파일만 만들고 자체 프로세스의 umask만 변경합니다. 파일을 저장한 디렉터리에서 실행합니다.

```bash
TMPDIR="$PWD" python3 linux-file-permissions-lab.py
```

| 실습에서 바꾸는 조건 | 기대하는 증거 |
| --- | --- |
| 부모의 기본 ACL 유무를 바꿔 각각 파일 생성 | 요청 모드 `0666`에 umask `077`만 적용하면 `0600`, 기본 ACL이 적용되면 `0640` |
| 지정 그룹 ACL 항목을 추가한 다음 파일 모드 변경 | 처음에는 항목이 `rw-`, 마스크가 `r--`입니다. 모드를 바꾸면 항목은 남고 마스크가 `---`가 됩니다 |
| 파일을 연 후 부모 디렉터리에서 탐색 권한 제거 | 같은 계정에서 새로 열기는 실패합니다. 이미 연 디스크립터로는 실습 내용을 계속 읽습니다 |

마지막 줄은 `6 checks passed.`입니다. 라이브러리 오류가 나면 `libacl` 설치 여부를, `Operation not supported` 같은 ACL 오류가 나면 `TMPDIR`의 파일시스템 지원 여부를 확인하세요. 새로 열기가 예상과 달리 성공하면 테스트 프로세스에 임의 접근 제어를 우회하는 capability가 있는지 확인합니다. 지정 그룹 실습에서는 같은 사용자로 커널의 ACL 메타데이터를 읽습니다. 다른 사용자로의 파일 접근은 실험하지 않습니다. Linux 6.18.57과 Python 3.12에서 여섯 항목을 실행했습니다. Linux Audit와 강제 접근 제어 동작은 문서로 검토했습니다.

## 6. 확인 문제와 완료 기준

- **파일 모드가 여전히 `0640`인데 열 수 없다면 어디를 볼까요?** 해당 프로세스가 모든 상위 디렉터리를 탐색할 수 있는지, 그 프로세스의 파일시스템 관점에서 ACL·자격 정보·정책이 어떤지 확인합니다.
- **지정 항목이 `rw-`이고 마스크가 `r--`이면 쓸 수 있나요?** 해당 항목에서 얻는 유효 권한은 읽기입니다. 상위 디렉터리와 별도 정책도 적용됩니다.
- **umask가 `077`인데 새 파일이 `0640`이면 이상한가요?** 요청 모드가 해당 비트를 허용하고 부모에 기본 ACL이 있다면 정상입니다. 실제 생성 경로와 부모 ACL을 확인합니다.
- **감사 검색 결과가 비어 있으면 권한 변경이 없었다고 볼 수 있나요?** 먼저 당시 규칙의 적용 범위, 보존 기간과 수집 상태를 확인합니다.

**완료 기준.** 파일 열기 실패 사례 하나를 골라 프로세스 신원, 경로, 요청한 작업, 증거로 확인한 첫 번째 제한, 다른 원인과 구분해 줄 관측 항목을 기록하세요.
