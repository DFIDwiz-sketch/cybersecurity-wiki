**학습 목표.** 서명 키 교체 시점에 API가 요청을 거부하기 시작했습니다. 새 공개키가 검증기의 캐시에 없었는지, 갱신이 실패했는지, 서명이 맞지 않았는지, API의 토큰 정책에 걸렸는지 구분해 봅니다.

## 1. 토큰을 받는 쪽에서 무엇을 확인하나요?

서명된 **JWT**에는 누가 발급했는지, 어느 서비스를 대상으로 하는지 같은 **클레임**이 담깁니다. 압축 형식의 **JWS**는 보호 헤더, 내용, 서명을 각각 인코딩합니다. 비대칭 서명을 사용하는 **발급자**는 개인키로 서명하고, API의 **검증기**는 신뢰하도록 설정된 공개키로 서명을 확인합니다. **JWK**는 키를 JSON으로 표현한 것이며 **JWKS**는 그 집합입니다. 발급자 메타데이터의 `jwks_uri`는 키 집합을 받는 주소입니다. 검증기는 미리 신뢰하도록 구성된 발급자의 메타데이터에서 이 주소를 확인하거나 운영 설정에서 직접 지정합니다.

| 필드 또는 제어 | 왜 필요한가요? | 해석 방법 |
| --- | --- | --- |
| `kid` | 키 교체 중 서명에 사용된 후보 키를 고르는 단서입니다. | 구성된 발급자와 키 집합 안에서 비교합니다. 발급자가 다르면 같은 문자열도 다른 키를 가리킬 수 있습니다. |
| `alg` | 서명 알고리즘을 나타냅니다. | 운영 정책에서 허용하며 키 종류와 용도에 맞는 알고리즘인지 확인합니다. |
| `typ`와 토큰 프로파일 | 용도가 다른 자격 증명을 구분합니다. | 엔드포인트가 수용하는 토큰의 검증 규칙을 적용하세요. RFC 9068 액세스 토큰 프로파일은 `at+jwt`를 정의합니다. ID 토큰에는 OIDC 클라이언트 검증 규칙이 적용됩니다. |
| `iss`, `aud`, `exp` | 발급자, 수신 대상, 만료 시각을 확인합니다. | 정확히 일치하는 발급자와 예상 대상을 확인하고 검증기 시계와 문서화한 허용 오차를 기준으로 만료를 판단합니다. 해당하는 경우 `nbf` 등 추가 필수 클레임도 검사합니다. |
| 서명 결과 | 서명된 바이트를 신뢰하는 후보 키로 확인합니다. | 서명이 맞으면 용도와 클레임도 확인합니다. 개별 작업의 인가 여부는 별도 결정입니다. |

검증을 마치기 전까지 헤더와 클레임은 신뢰할 수 없는 입력입니다. 여러 발급자를 지원한다면 검증 전 `iss`는 미리 승인한 유한한 목록에서 설정을 찾는 데만 사용하고, 검증 과정에서 발급자를 정확히 대조하세요. 액세스 토큰과 ID 토큰은 목적에 맞는 검증 규칙으로 구분합니다. 유지보수되는 프로토콜 라이브러리와 공급자 명세를 사용하세요. 내부를 읽는 용도로 제공되지 않는 불투명 액세스 토큰도 있으며, RFC 9068의 유형 검사는 그 프로파일을 적용하는 환경을 대상으로 합니다.

## 2. 정상적인 키 교체를 시간 순서로 읽기

가상의 발급자와 주문 API를 예로 들어 보겠습니다. 09:00 UTC에 승인된 JWKS에는 `k1`이 있습니다. 발급자는 09:15에 `k1`을 유지하면서 `k2`를 공개하고 09:20부터 새 토큰에 `k2`로 서명합니다. 09:17에 갱신한 API 복제본은 이미 새 키를 갖고 있습니다. 다른 복제본에는 `k1`만 남아 있어 `k2` 캐시 미스를 기록합니다. 설정된 갱신 정책에 따라 승인된 JWKS를 불러온 다음 키를 다시 찾습니다. 서명과 클레임이 검증되면 요청을 받아들이고 이어 해당 주문 작업에 권한이 있는지 판정합니다. 두 키가 함께 게시되는 기간에는 기존 `k1` 토큰도 클레임과 권한 요건을 충족하면 사용할 수 있습니다. 시각은 이해를 돕기 위한 가상 값입니다.

정기 교체의 중첩 기간을 정할 때는 키 게시·캐시 전파 시간, 이미 발급된 토큰과 그 수명을 고려합니다. OIDC Core는 계획된 교체에서 최근 사용을 끝낸 키를 일정 기간 공개 상태로 유지하는 방법을 설명합니다. 개인키 유출은 사고 대응이 필요한 상황입니다. 공개 목록에서 키를 제거해도 검증기 캐시에 있던 키가 즉시 사라지지는 않습니다. 발급자와 리소스 운영자가 문서화한 키 신뢰 철회, 캐시 갱신, 토큰·세션 대응 절차를 적용하고 관련 복제본 전체에서 효과를 확인하세요.

## 3. 장애와 오용을 증거로 구분하기

| 관측 | 가능한 설명 | 구분할 증거 |
| --- | --- | --- |
| 모르는 `kid`를 승인된 갱신 후 찾음 | 정기 교체 또는 검증기의 정기 갱신 누락 | 발급자 배포 이력, 복제본 캐시 버전, 갱신 후 키 일치 |
| 모르는 `kid`가 있고 갱신이 생략되거나 실패함 | 로컬 호출 제한, 상위 시스템 오류, TLS 또는 네트워크 장애 | 실제 요청 전송 여부, 승인된 주소, 응답과 시각, 영향을 받은 복제본 |
| 신뢰하는 최신 응답에도 키가 없음 | 다른 발급자나 키 범위, 키 사용 종료, 전파 지연 또는 유효하지 않은 입력 | 복제본별 발급자 설정, 사건 시점의 신뢰 가능한 키 집합, 게시 이력 |
| 후보 키가 일치하지만 서명이 실패함 | 입력 손상, 호환되지 않거나 교체된 키, 유효하지 않은 입력 | 라이브러리 판정, 허용 알고리즘, 당시 키 버전 또는 지문 |
| 서명은 맞지만 정책이 거부함 | 대상이나 토큰 유형 불일치, 만료 또는 다른 클레임 제한 | 거부 단계, 실제 배포된 정책, 검증기 시각 |
| 갱신 요청량이 예상보다 많음 | 여러 검증기의 동시 시작, 메타데이터 서비스 지연, 모르는 키를 지목하는 입력의 반복 | 신뢰하는 발급자·복제본별 갱신 요청 수, 캐시 적중률, 배포 기록, 안전한 형태의 오류 집계 |

신뢰하지 않는 토큰에 외부 키 위치를 담은 헤더나 발급자 값이 들어올 수 있습니다. 신뢰의 기준은 운영 설정에 두고, 조회와 갱신은 승인된 메타데이터와 JWKS 주소로 제한하세요. 신뢰하는 발급자 단위로 갱신 빈도를 제한하고, 구현이 지원하면 동시 갱신을 한 번으로 묶어 대기 시간을 제한합니다. 키를 찾을 수 없거나 검증에 실패하면 검증 정책에 따라 거부합니다. 이미 신뢰한 캐시 키는 문서화된 최신성 조건과 사고 대응 정책이 허용하는 동안만 사용합니다. 모르는 키가 몰리는 현상은 조사할 신호이며, 그 기록만으로 입력을 만든 주체를 특정할 수 없습니다.

## 4. 블루팀의 수집, 탐지, 대응

1. **검증기의 판정을 남깁니다.** 승인된 애플리케이션 진단에서 UTC, 요청 상관관계 ID, 서비스, 복제본, 배포 버전, 설정된 발급자 별칭, 토큰 프로파일과 판정 단계를 수집합니다. 캐시 적중·미스, 갱신 시도·억제, 서명 결과, 클레임 및 작업 판정을 별도 필드로 내보내세요. 필드 이름은 제품마다 다릅니다. 토큰 헤더의 후보 값은 신뢰하지 않는 입력으로 표시하고 길이를 제한합니다. 메트릭에는 값의 종류가 무한히 늘어날 수 있는 차원을 쓰지 않고, 일반 로그에는 토큰 원문, Authorization 헤더, 개인 클레임을 남기지 않습니다.
2. **당시 복제본이 본 키를 확인합니다.** 라이브러리가 공개하는 경우 영향받은 복제본의 캐시 버전이나 갱신 시각을 확보합니다. 승인된 공급자 기록이나 관측에서 시각, 상태, 캐시 검증 값, 키 집합 버전 또는 승인된 지문을 보존합니다. HTTP 304는 이전 응답을 다시 사용한다는 뜻입니다. 지금 조회한 키 집합으로 사라진 캐시 이력을 복원할 수는 없습니다. 메타데이터와 JWKS 중 어느 조회가 실패했는지 구분하고, 정확한 발급자와 승인된 주소를 확인한 뒤 자료를 연결하세요.
3. **영향 범위를 좁힙니다.** 지정한 구간에서 신뢰하는 발급자, 받는 서비스의 토큰 정책, 복제본별로 판정을 묶습니다. 정상 복제본과 영향받은 복제본을 비교합니다. 캐시 미스 중 갱신이 성공하고 키가 발견된 비율을 보세요. 평소보다 미스나 갱신 실패가 늘고 사용자 오류도 함께 증가하면 조사합니다. 키 교체가 원인인지 판단하기 전에 키 게시 또는 배포 변경을 대조하세요. 인증과 작업 인가의 판정을 분리합니다. 일반적인 401 응답만으로는 어느 검사가 실패했는지 알기 어렵습니다.
4. **검증 경로를 복구하고 확인합니다.** 발급자 담당자에게 변경을 확인하고, 증거가 가리키는 신뢰 설정, 교체 시각, 시계 또는 메타데이터 접속 문제를 바로잡습니다. 검증기의 갱신은 공급자가 지원하는 절차를 따르세요. 키 유출 시 지정된 키 신뢰 철회와 세션·토큰 절차를 적용한 뒤 복제본별 허용·거부 대조를 실행합니다. 사고 검토를 위해 최초 판정과 대응 효과를 기록하세요.

Microsoft의 서명 키 교체 문서는 Microsoft ID 플랫폼의 테넌트별 키 처리와 캐시 갱신 방식을 안내합니다. 실제 라이브러리와 공급자 버전의 문서를 확인하세요. 캐시 내부 상태를 모으려면 라이브러리 계측이나 제공되는 진단 인터페이스가 필요합니다. 게이트웨이 응답 코드만 확보했다면 그 관측 한계를 타임라인에 남기세요.

## 5. 승인된 오프라인 증거 실습

<a href="{{ '/assets/labs/jwt-key-rotation-evidence.py' | relative_url }}" download>Python 3 판정 도구</a>와 <a href="{{ '/assets/labs/jwt-key-rotation-evidence-cases.json' | relative_url }}" download>가상 사례 JSON</a>을 승인된 디렉터리 한 곳에 내려받으세요. JSON의 검증기 설정부터 보고 사례의 결과를 예상합니다. 각 사례는 공통 형식으로 정리한 가상의 검증 기록입니다. `signature`는 실습 자료에 미리 넣은 서명 판정입니다. 이 도구는 JSON만 읽으므로 토큰을 파싱하거나 서명을 계산하지 않으며, 네트워크나 Python 3 이외의 별도 설치 없이 실행됩니다.

```sh
python3 jwt-key-rotation-evidence.py
```

| 사례 | 설명할 내용 |
| --- | --- |
| A, B | 같은 키를 유효한 캐시에서 찾거나 승인된 갱신 후 찾아 검증을 마칩니다. |
| C, D, J | 승인된 조회 실패, 성공한 조회 응답에 키 없음, 호출 제한으로 갱신 미시도입니다. 각각 다른 증거 공백이 남습니다. |
| E, F, G, H, M | 발급자, 토큰 프로파일, 대상, 만료, 알고리즘 정책은 키 갱신과 별개로 거부를 일으킬 수 있습니다. |
| I | 후보 키는 있었지만 서명 확인이 실패했습니다. |
| K, L | 갱신 주소가 승인된 주소와 다르거나, 식별자 하나에 키 하나를 허용하는 실습 정책에서 후보가 둘 이상입니다. |

원본을 실행하면 `13/13 JWT evidence cases matched.`가 출력됩니다. 음성 대조로 JSON을 복사하고 B의 `refresh.kids` 배열에서 `k2`를 지운 뒤 복사본 이름을 명령 인수로 전달하세요. B는 `key-absent-after-refresh`로 바뀌며 13건 중 12건이 일치하고 종료 코드는 1입니다. 원본이 열리지 않으면 두 파일의 이름과 JSON 문법을 확인하세요. 수정본도 통과하면 명령에 넘긴 파일과 수정한 배열을 다시 확인하세요. 이 실습은 식별자에 맞는 키가 하나이고, 한 시계에서 허용 오차를 0으로 두는 모델입니다. 실제 라이브러리는 호환 후보의 선택 방식과 검증 순서가 다를 수 있으며 필수 클레임을 추가로 검사할 수 있습니다.

클라우드 Python에서 원본과 수정본을 실행했습니다. 토큰 프로파일과 플랫폼의 키 처리 방식은 아래 공식 문서로 검토했습니다. 실행 검증 범위는 가상 기록의 해석이며 실제 발급자, JWT 암호 연산, 리소스 API 호출은 포함되지 않습니다.

## 6. 확인 문제와 해설

1. **한 복제본만 새 키로 발급한 토큰을 거부합니다. 전파 지연과 발급자의 게시 문제는 어떻게 구분하나요?** 두 복제본의 발급자 설정, 캐시 버전과 갱신 결과를 같은 구간에 관측한 신뢰 가능한 게시 기록과 비교하세요.
2. **갱신은 성공했는데 API가 여전히 거부합니다. 무엇을 보나요?** 예상 키가 실제로 응답에 있었고 선택됐는지 확인한 뒤 서명, 토큰 유형, 수신 대상, 시간 판정을 확인하세요. 키 집합 응답은 한 시점의 키 가용성을 보여 줍니다.
3. **두 테넌트가 같은 `kid`를 씁니다. 이 문자열만으로 전역 캐시를 구성해도 되나요?** 신뢰하는 발급자 또는 테넌트와 키 출처에 따라 조회 범위를 정하세요. 후보가 여러 개라면 구현이 어떤 키와 용도를 선택했는지도 확인합니다.
4. **수락된 토큰으로 주문이 실제 변경됐다는 증거는 무엇인가요?** 검증 판정을 리소스 인가 판정과 연결하고, 실제 작업을 보여 주는 애플리케이션 또는 데이터 감사 기록을 확인합니다.

**완료 기준.** B·C·D·J에서 캐시와 갱신 증거의 차이를 설명하고, F·G·I에서 거부한 단계를 찾습니다. 원본과 수정본의 결과를 재현하고 실제 교체를 확인할 자료를 하나 제시하세요.
