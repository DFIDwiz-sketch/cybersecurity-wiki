**학습 목표.** IPv6 이웃 메시지가 무엇을 묻거나 알리는지 읽습니다. 특정 단말의 이웃 캐시나 주소 상태가 실제로 바뀌었는지 확인하고, 캡처 공백으로 판단할 수 없는 부분을 구분합니다.

## 1. 다음 홉에 보낼 때는 링크 계층 주소가 필요합니다

IPv6 패킷에는 네트워크 계층 목적지 주소가 들어 있습니다. 이 패킷을 담는 이더넷 프레임에는 목적지 MAC 주소도 필요합니다. 단말은 라우팅 테이블을 읽고 같은 링크의 **다음 홉**을 고릅니다. 목적지가 같은 링크에 있으면 그 주소 자체가, 외부에 있으면 일반적으로 링크에 연결된 라우터가 다음 홉입니다. 라우터를 거쳐도 IP 목적지는 원래 주소로 유지되고 프레임의 목적지 MAC에 라우터 주소가 들어갑니다. **이웃 탐색(Neighbor Discovery, ND)**으로 이 다음 홉의 MAC 주소를 알아내고 이웃 캐시에 저장합니다. 링크 로컬 주소가 서로 다른 링크에서 재사용될 수 있으므로 링크, 인터페이스, IPv6 주소를 함께 기록합니다.

| 메시지 또는 상태 | 의미 | 대조할 증거 |
| --- | --- | --- |
| 라우터 광고(RA, 유형 134) | 라우터와 네트워크 설정 정보를 알립니다. | 경로, 접두사, DNS 상태 |
| 이웃 요청(NS, 유형 135) | 주소 확인, 도달 가능성 점검, 중복 주소 탐지에 쓰입니다. | 출발지, 목적지, 대상, 링크, 단말 상태 |
| 이웃 광고(NA, 유형 136) | 대상 주소에 관한 정보를 전달합니다. | 대상, 플래그, 링크 계층 옵션, 수신 단말 캐시 |
| 이웃 도달 불가 탐지(NUD) | 기존 이웃의 도달 가능성을 확인합니다. | 캐시 상태, 확인 요청, 상위 계층 통신 진행 |
| 중복 주소 탐지(DAD) | 주소를 쓰기 전에 같은 링크에서 사용 중인지 점검합니다. | 임시 상태인 주소, 같은 링크의 메시지, 단말의 최종 결과 |

가상 VLAN 20의 워크스테이션이 라우터 `fe80::1`을 통해 다른 링크의 IPv6 목적지로 통신한다고 가정합니다.

1. 경로는 워크스테이션의 이더넷 인터페이스에 연결된 `fe80::1`을 가리킵니다. MAC 주소를 확인하기 전에는 이웃 항목이 `INCOMPLETE`일 수 있습니다.
2. 워크스테이션이 홉 제한(Hop Limit) 255인 NS를 보냅니다. IP 목적지는 대상의 요청 노드 멀티캐스트 그룹이며 이 예에서는 `ff02::1:ff00:1`입니다. 이 그룹은 대상 주소의 마지막 24비트로 정해져 여러 주소가 공유할 수 있습니다. 어떤 주소를 물었는지 알려면 ICMPv6 메시지의 **Target Address** 전체를 읽습니다.
3. 라우터는 대상의 링크 계층 주소 옵션을 포함한 유니캐스트 NA로 응답합니다. 워크스테이션은 확인한 MAC을 쓸 수 있습니다. 요청에 대한 주소 확인이 성공하면 캐시가 `REACHABLE`로 표시될 수 있습니다. 실제로 어디에 보냈는지 확인하려면 후속 프레임의 이더넷 목적지도 확인합니다.
4. 오래된 대응 관계는 `STALE`이 되어도 계속 쓸 수 있습니다. 다음에 사용할 때 도달 가능성을 확인하지 못하면 NUD가 `DELAY`를 거쳐 `PROBE`로 진행할 수 있습니다. 기존 대응 관계를 확인할 때는 유니캐스트 NS를 쓸 수 있습니다. 상위 계층에서 통신이 진행됐음을 확인하면 별도 확인 요청이 불필요할 수 있습니다. Linux의 `FAILED`는 확인 요청 후에도 이웃 확인이나 주소 해석에 실패했다는 뜻으로, 원인은 따로 살펴야 합니다.

NA의 **S**는 Solicited, **O**는 Override, **R**은 Router입니다. O는 수신 단말이 저장된 대응 관계를 바꿀 수 있는지 판단할 때 캐시 상태와 주소 옵션과 함께 쓰입니다. R은 라우터 여부를 전달합니다. 플래그는 메시지에 들어 있는 값이며 발신자를 인증하지 않습니다. IPv6 목적지가 멀티캐스트인 정상 NA에서는 S가 꺼져 있습니다. 정상 운영 중에도 먼저 알리는 NA가 나올 수 있습니다. RFC 9131은 첫 홉 라우터가 이런 광고에서 캐시 항목을 미리 만들 수 있는 경우를 설명합니다. 실제 환경에서는 장비 지원과 설정을 확인하세요.

### DAD 요청은 무엇을 확인하나요?

DAD를 하는 단말은 아직 확정하지 않은 주소를 Target Address에 넣습니다. NS 출발지는 미지정 주소 `::`, 목적지는 대상의 요청 노드 멀티캐스트 주소입니다. 출발지 링크 계층 주소 옵션은 넣지 않지만, 이더넷 프레임에는 출발지 MAC이 있을 수 있습니다. 같은 링크에서 이미 해당 주소를 쓰는 단말은 S를 끈 NA를 전체 노드 멀티캐스트 주소로 보낼 수 있습니다. 두 단말이 동시에 같은 주소를 확인 중이라면 서로의 NS도 탐지 단서가 됩니다. 단말이 보낸 DAD 요청 한 건은 점검을 시도했다는 증거입니다. 실제 주소를 할당했는지, 충돌을 감지했는지는 단말의 최종 주소 상태를 확인합니다.

## 3. 예상 밖의 주소 대응 관계 조사하기

잘못된 주소 주장을 단말이 받아들이면 프레임을 보내는 곳이 달라질 수 있습니다. 주소 충돌로 설정이 중단되거나, 해석 대기 중인 이웃 항목이 늘어 라우터 자원을 소모할 수도 있습니다. 정해진 장애 조치, VM 이동, ND 프록시, 센서 관측 공백도 비슷한 흔적을 남깁니다. 원인을 좁히려면 다른 증거와 대조합니다.

1. **올바른 링크에서 자료를 모읍니다.** 단말·센서 시계, 인터페이스, VLAN 또는 동등한 구간, 수집 방향과 누락 카운터를 기록합니다. 포트 미러링과 오프로딩이 패킷 표시 방식에 영향을 줬는지 살핍니다. NS/NA 유형, 출발지·목적지·대상 주소, 홉 제한, Code, 플래그, 이더넷 MAC, 링크 계층 주소 옵션을 보존합니다. 프레임의 출발지 MAC과 옵션에 적힌 MAC은 각자의 의미가 있으므로 별도로 기록합니다. 태그가 없는 센서 사본만으로 원래 구간을 정할 수 없습니다.
2. **메시지 유효성을 먼저 확인합니다.** RFC 4861의 수신 검사에는 홉 제한 255, 정상 체크섬, Code 0, ICMP 최소 길이, 멀티캐스트가 아닌 대상 주소, 옵션 길이 확인이 포함됩니다. 출발지가 `::`인 NS는 요청 노드 멀티캐스트 주소로 가며 출발지 링크 계층 주소 옵션이 없어야 합니다. 멀티캐스트로 향하는 NA는 S가 꺼져 있어야 합니다. RFC 6980에 따라 Fragment Header가 있는 NS/NA는 수신 측에서 무시합니다. 송신 오프로딩이 체크섬을 표시하는 방식에 영향을 줄 수 있으니 이상하다면 적절한 수집 지점에서 재확인합니다. 메시지 형식이 맞아도 발신자의 신원과 권한은 별도 확인 대상입니다.
3. **단말이 적용했는지 확인합니다.** 설정을 바꾸기 전에 경로, 이웃 캐시, 주소 상태를 저장합니다. 같은 대상 주소와 인터페이스의 전후 기록을 비교하세요. 미러에서 NA를 봤다는 사실은 센서 관측입니다. 해당 단말의 캐시 MAC이 바뀌면 적용을, 후속 송신 프레임의 목적지 MAC은 실제 사용을 뒷받침합니다. 시간이 가까운 광고와 변경만으로 둘의 인과관계까지 정할 수는 없습니다. 스위치 전달 기록, VLAN, 승인된 라우터 목록, 자산과 변경 기록을 확인합니다. 트렁크와 프록시 연결 포트에는 여러 장치가 모일 수 있습니다.
4. **영향 범위를 좁혀 대응합니다.** 링크와 대상별로 이상을 묶습니다. 게이트웨이 대응 관계가 바뀌고 실제 트래픽의 전달 위치가 달라졌거나, 신규 단말에서 DAD 실패가 반복되는 경우를 우선 확인합니다. 응답이 캡처에 없으면 단말 상태, 스위치 지표, 정상 대조 사례를 확인하고 손실 지점을 판단합니다. 네트워크 담당자와 함께 설정을 바로잡거나 미인가로 확인된 포트나 워크로드를 격리합니다. 변경 전후 증거를 남기고 정상 주소 확인과 DAD도 다시 확인합니다.

### 읽기 전용 수집 예시

IPv6와 iproute2를 사용하는 승인된 Linux 단말에서 올바른 네트워크 네임스페이스를 선택하고 `eth0`를 조사할 인터페이스 이름으로 바꿉니다. UTC 시각은 별도로 기록합니다. 아래 명령은 경로, 캐시, 주소를 조회합니다. `route get`은 로컬 경로 조회입니다. 문제가 발생하는 동안 기록을 저장하세요. 한 번의 출력은 그 시점의 상태만 보여줍니다.

```bash
ip -6 route get 2001:db8:42::80
ip -6 neigh show dev eth0
ip -6 addr show dev eth0
```

같은 링크에서 수집한 파일을 Wireshark에서 열고 아래 표시 필터를 적용합니다. 지정한 대상의 NS와 NA를 모두 검색합니다. 주소는 조사할 다음 홉이나 DAD 대상에 맞게 바꿉니다. 출발지와 목적지는 각각 확인하고, Fragment Header 또는 빠진 맥락을 확인할 때는 필터를 풀어 보세요. 수집되지 않은 패킷은 표시 필터로 복구할 수 없습니다.

```text
icmpv6.nd.ns.target_address == fe80::1 || icmpv6.nd.na.target_address == fe80::1
```

## 4. 가상 증거로 실습하기

본인이 소유하거나 승인받은 공간에서 <a href="{{ '/assets/labs/ipv6-neighbor-evidence.py' | relative_url }}" download="ipv6-neighbor-evidence.py">Python 스크립트</a>와 <a href="{{ '/assets/labs/ipv6-neighbor-evidence-cases.json' | relative_url }}" download="ipv6-neighbor-evidence-cases.json">사례 파일</a>을 같은 폴더에 저장합니다. Python 3.9 이상이 필요합니다. 사례는 가상 링크의 헤더와 단말 상태를 읽기 쉽게 정리한 자료입니다. 스크립트는 JSON 파일만 읽으며 네트워크로 패킷을 보내지 않습니다. 몇 가지 학습 조건을 확인하는 실습 도구입니다.

```bash
python3 ipv6-neighbor-evidence.py ipv6-neighbor-evidence-cases.json
```

| 사례 | 증거로 판단할 수 있는 내용 |
| --- | --- |
| `normal_resolution` | 요청·광고 관측. 단말에 도달 가능한 이웃 항목이 기록됐습니다. |
| `normal_dad` | DAD 요청 관측. 단말은 주소를 할당했습니다. |
| `dad_conflict` | DAD 요청과 같은 링크의 주소 주장 관측. 단말에서 DAD에 실패했습니다. |
| `wrong_hop_limit` | 광고가 헤더 검사에 맞지 않습니다. 캐시 MAC은 그대로였습니다. |
| `capture_only` | 광고는 보이지만 단말의 상태는 알 수 없습니다. |
| `separate_link` | 경쟁 주장처럼 보이는 광고는 다른 링크에서 관측됐습니다. |
| `changed_binding` | 캐시 MAC이 바뀌었습니다. 원인은 추가 조사 대상입니다. |
| `failed_without_reply` | 단말의 이웃 확인이 실패했습니다. 센서 자료에는 요청만 있고 해당 광고가 없습니다. |

사례별로 링크에서 관측한 내용과 단말에서 확인한 결과가 출력됩니다. 모두 PASS가 나와야 합니다. 사례의 복사본에서 `wrong_hop_limit` 광고의 홉 제한을 255로 바꿔 보세요. 헤더 검사에서 거부되던 결과가 바뀌어 해당 사례가 FAIL을 출력하지만, 단말 캐시는 여전히 그대로입니다. 파일을 열 수 없으면 작업 폴더와 두 파일 이름을 확인하세요. 예상과 다른 결과가 나오면 먼저 링크, 대상 주소 전체, 필드 값, 두 단말 스냅샷을 차례로 확인합니다.

Python 사례는 클라우드 작업 공간에서 실행했습니다. Linux 명령과 Wireshark 필드는 공식 자료로 검토했습니다. 이 실습에서는 실제 패킷 교환, 스위치 정책, Wireshark 실행을 검증하지 않았습니다.

## 5. 판단 확인하기

- **다른 링크로 보내는 패킷의 IPv6 목적지를 유지하면서 프레임을 라우터로 보내는 이유는 무엇인가요?** IP 목적지는 최종 목적지를 가리킵니다. 이더넷 목적지는 현재 링크에서 전달할 다음 홉입니다.
- **출발지가 `::`인 NS를 보았고 이후 단말에 새 주소가 할당됐습니다. 충돌 증거인가요?** NS는 주소를 점검했다는 증거이고, 단말의 후속 상태는 할당됐음을 보여줍니다. 충돌을 주장하려면 추가 증거가 필요합니다.
- **포트 미러에서 O가 켜진 NA와 낯선 MAC을 보았습니다. 단말이 적용했나요?** 같은 링크와 대상을 기준으로 수신 단말의 캐시를 확인하세요. 적용 결과와 변경을 일으킨 주체는 별도로 판단합니다.
- **한 항목이 `STALE`입니다. 이웃 장치가 꺼졌나요?** 최근 도달 가능성이 확인되지 않았다는 뜻입니다. 이후 상태와 트래픽을 확인한 뒤 판단하세요.

여덟 사례가 모두 통과하면 하나를 골라 관측한 메시지, 단말 결과, 가능한 원인, 확인에 필요한 다음 자료를 짧은 조사 메모로 정리해 보세요.
