## 1. 브라우저 요청 한 건 따라가기

브라우저에서 https://shop.example.test/catalog?lang=ko를 열면 HTTP 요청에는 메서드 GET, 대상 경로 /catalog, 쿼리 lang=ko가 들어갑니다. HTTP/1.1에서는 Host가 대상 호스트를 전달하고 HTTP/2·3에서는 보통 :authority가 그 역할을 합니다. TLS의 SNI는 연결에서 선택할 서버 이름을 알려 줍니다. SNI와 HTTP의 대상 정보는 서로 다른 위치에서 관측합니다.

서버는 상태 코드, 응답 헤더, 필요한 경우 본문을 돌려줍니다. 예를 들어 200과 Content-Type: application/json은 해당 요청에 대한 성공 응답과 본문 형식을 설명합니다. 인증된 사용자가 어떤 자료에 접근했는지 판단하려면 앱의 사용자·권한·리소스 기록도 확인하세요.

## 2. 메서드와 상태 코드 읽기

| 항목 | 의미 | 조사할 때 확인할 내용 |
| --- | --- | --- |
| GET / HEAD | 리소스 조회 / 본문 없이 응답 메타데이터 조회 | 라우트, 캐시 여부, 요청한 리소스 |
| POST | 대상 리소스에 데이터 처리 요청 | 처리 결과, 작업 ID, 재시도와 중복 실행 |
| PUT / DELETE | 지정 리소스의 교체·생성 / URI와 리소스의 현재 연결 관계 제거 요청 | 실제 상태 변경과 권한 결정 |
| 200 / 202 | 성공 응답 / 처리 접수 | 202 후 작업 결과는 큐·워커 로그에서 확인 |
| 301 / 302 | 리디렉션 | Location과 이후 요청을 별도로 연결 |
| 401 / 403 | 유효한 인증 자격 증명 부족 / 요청 거부 | 프록시와 앱 중 어느 계층이 응답했는지 |
| 404 / 429 | 대상을 찾지 못함 또는 존재를 공개하지 않음 / 요청 한도 초과 | 라우트·권한 정책과 제한 적용 위치 |
| 502 / 504 | 게이트웨이가 유효한 상위 응답을 얻지 못함 / 제때 응답을 받지 못함 | 연결·타임아웃·상위 앱 기록 |

HTTP에서 안전한 메서드는 클라이언트가 상태 변경을 요청하지 않는다는 의미입니다. 로그 저장이나 통계 집계는 발생할 수 있습니다. 멱등성은 동일 요청을 반복했을 때 의도한 효과가 한 번 실행했을 때와 같다는 뜻입니다. 응답 코드나 감사 기록까지 반복마다 같다는 보장은 없습니다.

## 3. 실제 응답은 어디에서 나왔나요?

![클라이언트부터 프록시·앱·워커까지 요청과 로그가 연결되는 흐름]({{ '/assets/diagrams/http-evidence-ko.svg' | relative_url }})

리버스 프록시는 TLS를 종료하고, 캐시에서 답하거나, WAF 정책으로 요청을 거절하거나, 앱으로 전달할 수 있습니다. 앱이 202를 반환한 뒤 작업은 별도 워커에서 실패할 수 있습니다. 반대로 프록시가 504를 보낸 뒤 앱이 처리에 성공할 수도 있습니다. 프록시와 앱의 코드가 다르면 먼저 **각 계층이 누구에게 어떤 응답을 언제 보냈는지**를 확인하세요.

HTTP/1.1과 HTTP/2는 일반적으로 TCP를, HTTP/3는 QUIC을 사용합니다. HTTP/2·3에서는 한 연결에서 여러 요청이 진행될 수 있습니다. IP·포트와 연결 ID는 범위를 좁히는 데 쓰고, 실제 요청은 승인된 요청 ID와 시간·호스트·라우트로 대조하세요. 암호화 구간의 수동 패킷 캡처에는 보통 HTTP 헤더·본문이 보이지 않습니다. 승인된 TLS 종단과 앱 로그를 활용하세요.

## 4. 웹 로그에서 증거를 수집하는 순서

1. UTC 시각과 오차, 환경, 관측 계층, 호스트·메서드·라우트·최종 상태·처리 시간을 기록합니다. 실제 URI가 필요하면 개인정보를 제거하고 접근을 제한합니다.
2. 프록시 로그에서 요청 ID, 정책 결정, 캐시 결과, 상위 응답 코드와 지연을 찾습니다. NGINX에서 사용할 필드는 설정한 log_format과 배포 구성에 따라 달라집니다. 테스트 요청을 보내 각 필드가 생성되는지 확인하세요.
3. 앱의 같은 요청 ID를 찾아 인증·권한 결정과 리소스 결과를 확인합니다. 재시도·팬아웃·중복 ID가 있다면 서비스·시간·시도 번호를 추가합니다. 202라면 별도 작업 ID를 워커 기록에 연결합니다.
4. 소켓의 상대 IP와 전달 헤더를 구분합니다. Forwarded나 X-Forwarded-For는 신뢰하는 프록시가 경계에서 검증하고 설정한 범위에서 해석하세요. 임의 헤더에서 읽은 첫 IP를 곧바로 사용자 주소로 쓰면 귀속 오류가 생길 수 있습니다.
5. Authorization, Cookie, 세션 토큰, 민감한 쿼리나 본문은 기본 수집에서 제외하거나 승인된 정책에 따라 마스킹합니다. Zeek http.log는 센서가 분석할 수 있는 HTTP의 관측 자료입니다. 프록시나 앱의 전체 요청 기록과 수집 범위가 다릅니다.

## 5. 경보에서 판단으로

특정 계정에 401이 반복되면 비밀번호 추측 가능성을 조사하세요. 만료 토큰, 잘못 설정된 앱, 공용 NAT도 비교합니다. 계정·라우트·시간대별 분모를 확인하고, 이후 인증 성공과 새 세션 또는 민감 리소스 접근이 이어졌는지 살펴보세요. 반복 404는 탐색의 단서가 될 수 있지만 오래된 링크와 정상 배포 오류도 같은 형태를 만듭니다.

403은 해당 계층의 거절 증거입니다. 실제로 상위 요청이 없었는지는 WAF 결정, 프록시 전달 필드와 앱 로그 수집 상태를 함께 확인합니다. 의심 활동이 입증되면 영향 계정과 라우트를 좁혀 세션 폐기나 정책 조정을 검토하고, 정상 요청을 재실행해 서비스와 로깅을 확인하세요. 자체 소유 환경에서는 허용 요청과 승인된 테스트용 거절로 수집 경로를 먼저 검증할 수 있습니다.

## 6. 오프라인 실습과 해설

두 파일을 한 폴더에 저장한 뒤 Python 3에서 실행하세요. 가상 자료 12행이 요청 7건을 나타냅니다. 프록시·앱은 request_id, 앱·워커는 work_id로 연결합니다. 이 단순화된 CSV는 제품의 원본 형식과 별개입니다.

[http-evidence.csv]({{ '/assets/labs/http-evidence.csv' | relative_url }}) · [http-evidence.py]({{ '/assets/labs/http-evidence.py' | relative_url }})

```bash
python3 http-evidence.py
```

| 요청 | 관측에서 말할 수 있는 내용 |
| --- | --- |
| r-101 | 프록시와 앱 모두 200 |
| r-102 | 202로 접수됐으나 작업 j-20은 실패 |
| r-103 | 프록시가 403을 반환하고 차단 결정 기록 |
| r-104 | 프록시 504 후 앱은 늦게 200으로 처리 |
| r-105 | 프록시 캐시에서 200 제공 |
| r-106 | 앱에서 404가 기록됨. 권한과 리소스 존재를 별도 확인 |
| r-107 | 프록시 502. 앱 기록이 관측되지 않아 원인은 미확인 |

PASS와 일곱 사례 출력이 예상 결과입니다. 파일 오류가 나면 이름과 위치를, ID 오류가 나면 중복·누락 행을 확인하세요. 배포 전 Python으로 가상 자료를 실행 검증했습니다. 실제 NGINX·Zeek·WAF 수집은 각자의 환경에서 확인해야 합니다.

## 7. 확인 문제와 다음 학습

- **프록시 200에 앱 행이 없다면?** 캐시 결정과 로그 누락 가능성을 구분하세요.
- **202를 작업 성공으로 집계해도 되나요?** 접수 성공과 워커 결과를 별도 집계하세요.
- **502에 앱 행이 없다면 앱이 요청을 받지 않은 건가요?** 이 자료에서 앱 행을 관측하지 못했습니다. 상위 연결 기록과 앱 수집 상태가 더 필요합니다.

세 계층의 기록을 연결하고, 각 요청에 대해 관측 사실 하나와 추가로 필요한 자료 하나를 적으면 실습을 완료한 것입니다.
