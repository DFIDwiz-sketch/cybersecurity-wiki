실제로 수행한 작업인데 Linux Audit 검색 결과에 보이지 않습니다. 당시 규칙이 그 작업을 수집하지 않았거나, 레코드가 유실됐거나, 로컬 로그 또는 전달에 문제가 있을 수 있습니다. 해당 작업의 증거를 마지막으로 확인한 지점부터 찾고, 그 호스트와 시간 구간에 적용되는 지표를 대조합니다.

## 1. 감사 레코드가 지나가는 경로

Linux Audit는 활성 감사 규칙과 다른 감사 발생원에서 작업에 대한 **레코드**를 만들 수 있습니다. 하나의 **이벤트**에는 `SYSCALL`, `PATH` 등 여러 레코드가 들어갈 수 있습니다. 일부 레코드가 빠진 이벤트도 검색 결과에 나타날 수 있습니다. 커널은 레코드를 대기열에 넣고 사용자 공간의 **auditd**에 전달합니다. 로컬 로깅이 설정되어 있으면 auditd가 로그 파일에 기록합니다. 활성 감사 플러그인이나 별도의 로그 전달 에이전트가 중앙 수집기로 보낼 수 있습니다. 먼저 실제 경로를 확인하세요. 플러그인 대기열 지표는 로컬 파일을 따로 읽는 전달 에이전트의 상태까지 보여 주지 않습니다.

| 관측 자료 | 무엇을 보여 주나요? | 이 자료만으로 알 수 없는 점 |
| --- | --- | --- |
| `auditctl -s`의 `backlog`와 `backlog_limit` | 현재 커널 대기열 사용량과 설정된 한도 | 높은 사용량은 대기열 압박의 신호입니다. 유실 건수는 별도로 확인합니다 |
| `auditctl -s`의 `lost` | 커널이 보고한 감사 레코드 유실 누계 | 구체적으로 어느 레코드나 이벤트가 빠졌는지 |
| `auditctl -s`의 `pid` | 관측 시점에 등록된 감사 데몬 PID. 0이면 등록된 데몬이 없음 | 이전에 관측한 데몬이 디스크 기록과 전달에 성공했는지 |
| auditd 상태 보고의 플러그인 대기열과 드롭 지표 | 해당 데몬의 플러그인 전달 경로. 지원 빌드에서 사용 가능 | 커널 유실 수, 로컬 파일의 완전성, 독립 전달 에이전트 상태 |
| 원본 로컬 로그와 중앙 수집 기록 | 확인 대상 이벤트의 레코드가 각 관측 지점에 있는지 | 다른 이벤트나 호스트까지 수집이 완전했는지 |

## 2. 정상 구간과 공백 비교하기

가상 Linux 호스트에서 규칙에 맞는 테스트 작업이 예상한 로컬 레코드를 남겼고, 합의한 90초 안에 중앙 수집기에도 도착했습니다. 같은 부팅에서 15초 간격으로 읽은 `lost`는 모두 7입니다. 커널 대기열은 한도 512에서 15건이던 것이 2건으로 줄었습니다. 7은 누계이고 이 구간에서 측정한 증가분은 0입니다. 관측한 테스트 작업의 전달을 확인했고, 해당 구간에 커널 유실 카운터 증가도 없었습니다.

나중에 같은 부팅에서 비교 가능한 두 값이 7과 12로 나왔습니다. 커널이 유실 레코드 5건을 추가로 보고한 것입니다. 한 이벤트에 여러 레코드가 담길 수 있고, 카운터는 규칙이나 테스트 표식에 유실을 연결해 주지 않습니다. 레코드가 유실된 뒤 다음 샘플까지 대기열이 줄어들 수도 있습니다. 지속적인 대기열 압박, 순간적으로 몰린 이벤트, 전송률 한도, 자원 부족을 살펴봅니다. 커널은 여러 이유로 레코드 유실을 보고할 수 있습니다.

또 다른 구간에서는 `lost`가 그대로인데 로컬에는 온전한 이벤트가 있고, 허용 시간이 지나도 중앙에 같은 이벤트가 없습니다. 이 건의 전달 경로, 파싱, 조회 범위부터 확인합니다. 아직 허용 시간 안이라면 잠정 관측으로 기록하고 마감 후 다시 확인합니다. 로컬 기록이 의도적으로 꺼져 있다면 실제 경로에서 처음 확인할 수 있는 지점을 사용하고, 로컬과 대조할 수 없다는 제한을 남깁니다.

## 3. 초기화와 관측 한계, 오용 가능성

커널 카운터는 같은 호스트와 같은 부팅끼리 비교하고, 확인된 관리 작업에 의한 초기화 여부를 기록합니다. 누계가 감소하거나 부팅이 달라지면 두 수치를 그대로 빼서 해석할 수 없습니다. auditd는 같은 부팅 중에도 재시작할 수 있습니다. 플러그인의 누계가 이어지는지 확인하려면 PID와 시작 시각을 함께 비교합니다. 상태 파일이 오래됐거나 필드가 없으면 그 지표를 알 수 없다고 남깁니다. 숫자보다 리포트 시각을 먼저 보세요. 커널과 플러그인 지표는 단계와 단위가 다를 수 있으므로 더하지 않습니다.

유지보수 중 호출량 증가, 디스크 공간 부족, 보존 한도, 과도하게 넓은 규칙, 전달 장애도 공백의 원인입니다. 규칙이나 수집을 고의로 변경해 가시성을 줄이는 경우도 있으므로 승인 내역과 사고 타임라인, 남아 있는 다른 증거를 대조한 뒤 의도를 판단합니다. 현재 규칙은 지금의 상태를 보여 줍니다. 일련번호 하나가 건너뛰었다고 유실량을 계산할 근거가 생기지는 않습니다. 로컬에 온전하게 남은 이벤트는 그 한 건이 커널과 로컬 경로를 통과했다는 근거입니다. 전체 사고 기간의 호스트나 전달 경로까지 평가하려면 다른 증거가 필요합니다.

## 4. 블루팀 수집·탐지·대응

1. **원본 범위를 기록합니다.** 커널 Audit와 사용자 공간 도구를 갖추고 상태·규칙 조회 권한이 있는 승인된 Linux 호스트에서 아래 값을 호스트 식별자와 함께 수집합니다. 호스트의 감사 컨텍스트에서 실행하고 UTC 구간 경계를 보존합니다. 설치된 배포판·커널·감사 패키지 버전, 적용 규칙과 키, 로컬 로그 위치와 보존 기간, 전달 방식을 기록합니다. 원시 로그와 규칙에 민감한 경로나 주체 정보가 있으면 접근을 제한합니다.

~~~bash
date -u
cat /proc/sys/kernel/random/boot_id
sudo auditctl -s
sudo auditctl -l
~~~

2. **auditd와 실제 출력 경로를 확인합니다.** 적용된 설정에서 `write_logs`, `log_file`, 디스크 관련 동작과 플러그인을 확인합니다. 최신 상태 보고는 로깅 중단이나 플러그인 압박을 보여 줄 수 있습니다. 지원 빌드에서 승인받아 실행하는 `sudo auditctl --signal state`는 진단 상태 파일을 쓰도록 요청합니다. 업스트림의 예시는 `/run/audit/auditd.state`이며 배포판 경로와 보고 시각을 확인하세요. 주기 보고용 `report_interval`은 업스트림 audit-userspace 4.0.5부터 문서화되어 있습니다. 상태 스냅샷은 관측한 데몬의 정보입니다. 별도 전달 에이전트를 쓴다면 그 대기열과 수신 측 파싱을 따로 점검합니다.
3. **예정된 작업 한 건을 연결합니다.** 알고 있는 규칙에 해당하는 무해한 승인 작업을 사용합니다. 규칙과 작업 흐름에서 가능하면 고유 테스트 식별자를 남기세요. 로컬 원본을 보존하고 동일 호스트, 감사 이벤트 식별자, 규칙 키와 원본 시각으로 중앙 기록을 찾습니다. 전달 지연과 시계 오차를 포함한 제한된 시간 구간을 쓰고, 회전된 로그와 필요한 레코드가 파서에 모두 왔는지도 확인합니다. 기록 부재, 일부 존재, 미수집을 구분합니다.
4. **탐지하고 복구를 검증합니다.** 같은 부팅 내 커널 유실 증가, 같은 데몬 실행 구간 내 플러그인 유실 증가, 지정된 시간 이후의 테스트 이벤트 누락을 추적합니다. 대기열 사용량의 정상 범위를 잡고 지속 압박은 따로 관찰하세요. 복구 전에 증거를 보존하고 로컬 디스크와 전달 상태를 확인합니다. 수정 후 승인된 테스트 작업 한 건을 처음부터 끝까지 다시 대조합니다. 카운터 한 번이 0이라고 가시성 문제를 종결하지 않습니다.

## 5. 승인된 오프라인 실습

~~~bash
python3 linux-audit-loss-evidence.py
~~~

| 사례 | 기대 관측 |
| --- | --- |
| A–C | 전체 경로에서 전달 확인, 테스트 이벤트에 귀속할 수 없는 커널 유실 증가, 로컬 이벤트가 있는 구간의 플러그인 유실 |
| D–F | 허용 시간 이후 중앙 이벤트 누락, 허용 시간 진행 중, 부팅 변경 |
| G–I | 같은 부팅의 카운터 감소, 데몬 재시작, 플러그인 지표 없음 |
| J | 일부 로컬 레코드는 있으나 예상 이벤트는 불완전 |

`10/10 cases matched.`가 나오는지 확인하세요. 대조 실험은 사본에서 D의 `delivery.window_elapsed`만 `false`로 바꾸고 기대값을 그대로 둡니다. 사본 파일명을 검사기 인자로 주면 D가 `pending-window`로 바뀌고 종료 코드 1이 나와야 합니다. 기본 실습이 실패하면 두 파일의 판본과 저장 폴더를 확인합니다. Python 실습은 가상 데이터로 실행했습니다. 커널과 auditd 명령은 업스트림 문서로 검토했으며 감사가 활성화된 실제 호스트나 운영 수집 경로에서는 실행하지 않았습니다.

## 6. 확인 문제와 완료 기준

1. **lost가 다섯 건 늘면 이벤트 다섯 건이 사라진 건가요?** 레코드 단위입니다. 이벤트 하나는 여러 레코드를 포함할 수 있으며 지표는 그 정체를 알려 주지 않습니다.
2. **온전한 로컬 테스트 이벤트가 있는데 중앙에는 없으면요?** 해당 이벤트의 전달 허용 시간, 사용된 경로와 파서, 조회 범위를 확인합니다.
3. **부팅 ID는 같지만 데몬이 재시작했다면 무엇을 비교할 수 있나요?** 재시작을 가로질러 플러그인 값을 빼면 안 됩니다. 커널은 같은 부팅에서 누계가 이어졌는지와 초기화 여부를 확인하고 비교합니다.
4. **두 카운터가 0이면 찾지 못한 작업은 없었던 건가요?** 규칙 적용 범위, 데몬과 로컬 로그 상태, 보존·전달을 확인해야 합니다. 카운터가 모든 공백을 설명하지는 않습니다.

**완료 기준.** 기본 사례와 대조 실험을 재현합니다. 테스트 이벤트 한 건이 없을 때 마지막 확인 지점과 비교 가능한 지표, 다음에 수집할 근거를 설명합니다. 이어서 [Linux 파일 감사 증거]({{ '/ko/wiki/linux-audit-file-evidence/' | relative_url }})와 [Linux 저널 수집 범위]({{ '/ko/wiki/linux-journal-coverage/' | relative_url }})를 읽어 보세요.
