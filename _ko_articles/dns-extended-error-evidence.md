두 클라이언트에서 같은 호스트 이름을 쓸 수 없다는 보고가 들어왔고, 둘 다 `REFUSED`를 받았습니다. 한쪽은 승인된 리졸버에서 도메인 보안 정책에 걸렸습니다. 다른 쪽은 해당 클라이언트에 질의 권한을 부여하지 않는 리졸버에 도달했습니다. 응답 코드만으로는 어느 팀이 확인해야 할지 알기 어렵습니다. 확장 DNS 오류(EDE)는 다음에 수집할 증거를 고르는 데 도움이 됩니다.

## 1. 응답 코드와 확장 오류를 함께 읽기

**응답 코드(RCODE)**는 DNS 응답이 보고하는 결과입니다. `NOERROR`는 DNS 처리에서 오류가 보고되지 않았음을 뜻하며 답변 레코드가 비어 있을 수도 있습니다. `NXDOMAIN`은 응답 서버가 이름이 없다고 보고하는 값입니다. `SERVFAIL`은 이름 해석을 끝내지 못했음을, `REFUSED`는 요청한 작업을 거부했음을 나타냅니다. 타임아웃은 사용 가능한 응답을 받지 못했다는 클라이언트 관측이므로 해당 건에서 받은 RCODE도 없습니다.

**EDNS(0)**는 DNS 추가 섹션의 **OPT 의사 레코드**를 사용해 기존 메시지를 확장합니다. 질의에 OPT가 있으면 응답 서버가 자신의 OPT에 **확장 DNS 오류** 옵션을 넣을 수 있습니다. 옵션 종류를 나타내는 16비트 **옵션 코드 15**는 EDE입니다. 별도의 16비트 **INFO-CODE**가 보고된 원인을 가리킵니다. 두 숫자가 우연히 같지만 **INFO-CODE 15**는 Blocked라는 별도의 의미입니다. `NOERROR`를 포함한 응답에 EDE가 없거나, 하나 또는 여러 개 들어갈 수 있습니다. 클라이언트는 EDE 유무와 상관없이 기존 규칙에 따라 RCODE를 처리합니다.

옵션은 네트워크 바이트 순서로 기록된 옵션 코드와 페이로드 길이로 시작합니다. EDE의 페이로드는 INFO-CODE와 선택적인 UTF-8 설명으로 이어집니다. 다음 옵션의 시작점은 인코딩된 길이로 계산합니다. 정규화한 로그에는 숫자 코드 배열과 EDNS 및 응답 전체의 관측 여부를 남깁니다. 설명 문자열은 신뢰하지 않고 탐지 규칙의 조건에서도 제외합니다. 공유 전 민감 정보를 지우고, 화면에 표시할 때 제어 문자를 이스케이프하세요.

| EDE INFO-CODE | 응답 서버가 보고하는 의미 | 다음에 확인할 근거 |
| --- | --- | --- |
| 4 Forged Answer | 정책에 따라 대체 답변을 반환함 | 실제 답변 레코드와 리졸버의 정책 결정 로그 |
| 15 Blocked | 해석 또는 전달 서비스 운영자의 차단 목록이 적용됨 | 일치한 규칙, 적용 버전과 뷰, 정책 담당자 |
| 16 Censored | 운영자 외부에서 요구한 정책으로 차단 목록에 포함됨 | 정책 출처와 담당자의 문서 |
| 17 Filtered | 클라이언트가 요청한 필터링이 적용됨 | 클라이언트 프로필, 서비스 설정, 실제 적용 정책 |
| 18 Prohibited | 해당 클라이언트에 작업 권한이 없음 | 원본 주소나 서브넷, 뷰, 재귀 접근 제어 목록(ACL), 실제 질의 경로 |
| 6 DNSSEC Bogus 또는 13 Cached Error | 각각 검증 실패, 캐시에 저장된 SERVFAIL을 보고함 | 검증 로그, 캐시 시각, 최초 실패 근거 |
| 22 No Reachable Authority 또는 23 Network Error | 권한 서버 도달 불가 또는 통신 오류를 보고함 | 리졸버의 외부 연결, 재시도, 승인된 업스트림 관측 |

## 2. 정상 조회에서 두 가지 거부 사례로

다음은 가상 사례입니다. 관리되는 클라이언트가 재귀 리졸버에 `docs.corp.test.`의 A 레코드를 질의합니다. UTC 10:00에 `NOERROR`와 `192.0.2.42`를 받습니다. 정상 응답에 EDE가 없어도 자연스럽습니다. 10:05에 승인받은 테스트 정책을 적용해 관리 뷰에서 해당 이름의 처리 방식을 바꿉니다. 같은 클라이언트가 이번에는 `REFUSED`와 EDE 15를 받습니다. 리졸버의 정책 로그에서 같은 시각의 질의, 클라이언트, 선택된 규칙을 찾아 어느 정책이 적용됐는지 확인합니다.

10:06에는 승인된 다른 구간의 테스트 클라이언트가 같은 서비스 주소로 연결해 `REFUSED`와 EDE 18을 받습니다. 이 요청은 도메인 차단 규칙에 일치하지 않았습니다. 대신 해당 구간의 재귀 질의를 허용하지 않는 뷰에 배정됐습니다. 변경하기 전에 리졸버 로그나 활성 설정에서 그 뷰와 ACL을 확인합니다. 프록시, NAT, VPN이 있다면 리졸버에서 실제로 본 클라이언트 정보도 기록합니다.

## 3. 오해를 부르는 응답과 관측 공백

예상하지 않은 리졸버, 침해된 중간 장비, 승인되지 않은 정책 변경은 잘못된 답변이나 진단 코드를 돌려줄 수 있습니다. 망 구간에 따라 답변을 달리하는 정상 DNS 설정, VPN 연결 후 리졸버 변경, 정책 배포 시차, 업스트림 장애도 비슷한 증상을 만듭니다. EDE는 DNSSEC 서명이 적용된 진술이 아닙니다. 알려진 리졸버와 인증된 암호화 연결을 쓰면 그 전송 구간이 보호됩니다. 진단 이유는 여전히 응답 서버의 관점이므로 자체 정책 로그 또는 검증 로그와 대조해야 합니다. 도메인 이름, User-Agent, 오류 코드 하나로 침해나 실행을 확정할 수 없습니다.

EDE는 선택 사항입니다. 질의에 OPT가 없었거나, 제품이 코드를 내보내지 않거나, 중간 장비가 제외했을 수 있습니다. UDP 응답이 크기 한계에 걸리면 서버는 다른 데이터보다 EDE를 먼저 뺄 수 있고, 이때 잘림 플래그를 설정하는 것이 권고됩니다. `TC=1`이면 승인된 재시도에서 받은 응답의 RCODE와 EDE를 따로 확인합니다. 알 수 없는 코드는 숫자로 보존한 뒤 최신 IANA 등록부를 확인합니다. 사설 범위 코드라면 운영자의 정의가 필요합니다. 타임아웃과 EDE만 없는 완전한 응답은 별개로 기록합니다.

## 4. 블루팀 수집·탐지·대응

1. **관측 경로를 보존합니다.** UTC 시각, 확인 가능한 클라이언트나 프로세스, QNAME, QTYPE, 리졸버 주소와 뷰, 전송 방식, RCODE, 플래그, 레코드와 EDE를 모두 남깁니다. 패킷 캡처나 리졸버 트랜잭션 로그에서 질의와 응답의 대응을 보존합니다. 16비트 트랜잭션 ID 하나만으로는 전체 기록에서 유일하게 연결할 수 없습니다. DoH·DoT에서 센서가 DNS 본문을 볼 수 없다면 승인된 엔드포인트나 리졸버 로그를 사용합니다.
2. **보고한 계층에서 대조합니다.** 질의를 정책 결정 로그, 클라이언트 ACL, DNSSEC 검증 기록과 연결합니다. 적용 규칙과 배포 시각, 클라이언트 뷰를 확인합니다. 수집기에 남은 원본 필드도 기록합니다. 아래 읽기 전용 BIND `dig` 예제는 헤더와 OPT 의사 레코드를 표시합니다. 본인이 관리하거나 질의 승인을 받은 실습 리졸버와 이름으로 문서용 값을 바꾸세요. EDE를 표시하는 BIND 빌드가 필요합니다. 이 질의와 애플리케이션의 실제 해석 경로는 다를 수 있습니다.

~~~bash
dig @192.0.2.53 docs.corp.test. A +edns=0 +comments
~~~

3. **같은 뷰 안에서 변화량을 봅니다.** 비교 가능한 응답을 리졸버·뷰별로 묶고 RCODE 및 INFO-CODE를 집계합니다. EDE가 해석된 응답, EDE 없는 응답, 응답이 없었던 시도의 건수와 비율을 따로 추적합니다. 급변했다면 정책 배포, 파서 변경, 질의량을 함께 조사합니다. EXTRA-TEXT를 자동 조치의 조건으로 사용하지 않습니다.
4. **영향받은 경로에서 복구를 확인합니다.** 15–17은 승인된 정책, 18은 클라이언트의 질의 권한과 비교합니다. SERVFAIL은 필요에 따라 검증 로그나 업스트림 기록을 확인합니다. 승인된 수정 뒤 같은 이름·유형·뷰·전송 방식으로 재확인하고 DNS 응답과 애플리케이션 결과를 모두 살펴봅니다.

## 5. 승인된 오프라인 실습

<a href="{{ '/assets/labs/dns-extended-error-evidence.py' | relative_url }}" download>Python 디코더</a>와 <a href="{{ '/assets/labs/dns-extended-error-evidence.json' | relative_url }}" download>가상 관측 JSON</a>을 같은 폴더에 저장하세요. 본인이 소유했거나 사용 승인을 받은 환경에서 Python 3으로 실행합니다. JSON에는 이미 관측했다고 가정한 RCODE와 OPT 유무가 담깁니다. 바이트 단위 형식을 따르는 부분은 16진수로 적은 EDNS 옵션뿐입니다. 디코더는 로컬 파일만 읽으며 소켓을 열거나 DNS 메시지 전체를 파싱하지 않습니다. 옵션 경계를 검증하고 관련 없는 옵션은 건너뛰며, 여러 INFO-CODE와 기존 RCODE를 유지합니다.

~~~bash
python3 dns-extended-error-evidence.py
~~~

| 사례 | 기대 관측 |
| --- | --- |
| A, G, H | EDE 없는 정상 OPT, OPT 없는 NXDOMAIN, 타임아웃을 구분합니다 |
| B, C, D, L | REFUSED와 15, REFUSED와 18, NXDOMAIN과 17, 관련 없는 패딩 옵션 뒤의 REFUSED와 16을 구분합니다 |
| E, F | SERVFAIL에 6과 13이 모두 있습니다. NOERROR에는 4와 대체 답변 레코드 수가 있습니다 |
| I, J, K | 잘못된 옵션 길이, 사설 코드 49152의 보존, EDE 없이 잘린 응답을 확인합니다 |

`12/12 observations matched.`가 나오면 됩니다. 대조 실험은 JSON 사본에서 B의 `opt_hex`만 `000f0002000f`에서 `000f00020012`로 바꾸고, `expected`는 유지한 뒤 분석기 인자로 사본 파일명을 전달합니다. 관측 코드는 15에서 18로 바뀌고 RCODE는 REFUSED로 유지돼야 합니다. 검사기의 종료 코드는 1입니다. 기본 파일에서 실패하면 파일명과 옵션 길이를 확인하세요. Python 검증에는 가상 데이터를 사용했습니다. BIND 질의와 공급자 동작은 공식 문서로 검토했으며 실제 DNS 서비스에 질의하지 않았습니다.

## 6. 확인 문제와 완료 기준

1. **NOERROR에 EDE가 들어갈 수 있나요?** 들어갈 수 있습니다. EDE 4는 정책으로 대체 답변을 보냈다는 진단입니다. 답변 섹션과 정책 로그를 함께 봐야 실제 반환 값과 이유를 알 수 있습니다.
2. **REFUSED와 EDE 18이면 도메인 차단 목록이 적용된 건가요?** 서버는 클라이언트의 작업 권한을 문제로 보고합니다. 관측한 출발지, 리졸버 뷰, 적용 ACL을 확인합니다.
3. **EDE가 안 보이면 필터링도 없었다고 봐도 되나요?** EDNS 사용 여부와 잘림, 중간 구간 및 정책 결정 로그를 확인해야 합니다.
4. **6과 13이 함께 있다면 무엇을 알 수 있나요?** 검증과 캐시된 오류에 대한 진단이 함께 왔습니다. 최초 실패 지점은 리졸버 기록으로 시간 순서를 복원해 확인합니다.

**완료 기준.** 가상 관측 12건과 코드 변경 대조 실험을 재현합니다. 거부 응답 한 건에 대해 받은 RCODE와 전체 EDE, 보고한 서버, 해당 결정을 확인할 기록을 설명합니다. 이어서 [DNS 조사]({{ '/ko/wiki/dns-investigation/' | relative_url }})와 [부정 응답 캐시]({{ '/ko/wiki/dns-negative-cache-evidence/' | relative_url }})를 참고하세요.
