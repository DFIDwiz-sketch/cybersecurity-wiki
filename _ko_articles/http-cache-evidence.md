브라우저에는 응답이 표시되는데 애플리케이션 서버의 접근 로그에서는 요청을 찾을 수 없습니다. 캐시가 저장해 둔 응답을 돌려줬을 수 있습니다. 먼저 어느 계층에서 응답했는지 확인하고, 재사용이 예상된 동작인지, 저장된 내용을 어떤 사용자에게 제공할 수 있었는지 조사합니다.

## 1. 응답을 재사용하는 지점

**원본 서버**(origin)는 요청한 리소스를 책임지는 서버입니다. **개인 캐시**는 브라우저의 HTTP 캐시처럼 한 사용자를 위해 동작합니다. **공유 캐시**는 CDN 엣지처럼 여러 사용자에게 저장된 응답을 재사용할 수 있습니다. **캐시 키**는 재사용 후보를 찾는 기준입니다. HTTP 모델에서는 적어도 요청 메서드와 대상 URI를 사용하며, 배포 환경의 캐시 규칙에 따라 키에 다른 기준이 추가될 수 있습니다.

**표현**(representation)은 특정 요청에 대해 선택한 내용과 관련 메타데이터입니다. 같은 URL에서 영어와 한국어 표현이 각각 선택될 수 있습니다. **검증자**(validator)인 `ETag` 등은 조건부 요청에서 표현을 식별합니다. 클라이언트는 태그의 내부 의미에 의존하지 않습니다. `W/`가 붙는 약한 ETag는 일부 바이트가 달라도 동등한 것으로 비교될 수 있습니다.

| 증거 | 읽는 내용 | 판단 한계 |
| --- | --- | --- |
| `Cache-Control` | 요청·응답의 저장 또는 재사용 규칙 | 어느 방향의 헤더인지, 캐시 종류와 실제 설정은 무엇인지 확인합니다. |
| `Age`, `Date` | 초 단위의 추정 경과 시간과 메시지 생성 날짜 | Age로 특정 엣지에 머무른 시간을 계산하기 어렵습니다. 헤더가 없어도 원본에 접속했는지 알 수 없습니다. |
| `Vary` | 응답 선택에 영향을 주는 요청 헤더 | 실제 관측 지점의 요청 헤더 값을 비교합니다. `Vary: *`는 일반적인 저장 응답 조건에 일치하지 않습니다. |
| `ETag`, `If-None-Match` | 응답이 제공한 검증자와 조건부 요청 값 | 선택한 표현과 비교 규칙을 확인합니다. 태그를 신뢰 가능한 파일 해시로 간주하지 않습니다. |
| `Cache-Status` | 각 캐시가 요청을 처리한 방식을 담는 선택적 응답 헤더 | 원본에 가까운 캐시부터 사용자에 가까운 캐시 순서입니다. 누가 넣은 헤더인지 확인하고 운영 로그와 대조합니다. |

## 2. 언제 저장하고 언제 다시 확인하나요?

**신선도**(freshness)는 저장된 응답을 별도 검증 없이 재사용할 수 있는 기간과 관련됩니다. 파일 자체가 얼마나 오래됐는지와는 별개입니다. 응답의 경과 시간과 허용 기간을 비교합니다. 기간을 벗어나면 해당 규칙에서 오래된 응답 사용을 허용하는 경우를 제외하고 재검증하거나 새로 받습니다. 제한된 상황에서 오래된 응답을 허용하는 캐시 설정도 있습니다.

| 응답 지시어 | 효과 |
| --- | --- |
| `max-age=60` | 적용되는 정책에서 신선도 기간을 60초로 지정합니다. |
| `s-maxage=120` | 공유 캐시의 기간을 지정하며 그곳에서는 `max-age`보다 우선합니다. 개인 캐시는 다른 적용 가능한 지시어를 따릅니다. |
| 인수가 없는 `no-cache` | 저장할 수 있으나 재사용 전에 검증이 성공해야 합니다. |
| `no-store` | 이번 요청·응답을 저장하지 않도록 지시합니다. 기존 캐시 사본을 제거하는 기능은 아닙니다. |
| 인수가 없는 `private` | 일반적인 공유 캐시 저장을 금지합니다. 개인 캐시에는 저장할 수 있습니다. |
| `public` | 다른 조건도 충족하면 공유 캐싱을 명시적으로 허용합니다. 응답 전체가 그 대상에게 안전한지 확인합니다. |

RFC 9111은 `Authorization` 요청 헤더가 있는 경우 응답 지시어가 공유 캐시 사용을 명시적으로 허용하고 해당 조건을 충족해야 재사용할 수 있다고 설명합니다. `public`, `s-maxage`, `must-revalidate` 등이 조건에 따라 해당합니다. 쿠키 기반 세션은 별개의 경우입니다. HTTP 표준에서 `Set-Cookie`만으로 캐싱이 금지되지는 않습니다. 개인화된 응답에는 명시적인 정책이 필요하며, 배포 제품의 우선 적용 규칙도 확인하세요.

## 3. 정상적인 응답 흐름 읽기

가상 예시의 공개 페이지 `/notice`에는 `Vary: Accept-Language`가 있습니다. 응답의 캐시 정책은 `public, max-age=60, s-maxage=120`입니다. 엣지가 `Cache-Status: edge; hit; ttl=100`과 `Age: 20`을 보고했다면 공유 캐시에서 20초가 경과해 100초가 남은 적중 사례와 맞습니다. 저장 당시 언어와 새 요청 언어가 다르면 표현 선택 결과를 확인하세요. 프랑스어 요청에 맞는 저장 응답이 없다면 상위로 전달될 수 있습니다. H03의 `fwd=vary-miss`가 그런 경우입니다.

이후 엣지는 일치하는 저장 표현의 검증자를 넣어 상위 서버에 조건부 GET을 보낼 수 있습니다. 표현이 바뀌지 않았다면 서버가 본문 없이 **304 Not Modified**를 반환할 수 있습니다. 브라우저가 직접 조건부 요청을 보냈다면 304를 받아 저장한 본문을 사용할 수 있습니다. 브라우저는 일반 GET을 보냈고 엣지가 자기 사본을 재검증했다면, 엣지는 검증된 본문을 담아 **200**을 보낼 수 있습니다. 따라서 엣지의 200과 원본의 304가 한 요청 흐름에 함께 기록될 수 있습니다.

표준 헤더와 제품별 헤더는 구분합니다. Cloudflare는 `CF-Cache-Status`의 `HIT`, `MISS`, `BYPASS`, `REVALIDATED` 등을 별도로 정의합니다. 한 캐시의 `MISS`로 상위 캐시의 처리 결과까지 알 수는 없습니다. 조사 시점에 적용된 제품 정의와 설정을 확인하세요.

## 4. 예상 밖 재사용을 조사하는 순서

응답의 공개 범위보다 캐시의 재사용 범위가 넓으면, 사용자나 테넌트에 제한되어야 할 내용이 공유될 수 있습니다. 공개 안내문 적중은 정상적입니다. 계정별 내용이 실린 응답의 공유 적중을 확인했다면 조사가 필요합니다. 승인된 가상 계정 또는 이미 수집 권한이 있는 자료에서 대조하세요. 적중 표시나 언어 차이만으로 노출을 확정할 수 없습니다.

1. **요청 흐름을 보존합니다.** UTC 시각, 메서드, 정규화한 경로와 호스트명, 상태 코드, 요청 ID, 캐시 노드나 리전, 캐시 상태·검증자·정책을 남깁니다. `Vary`에 지정된 요청 헤더 값, 캐시 설정과 앱 배포 버전도 확보하세요. 자료의 접근 권한을 제한하고 조사용 내보내기 자료에서 자격 증명, 쿠키, 개인정보를 적절히 가립니다.
2. **엣지와 상위 서버를 구분합니다.** 전달된 요청 ID가 있다면 이를 맞추고, ID가 다르면 시각과 경로를 함께 확인합니다. 단말·엣지 로그와 상위 상태 코드, 원본 로그 수집 범위를 대조합니다. 브라우저의 개인 캐시나 서비스 워커가 관여했다면 화면에 보이는 응답을 만든 계층부터 찾습니다. 정상적인 캐시 적중과 로그 누락 모두 원본 기록 부재의 원인이 될 수 있습니다.
3. **의도한 공개 범위를 확인합니다.** 계정별 경로와 공개 경로, 실제 캐시 키 및 선택 기준이 되는 헤더를 비교합니다. 승인된 범위에서 무해한 실습 응답으로 정책을 확인하세요. 위험해 보이는 설정과 다른 계정에 실제로 전달된 응답은 별도로 기록합니다. 의도를 판단하기 전에 규칙 변경과 배포 이력을 확인합니다.
4. **서비스 담당자와 대응합니다.** 승인된 대응 전에 관련 시간대, 정책 버전, 실제 전달 범위를 뒷받침하는 자료를 보존합니다. 부적절한 공유 규칙을 바로잡고, 필요한 경우 영향을 받은 항목을 무효화한 뒤 정상 재사용과 차단 사례를 함께 확인합니다. 오늘 우회되거나 헤더가 수정됐다는 사실로 과거 노출 여부를 판단할 수는 없습니다. 이전 전달 로그를 별도로 조사하세요.

## 5. 오프라인 기록과 실제 루프백 실습

[가상 기록]({{ '/assets/labs/http-cache-cases.json' | relative_url }})과 [Python 실습]({{ '/assets/labs/http-cache-review.py' | relative_url }})을 같은 폴더에 저장하세요. Python 3과 루프백 소켓을 열 수 있는 환경이 필요합니다. 스크립트는 먼저 가상 기록을 읽습니다. 이후 `127.0.0.1`의 자동 선택 포트에 작은 HTTP 원본 서버를 띄워 요청 3건을 보내고 종료합니다. 실제 캐시나 CDN에는 연결하지 않습니다. 서버의 언어 선택과 ETag 검증은 실습에 쓰는 고정 입력을 처리합니다.

1. 행마다 어떤 캐시가 관측됐는지, 상위 서버 응답이 있는지 구분합니다. `scope`와 `vary_matches`는 실습에서 제공하는 조사 맥락입니다.
2. 아래 명령을 실행한 뒤 가상 입출력과 실제 루프백 응답을 비교합니다.

```bash
python3 http-cache-review.py
```

| 사례 | 기대 결과 |
| --- | --- |
| `H01` / `H02` | 엣지 재사용 / 상위 304와 하위 200입니다. |
| `H03` / `H04` | 맞는 저장 표현 없음 / 캐시 경로를 확인할 증거가 부족합니다. |
| `H05` / `H06` | 개인화 응답의 공유 적중으로 조사 필요 / 관측 엣지가 이번 요청을 우회했습니다. |
| 루프백 | 영어 200에는 본문과 ETag가 있고, 같은 태그의 영어 조건부 요청은 본문 없는 304입니다. 영어 태그로 요청한 한국어 응답은 다른 태그와 본문을 담은 200입니다. |

파일이 없다는 오류가 나면 두 파일 이름과 폴더를 확인합니다. 환경에서 루프백을 열 수 없다면 소켓 오류 전에 완료된 오프라인 검사 6건을 사용하세요. 실습 스크립트 밖에서 확인할 때도 루프백만 사용하고 요청 헤더를 그대로 유지합니다. 다른 언어 표현에 영어 태그를 보내면 영어 본문을 재검증하는 요청이 되지 않습니다.

**검증 범위.** 가상 검사 6건과 실제 루프백 HTTP 요청 3건을 실행했습니다. CDN 동작은 공식 문서로 확인했습니다. 브라우저나 상용 CDN의 캐시 동작을 이 실습에서 실행하지는 않았습니다.

## 6. 확인 문제와 해설

1. **서버가 304를 반환했습니다. 새 본문이 왔나요?** 304에는 본문이 없습니다. 저장된 응답과 어느 구간에서 검증이 일어났는지 확인합니다.
2. **같은 URL에서 서로 다른 언어가 나오는 이유는 무엇인가요?** 원본이 요청에 따라 표현을 선택합니다. 적용되는 `Vary`가 언어 헤더를 지정하면, 일반적인 재사용에서는 그 값도 일치해야 합니다.
3. **`Age`가 없으면 원본에서 응답했다고 볼 수 있나요?** 캐시 및 상위 서버 로그로 실제 경로를 확인합니다. 헤더 부재만으로는 원본 접속을 입증할 수 없습니다.
4. **수정 후 우회됐으니 예전에도 공유 응답을 받은 사람이 없었다고 볼 수 있나요?** 현재 관측한 엣지의 동작을 보여 줍니다. 과거 노출 여부는 당시 전달 기록으로 판단합니다.

**완료 기준.** 가상 기록 여섯 건과 실제 HTTP 응답 세 건을 설명합니다. 관측된 재사용, 의도된 공개 범위, 노출 판단에 필요한 다음 증거를 구분해 짧게 기록하세요.
