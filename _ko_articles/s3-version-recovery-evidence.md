**학습 목표.** S3 객체가 사라졌다는 신고를 받았을 때 어떤 요청이나 수명 주기 작업이 있었는지, 어떤 버전이 남았는지, 복원 전에 무엇을 검증해야 하는지 설명합니다. 버킷, 객체 키, CloudTrail 데이터 이벤트가 처음이라면 [S3 객체 읽기 조사]({{ '/ko/wiki/s3-object-read-evidence/' | relative_url }})부터 읽어 보세요.

## 1. 키가 보이지 않는 이유는 여러 가지입니다

애플리케이션은 보통 **버전 ID**를 지정하지 않고 `reports/daily.csv` 같은 S3 **키**를 읽습니다. 버전 관리가 켜진 범용 버킷에는 같은 키의 여러 버전이 함께 존재할 수 있습니다. **현재 버전**은 S3가 일반 조회에 사용하는 버전입니다. **이전 버전**은 ID를 지정해 조회할 수 있습니다. **삭제 마커**에도 ID가 있고 현재 버전이 될 수 있지만, 마커에는 객체 본문이 없습니다. 삭제 마커가 현재 버전이면 일반 조회에서 키가 없는 것처럼 보입니다.

**S3 수명 주기(S3 Lifecycle)**는 설정한 규칙을 조건에 맞는 객체나 버전에 적용합니다. **S3 객체 잠금(S3 Object Lock)**은 보존 기간이나 법적 보존(legal hold)을 통해 특정 데이터 버전을 보호합니다. 두 제어를 함께 적용할 수도 있습니다. 보호된 데이터가 남아 있어도 더 최근에 만들어진 삭제 마커 때문에 일반 조회가 실패할 수 있습니다. 현재 키가 보이는지와 남아 있는 데이터 버전이 무엇인지를 각각 기록하세요.

## 2. 시간순으로 버전 상태를 읽어 봅시다

보고서 작업이 09:00 UTC에 `v1`, 10:00에 `v2`를 썼다고 가정합니다. 10:05에는 승인된 정리 작업이 버전 ID 없이 삭제를 요청했습니다. 응답은 HTTP 204였고 `m1` 마커가 생겼습니다. 10:06에 애플리케이션이 현재 키를 조회하자 404가 돌아왔습니다. 조사자가 버전을 나열한 결과 `IsLatest=true`인 `m1`이 있었고, `Versions`에는 `v2`와 `v1`이 있었습니다. 권한이 있는 조사자가 `v2`를 지정해 HEAD를 요청하자 200이 돌아왔습니다. 가상의 정상 사례입니다. 404는 현재 키의 조회 결과이고, 목록과 버전별 HEAD는 어떤 데이터 버전을 더 확인해야 하는지 알려 줍니다.

| 요청 또는 관측 | 버전 관리가 켜진 경우 | 확인할 근거 |
| --- | --- | --- |
| 버전 ID를 생략한 삭제 요청 | 삭제 마커를 추가하고 현재 버전으로 지정 | 버전 목록에서 마커와 남은 데이터 버전 확인 |
| 특정 데이터 버전 삭제에 성공 | 해당 버전을 버킷에서 영구 삭제 | 이전 인벤토리나 신뢰할 수 있는 변경 기록과 ID 대조 |
| 특정 삭제 마커 제거에 성공 | 현재 마커였다면 다음으로 최근인 항목이 조회 결과를 결정 | 이전 데이터 버전, 다른 마커, 또는 남은 항목 없음 |
| 현재 버전 HEAD가 마커에 도달 | S3가 404를 반환하고 삭제 마커임을 표시 | 도구가 노출하는 마커 헤더와 버전 목록 확인 |
| 존재하는 마커 ID를 직접 지정한 HEAD | S3가 마커 정보와 함께 405 반환 | 지정한 ID는 마커로 기록하고 데이터 버전을 따로 확인 |

**사건 당시** 버전 관리 상태를 확인하세요. 버전 관리를 한 번도 켜지 않은 버킷에서는 일반 삭제가 객체를 영구 제거합니다. 버전 관리가 일시 중지된 버킷에서는 버전 ID가 `null`인 데이터가 있다면 일반 삭제 요청이 그 데이터를 제거하고 삭제 마커를 만들 수 있습니다. 다른 ID를 가진 데이터 버전은 남을 수 있습니다. 이 장의 타임라인과 실습은 버전 관리가 계속 켜져 있었다고 가정합니다.

## 3. 데이터가 사라지거나 보이지 않게 되는 경로

객체 삭제 권한을 가진 역할이 오용되거나 정리 작업이 잘못 설정되면 현재 키가 보이지 않을 수 있습니다. 특정 버전을 삭제할 권한이 있고 정책과 보존 제어가 허용하면 데이터 버전을 영구적으로 잃을 수 있습니다. 수명 주기 만료도 고객이 키별로 삭제 API를 호출하지 않아도 현재 키를 숨기거나 조건을 충족한 이전 버전을 영구 삭제할 수 있습니다. 정기 정리 시간에 많은 키가 영향을 받는 것은 정상일 수 있습니다. 작업에 허용된 버킷·접두사와 요청한 버전 범위를 먼저 대조하세요.

객체 잠금의 거버넌스 모드에서는 `s3:BypassGovernanceRetention` 권한을 가진 호출자가 명시적으로 우회를 요청할 수 있습니다. 규정 준수 모드에서는 보존 기간 동안 계정 루트 사용자를 포함해 보호된 버전을 삭제할 수 없습니다. 법적 보존에는 만료 시각이 없으며, 권한이 있는 주체가 해제할 때까지 유지됩니다. 두 제어가 한 버전에 함께 적용될 수 있으므로 데이터 버전별로 모드, 보존 종료 시각, 법적 보존 상태를 확인하세요. 마커 추가가 성공한 상태에서 데이터 버전의 영구 삭제가 거절될 수 있습니다.

## 4. 증거를 수집하고 복원 후보를 판단하기

| 자료 | 수집할 항목 | 해석할 때 확인할 점 |
| --- | --- | --- |
| CloudTrail 객체 데이터 이벤트 | UTC 시각, 계정, 리전, 세션 신원, 버킷, 키, 기록된 버전 ID, 요청 ID, 오류 | 사건 당시 쓰기 데이터 이벤트 선택기가 버킷과 접두사를 포함했는지 확인하고, 확보할 수 있다면 `DeleteObjects`의 객체별 결과도 검토 |
| 버킷 설정과 변경 이력 | 버전 관리 상태, 수명 주기, 객체 잠금, 승인된 변경과 작업 이력 | 규칙의 조건과 변경 시각을 영향을 받은 키와 대조. 현재 설정으로 과거 상태를 단정하기 어려움 |
| S3 서버 액세스 로그 | 기록된 요청 ID와 작업 이름. 수명 주기 작업에는 `S3.CREATE.DELETEMARKER`, `S3.EXPIRE.OBJECT` 등이 있음 | 로그 활성화 범위와 전달 상태 확인. 최선형 전달이므로 기록이 빠질 수 있음 |
| 버전 목록, 이전 인벤토리, 복원 확인 | 정확한 키, `VersionId`, `IsLatest`, 마커 여부, 시각, 애플리케이션 체크포인트 | 목록은 수집 시점에 조회 가능한 상태를 보여 줌. 이전 인벤토리는 과거에 있던 버전을 판단하는 데 도움이 됨 |

영향받은 범위의 `s3.amazonaws.com` 이벤트에서 `DeleteObject`와 `DeleteObjects`를 확인하세요. 세션·버킷·시간으로 묶기 전에 원본 기록을 보존하고, 로그에 있으면 서로 다른 키와 버전 ID를 셉니다. S3 세션은 사용된 자격 증명을 나타냅니다. 누가 사용했는지는 워크로드나 로그인 기록이 더 필요할 수 있습니다. 오류 필드가 없거나 배치 응답을 받았다는 사실, 로그가 없다는 사실, 현재 404라는 사실만으로는 개별 데이터 버전의 상태를 확정하기 어렵습니다. 확보한 요청 ID, 작업 이력, 선택기 범위, 버전 목록과 변경 근거를 대조하세요. 2026년 11월 22일 검토 기준으로 AWS는 이미 S3 데이터 이벤트를 기록 중인 트레일에 S3 수명 주기 및 S3 인증 실패 이벤트를 **2026년 12월 21일**부터 전달할 예정입니다. 과거 사건은 당시 사용할 수 있던 자료를 확인하고, 배포 후에는 해당 계정에서 실제 전달 여부와 선택기 동작을 확인하세요.

소유하거나 명시적으로 승인받은 버킷에서 다음 AWS CLI v2 명령으로 메타데이터를 수집할 수 있습니다. 사건에 맞게 `BUCKET`, `KEY`, `VERSION_ID`를 지정하세요. 첫 명령에는 `s3:ListBucketVersions` 권한이 필요합니다. 같은 접두사의 키가 여러 개일 수 있으므로 전체 페이지를 확보한 뒤 두 배열에서 정확히 일치하는 `Key`를 찾습니다. 두 번째 명령에는 데이터 버전 ID와 `s3:GetObjectVersion` 권한이 필요합니다. 403이면 리전, 계정과 정책부터 확인하세요. 버킷 목록 권한이 없는 호출자는 객체가 없어도 403을 볼 수 있습니다.

```sh
aws s3api list-object-versions --bucket "$BUCKET" --prefix "$KEY" --output json
aws s3api head-object --bucket "$BUCKET" --key "$KEY" --version-id "$VERSION_ID"
```

관련 기록을 보존하고 사고 대응 담당자와 저장소 담당자가 함께 승인되지 않은 작업을 중지하거나 필요한 권한을 제한하세요. 복구 후보 버전 ID, 애플리케이션 체크포인트와 복원 승인을 기록합니다. 복구 절차에 따라 격리된 위치로 후보 버전을 읽어 오세요. 아카이브 스토리지 여부와 KMS 접근 권한도 확인해야 할 수 있습니다. 신뢰할 수 있는 체크섬이나 명세서로 내용을 대조하고, 애플리케이션이 실제 사용할 권한으로 읽히는지 확인합니다. HEAD는 메타데이터 접근까지만 확인합니다. ETag만으로 모든 객체의 내용 해시를 검증할 수는 없습니다. 후보가 없거나 읽을 수 없다면 독립적으로 관리되는 백업과 복제본을 확인하고 마지막으로 검증한 복구 시점을 기록하세요. 서비스 재개 여부는 [백업 복구 검증]({{ '/ko/wiki/backup-restore-evidence/' | relative_url }})을 참고하세요.

## 5. 승인된 오프라인 실습

[s3-version-recovery.py]({{ '/assets/labs/s3-version-recovery.py' | relative_url }}){: download="s3-version-recovery.py" }를 내려받아 본인의 작업 공간에서 Python 3.8 이상으로 실행하세요. 표준 라이브러리 프로그램이 버전 관리가 켜진 버킷의 가상 키 하나를 최근 버전부터 순서대로 읽고, 목록과 HEAD 결과를 만들어 냅니다. 자격 증명, 네트워크, 클라우드 호출이나 별도 입력 파일 없이 실행됩니다.

```sh
python3 s3-version-recovery.py
```

| 비교할 사례 | 기대 결과 | 해석 |
| --- | --- | --- |
| `normal`, `marker-added` | 현재 HEAD는 200 → 404로 바뀌고 `v2`, `v1`은 남음 | 현재 키의 가시성이 바뀜 |
| `marker-added`, `older-version-removed` | 둘 다 현재 HEAD는 404. 앞 사례에만 `v1`이 있음 | 현재 HEAD만으로 `v1`의 존속 여부를 판단하기 어려움 |
| `older-version-removed`, `protected-version-denied` | 마지막 버전 목록이 같음 | 거절된 요청은 상태를 바꾸지 않았음. 두 경우를 구별하려면 요청 증거가 필요함 |
| `marker-removed`, `marker-only`, `empty` | 현재 HEAD는 각각 200, 404, 404. `m1`을 지정한 HEAD는 마커만 남은 사례에서 405 | 남은 데이터 버전 없이 마커만 있을 수도 있음 |

7개 사례가 모두 출력되고 종료 코드는 0이어야 합니다. 모델 결과가 예상과 다르면 메시지에 사례 이름과 두 값이 나옵니다. 파일을 열 수 없으면 다운로드 이름과 작업 디렉터리를 확인하세요. 결과를 비교할 때는 같은 실습 데이터를 사용합니다. 이 모델은 읽기와 버킷 목록 조회 권한이 있다고 가정합니다. IAM, 보존 제어, 수명 주기 처리 시점과 실제 복원된 바이트는 실습 범위 밖입니다. Python 3.12.14에서 가상 사례 7개를 실행했습니다. AWS 동작과 CLI 예시는 공식 문서로 검토했고, 실제 AWS 환경에서의 실행은 검증 범위에 포함되지 않습니다.

## 6. 확인 문제와 해설

1. **현재 HEAD는 404이고 목록에는 현재 마커 `m1`과 데이터 버전 `v2`가 있습니다. 복구를 입증했나요?** `v2`는 복구 후보입니다. 접근 권한, 읽을 수 있는 콘텐츠, 무결성과 애플리케이션 체크포인트를 확인하세요.
2. **삭제 경보가 수명 주기 규칙과 맞아 보이고 고객 삭제 이벤트는 없습니다. 무엇을 알 수 있나요?** 수명 주기 규칙은 가능한 설명 중 하나입니다. 규칙의 필터와 시각을 실제 수명 주기 기록, 버전 목록, 로그 수집 범위와 대조하세요.
3. **최신 삭제 마커를 제거하면 언제나 키를 읽을 수 있나요?** 다음 항목은 데이터 버전일 수도, 다른 마커일 수도 있으며 아무 항목도 남지 않았을 수도 있습니다. 접근 권한과 실제 읽기 결과도 확인해야 합니다.

**완료 기준.** 마커와 데이터 버전의 차이를 설명하고, 마커만 남은 경우와 아무 항목도 없는 경우가 어떻게 다른지 예측하세요. 관측된 상태, 가능한 원인, 아직 모르는 점과 다음 복구 확인을 담은 짧은 사고 기록을 작성하면 완료입니다.
